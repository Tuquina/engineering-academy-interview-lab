## Ingesta: aceptar rápido, procesar después

- **API de eventos:** valida el esquema, inserta el evento en `inbound_events` con `UNIQUE (tenant_id, external_id)`
  y responde `202`. Si el ID ya existe, responde `200` con el resultado anterior: el reintento del cliente es
  inofensivo. La inserción y el mensaje a la cola van por **outbox** para no perder eventos.
- **Archivos:** se suben a object storage con una URL firmada; un job los procesa por **lotes de 1.000 filas**,
  guarda el avance (`import_jobs.last_row`) y es reanudable. Las filas inválidas se reportan al tenant sin frenar el
  resto.

## Modelo de datos

```sql
customers (id, tenant_id, external_id, ..., UNIQUE (tenant_id, external_id))
debts (id, tenant_id, customer_id, external_id, status, UNIQUE (tenant_id, external_id))
ledger_entries (id, tenant_id, debt_id, kind, amount_cents, source_event_id UNIQUE, created_at)  -- append-only
debt_balances (debt_id PRIMARY KEY, balance_cents, version)  -- derivado del ledger
customer_priority (customer_id PRIMARY KEY, tenant_id, score, reasons jsonb, computed_at)
```

El saldo se **deriva de movimientos inmutables**: un pago es un `ledger_entry` con `source_event_id` único. Aplicar
dos veces el mismo evento choca contra la restricción. Así el ledger es, además, la auditoría de saldos.

## Procesamiento

- Workers stateless consumen la cola con **entrega al menos una vez** y son idempotentes por `source_event_id`.
- Los errores transitorios se reintentan con **backoff exponencial y jitter**; tras N intentos, el mensaje va a una
  **DLQ** con alerta y herramienta de reproceso.
- **Aislamiento entre tenants:** una cola (o grupo de mensajes) por tenant y concurrencia máxima por tenant. El
  archivo de 200.000 filas de un tenant no retrasa los pagos en tiempo real de otro; los pagos van en una cola
  prioritaria.

## Priorización

- La unidad de gestión es el **cliente**: la prioridad agrega sus deudas (monto vencido total, mora máxima, promesas
  activas).
- Las reglas son **configuración versionada por tenant** (pesos y umbrales), evaluadas por una estrategia por tenant.
- Se recalcula **incrementalmente** cuando llega un evento que afecta al cliente, y un job nocturno recalcula todo
  para corregir derivas.
- `reasons` guarda por qué el cliente tiene esa prioridad: explicable al operador y auditable.

## Fallos y observabilidad

| Falla                           | Comportamiento                                                          |
| ------------------------------- | ----------------------------------------------------------------------- |
| Worker cae a mitad de un evento | El mensaje se reentrega; la idempotencia evita doble efecto.            |
| Base lenta                      | La cola absorbe; el lag crece y dispara alerta antes de afectar la API. |
| Proveedor de mensajería caído   | Circuit breaker y reprogramación del contacto; no bloquea la ingesta.   |
| Evento venenoso                 | Va a la DLQ tras N intentos; alerta y reproceso tras corregir.          |

Métricas: lag por cola y por tenant, antigüedad del mensaje más viejo, tamaño de la DLQ, tasa de duplicados
descartados. Cada evento lleva un `trace_id` desde la API hasta el ledger.

## Compromisos

- **Asíncrono vs inmediato:** el saldo visible puede tardar segundos en reflejar un pago; a cambio, la API no se
  degrada con los picos. Para pagos, una cola prioritaria acota esa demora.
- **Ledger vs actualizar saldo:** más filas y una tabla derivada, pero auditoría y corrección de errores gratis.
- **Una base compartida con `tenant_id`** (y Row Level Security) en lugar de base por tenant: más simple de operar a
  esta escala; se revisaría si aparecen requisitos de aislamiento físico.
