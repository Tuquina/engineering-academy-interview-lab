## API

```http
POST /v1/urls
{ "url": "https://ejemplo.com/una/ruta/muy/larga", "alias": "promo", "expiresAt": "2027-01-01" }
→ 201 { "code": "a9X3kQ2", "shortUrl": "https://sho.rt/a9X3kQ2" }

GET /{code}
→ 302 Location: https://ejemplo.com/una/ruta/muy/larga
→ 404 si no existe o expiró
```

**301 o 302**: un 301 (permanente) lo cachea el navegador y ahorra tráfico, pero los clics siguientes no pasan por el
servicio y se pierden para las analíticas. Si las estadísticas importan, 302.

## Modelo de datos

| Campo        | Tipo      | Nota                                |
| ------------ | --------- | ----------------------------------- |
| `code`       | string(7) | Clave primaria y de partición       |
| `url`        | text      | URL original validada               |
| `owner_id`   | id        | Opcional, para el panel del usuario |
| `created_at` | timestamp |                                     |
| `expires_at` | timestamp | Opcional; TTL nativo en DynamoDB    |

El acceso es siempre por `code`: una base **clave-valor** (DynamoDB, Cassandra) escala horizontalmente sin esfuerzo.
PostgreSQL con un índice por código también funciona hasta varios miles de millones de filas con particionado.

## Diseño de alto nivel

Dos caminos separados que escalan distinto:

- **Escritura** (poca carga): valida la URL, obtiene un ID único, lo codifica en base62 y lo guarda.
- **Lectura** (el camino crítico): resuelve el código desde Redis y redirige; la base sólo recibe los cache miss.

Las analíticas salen del camino crítico: cada clic publica un evento y un consumidor agrega los datos.

## Profundización

**Generar el código sin colisiones.** Opciones:

1. **Hash de la URL** (MD5/SHA) truncado a 7 caracteres: la misma URL da el mismo código, pero hay colisiones y hay
   que detectarlas con una restricción única y reintentar con sal.
2. **Contador + base62**: un ID único codificado en base62 nunca colisiona. Para no tener un único contador como
   cuello de botella, cada instancia pide **rangos** (por ejemplo, 10.000 IDs) a una secuencia central y los consume
   localmente; si una instancia muere, se pierde un rango sin consecuencias.
3. **Snowflake**: IDs de 64 bits con timestamp, máquina y secuencia, generados sin coordinación.

Si los códigos consecutivos son un problema (enumeración), se aplica una **permutación** biyectiva al ID antes de
codificarlo o se agregan caracteres aleatorios.

**Caché.** Los clics siguen una ley de potencia: con el 20 % de los enlaces más populares en Redis se resuelve la
gran mayoría del tráfico. TTL con jitter, LRU como política de desalojo y caché negativa para códigos inexistentes
(evita que un bot que prueba códigos golpee la base).

**Expiración.** No se borra en el camino de lectura: se verifica `expires_at` al leer y un job (o el TTL nativo de la
base) elimina en lotes.

## Compromisos

- **Consistencia**: un enlace recién creado puede tardar unos milisegundos en replicarse; si el usuario lo prueba al
  instante, la lectura puede ir al primario o reintentarse ante un 404 recién creado.
- **Hash vs contador**: el hash deduplica URLs iguales; el contador es más simple y sin colisiones. La mayoría de los
  diseños eligen contador por rangos.
- **301 vs 302**: menos carga contra analíticas completas.
- **Costo**: la caché y la CDN reducen drásticamente la carga de la base; el componente más caro suele ser el
  almacenamiento de analíticas, no el de los enlaces.
