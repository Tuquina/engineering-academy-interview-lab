## El host y Program.cs

Una aplicación ASP.NET Core se arma en `Program.cs` en dos fases: **registrar servicios** y **definir el pipeline**.

```csharp
var builder = WebApplication.CreateBuilder(args);

// 1. Servicios (inyección de dependencias)
builder.Services.AddScoped<IOrderRepository, PostgresOrderRepository>();
builder.Services.AddScoped<CheckoutService>();
builder.Services.AddProblemDetails();
builder.Services.AddHttpClient<IPaymentGateway, PaymentGatewayClient>(c =>
    c.BaseAddress = new Uri(builder.Configuration["Payments:BaseUrl"]!));

var app = builder.Build();

// 2. Pipeline de middleware
app.UseExceptionHandler();
app.UseHttpsRedirection();
app.UseAuthentication();
app.UseAuthorization();

// 3. Endpoints
app.MapGet("/orders/{id}", async (string id, IOrderRepository orders, CancellationToken ct) =>
    await orders.FindAsync(id, ct) is { } order ? Results.Ok(order) : Results.NotFound());

app.Run();
```

ASP.NET Core corre sobre **Kestrel**, un servidor web multiplataforma; en producción suele ir detrás de un proxy o un
balanceador.

## El pipeline de middleware

Cada **middleware** recibe el contexto HTTP, puede hacer algo antes, llamar al siguiente y hacer algo después, o
**cortar** la cadena respondiendo directamente.

  chart={`

  AZ --> EP["Endpoint"]

  AZ -. "respuesta" .-> AN

```csharp
app.Use(async (context, next) =>
{
    var started = Stopwatch.GetTimestamp();
    await next(context);                                   // el resto del pipeline
    var elapsed = Stopwatch.GetElapsedTime(started);
    app.Logger.LogInformation("{Method} {Path} {Status} en {Elapsed}",
        context.Request.Method, context.Request.Path, context.Response.StatusCode, elapsed);
});
```

**El orden importa**: el manejador de excepciones va primero para capturar los errores de todo lo que sigue, la
autenticación antes que la autorización, y los endpoints al final.

## Minimal APIs y controladores

**Minimal APIs** definen endpoints con lambdas y se agrupan con `MapGroup`:

```csharp
var products = app.MapGroup("/api/products").RequireAuthorization();

products.MapPost("/", async (CreateProductRequest request, ProductService service, CancellationToken ct) =>
{
    var created = await service.CreateAsync(request, ct);
    return Results.Created($"/api/products/{created.Id}", created);
});
```

**Controladores** organizan endpoints en clases, con atributos:

```csharp
[ApiController]
[Route("api/products")]
public class ProductsController(ProductService service) : ControllerBase   // constructor primario (C# 12)
{
    [HttpGet("{id}")]
    public async Task<ActionResult<ProductResponse>> Get(string id, CancellationToken ct) =>
        await service.FindAsync(id, ct) is { } product ? product : NotFound();
}
```

Ambos comparten pipeline, inyección de dependencias, **model binding** (ruta, query, body y servicios se resuelven
como parámetros) y configuración. Con `[ApiController]`, un modelo inválido responde 400 automáticamente con
`ValidationProblemDetails`.

## Inyección de dependencias y lifetimes

El contenedor de dependencias viene integrado. Cada servicio se registra con un **lifetime**:

| Lifetime       | Instancias                         | Uso típico                                           |
| -------------- | ---------------------------------- | ---------------------------------------------------- |
| `AddTransient` | Una nueva cada vez que se resuelve | Servicios livianos sin estado                        |
| `AddScoped`    | Una por request                    | `DbContext`, unidad de trabajo, contexto del usuario |
| `AddSingleton` | Una para toda la aplicación        | Cachés, configuración, clientes thread-safe          |

<Callout type="danger" title="Dependencia cautiva">
  Si un **singleton** recibe un servicio **scoped** (por ejemplo, un `DbContext`), lo retiene para siempre y
  lo comparte entre requests y hilos: errores de concurrencia y datos viejos. En el entorno Development, el
  contenedor valida los scopes y lanza un error al resolverlo. Si un singleton necesita algo scoped, crea un
  scope con `IServiceScopeFactory`.
</Callout>

## Configuración y options

La configuración se arma en **capas**, donde la última gana: `appsettings.json`, `appsettings.{Environment}.json`,
User Secrets en desarrollo, variables de entorno y argumentos.

```json
{
  "Payments": { "BaseUrl": "https://api.payments.example", "TimeoutSeconds": 5 }
}
```

```csharp
public sealed class PaymentsOptions
{
    [Required, Url] public string BaseUrl { get; init; } = "";
    [Range(1, 30)] public int TimeoutSeconds { get; init; }
}

builder.Services.AddOptions<PaymentsOptions>()
    .Bind(builder.Configuration.GetSection("Payments"))
    .ValidateDataAnnotations()
    .ValidateOnStart();                         // falla al arrancar si la configuración es inválida

public class PaymentGatewayClient(HttpClient http, IOptions<PaymentsOptions> options) { /* ... */ }
```

Las variables de entorno usan `__` para las secciones: `Payments__BaseUrl`. Los secretos van en variables de entorno o
en un gestor de secretos, nunca en `appsettings.json` del repositorio.

## Errores y validación

```csharp
builder.Services.AddProblemDetails();
builder.Services.AddExceptionHandler<DomainExceptionHandler>();

public sealed class DomainExceptionHandler(IProblemDetailsService problems) : IExceptionHandler
{
    public async ValueTask<bool> TryHandleAsync(HttpContext context, Exception exception, CancellationToken ct)
    {
        if (exception is not OutOfStockException outOfStock) return false;   // que lo maneje el siguiente
        context.Response.StatusCode = StatusCodes.Status409Conflict;
        return await problems.TryWriteAsync(new ProblemDetailsContext
        {
            HttpContext = context,
            ProblemDetails = { Title = "Sin stock", Detail = outOfStock.Message },
        });
    }
}
```

`ProblemDetails` produce el formato estándar de errores HTTP (RFC 9457). Para validar la entrada se usan Data
Annotations o librerías como FluentValidation.

## Resumen

ASP.NET Core se arma registrando servicios y definiendo un pipeline de middlewares en orden. Minimal APIs y
controladores comparten la misma base. Los lifetimes correctos, la configuración tipada y validada al arrancar, y
ProblemDetails para errores son la base de una API .NET profesional.
