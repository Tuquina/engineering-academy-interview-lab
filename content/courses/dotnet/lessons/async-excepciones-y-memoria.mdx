## Task y async/await

Una **`Task`** representa una operación en curso que eventualmente produce un resultado (`Task<T>`) o termina
(`Task`). `async`/`await` permite escribir código asíncrono con forma secuencial:

```csharp
public async Task<DeviceStatus> GetDeviceStatusAsync(string deviceId, CancellationToken ct)
{
    var device = await _registry.GetAsync(deviceId, ct);          // libera el hilo mientras espera
    var reading = await _telemetry.GetLatestAsync(deviceId, ct);
    return new DeviceStatus(device, reading);
}
```

Cuando el código llega a un `await` de una tarea que no terminó, **devuelve el control** sin bloquear el hilo. El
compilador transforma el método en una **máquina de estados** que continúa cuando la tarea termina. `async/await` no
crea hilos: en un servidor, eso significa que mientras una request espera a la base, el mismo hilo atiende otras.

### Concurrencia

```csharp
// Las dos llamadas en paralelo: el tiempo total es el de la más lenta
var deviceTask = _registry.GetAsync(deviceId, ct);
var readingTask = _telemetry.GetLatestAsync(deviceId, ct);
await Task.WhenAll(deviceTask, readingTask);
var status = new DeviceStatus(deviceTask.Result, readingTask.Result);   // ya terminaron: .Result no bloquea acá

// Muchas operaciones con concurrencia limitada
await Parallel.ForEachAsync(devices, new ParallelOptions { MaxDegreeOfParallelism = 10, CancellationToken = ct },
    async (device, token) => await _firmware.CheckForUpdateAsync(device, token));
```

### Cancelación

Toda operación de I/O debería aceptar un **`CancellationToken`** y pasarlo hacia abajo. En ASP.NET Core, el token de
la request se cancela si el cliente se desconecta.

```csharp
using var cts = CancellationTokenSource.CreateLinkedTokenSource(ct);
cts.CancelAfter(TimeSpan.FromSeconds(2));                 // timeout
var rate = await _shipping.GetRateAsync(order, cts.Token);
```

<Callout type="danger" title="No bloquees código asíncrono con .Result o .Wait()">
  Bloquear una tarea ocupa un hilo esperando. En contextos con `SynchronizationContext` (aplicaciones de
  escritorio, ASP.NET clásico) puede producir **deadlocks**, y en un servidor con carga contribuye a **agotar
  el thread pool**: las requests empiezan a demorarse sin que la CPU esté ocupada. La regla es *async de punta
  a punta*.
</Callout>

Otras reglas:

- `async void` sólo para manejadores de eventos: sus excepciones no se pueden esperar ni capturar desde afuera.
- `ConfigureAwait(false)` evita volver al contexto original; es relevante en librerías que pueden usarse en
  aplicaciones con `SynchronizationContext`. ASP.NET Core no tiene uno.
- `ValueTask` reduce asignaciones en métodos que muchas veces terminan de forma síncrona; usalo sólo si hace falta.

## Excepciones

```csharp
try
{
    await _inventory.ReserveAsync(sku, quantity, ct);
}
catch (OutOfStockException ex) when (ex.Available > 0)     // filtro de excepción
{
    return Result.Partial(ex.Available);
}
catch (HttpRequestException ex)
{
    _logger.LogWarning(ex, "Inventario no disponible");
    throw new CheckoutException("No se pudo reservar stock", ex);   // conserva la causa en InnerException
}
finally
{
    _metrics.CheckoutAttempted();
}
```

- C# no tiene excepciones checked: el compilador no obliga a capturarlas.
- Capturá excepciones específicas; `catch (Exception)` sólo en el borde (middleware), registrando el error.
- Para relanzar dentro de un `catch` usá `throw;` (conserva el stack trace), no `throw ex;`.
- Los filtros `when` permiten decidir sin capturar.
- Para errores esperables del dominio, muchos equipos usan resultados tipados en lugar de excepciones.

## IDisposable y using

El garbage collector administra **memoria**, pero no libera de forma determinista recursos como conexiones,
archivos o sockets. Esos tipos implementan **`IDisposable`** (o `IAsyncDisposable`) y se liberan con `using`:

```csharp
await using var connection = new NpgsqlConnection(connectionString);   // se libera al salir del ámbito
await connection.OpenAsync(ct);

using (var stream = File.OpenRead("readings.csv"))
{
    // ...
} // Dispose acá, aunque haya una excepción
```

<Callout type="warning" title="HttpClient">
  Crear y descartar un `HttpClient` por request puede agotar los sockets disponibles. En ASP.NET Core se usa
  `IHttpClientFactory` (o clientes tipados registrados con `AddHttpClient`), que administra las conexiones.
</Callout>

## El garbage collector

<MermaidDiagram
  caption="El GC de .NET es generacional: los objetos nacen en la generación 0; los que sobreviven a una recolección pasan a la siguiente."
  chart={`

  G0 -->|"sobrevive"| G1["Generación 1: intermedia"]

  L["Objetos de 85.000 bytes o más"] --> LOH["Large Object Heap: se recolecta con la generación 2"]
`}
/>

- La mayoría de los objetos muere joven: la generación 0 se recolecta seguido y es barata.
- En ASP.NET Core se usa por defecto el **Server GC**, optimizado para throughput con varios núcleos.
- Un **memory leak** en .NET es retener referencias sin querer: suscripciones a eventos que nunca se quitan, cachés
  estáticas sin límite, servicios con lifetime equivocado.
- Para reducir asignaciones en código caliente: `Span<T>`, `ArrayPool<T>`, evitar boxing y LINQ en bucles muy
  ajustados (midiendo con BenchmarkDotNet).

## Resumen

async/await libera hilos mientras se espera I/O: usalo de punta a punta, con CancellationToken y sin .Result. Las
excepciones se capturan específicas y se relanzan con throw;. Los recursos se liberan con using, y entender el GC
generacional ayuda a diagnosticar problemas de memoria.
