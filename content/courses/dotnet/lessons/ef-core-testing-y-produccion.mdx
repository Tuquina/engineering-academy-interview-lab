## DbContext y entidades

**Entity Framework Core** es el ORM oficial de .NET. El **`DbContext`** representa una sesión con la base y funciona
como **unidad de trabajo**: registra los cambios y los confirma juntos en `SaveChanges`.

```csharp
public class ShopDbContext(DbContextOptions<ShopDbContext> options) : DbContext(options)
{
    public DbSet<Order> Orders => Set<Order>();
    public DbSet<Product> Products => Set<Product>();

    protected override void OnModelCreating(ModelBuilder model)
    {
        model.Entity<Order>(order =>
        {
            order.HasKey(o => o.Id);
            order.Property(o => o.Status).HasConversion<string>().HasMaxLength(20);
            order.HasMany(o => o.Items).WithOne().HasForeignKey(i => i.OrderId);
            order.Property(o => o.Version).IsConcurrencyToken();
        });
    }
}

builder.Services.AddDbContext<ShopDbContext>(o =>
    o.UseNpgsql(builder.Configuration.GetConnectionString("Shop")));   // Scoped por defecto
```

```csharp
public async Task PayAsync(Guid orderId, CancellationToken ct)
{
    var order = await _db.Orders.SingleOrDefaultAsync(o => o.Id == orderId, ct)
                ?? throw new OrderNotFoundException(orderId);
    order.Pay();                         // regla de negocio en la entidad
    await _db.SaveChangesAsync(ct);      // EF detecta el cambio (change tracking) y genera el UPDATE
}
```

## Migraciones

El esquema se versiona con **migraciones** generadas a partir del modelo:

```bash
dotnet ef migrations add AddOrderVersion    # genera la migración en código
dotnet ef database update                    # la aplica
dotnet ef migrations script --idempotent     # genera SQL para aplicar en el pipeline
```

En producción conviene aplicarlas desde el pipeline de despliegue (con un script SQL revisado o un _bundle_), no
automáticamente al arrancar cada instancia, para evitar que varias réplicas migren al mismo tiempo.

```csharp
// Lectura: proyección a DTO, sin tracking implícito y sólo las columnas necesarias
var summaries = await _db.Orders
    .Where(o => o.CustomerId == customerId)
    .OrderByDescending(o => o.CreatedAt)
    .Select(o => new OrderSummary(o.Id, o.Status, o.Items.Sum(i => i.Price * i.Quantity), o.Items.Count))
    .Take(20)
    .ToListAsync(ct);

// Cuando necesitás entidades para leer: AsNoTracking
var products = await _db.Products.AsNoTracking().Where(p => p.Active).ToListAsync(ct);

// Cargar una relación en la misma consulta
var order = await _db.Orders.Include(o => o.Items).SingleAsync(o => o.Id == id, ct);
```

| Problema                                                    | Solución                                                                       |
| ----------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **N+1**: recorrer pedidos y acceder a sus ítems uno por uno | `Include` o proyección con `Select`                                            |
| Traer columnas de más                                       | Proyectar a DTOs                                                               |
| Explosión de filas al incluir varias colecciones            | `AsSplitQuery()`                                                               |
| Tracking innecesario en lecturas                            | `AsNoTracking()`                                                               |
| Actualizar o borrar miles de filas                          | `ExecuteUpdateAsync` / `ExecuteDeleteAsync` (EF Core 7+), sin cargar entidades |
| Filtrar en memoria por llamar `ToList()` antes de `Where`   | Mantener `IQueryable` hasta el final                                           |

Activá el log de SQL en desarrollo para ver qué consultas se generan: es la forma más rápida de detectar estos
problemas.

## Transacciones y concurrencia

`SaveChanges` ya es **transaccional**: todos los cambios pendientes se confirman o se revierten juntos. Para agrupar
varias operaciones:

```csharp
await using var tx = await _db.Database.BeginTransactionAsync(ct);
// ... varias operaciones y SaveChangesAsync
await tx.CommitAsync(ct);
```

**Concurrencia optimista**: con un token de concurrencia (una columna de versión, `xmin` en PostgreSQL o `rowversion`
en SQL Server), EF agrega la versión al `WHERE` del `UPDATE`. Si otro proceso modificó la fila, `SaveChanges` lanza
`DbUpdateConcurrencyException`, y se decide si recargar y reintentar o informar el conflicto.

## Testing

| Nivel       | Herramientas                                       | Qué prueba                                |
| ----------- | -------------------------------------------------- | ----------------------------------------- |
| Unitario    | xUnit (o NUnit) + fakes                            | Dominio y servicios sin infraestructura   |
| Integración | `WebApplicationFactory` + PostgreSQL en contenedor | La API completa con su pipeline y su base |

```csharp
public class OrdersApiTests(ShopApiFactory factory) : IClassFixture<ShopApiFactory>
{
    [Fact]
    public async Task Get_returns_404_for_unknown_order()
    {
        var client = factory.CreateClient();
        var response = await client.GetAsync($"/orders/{Guid.NewGuid()}");
        Assert.Equal(HttpStatusCode.NotFound, response.StatusCode);
    }
}

public class ShopApiFactory : WebApplicationFactory<Program>
{
    protected override void ConfigureWebHost(IWebHostBuilder builder) =>
        builder.UseSetting("ConnectionStrings:Shop", TestDatabase.ConnectionString);   // base de prueba (por ejemplo, con Testcontainers)
}
```

`WebApplicationFactory` levanta la aplicación en memoria con un servidor de prueba: los tests recorren el mismo
pipeline, middlewares e inyección de dependencias que producción. El proveedor en memoria de EF Core no reemplaza a una
base real: no tiene transacciones ni las mismas restricciones.

## Producción

- **Logging estructurado** con `ILogger` y plantillas de mensaje (`"Pedido {OrderId} pagado"`), exportado con
  OpenTelemetry o Serilog.
- **Health checks**: `builder.Services.AddHealthChecks()` y `app.MapHealthChecks("/health")` para los probes del
  orquestador; chequeos de dependencias como `AddNpgSql(...)` vienen de paquetes de la comunidad
  (AspNetCore.HealthChecks.\*).
- **Contenedores**: imagen multi-stage con `mcr.microsoft.com/dotnet/sdk` para compilar y `mcr.microsoft.com/dotnet/aspnet`
  para ejecutar; el SDK también puede publicar imágenes con `dotnet publish /t:PublishContainer`.
- **Apagado ordenado**: el host recibe SIGTERM y espera a que terminen las requests en curso durante un tiempo
  configurable.
- **Native AOT**: binarios con arranque muy rápido y menos memoria, con restricciones (sin reflexión dinámica
  irrestricta); conviene para funciones serverless o microservicios muy chicos.

## Resumen

EF Core simplifica el acceso a datos con DbContext, LINQ y migraciones, pero hay que mirar el SQL que genera:
proyecciones, AsNoTracking, Include sin N+1 y concurrencia optimista. Con tests de integración sobre
WebApplicationFactory, logging estructurado, health checks y contenedores, la API está lista para producción.
