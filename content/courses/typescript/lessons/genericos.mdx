## ¿Qué problema resuelve?

Imaginá una función que devuelve el primer elemento de un array. Sin genéricos hay dos opciones malas:

```ts
function firstAny(items: any[]): any {
  return items[0]; // perdés el tipo: todo lo que toques después es any
}

function firstMember(items: Member[]): Member | undefined {
  return items[0]; // correcto, pero hay que repetirla para Organization, Invoice...
}
```

Un **genérico** dice: "esta función funciona con cualquier tipo, y **el tipo de salida depende del de entrada**".

```ts
function first<T>(items: readonly T[]): T | undefined {
  return items[0];
}

const member = first(members); // Member | undefined (T se infiere como Member)
const name = first(["Ana", "Luis"]); // string | undefined
```

La idea es la misma que `List<T>` en C# o Java. Lo que cambia es **qué pasa en runtime** y **cómo se razona la
compatibilidad**.

## Funciones, interfaces y clases genéricas

```ts
// Función con dos parámetros de tipo relacionados
function mapValues<K extends string, V, R>(record: Record<K, V>, fn: (value: V) => R): Record<K, R> {
  const result = {} as Record<K, R>;
  for (const key in record) result[key] = fn(record[key]);
  return result;
}

// Interface genérica: el contrato de un repositorio
interface Repository<T, Id = string> {
  findById(id: Id): Promise<T | undefined>;
  save(entity: T): Promise<void>;
}

// Clase genérica
class InMemoryRepository<T extends { id: string }> implements Repository<T> {
  private readonly items = new Map<string, T>();

  async findById(id: string): Promise<T | undefined> {
    return this.items.get(id);
  }

  async save(entity: T): Promise<void> {
    this.items.set(entity.id, entity);
  }
}

const memberRepository = new InMemoryRepository<Member>();
```

`Id = string` es un **valor por defecto**: `Repository<Member>` equivale a `Repository<Member, string>`.

### Inferencia de argumentos genéricos

Casi nunca hace falta escribir `<Member>` al llamar una función: el compilador infiere `T` desde los argumentos.
Sólo se escribe cuando no hay nada de dónde inferir (como en `new InMemoryRepository<Member>()`, que no recibe
argumentos) o cuando la inferencia da un tipo más amplio que el deseado.

Para que la inferencia conserve literales en lugar de ensancharlos, existen los **const type parameters**:

```ts
function defineChannels<const T extends readonly string[]>(channels: T): T {
  return channels;
}

const channels = defineChannels(["sms", "email"]); // readonly ["sms", "email"], no string[]
```

## Restricciones con extends

`T extends X` significa "T puede ser cualquier tipo **asignable a X**". Como la compatibilidad es estructural, no
hace falta que T herede de nada: basta con que tenga la forma.

```ts
interface HasId {
  id: string;
}

function indexById<T extends HasId>(items: readonly T[]): Map<string, T> {
  return new Map(items.map((item) => [item.id, item]));
}

indexById(members); // ✅ Member tiene id
indexById([{ id: "x", extra: true }]); // ✅ cualquier objeto con id
indexById([1, 2, 3]); // ❌ number no tiene id
```

En C# esto sería `where T : IHasId` y requeriría que `Member` implemente `IHasId`. En TypeScript, cualquier objeto
con `id: string` cumple la restricción.

## keyof, typeof e indexed access

Tres operadores que trabajan **en el espacio de tipos** y permiten derivar un tipo de otro.

```ts
interface Organization {
  id: string;
  name: string;
  plan: "free" | "pro" | "enterprise";
  seats: number;
}

type OrganizationKey = keyof Organization; // "id" | "name" | "plan" | "seats"
type Plan = Organization["plan"]; // "free" | "pro" | "enterprise"   (indexed access)
type IdOrName = Organization["id" | "name"]; // string

const defaults = { channel: "sms", retries: 3 };
type Defaults = typeof defaults; // { channel: string; retries: number }  (typeof en posición de tipo)
```

Combinados con genéricos, permiten funciones que relacionan una clave con el tipo de su valor:

```ts
function getProperty<T, K extends keyof T>(obj: T, key: K): T[K] {
  return obj[key];
}

const organization: Organization = { id: "org_1", name: "Acme Learning", plan: "pro", seats: 25 };
const plan = getProperty(organization, "plan"); // "free" | "pro" | "enterprise"
getProperty(organization, "email"); // ❌ "email" no es keyof Organization

function sortBy<T, K extends keyof T>(items: readonly T[], key: K): T[] {
  return items.toSorted((a, b) => (a[key] < b[key] ? -1 : a[key] > b[key] ? 1 : 0));
}

sortBy(organizations, "seats"); // el editor autocompleta las claves válidas
```

### Derivar en lugar de duplicar

El valor de estos operadores es mantener **una sola fuente de verdad**. Por ejemplo, una lista de estados que se
usa en runtime (para un `<select>`) y también como tipo:

```ts
export const SUBSCRIPTION_STATUSES = ["trialing", "active", "cancelled"] as const;
export type SubscriptionStatus = (typeof SUBSCRIPTION_STATUSES)[number]; // "trialing" | "active" | "cancelled"
```

Agregar un estado al array actualiza el tipo automáticamente.

## Genéricos que sobran (y los que mienten)

```ts
// ❌ T aparece una sola vez: no relaciona nada
function logValue<T>(value: T): void {
  console.log(value);
}
// ✅ equivalente y más honesto
function logValueFixed(value: unknown): void {
  console.log(value);
}

// ❌ El genérico sólo sirve para "castear" el retorno: falsa seguridad
async function getJson<T>(url: string): Promise<T> {
  const response = await fetch(url);
  return response.json(); // any, se convierte en T sin verificar nada
}

// ✅ Un valor de runtime representa el tipo: el genérico se infiere del esquema
async function getJsonWith<T>(url: string, schema: { parse(data: unknown): T }): Promise<T> {
  const response = await fetch(url);
  return schema.parse(await response.json());
}
```

La regla: **un parámetro de tipo debería aparecer al menos dos veces** (en dos parámetros, o en un parámetro y el
retorno). Si aparece una vez, no aporta.

## Varianza en una sola sección

En C# se declara la varianza (`IEnumerable<out T>`, `Action<in T>`) y en Java se usa en el sitio de uso
(`List<? extends Member>`). TypeScript la **calcula estructuralmente**: un tipo genérico es compatible con otro si
sus miembros lo son.

```ts
interface Animal {
  name: string;
}
interface Dog extends Animal {
  bark(): void;
}

const dogs: Dog[] = [];
const animals: Animal[] = dogs; // ✅ compila (arrays son covariantes)
animals.push({ name: "gato" }); // ✅ compila... y ahora dogs contiene algo que no ladra
```

Los arrays mutables son covariantes por pragmatismo, lo que es técnicamente inseguro (Java tiene el mismo problema
con arrays y lanza `ArrayStoreException`; TypeScript no lanza nada). Usar `readonly Dog[]` en los parámetros evita
el problema. Para parámetros de funciones, `strictFunctionTypes` (incluido en `strict`) los chequea de forma
contravariante cuando se declaran como propiedades (`onEvent: (e: Event) => void`), pero no cuando se declaran como
métodos (`onEvent(e: Event): void`).

## Comparación con C# y Java

| Aspecto                 | C#                                 | Java                                      | TypeScript                                   |
| ----------------------- | ---------------------------------- | ----------------------------------------- | -------------------------------------------- |
| Runtime                 | Reificados: `typeof(T)`, `new T()` | Borrados, pero las clases existen         | Borrados por completo                        |
| Restricciones           | `where T : IHasId, new()`          | `<T extends HasId>` nominal               | `<T extends { id: string }>` estructural     |
| Varianza                | Declarada: `in`/`out`              | En el sitio de uso: `? extends`/`? super` | Calculada estructuralmente                   |
| Inferencia              | Desde argumentos                   | Desde argumentos y diamante `<>`          | Desde argumentos, contexto y retorno         |
| Derivar tipos de claves | `nameof`, reflection               | Reflection                                | `keyof`, `T[K]`, `typeof` en compilación     |
| Genéricos sobre valores | No                                 | No                                        | Literales como tipos: `K extends "a" \| "b"` |

## Errores frecuentes

- **Escribir `<T>` sin necesidad.** Si T no relaciona entradas y salidas, usá el tipo concreto o `unknown`.
- **`parseJson<T>()` sin validación.** El genérico sólo cambia el tipo estático; el dato sigue sin verificar.
- **Intentar `new T()` o `instanceof T`.** T no existe en runtime: pasá una fábrica (`() => T`) o un constructor.
- **Restricciones demasiado amplias.** `T extends object` acepta arrays y funciones; preferí la forma mínima que
  necesitás (`T extends { id: string }`).
- **Pasar argumentos genéricos explícitos que contradicen la inferencia.** Si la inferencia da un tipo inesperado,
  casi siempre el problema está en la firma.
- **Confundir `typeof` de JavaScript con el de tipos.** En una expresión devuelve un string en runtime; en una
  posición de tipo obtiene el tipo de una variable.
