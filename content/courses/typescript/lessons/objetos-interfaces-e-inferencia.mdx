## ¿Qué problema resuelve?

En C# o Java, para pasar datos entre capas se crea una clase o un `record`: `GuestDto`, `BookingResponse`. En
TypeScript casi nunca se hace eso. Los datos son **objetos simples** (vienen de JSON, de la base de datos, de un
formulario) y lo que se necesita es **describir su forma** para que el compilador ayude.

Modelar bien esas formas tiene consecuencias directas: un estado de reserva tipado como `string` acepta `"confirmada"`,
`"Confirmed"` o `"cnfrmd"`; tipado como `"pending" | "confirmed" | "cancelled"`, el compilador rechaza cualquier otro valor y el
editor autocompleta los válidos. Esta lección cubre las herramientas para lograrlo.

## interface y type

```ts
// interface: describe la forma de un objeto
interface Guest {
  id: string;
  name: string;
  email?: string;
}

// type alias: le da nombre a cualquier tipo
type GuestId = string;
type BookingStatus = "pending" | "confirmed" | "cancelled";
type Money = { amountCents: number; currency: "ARS" | "USD" };
```

Para objetos, ambos sirven y son casi equivalentes. Las diferencias reales:

| Capacidad                                    | `interface` |       `type`        |
| -------------------------------------------- | :---------: | :-----------------: |
| Describir objetos                            |     Sí      |         Sí          |
| Extender (`extends`) / componer (`&`)        |     Sí      |         Sí          |
| Uniones (`A \| B`), tuplas, primitivos       |     No      |         Sí          |
| Tipos derivados (mapped, conditional)        |     No      |         Sí          |
| Declaration merging (se reabre y amplía)     |     Sí      |         No          |
| Una clase puede implementarlo (`implements`) |     Sí      | Sí, si es un objeto |

```ts
interface Auditable {
  createdAt: string;
  updatedAt: string;
}

// Extender con interface
interface Booking extends Auditable {
  id: string;
  status: BookingStatus;
}

// Componer con type (intersection)
type BookingWithGuest = Booking & { guest: Guest };
```

**Declaration merging** permite ampliar un tipo declarado en otro lugar, por ejemplo para agregar propiedades a un
tipo de una librería:

```ts
declare global {
  interface Window {
    analytics?: { track(event: string): void };
  }
}
```

<Callout type="tip" title="Una convención práctica">
  `interface` para contratos de objetos (DTOs, puertos, props) y `type` para uniones, alias y tipos derivados.
  Más importante que la regla elegida es que todo el equipo la siga.
</Callout>

## Propiedades opcionales y readonly

```ts
interface RoomHold {
  readonly id: string; // no se puede reasignar a través de este tipo
  roomId: string;
  checkIn: string;
  note?: string; // puede no estar
}

const hold: RoomHold = { id: "hold_1", roomId: "room_204", checkIn: "2026-12-01" };
hold.note = "Llega tarde, después de las 23"; // ✅
hold.id = "hold_2"; // ❌ Cannot assign to 'id' because it is a read-only property
```

Tres matices importantes:

1. **`readonly` sólo existe en compilación.** En runtime el objeto es mutable. Para congelarlo hace falta
   `Object.freeze`, que además es superficial.
2. **Es superficial:** `readonly guest: Guest` impide reasignar `guest`, pero no `guest.name`.
3. **Para arrays** se usa `readonly Booking[]` o `ReadonlyArray<Booking>`, que quita `push`, `sort` y el resto de los
   métodos que mutan. Es una buena práctica en parámetros: documenta que la función no modifica lo que recibe.

```ts
function countBookings(bookings: readonly Booking[]): number {
  bookings.push(); // ❌ Property 'push' does not exist on type 'readonly Booking[]'
  return bookings.length;
}
```

Con `exactOptionalPropertyTypes`, `note?: string` significa "puede faltar", y asignar explícitamente
`note: undefined` es un error. Sin esa opción, ambos casos son iguales. La distinción importa cuando "ausente" y
"vacío" tienen significados distintos, por ejemplo en un `PATCH` donde `undefined` es "no cambiar".

## Diccionarios: index signatures y Record

```ts
// Index signature: cualquier clave string
interface FreeRoomsByDate {
  [date: string]: number;
}

// Record: forma abreviada, muy usada
type AvailabilityMap = Record<string, number>;

// Record con claves finitas: obliga a definir todas
const statusLabel: Record<BookingStatus, string> = {
  pending: "Pendiente de pago",
  confirmed: "Confirmada",
  cancelled: "Cancelada",
}; // si falta una clave o sobra otra, error de compilación

const availability: AvailabilityMap = {};
const freeRooms = availability["2026-12-01"]; // number | undefined con noUncheckedIndexedAccess
```

Para diccionarios dinámicos con muchas inserciones y borrados, `Map<string, number>` es mejor opción: tiene
`has`, `size`, iteración ordenada y no mezcla claves con propiedades heredadas.

## Literal types y widening

Un **literal type** es un tipo que admite un solo valor: `"confirmed"`, `42`, `true`. Por sí solos parecen inútiles; en
uniones son la forma idiomática de modelar conjuntos cerrados de valores (lo que en C# o Java sería un `enum`):

```ts
type Channel = "sms" | "email" | "whatsapp";
type HttpSuccess = 200 | 201 | 204;

function send(channel: Channel, message: string) {}

send("sms", "Hola"); // ✅
send("fax", "Hola"); // ❌ '"fax"' is not assignable to parameter of type 'Channel'
```

¿Qué tipo infiere el compilador para un valor literal? Depende de si puede cambiar:

```ts
const a = "sms"; // tipo: "sms"  (const no puede cambiar, se conserva el literal)
let b = "sms"; // tipo: string (let puede reasignarse: se "ensancha")

const config = { channel: "sms", retries: 3 };
// tipo: { channel: string; retries: number }: las propiedades son mutables, se ensanchan

send(config.channel, "Hola"); // ❌ string no es asignable a Channel
```

Ese ensanchamiento se llama **widening**. Hay tres formas de evitarlo, con significados distintos:

```ts
// 1. as const: todo pasa a ser literal y readonly
const config1 = { channel: "sms", retries: 3 } as const;
// { readonly channel: "sms"; readonly retries: 3 }

// 2. Anotación: el valor se verifica contra el tipo, pero el tipo de la variable ES el anotado
interface ReminderConfig {
  channel: Channel;
  retries: number;
}
const config2: ReminderConfig = { channel: "sms", retries: 3 };
// config2.channel es Channel, no "sms"

// 3. satisfies: verifica contra el tipo y conserva lo inferido
const config3 = { channel: "sms", retries: 3 } satisfies ReminderConfig;
// config3.channel es "sms"; un typo como "smss" sería un error
```

`satisfies` brilla en objetos de configuración, mapas de rutas o tablas de traducciones: querés que el compilador
**verifique** la estructura sin **perder** el detalle de las claves concretas.

```ts
const routes = {
  bookings: "/bookings",
  rooms: "/rooms",
} satisfies Record<string, `/${string}`>;

routes.bookings; // tipo "/bookings": autocompletado de claves concretas
routes.payments; // ❌ no existe: con una anotación Record<string, ...> habría compilado
```

## Enums: por qué se usan menos

TypeScript tiene `enum`, pero la mayoría de los equipos prefiere uniones de literales:

```ts
enum BookingStatusEnum {
  Pending = "pending",
  Confirmed = "confirmed",
}

type BookingStatusUnion = "pending" | "confirmed";
const BOOKING_STATUSES = ["pending", "confirmed"] as const; // si además necesitás iterar los valores
type BookingStatusFromArray = (typeof BOOKING_STATUSES)[number]; // "pending" | "confirmed"
```

Razones: un `enum` genera código en runtime (no es borrable), los enums numéricos aceptan cualquier número y los
valores de un JSON (`"confirmed"`) no son asignables a un enum sin conversión. La unión de literales no tiene ninguno de
esos problemas.

## Funciones como tipos

```ts
// Tipo de función
type Formatter = (amountCents: number, currency: string) => string;

// Método en una interface: dos sintaxis
interface Notifier {
  send(to: string, message: string): Promise<void>; // sintaxis de método
  onError: (error: unknown) => void; // sintaxis de propiedad
}

// Sobrecargas: varias firmas, una implementación
function parseAmount(value: string): number;
function parseAmount(value: number): number;
function parseAmount(value: string | number): number {
  return typeof value === "number" ? value : Number.parseInt(value, 10);
}
```

Las sobrecargas existen, pero se usan poco: una unión en el parámetro o dos funciones con nombres distintos suelen
ser más claras. Una sola implementación recibe todas las variantes, porque en runtime no hay dispatch por tipo.

## Comparación con C# y Java

| Necesidad                      | C#                         | Java                       | TypeScript                      |
| ------------------------------ | -------------------------- | -------------------------- | ------------------------------- |
| DTO / forma de datos           | `record`, clase            | `record`, clase            | `interface` o `type`, sin clase |
| Conjunto cerrado de valores    | `enum`                     | `enum`                     | Unión de literales              |
| Propiedad inmutable            | `init`, `readonly`         | `final`                    | `readonly` (sólo compilación)   |
| Diccionario                    | `Dictionary<K,V>`          | `Map<K,V>`                 | `Record<K,V>` o `Map<K,V>`      |
| Ampliar un tipo de librería    | Métodos de extensión       | No                         | Declaration merging             |
| Verificar sin perder precisión | No hay equivalente directo | No hay equivalente directo | `satisfies`                     |

## Errores frecuentes

- **Tipar estados como `string`.** Perdés autocompletado y verificación. Usá uniones de literales.
- **Creer que `readonly` protege en runtime.** Es un contrato del compilador; los datos se pueden mutar desde otra
  referencia o desde JavaScript.
- **Usar `as const` para todo.** Convierte todo en readonly y literal; está bien para constantes, no para objetos que
  después vas a modificar.
- **Anotar configuraciones con `Record<string, X>`.** Perdés la verificación de claves concretas; usá `satisfies`.
- **Confiar en que una propiedad de un index signature existe.** Sin `noUncheckedIndexedAccess`, `availability[date]` se
  tipa como `number` aunque la clave no exista.
- **Usar enums numéricos.** `enum Level { Low, High }` acepta `Level = 99` sin error.
