## ¿Qué problema resuelve?

Pensá en el estado de un viaje en una app de movilidad. Un modelo típico de C# o Java sería una clase con todos los
campos posibles y muchos nullables:

```ts
interface TripBad {
  status: "requested" | "assigned" | "completed" | "cancelled";
  driverId?: string; // sólo si status es "assigned" o "completed"
  completedAt?: string; // sólo si status es "completed"
  fareCents?: number; // sólo si status es "completed"
  cancellationReason?: string; // sólo si status es "cancelled"
}
```

Este modelo admite estados absurdos: un viaje `"completed"` sin `fareCents`, o `"requested"` con
`cancellationReason`. Cada
función que la use tiene que adivinar qué campos existen, y el compilador no puede ayudar. **Uniones y narrowing**
permiten modelar sólo los estados válidos y que el compilador verifique que cada caso se maneja.

## Uniones e intersecciones

Una **unión** `A | B` es un valor que puede ser de cualquiera de los tipos. Una **intersección** `A & B` es un valor
que es de ambos tipos a la vez.

```ts
type Identifier = string | number;

function normalize(id: Identifier): string {
  id.toUpperCase(); // ❌ toUpperCase no existe en number
  return String(id); // ✅ String() acepta ambos
}

type WithTimestamps = { createdAt: string; updatedAt: string };
type Trip = { id: string; passengerId: string };
type StoredTrip = Trip & WithTimestamps; // tiene las cuatro propiedades
```

Con una unión, **sólo podés usar lo que es común a todos los miembros**. Para usar algo específico, primero hay que
averiguar cuál de los tipos es: eso es el **narrowing**.

<Callout type="info" title="Pensar en conjuntos">
  Un tipo es un conjunto de valores. `string | number` es la unión de dos conjuntos (más valores posibles,
  menos operaciones seguras). `A & B` es la intersección (menos valores posibles, más propiedades
  garantizadas). `never` es el conjunto vacío y `unknown` es el conjunto de todos los valores.
</Callout>

## null, undefined y strictNullChecks

Con `strict` activado, `null` y `undefined` **no** forman parte de `string` ni de ningún otro tipo. Si un valor puede
faltar, el tipo lo dice:

```ts
function findDriver(id: string): Driver | undefined {
  return drivers.get(id);
}

const driver = findDriver("drv_1");
driver.name; // ❌ 'driver' is possibly 'undefined'
driver?.name; // ✅ string | undefined
if (driver) driver.name; // ✅ string
```

Es lo mismo que los _nullable reference types_ de C# (`Driver?`), pero obligatorio y sin warnings ignorables.
Java no tiene equivalente en el lenguaje: se usa `Optional<T>` o anotaciones `@Nullable`.

## Narrowing: cómo el compilador estrecha tipos

El compilador sigue el **flujo de control** de tu código. Dentro de una rama en la que se verificó algo, el tipo de
la variable se reduce.

```ts
function describe(value: string | number | Date | null | undefined): string {
  if (value == null) return "vacío"; // cubre null y undefined

  if (typeof value === "string") return value.toUpperCase(); // value: string
  if (typeof value === "number") return value.toFixed(2); // value: number

  return value.toISOString(); // value: Date (lo único que queda)
}
```

| Técnica         | Ejemplo                         | Estrecha a                                                                       |
| --------------- | ------------------------------- | -------------------------------------------------------------------------------- |
| `typeof`        | `typeof x === "string"`         | Primitivos: string, number, boolean, bigint, symbol, undefined, function, object |
| `instanceof`    | `error instanceof HttpError`    | Instancias de una clase (existe en runtime)                                      |
| `in`            | `"fareCents" in trip`           | Miembros de la unión que tienen esa propiedad                                    |
| Igualdad        | `trip.status === "completed"`   | Miembros con ese literal                                                         |
| Truthiness      | `if (driver)`                   | Quita `null`, `undefined` (y otros falsy)                                        |
| `Array.isArray` | `Array.isArray(input)`          | Arrays                                                                           |
| Asignación      | `let x: string \| number = "a"` | El tipo del valor asignado                                                       |

<Callout type="warning" title="typeof null es 'object'">
  Es un error histórico de JavaScript que se mantiene por compatibilidad. Por eso un chequeo de objeto
  correcto es `typeof value === "object" && value !== null`.
</Callout>

### Type predicates: narrowing reutilizable

Cuando el chequeo es complejo o se repite, se encapsula en una función que devuelve `value is T`:

```ts
interface ToolCall {
  name: string;
  arguments: Record<string, unknown>;
}

function isToolCall(value: unknown): value is ToolCall {
  return (
    typeof value === "object" &&
    value !== null &&
    "name" in value &&
    typeof value.name === "string" &&
    "arguments" in value &&
    typeof value.arguments === "object" &&
    value.arguments !== null
  );
}

const messages: unknown[] = await loadMessages();
const toolCalls = messages.filter(isToolCall); // ToolCall[]
```

Desde TypeScript 5.5, el compilador **infiere** predicates simples: `items.filter((x) => x !== undefined)` ya
devuelve un array sin `undefined`.

**El riesgo:** el compilador confía en el predicate sin verificar su implementación. Si te olvidás de chequear una
propiedad, el tipo miente. Para contratos externos, un esquema (Zod) es más seguro; lo vemos en _APIs type-safe_.

### Assertion functions

Una variante que, en lugar de devolver un booleano, **lanza** si el valor no cumple:

```ts
function assertDefined<T>(value: T, message: string): asserts value is NonNullable<T> {
  if (value === undefined || value === null) throw new Error(message);
}

const driver = findDriver("drv_1");
assertDefined(driver, "El conductor debería existir");
driver.name; // ✅ a partir de acá es Driver
```

## Discriminated unions

La solución al modelo de viaje del principio: **un tipo por estado**, todos con una propiedad literal común.

```ts
type Trip =
  | { status: "requested"; id: string; passengerId: string }
  | { status: "assigned"; id: string; passengerId: string; driverId: string }
  | {
      status: "completed";
      id: string;
      passengerId: string;
      driverId: string;
      completedAt: string;
      fareCents: number;
    }
  | { status: "cancelled"; id: string; passengerId: string; cancellationReason: string };

function describeTrip(trip: Trip): string {
  switch (trip.status) {
    case "requested":
      return "Buscando conductor";
    case "assigned":
      return `Conductor ${trip.driverId} en camino`; // driverId existe sólo en assigned y completed
    case "completed":
      return `Finalizado el ${trip.completedAt}: ${trip.fareCents}`;
    case "cancelled":
      return `Cancelado: ${trip.cancellationReason}`;
  }
}
```

Ventajas concretas:

- **Estados inválidos imposibles:** no se puede construir un viaje `"completed"` sin `fareCents`.
- **Autocompletado preciso:** dentro de cada `case`, el editor muestra sólo las propiedades de ese estado.
- **Transiciones tipadas:** una función `complete(trip: Extract<Trip, { status: "assigned" }>)` sólo acepta
  viajes con conductor asignado.

### Chequeo exhaustivo con never

¿Qué pasa si mañana se agrega el estado `"in_progress"`? Con un `default` que asigna a `never`, **cada switch
incompleto deja de compilar**:

```ts
function assertNever(value: never): never {
  throw new Error(`Caso no contemplado: ${JSON.stringify(value)}`);
}

function nextAction(trip: Trip): string {
  switch (trip.status) {
    case "requested":
      return "find_driver";
    case "assigned":
      return "track_driver";
    case "completed":
    case "cancelled":
      return "none";
    default:
      return assertNever(trip); // si falta un caso, trip no es never y no compila
  }
}
```

Después de los `case`, el narrowing deja a `trip` sin tipos posibles: `never`. Si se agrega un estado nuevo y no se
maneja, en el `default` `trip` tiene el tipo del estado nuevo, que no es asignable a `never`, y aparece el error.

## Type assertions y non-null: cuándo mienten

```ts
const input = document.getElementById("destination") as HTMLInputElement; // afirmación: puede ser null o un div
const driver = drivers.get(id)!; // ! afirma que no es undefined
```

Ninguna de las dos ejecuta un chequeo. Si estás equivocado, el error aparece después, como un `TypeError: Cannot
read properties of undefined`, lejos de donde se originó. Alternativas más seguras:

```ts
const element = document.getElementById("destination");
if (!(element instanceof HTMLInputElement)) throw new Error("Falta el input de destino");

const driver = drivers.get(id);
if (!driver) throw new DriverNotFoundError(id);
```

Las aserciones tienen usos legítimos (el constructor de un branded type después de validar, tipos que el
compilador no puede inferir en código de bajo nivel), pero cada una es un punto donde **vos** sos responsable de la
corrección.

## Comparación con C# y Java

| Concepto             | C#                                           | Java                                                 | TypeScript                                 |
| -------------------- | -------------------------------------------- | ---------------------------------------------------- | ------------------------------------------ |
| Tipo "uno de varios" | Jerarquía de clases o `OneOf` (librería)     | `sealed interface` + `record` (Java 17+)             | Unión `A \| B`, sin clases                 |
| Estrechar el tipo    | `if (x is Completed c)`, switch con patrones | `if (x instanceof Completed c)`, switch con patrones | `typeof`, `in`, igualdad del discriminante |
| Exhaustividad        | Warning en switch expressions                | Error con sealed + switch                            | `never` en el default                      |
| Nulabilidad          | `string?` (warnings)                         | `Optional<T>`                                        | `string \| undefined` (errores)            |
| Cast                 | `(Completed)x` con chequeo en runtime        | `(Completed) x` con chequeo en runtime               | `x as Completed` **sin** chequeo           |

La diferencia clave está en la última fila: un cast en C# o Java lanza `InvalidCastException` o
`ClassCastException` si el objeto no es del tipo. En TypeScript, `as` no hace nada en runtime.

## Errores frecuentes

- **Modelar estados con propiedades opcionales** en lugar de una discriminated union.
- **Olvidar el `default` con `assertNever`.** Sin él, un caso nuevo puede devolver `undefined` silenciosamente.
- **Usar `if (value)` para chequear números o strings.** `0` y `""` son falsy; usá `!== undefined`.
- **Discriminar por una propiedad que no es literal.** Si `status` es `string` en algún miembro, el narrowing no
  funciona.
- **Predicates incompletos.** `value is ToolCall` que sólo verifica `name` deja pasar objetos sin `arguments`.
- **Desestructurar antes de estrechar.** `const { status, fareCents } = trip` falla porque `fareCents` no existe en
  todos los miembros; primero se chequea `trip.status`.
