## ¿Qué problema resuelve?

Las lecciones anteriores cubrieron el lenguaje. Esta cubre **cómo se diseña** con él. Quien viene de C# o Java
suele hacer una de dos cosas: replicar todo el andamiaje del ecosistema (`ICartService`, `CartServiceImpl`,
contenedores de DI con decoradores, clases para todo) o, al revés, abandonar toda estructura porque "en JavaScript
se hace así". Ninguna de las dos escala.

El objetivo es un código donde **la lógica de negocio sea pura y testeable**, **los efectos estén en los bordes** y
**los errores esperables sean visibles en los tipos**.

## Organización de módulos

Organizá por **funcionalidad** (lo que el sistema hace), no por tipo técnico:

```text
src/
  modules/
    cart/
      domain/          entidades, reglas puras, tipos
      application/     casos de uso; definen los puertos que necesitan
      infrastructure/  implementaciones: Postgres, HTTP, colas
      index.ts         API pública del módulo
    orders/
    payments/
  infrastructure/
    composition/       crea y conecta las implementaciones
```

Reglas que mantienen esto sano:

- **API pública explícita:** otros módulos importan desde `modules/cart` (su `index.ts`), no desde archivos
  internos.
- **Dependencias hacia el dominio:** `domain` no importa nada de `infrastructure`; `infrastructure` sí importa del
  dominio.
- **Sin ciclos:** si `orders` importa de `payments` y `payments` de `orders`, falta un concepto o un evento en el
  medio. Herramientas como `dependency-cruiser` o reglas de lint lo verifican.
- **Cuidado con los barrels gigantes:** un `index.ts` que reexporta todo un proyecto empeora los tiempos de build y
  favorece los ciclos. Un barrel por módulo, con lo que es realmente público, está bien.

Este mismo proyecto usa esa estructura (ver `src/modules`) y un test de arquitectura verifica la dirección de las
dependencias.

## Funciones puras e inmutabilidad

Una **función pura** devuelve siempre lo mismo para la misma entrada y no produce efectos (no lee el reloj, no
escribe en la base, no muta sus argumentos).

```ts
// ❌ Impura: lee el reloj, muta el argumento y escribe en la base
async function registerCoupon(cart: Cart, coupon: Coupon): Promise<void> {
  if (new Date(coupon.expiresAt) < new Date()) throw new Error("Cupón vencido");
  cart.couponCode = coupon.code;
  cart.discountPct = coupon.discountPct;
  await db.carts.update(cart);
}

// ✅ Núcleo puro: recibe el "ahora" y devuelve un carrito nuevo
type CouponError = { kind: "coupon_expired" } | { kind: "cart_checked_out" };

function applyCoupon(cart: Cart, coupon: Coupon, now: Date): Result<Cart, CouponError> {
  if (cart.status === "checked_out") return err({ kind: "cart_checked_out" });
  if (new Date(coupon.expiresAt) < now) return err({ kind: "coupon_expired" });
  return ok({ ...cart, couponCode: coupon.code, discountPct: coupon.discountPct });
}
```

La versión pura se testea con una línea, sin base de datos ni fechas falsas globales. El caso de uso que la llama
se encarga de los efectos: leer el carrito y el cupón, obtener la hora, persistir el resultado.

Para no mutar, se usan copias (`{ ...cart, couponCode }`), `readonly` en los tipos y métodos no mutantes (`toSorted`,
`map`, `filter`). La inmutabilidad no es dogma: dentro de una función, mutar una variable local es perfectamente
razonable; lo que se evita es mutar **lo que recibiste o lo compartido**.

## Inversión de dependencias sin framework

El caso de uso define **qué necesita** con interfaces; la infraestructura las implementa; un único lugar las conecta.

```ts
// application/ports.ts: el caso de uso define lo que necesita
export interface CartRepository {
  findById(id: CartId): Promise<Cart | undefined>;
  save(cart: Cart): Promise<void>;
}

export interface CouponRepository {
  findByCode(code: string): Promise<Coupon | undefined>;
}

export interface Clock {
  now(): Date;
}

// application/apply-coupon.ts
export class ApplyCouponUseCase {
  constructor(
    private readonly carts: CartRepository,
    private readonly coupons: CouponRepository,
    private readonly clock: Clock,
  ) {}

  async execute(input: {
    cartId: CartId;
    couponCode: string;
  }): Promise<Result<void, CouponError | { kind: "cart_not_found" } | { kind: "coupon_not_found" }>> {
    const cart = await this.carts.findById(input.cartId);
    if (!cart) return err({ kind: "cart_not_found" });
    const coupon = await this.coupons.findByCode(input.couponCode);
    if (!coupon) return err({ kind: "coupon_not_found" });

    const result = applyCoupon(cart, coupon, this.clock.now());
    if (!result.ok) return result;

    await this.carts.save(result.value);
    return ok(undefined);
  }
}

// infrastructure/composition/cart.ts: el composition root
export function createCartModule(db: Database) {
  return {
    applyCoupon: new ApplyCouponUseCase(new PostgresCartRepository(db), new PostgresCouponRepository(db), {
      now: () => new Date(),
    }),
  };
}
```

No hacen falta decoradores ni contenedores: el constructor **es** la inyección. Si preferís un estilo funcional,
una función fábrica (`createApplyCoupon({ carts, coupons, clock })`) que devuelve una función cumple el mismo rol.

## Errores esperables: el tipo Result

TypeScript no tiene excepciones chequeadas: **nada en la firma dice qué puede lanzar una función**. Para errores
que son parte del negocio (y que el llamador **tiene** que manejar), un tipo `Result` los hace visibles:

```ts
export type Result<T, E> = { ok: true; value: T } | { ok: false; error: E };

export const ok = <T>(value: T): Result<T, never> => ({ ok: true, value });
export const err = <E>(error: E): Result<never, E> => ({ ok: false, error });
```

```ts
const result = await applyCouponUseCase.execute({ cartId, couponCode });

if (!result.ok) {
  switch (result.error.kind) {
    case "cart_not_found":
    case "coupon_not_found":
      return Response.json({ error: result.error.kind }, { status: 404 });
    case "cart_checked_out":
      return Response.json({ error: "cart_already_checked_out" }, { status: 409 });
    case "coupon_expired":
      return Response.json({ error: "coupon_expired" }, { status: 422 });
  }
}
return new Response(null, { status: 204 });
```

| Situación                                    | Mecanismo                               |
| -------------------------------------------- | --------------------------------------- |
| Regla de negocio no cumplida (stock, estado) | `Result` con un error tipado            |
| Dato de entrada inválido                     | Parseo en el límite (esquema) → 4xx     |
| Falla de infraestructura (DB caída, timeout) | Excepción; se captura en el borde → 5xx |
| Bug (estado imposible, invariante rota)      | Excepción; se registra y se alerta      |

Practicá esta técnica en el challenge [Tipo Result](/challenges/result-type).

## Testing con Vitest

Vitest es el runner estándar en proyectos con Vite o TypeScript moderno; su API es compatible con Jest.

```ts
import { describe, expect, it } from "vitest";

describe("applyCoupon", () => {
  const now = new Date("2026-11-19T10:00:00Z");
  const cart: Cart = { id: "cart_1" as CartId, status: "open", items: [] };
  const blackFriday: Coupon = { code: "BF2026", discountPct: 20, expiresAt: "2026-12-01T00:00:00Z" };

  it("aplica un cupón vigente", () => {
    expect(applyCoupon(cart, blackFriday, now)).toEqual({
      ok: true,
      value: { ...cart, couponCode: "BF2026", discountPct: 20 },
    });
  });

  it("rechaza cupones vencidos", () => {
    const expired = { ...blackFriday, expiresAt: "2026-11-01T00:00:00Z" };
    expect(applyCoupon(cart, expired, now)).toEqual({
      ok: false,
      error: { kind: "coupon_expired" },
    });
  });
});
```

Para el caso de uso, en lugar de mockear cada método, se usa un **fake en memoria** que implementa el puerto:

```ts
class InMemoryCartRepository implements CartRepository {
  readonly items = new Map<string, Cart>();
  async findById(id: CartId) {
    return this.items.get(id);
  }
  async save(cart: Cart) {
    this.items.set(cart.id, cart);
  }
}

it("guarda el carrito con el cupón aplicado", async () => {
  const carts = new InMemoryCartRepository();
  carts.items.set("cart_1", cart);
  const coupons = { findByCode: async () => blackFriday };
  const useCase = new ApplyCouponUseCase(carts, coupons, { now: () => now });

  await useCase.execute({ cartId: "cart_1" as CartId, couponCode: "BF2026" });

  expect(carts.items.get("cart_1")?.couponCode).toBe("BF2026"); // se verifica el estado, no las llamadas
});
```

El test verifica **comportamiento observable** (el estado final), no **cómo** se llegó (qué métodos se llamaron).
Si mañana el caso de uso hace una consulta menos, el test sigue pasando. Los mocks (`vi.fn()`, `vi.spyOn`) se
reservan para efectos que no se pueden observar de otra forma, como "se envió un email".

<Callout type="tip" title="La pirámide en TypeScript">
  Muchos tests unitarios del núcleo puro (milisegundos), algunos de integración contra una base real o
  embebida (en este proyecto, PGlite) y pocos end-to-end con Playwright para los flujos críticos.
</Callout>

## Refactoring y anti-patterns

El sistema de tipos es la mejor red de seguridad para refactorizar: renombrar, extraer funciones o cambiar una
unión produce errores en todos los lugares afectados. Algunos anti-patterns frecuentes al venir de C# o Java:

| Anti-pattern                                                   | Por qué molesta en TypeScript                | Alternativa                                |
| -------------------------------------------------------------- | -------------------------------------------- | ------------------------------------------ |
| `ICartService` + `CartServiceImpl` con una sola implementación | Ceremonia sin beneficio                      | Interface sólo donde hay un puerto real    |
| Clases sólo con métodos estáticos                              | Un módulo ya agrupa funciones                | Funciones exportadas                       |
| Getters y setters triviales                                    | Ruido; las propiedades ya son accesibles     | Propiedades `readonly` o públicas          |
| DTO = entidad = fila de la base                                | Acopla API, dominio y persistencia           | Tipos por capa con mapeo en los límites    |
| `any` "temporal"                                               | Se contagia y nunca se saca                  | `unknown` + validación                     |
| Excepciones para el flujo normal                               | Invisibles en la firma                       | `Result` para errores esperables           |
| Mocks de todo                                                  | Tests frágiles que repiten la implementación | Fakes en memoria y tests de comportamiento |

### Optimización

Optimizá con mediciones, no por intuición. En TypeScript los costos reales suelen estar en la I/O (consultas N+1,
llamadas secuenciales que podían ser concurrentes, falta de caché) y no en la diferencia entre `for` y `map`. En el
compilador, los tipos recursivos profundos y los barrels gigantes son los que alargan los tiempos de build.

## Comparación con C# y Java

| Tema                      | C#                                         | Java                   | TypeScript                                     |
| ------------------------- | ------------------------------------------ | ---------------------- | ---------------------------------------------- |
| Unidad de organización    | Proyecto, namespace                        | Módulo, package        | Módulo ES (archivo) y carpetas por feature     |
| Inyección de dependencias | Contenedor integrado (MS.DI)               | Spring                 | Constructor/fábricas + composition root        |
| Errores esperables        | Excepciones o `OneOf`/`Result` (librerías) | Excepciones chequeadas | `Result` como discriminated union              |
| Tests                     | xUnit/NUnit + Moq                          | JUnit + Mockito        | Vitest/Jest + fakes; `vi.fn` cuando hace falta |
| Inmutabilidad             | `record`, `init`, `ImmutableList`          | `record`, `List.of`    | `readonly`, spread, `as const`                 |

## Errores frecuentes

- **Lógica de negocio en el handler HTTP o en el componente.** No se puede testear sin levantar todo.
- **Leer `new Date()` o `Math.random()` dentro del dominio.** Inyectá el reloj y la fuente de aleatoriedad.
- **Funciones que a veces devuelven Result y a veces lanzan** por errores de negocio.
- **Tests que verifican llamadas internas** en lugar de resultados.
- **Ciclos entre módulos** resueltos con imports dinámicos o "hacks" en lugar de revisar los límites.
- **Copiar la arquitectura de un proyecto Java grande** a un servicio de 2.000 líneas.
