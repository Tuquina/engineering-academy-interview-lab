## ¿Qué problema resuelve?

La lección anterior explicó qué es una Promise y cómo combinarlas. Con eso alcanza para escribir código que
funciona **cuando todo sale bien**. En producción, una plataforma que llama a transportistas, proveedores de mensajería,
modelos de lenguaje y APIs de terceros enfrenta otra realidad:

- La API de un transportista tarda 40 segundos en responder en lugar de 300 ms.
- El usuario cerró la pestaña y la request ya no le importa a nadie, pero el servidor sigue trabajando.
- El cierre del día dispara 10.000 cotizaciones de envío a la vez y el transportista responde `429 Too Many Requests`.
- Dos webhooks del mismo pago llegan casi juntos y el saldo queda mal.
- Un error transitorio se reintenta inmediatamente, mil veces, y empeora la caída del proveedor.

Esta lección cubre las herramientas para cada uno de esos problemas.

## Cancelación con AbortController

Una Promise **no se puede cancelar**: representa un resultado futuro, no el trabajo que lo produce. Lo que se
cancela es **el trabajo**, y para eso JavaScript usa un mecanismo cooperativo: `AbortController` y `AbortSignal`.

```ts
const controller = new AbortController();

const responsePromise = fetch("https://api.carrier.example/rates", { signal: controller.signal });

controller.abort(); // fetch se interrumpe y la Promise se rechaza con un AbortError
```

- El **controller** es quien cancela; la **signal** es lo que se pasa a quien trabaja.
- `fetch`, `setTimeout` de `node:timers/promises`, `fs/promises`, streams y la mayoría de los SDKs modernos aceptan
  `signal`.
- El código propio debe **cooperar**: chequear `signal.aborted`, llamar a `signal.throwIfAborted()` o escuchar el
  evento `abort`.

```ts
/** Actualiza el seguimiento de los envíos hasta terminar o hasta que se cancele la señal. */
async function syncTracking(shipmentIds: readonly string[], signal: AbortSignal): Promise<number> {
  let updated = 0;
  for (const shipmentId of shipmentIds) {
    signal.throwIfAborted(); // corta entre iteraciones si se canceló
    await carrier.track(shipmentId, { signal }); // y propaga la señal hacia abajo
    updated++;
  }
  return updated;
}
```

La señal se pasa **como parámetro por todas las capas**, del handler HTTP al cliente del proveedor. Es exactamente
el patrón de `CancellationToken` en .NET.

## Timeouts

Una llamada de red sin timeout es un recurso que puede quedar retenido para siempre. `AbortSignal.timeout(ms)` crea
una señal que se aborta sola:

```ts
const response = await fetch(url, { signal: AbortSignal.timeout(5_000) });
```

Para combinar "el cliente se fue" con "se agotó el tiempo", `AbortSignal.any` crea una señal que se aborta cuando
cualquiera de las otras lo hace:

```ts
export async function GET(request: Request): Promise<Response> {
  const signal = AbortSignal.any([request.signal, AbortSignal.timeout(8_000)]);
  try {
    const summary = await llmClient.summarize(conversationId, { signal });
    return Response.json(summary);
  } catch (error) {
    if (error instanceof DOMException && error.name === "TimeoutError") {
      return Response.json({ error: "upstream_timeout" }, { status: 504 });
    }
    throw error;
  }
}
```

Cuando el timeout dispara, el error es un `DOMException` con `name === "TimeoutError"`; cuando se cancela
manualmente, `name === "AbortError"`. Distinguirlos permite responder 504 en un caso y no hacer nada en el otro.

<Callout type="warning" title="Promise.race no cancela al perdedor">
  El patrón `Promise.race([operation, timeout(5000)])` devuelve a tiempo, pero la operación sigue corriendo en
  segundo plano y consumiendo recursos. Con una señal, la operación realmente se detiene.
</Callout>

## Concurrencia limitada

`Promise.all(items.map(send))` **no es concurrencia controlada**: dispara todas las operaciones en el mismo
instante. Con 10.000 elementos, son 10.000 sockets, 10.000 respuestas en memoria y un proveedor que te bloquea.

La solución es un **pool de workers**: N funciones async que toman tareas de una cola compartida hasta vaciarla.

```ts
/**
 * Ejecuta `task` sobre cada elemento con como máximo `limit` operaciones simultáneas.
 * Devuelve los resultados en el mismo orden que la entrada y no aborta el lote si una tarea falla.
 */
export async function mapWithConcurrency<T, R>(
  items: readonly T[],
  limit: number,
  task: (item: T, index: number) => Promise<R>,
): Promise<PromiseSettledResult<R>[]> {
  const results: PromiseSettledResult<R>[] = new Array(items.length);
  let nextIndex = 0;

  async function worker(): Promise<void> {
    while (nextIndex < items.length) {
      const index = nextIndex++; // seguro: no hay await entre leer e incrementar
      try {
        results[index] = { status: "fulfilled", value: await task(items[index]!, index) };
      } catch (reason) {
        results[index] = { status: "rejected", reason };
      }
    }
  }

  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}
```

Por qué funciona sin locks: JavaScript ejecuta un solo flujo a la vez y `nextIndex++` ocurre **sin un `await` en el
medio**, así que dos workers nunca toman el mismo índice. Podés practicar esta implementación en el challenge
[Limitador de concurrencia](/challenges/concurrency-limiter).

Limitar la concurrencia no es lo mismo que limitar la **tasa** (requests por segundo). Si el proveedor impone
"100 por minuto", hace falta un rate limiter (token bucket), tema del curso de System Design.

## Race conditions con un solo hilo

Node.js tiene un solo hilo de JavaScript, pero **entre dos `await` puede ejecutarse cualquier otro código**. Eso
alcanza para producir race conditions clásicas:

```ts
// ❌ Lost update: dos pagos concurrentes desde la misma billetera
async function applyPayment(walletId: string, paidCents: number): Promise<void> {
  const wallet = await walletRepository.findById(walletId); // 1. lee saldo: 10.000
  // ← acá puede ejecutarse otro applyPayment del mismo walletId y leer también 10.000
  const newBalance = wallet.balanceCents - paidCents;
  await walletRepository.updateBalance(walletId, newBalance); // 2. escribe: el último pisa al primero
}
```

Soluciones, de la más recomendable a la más local:

1. **Operación atómica en la base:** `UPDATE wallets SET balance_cents = balance_cents - $1 WHERE id = $2 AND balance_cents >= $1`. La base
   serializa las escrituras.
2. **Concurrencia optimista:** un campo `version`; el `UPDATE ... WHERE version = $v` falla si otro escribió antes y
   se reintenta.
3. **Idempotencia:** guardar el `paymentId` con una constraint única para que el mismo webhook no se aplique dos
   veces.
4. **Serializar por clave en memoria:** encadenar las operaciones del mismo `walletId`. Sólo funciona con **una única
   instancia** del proceso; con varias réplicas, no protege nada.

## Reintentos con backoff exponencial y jitter

Reintentar bien tiene cuatro reglas:

1. **Sólo errores transitorios:** timeouts, errores de red, `429`, `502`, `503`, `504`. Un `400` o un `422` va a
   fallar igual en el próximo intento.
2. **Sólo operaciones idempotentes**, o con una _idempotency key_ que el servidor respete. Reintentar un cobro que
   quizá se ejecutó puede cobrar dos veces.
3. **Esperas crecientes con tope:** `base * 2^intento`, con un máximo.
4. **Jitter:** aleatorizar la espera para que miles de clientes que fallaron juntos no reintenten juntos.

```ts
import { setTimeout as sleep } from "node:timers/promises";

class RetryableError extends Error {
  constructor(
    message: string,
    readonly retryAfterMs?: number,
  ) {
    super(message);
    this.name = "RetryableError";
  }
}

interface RetryOptions {
  maxAttempts: number;
  baseDelayMs: number;
  maxDelayMs: number;
  signal?: AbortSignal;
}

/** Reintenta sólo errores marcados como reintentables, con backoff exponencial y full jitter. */
export async function withRetry<T>(
  operation: (attempt: number) => Promise<T>,
  options: RetryOptions,
): Promise<T> {
  for (let attempt = 1; ; attempt++) {
    try {
      return await operation(attempt);
    } catch (error) {
      const retryable = error instanceof RetryableError;
      if (!retryable || attempt >= options.maxAttempts) throw error;

      const exponential = Math.min(options.maxDelayMs, options.baseDelayMs * 2 ** (attempt - 1));
      const delay = error.retryAfterMs ?? Math.random() * exponential; // respeta Retry-After si existe
      await sleep(delay, undefined, { signal: options.signal }); // la espera también se cancela
    }
  }
}
```

El simulador [Retry y backoff](/system-design/simulators/retry-backoff) muestra cómo cambia la carga sobre un
servicio en recuperación con y sin jitter.

## Rechazos no manejados

Una Promise rechazada que nadie espera ni captura es un **unhandled rejection**. En Node.js moderno, eso **termina el
proceso** por defecto.

```ts
// ❌ Se lanza y se olvida: si falla, el proceso puede caerse
void auditLog.write(event);
notifier.send(userId); // sin await ni catch

// ✅ Fire-and-forget explícito y capturado
auditLog.write(event).catch((error) => logger.error({ error }, "audit_log_failed"));
```

La regla `@typescript-eslint/no-floating-promises` detecta Promises que no se esperan ni se capturan.

## Comparación con C# y Java

| Necesidad              | C#                                       | Java                                                 | TypeScript                                     |
| ---------------------- | ---------------------------------------- | ---------------------------------------------------- | ---------------------------------------------- |
| Cancelación            | `CancellationToken`                      | `Future.cancel`, interrupción, `StructuredTaskScope` | `AbortSignal`                                  |
| Timeout                | `CancelAfter`, `WaitAsync(timeout)`      | `orTimeout`, `completeOnTimeout`                     | `AbortSignal.timeout`                          |
| Combinar cancelaciones | `CreateLinkedTokenSource`                | Manual                                               | `AbortSignal.any`                              |
| Limitar concurrencia   | `SemaphoreSlim`, `Parallel.ForEachAsync` | `Semaphore`, executors con N threads                 | Pool de workers o semáforo con Promises        |
| Race conditions        | Hilos reales + `lock`                    | Hilos reales + `synchronized`                        | Entre `await`s, sin paralelismo de JS          |
| Reintentos             | Polly                                    | Resilience4j                                         | Función propia o librería (p-retry, cockatiel) |

La diferencia más importante: en C# y Java las race conditions pueden ocurrir **entre cualquier par de
instrucciones**, porque hay hilos reales. En JavaScript sólo pueden ocurrir **en los puntos de `await`**. Eso hace
el código más fácil de razonar, pero no elimina el problema.

## Errores frecuentes

- **Llamadas a red sin timeout.** Toda llamada saliente necesita un límite de tiempo.
- **`Promise.all` sobre lotes grandes.** Usá un pool con límite.
- **Cancelar sin propagar la señal.** Si la capa intermedia no pasa `signal` al cliente HTTP, la cancelación no
  llega a ningún lado.
- **Reintentar todo.** Un `400` reintentado tres veces son tres requests inútiles; un cobro no idempotente
  reintentado puede ser un doble cobro.
- **Backoff sin jitter.** Sincroniza a todos los clientes y produce picos justo cuando el servicio se recupera.
- **Proteger datos compartidos con un mutex en memoria** en un servicio con varias réplicas.
- **Promises flotantes.** Un rechazo no manejado puede tirar el proceso.
