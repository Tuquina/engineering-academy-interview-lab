## ¿Qué problema resuelve?

En un servicio de cobranzas hay decenas de valores que son "un string" para el compilador pero tienen reglas muy
distintas: el ID de un cliente, el de una deuda, un email, un teléfono en formato E.164, una fecha ISO. Si todos
son `string`, el compilador no puede impedir que pases el teléfono donde iba el email, o el ID del cliente a
`cancelDebt`.

Y en los bordes del sistema hay datos sin verificar: el body de un request, un mensaje de una cola, la salida de un
LLM, `process.env`. La pregunta de diseño es **dónde** y **cómo** se convierten esos datos en tipos confiables, para
que el resto del código no tenga que desconfiar.

## Parse, don't validate

Comparemos dos funciones que "verifican" un email:

```ts
// Validar: devuelve un booleano. El tipo no cambia; nadie sabe después si se validó.
function isValidEmail(value: string): boolean {
  return /^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(value);
}

// Parsear: devuelve un tipo nuevo que prueba que se validó.
type Email = string & { readonly __brand: "Email" };

function parseEmail(value: string): Email {
  if (!/^[^@\s]+@[^@\s]+\.[^@\s]+$/.test(value)) throw new InvalidEmailError(value);
  return value as Email; // única aserción permitida: justo después de validar
}

function sendReceipt(to: Email, debtId: DebtId) {} // no necesita volver a validar
```

Con validación, cada función que recibe un `string` tiene que preguntarse si ya alguien lo validó. Con parseo, el
tipo **es la prueba**: `sendReceipt` no puede recibir un string cualquiera.

## Branded types

Un branded type es un primitivo con una **marca que sólo existe para el compilador**:

```ts
declare const brand: unique symbol;
export type Brand<T, B extends string> = T & { readonly [brand]: B };

export type CustomerId = Brand<string, "CustomerId">;
export type DebtId = Brand<string, "DebtId">;
export type AmountCents = Brand<number, "AmountCents">;

export function toDebtId(raw: string): DebtId {
  if (!/^debt_[a-z0-9]{6,}$/.test(raw)) throw new Error(`DebtId inválido: ${raw}`);
  return raw as DebtId;
}

export function toAmountCents(raw: number): AmountCents {
  if (!Number.isSafeInteger(raw) || raw <= 0) throw new Error(`Monto inválido: ${raw}`);
  return raw as AmountCents;
}

declare function cancelDebt(id: DebtId): Promise<void>;
declare const customerId: CustomerId;

cancelDebt(customerId); // ❌ CustomerId no es asignable a DebtId
cancelDebt("debt_abc123"); // ❌ un string literal tampoco: hay que pasar por toDebtId
```

Propiedades importantes:

- **Costo cero en runtime:** la marca se borra; un `DebtId` es un string normal al ejecutar.
- **Se usan como el primitivo:** `id.startsWith("debt_")` funciona, y un `AmountCents` se suma como un número (el
  resultado de una suma es `number`, sin marca, y está bien: hay que revalidar si querés el brand).
- **El único constructor es la función que valida.** Si el equipo respeta esa regla (con lint o revisión), el tipo
  prueba la invariante.

Es la forma de conseguir en TypeScript algo parecido a los `record struct CustomerId(string Value)` de C# o los
value objects de Java, sin crear objetos envoltorio.

## Esquemas con Zod

Un esquema Zod es un **valor de runtime** que valida datos y del que se deriva el tipo. Es la herramienta estándar
para los límites:

```ts
import { z } from "zod";

export const CreatePaymentPromiseSchema = z.object({
  debtId: z
    .string()
    .regex(/^debt_[a-z0-9]{6,}$/)
    .transform((value) => value as DebtId),
  promisedFor: z.iso.date(), // "2026-12-01"
  amountCents: z.number().int().positive(),
  channel: z.enum(["sms", "email", "whatsapp"]).default("sms"),
  note: z.string().max(500).optional(),
});

// Lo que el cliente puede mandar (channel opcional) y lo que obtenés después de parsear (channel presente)
export type CreatePaymentPromiseInput = z.input<typeof CreatePaymentPromiseSchema>;
export type CreatePaymentPromise = z.output<typeof CreatePaymentPromiseSchema>; // igual a z.infer
```

```ts
export async function POST(request: Request): Promise<Response> {
  const body: unknown = await request.json().catch(() => null);
  const parsed = CreatePaymentPromiseSchema.safeParse(body);

  if (!parsed.success) {
    return Response.json(
      { error: "invalid_body", issues: z.flattenError(parsed.error).fieldErrors },
      { status: 422 },
    );
  }

  const promise = await createPaymentPromise(parsed.data); // parsed.data: CreatePaymentPromise
  return Response.json(toPaymentPromiseDto(promise), { status: 201 });
}
```

- **`parse`** lanza un `ZodError`; **`safeParse`** devuelve `{ success: true, data } | { success: false, error }`,
  una discriminated union. En límites HTTP se prefiere `safeParse` para devolver un 4xx controlado.
- **`transform`** convierte durante el parseo (strings a branded types, fechas a `Date`, normalizar mayúsculas).
- **`default`** completa valores faltantes; por eso el tipo de entrada y el de salida pueden diferir.
- Los mensajes de error no deben filtrar detalles internos ni repetir datos sensibles del input.

### Componer esquemas

```ts
const MoneySchema = z.object({ amountCents: z.number().int().positive(), currency: z.enum(["ARS", "USD"]) });

const DebtSchema = z.object({
  id: z.string(),
  customerId: z.string(),
  balance: MoneySchema,
  status: z.enum(["pending", "promised", "paid"]),
});

const DebtListSchema = z.array(DebtSchema);
const DebtPatchSchema = DebtSchema.pick({ status: true }).partial();

// Discriminated union en runtime: el equivalente validado de la lección de narrowing
const WebhookEventSchema = z.discriminatedUnion("type", [
  z.object({ type: z.literal("payment.succeeded"), debtId: z.string(), paidCents: z.number().int() }),
  z.object({ type: z.literal("payment.failed"), debtId: z.string(), reason: z.string() }),
]);
```

## DTOs y contratos en los límites

Un **DTO** (Data Transfer Object) describe cómo viaja un dato: JSON, nombres que eligió el proveedor, fechas como
strings, montos en la unidad que use el contrato. El **dominio** usa sus propios tipos. Mezclarlos acopla el núcleo
a cada detalle de transporte.

```ts
// Contrato del proveedor de pagos (como llega)
const ProviderPaymentDtoSchema = z.object({
  payment_id: z.string(),
  debt_reference: z.string(),
  amount: z.string(), // "1500.00": el proveedor manda strings decimales
  paid_at: z.iso.datetime(),
});

// Tipo del dominio (como lo usamos)
interface Payment {
  id: string;
  debtId: DebtId;
  amount: AmountCents;
  paidAt: Date;
}

// El mapeo vive en el adaptador, no en el dominio
function toPayment(dto: z.infer<typeof ProviderPaymentDtoSchema>): Payment {
  return {
    id: dto.payment_id,
    debtId: toDebtId(dto.debt_reference),
    amount: toAmountCents(Math.round(Number.parseFloat(dto.amount) * 100)),
    paidAt: new Date(dto.paid_at),
  };
}
```

<Callout type="tip" title="Contratos compartidos entre frontend y backend">
  En un monorepo, el esquema Zod del contrato público puede vivir en un paquete compartido: el backend valida
  con él y el frontend obtiene los tipos. Para APIs públicas o entre equipos, un contrato OpenAPI del que se
  generan tipos (y esquemas) es más apropiado.
</Callout>

## Variables de entorno

`process.env.DATABASE_URL` es `string | undefined`. Usarlo directamente reparte el problema por todo el código y
el error aparece en la primera request que lo necesite. Mejor validarlo **al arrancar**:

```ts
const EnvSchema = z.object({
  NODE_ENV: z.enum(["development", "test", "production"]),
  DATABASE_URL: z.url(),
  LLM_API_KEY: z.string().min(1),
  MAX_CONCURRENT_CALLS: z.coerce.number().int().positive().default(20),
});

export const env = EnvSchema.parse(process.env); // si falta algo, el proceso no arranca
```

`z.coerce.number()` convierte el string `"20"` en número: todas las variables de entorno son strings.

## Comparación con C# y Java

| Necesidad                      | C#                                               | Java                                      | TypeScript                              |
| ------------------------------ | ------------------------------------------------ | ----------------------------------------- | --------------------------------------- |
| Validar el body de un request  | Model binding + DataAnnotations/FluentValidation | Bean Validation (`@Valid`)                | Esquema Zod + `safeParse`               |
| ID con tipo propio             | `record struct DebtId(string Value)`             | `record DebtId(String value)`             | Branded type, sin objeto envoltorio     |
| Configuración validada         | Options pattern + `ValidateOnStart`              | `@ConfigurationProperties` + `@Validated` | Esquema sobre `process.env` al arrancar |
| DTO y mapeo                    | Clases + AutoMapper/Mapperly                     | Clases + MapStruct                        | Esquema del DTO + función de mapeo      |
| Tipo derivado de la validación | No (dos definiciones)                            | No (dos definiciones)                     | Sí: `z.infer` desde el esquema          |

La última fila es la diferencia de fondo: en C# y Java la clase y sus anotaciones de validación son lo mismo en
runtime. En TypeScript eso se logra haciendo que **el esquema sea la fuente** y el tipo una derivación.

## Errores frecuentes

- **Definir la interfaz y el esquema por separado.** Divergen con el tiempo; derivá el tipo del esquema.
- **Validar en cada función interna.** Es ruido y costo; validá una vez en el límite y confiá en los tipos.
- **Crear branded types con `as` fuera del constructor.** Rompe la garantía; restringilo con revisión o lint.
- **Exponer entidades del dominio como respuesta de la API.** Filtra campos internos y acopla los clientes al modelo.
- **Usar `parseFloat` para dinero sin redondear.** `Math.round(parseFloat("19.99") * 100)` evita errores de
  representación; mejor aún, parsear el string decimal sin pasar por punto flotante.
- **Mensajes de validación con datos sensibles.** No devuelvas el valor recibido en el error si puede contener datos
  personales.
