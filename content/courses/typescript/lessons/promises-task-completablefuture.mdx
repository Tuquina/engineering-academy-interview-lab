## ¿Qué problema resuelve?

Un servicio de notificaciones necesita, antes de avisarle a un usuario que su pedido salió, tres datos: sus
preferencias de canal, sus dispositivos registrados para push y la plantilla del mensaje en su idioma. Cada consulta
tarda unos 120 ms contra servicios distintos. La primera versión que escribe casi todo el mundo es esta:

```ts
const preferences = await preferencesService.get(userId);
const devices = await deviceService.list(userId);
const template = await templateService.get("order_shipped", userId);
// ≈ 360 ms: cada await espera a que termine el anterior aunque no dependan entre sí
```

Las tres consultas son independientes, pero el código las encadena. Con miles de notificaciones por minuto, esa
latencia se acumula en cada envío. El problema contrario también es frecuente: lanzar 10.000 llamadas a la
vez con `Promise.all` y tumbar al proveedor o agotar el pool de conexiones.

Dominar las Promises es saber **qué lanzar en paralelo, cuánto paralelismo permitir, qué hacer cuando algo falla y
cómo cortar lo que tarda demasiado**.

## El modelo mental de una Promise

Una Promise representa un resultado que todavía no existe. Tiene tres estados y cambia de estado **una sola vez**:

- **pending:** la operación sigue en curso.
- **fulfilled:** terminó con un valor.
- **rejected:** terminó con un error (el _reason_).

Tres reglas explican casi todo su comportamiento:

1. **Es eager.** La función que se pasa a `new Promise(executor)` corre de inmediato, de forma síncrona. Llamar a una
   función `async` ya inicia su trabajo; `await` sólo espera el resultado.
2. **Las continuaciones son microtasks.** Los callbacks de `then`, `catch` y lo que sigue a un `await` se encolan como
   microtasks y se ejecutan cuando la pila de llamadas actual termina, nunca de forma síncrona.
3. **`await` suspende la función, no el hilo.** Mientras una función espera, el event loop atiende otras requests.

```ts
async function loadPreferences(userId: string) {
  console.log("1. empieza");
  const preferences = await preferencesService.get(userId); // la función se suspende acá
  console.log("3. reanuda con", preferences.channel);
  return preferences;
}

const pending = loadPreferences("usr_1"); // imprime "1. empieza" de inmediato
console.log("2. sigo ejecutando mientras tanto");
await pending;
```

## Combinadores: elegir por la semántica de fallo

Los cuatro combinadores reciben varias promesas, pero difieren en **cuándo terminan** y **qué hacen ante un error**:

| Combinador           | Se resuelve cuando…                 | Rechaza cuando…                          | Equivalente aproximado                            |
| -------------------- | ----------------------------------- | ---------------------------------------- | ------------------------------------------------- |
| `Promise.all`        | todas se cumplen (valores en orden) | la primera rechaza (las demás siguen)    | `Task.WhenAll` · `CompletableFuture.allOf`        |
| `Promise.allSettled` | todas terminan, bien o mal          | nunca                                    | `Task.WhenAll` + inspeccionar cada `Task`         |
| `Promise.race`       | la primera que termina, bien o mal  | la primera que termina lo hace con error | `Task.WhenAny` · `CompletableFuture.anyOf`        |
| `Promise.any`        | la primera que se cumple            | todas rechazan (`AggregateError`)        | Sin equivalente directo en las librerías estándar |

```ts
// Todo o nada: sin cualquiera de los tres datos no se puede armar la notificación.
const [preferences, devices, template] = await Promise.all([
  preferencesService.get(userId),
  deviceService.list(userId),
  templateService.get("order_shipped", userId),
]);

// Lote independiente: un fallo no debe impedir notificar al resto, pero hay que saber cuáles fallaron.
const results = await Promise.allSettled(users.map((u) => notifier.send(u)));
const failed = results.flatMap((result, i) => (result.status === "rejected" ? [users[i]!.id] : []));
```

<Callout type="warning" title="Promise.all no cancela nada">
  Si `deviceService.list` rechaza a los 20 ms, `Promise.all` rechaza en ese momento, pero las otras dos
  consultas **siguen ejecutándose**: sus resultados simplemente se descartan. Si esas operaciones tienen
  efectos (escribir, cobrar, enviar), seguirán ocurriendo. Para cortarlas hace falta cancelación cooperativa
  con `AbortSignal`.
</Callout>

## Comparación con `Task<T>` y `CompletableFuture<T>`

Si venís de .NET o Java, la sintaxis de `async`/`await` resulta familiar, pero el modelo de ejecución no es igual:

| Aspecto                       | JavaScript `Promise<T>`                               | C# `Task<T>`                                                   | Java `CompletableFuture<T>`                                      |
| ----------------------------- | ----------------------------------------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------- |
| ¿Dónde corre el trabajo?      | I/O en el sistema operativo o el thread pool de libuv | Thread pool o I/O asíncrono del sistema operativo              | `ForkJoinPool.commonPool()` o el `Executor` indicado             |
| ¿Dónde corre la continuación? | En el único hilo de JS, como microtask                | Thread pool o `SynchronizationContext` capturado               | En el hilo que completa el futuro o en el `Executor` de `*Async` |
| Esperar bloqueando            | Imposible: no existe un `.Result`                     | `.Result` / `.Wait()` (riesgo de deadlock con contexto)        | `.join()` / `.get()` bloquean el hilo                            |
| Cancelación                   | `AbortSignal`, cooperativa                            | `CancellationToken`, cooperativa                               | `cancel()` marca el futuro; no interrumpe el trabajo en curso    |
| Error al esperar              | Se lanza el _reason_ tal cual                         | `await` relanza la excepción original                          | `join()` envuelve en `CompletionException`                       |
| Rechazo sin manejar           | `unhandledRejection` (Node termina el proceso)        | `TaskScheduler.UnobservedTaskException`, no termina el proceso | Se pierde en silencio si nadie consulta el futuro                |

La diferencia más importante es la primera fila: en Node.js **todo tu JavaScript corre en un solo hilo**. No hay
condiciones de carrera por memoria compartida entre callbacks, pero un cálculo síncrono largo bloquea todas las
requests (lo vemos en la lección del event loop).

## Ejemplo incorrecto

```ts
// ❌ Tres errores frecuentes en un mismo job de notificaciones.
export async function sendDailyDigest(users: User[]): Promise<void> {
  // 1. forEach ignora las promesas que devuelve el callback: la función termina antes de enviar nada
  //    y cualquier rechazo queda sin manejar.
  users.forEach(async (user) => {
    await notifier.send(user);
  });

  // 2. Promesa flotante: nadie la espera ni captura su error.
  auditLog.record("daily-digest-started");

  // 3. Timeout con race que no cancela la operación: la llamada sigue viva consumiendo recursos.
  await Promise.race([templates.syncAll(), sleep(5_000).then(() => Promise.reject(new Error("timeout")))]);
}
```

Por qué falla:

1. `Array.prototype.forEach` no espera promesas. El job informa éxito sin haber enviado nada, y si un envío falla,
   el rechazo no tiene handler: en Node.js 15+ eso **termina el proceso**.
2. Una promesa sin `await` ni `.catch` es un error silencioso esperando ocurrir.
3. `Promise.race` decide qué resultado usar, pero no detiene a la perdedora: `templates.syncAll()` sigue en curso.

## Implementación recomendada

```ts
/**
 * Aplica `fn` a cada elemento con un máximo de `limit` operaciones simultáneas.
 * Conserva el orden de los resultados y rechaza ante el primer error (como Promise.all).
 */
export async function mapWithConcurrency<T, R>(
  items: readonly T[],
  limit: number,
  fn: (item: T, index: number) => Promise<R>,
): Promise<R[]> {
  const results = new Array<R>(items.length);
  let nextIndex = 0;

  async function worker(): Promise<void> {
    while (nextIndex < items.length) {
      const index = nextIndex++; // seguro: no hay otro hilo de JS que intercale entre leer e incrementar
      results[index] = await fn(items[index]!, index);
    }
  }

  await Promise.all(Array.from({ length: Math.min(limit, items.length) }, worker));
  return results;
}

export async function sendDailyDigest(users: User[]): Promise<DigestReport> {
  await auditLog.record("daily-digest-started"); // esperada: si falla, el job falla de forma visible

  const outcomes = await mapWithConcurrency(users, 10, async (user) => {
    try {
      // Cada envío tiene su propio timeout real: el AbortSignal cancela la request HTTP subyacente.
      await notifier.send(user, { signal: AbortSignal.timeout(3_000) });
      return { userId: user.id, ok: true as const };
    } catch (error) {
      return { userId: user.id, ok: false as const, error: String(error) };
    }
  });

  return { sent: outcomes.filter((o) => o.ok).length, failed: outcomes.filter((o) => !o.ok) };
}
```

Decisiones clave:

- **Concurrencia acotada (10):** protege al proveedor y al pool de conexiones; el límite se ajusta a su rate limit.
- **Errores como datos por elemento:** un envío fallido no aborta el lote, pero queda reportado.
- **`AbortSignal.timeout`:** el timeout cancela la operación de verdad, siempre que la API subyacente acepte una
  señal (como `fetch`). Para combinar un timeout con una cancelación externa existe `AbortSignal.any([a, b])`.

## Casos límite y errores frecuentes

- **`return await` dentro de `try`.** `return promise` dentro de un `try/catch` no captura su rechazo; `return await
promise` sí, porque el rechazo ocurre dentro del bloque.
- **`await` en un bucle no siempre es un error.** Si el orden importa o hay un rate limit estricto, el procesamiento
  secuencial es correcto: la clave es que sea una decisión, no un accidente.
- **Rechazos tardíos con `Promise.all`.** Si dos promesas rechazan, `all` informa la primera; la segunda queda
  manejada internamente y se pierde. Si necesitás todos los errores, usá `allSettled`.
- **Un `Promise.all` vacío** se resuelve de inmediato con `[]`; un `Promise.any` vacío rechaza con `AggregateError`.
- **Cancelar no deshace.** Abortar una request que ya llegó al servidor no garantiza que la operación no se haya
  aplicado: para efectos como cobros hace falta idempotencia del lado del servidor.
- **Errores que no son `Error`.** Se puede rechazar con cualquier valor; en un `catch`, el error es `unknown` y
  conviene normalizarlo antes de leer `.message`.
- **Detección automática.** La regla `@typescript-eslint/no-floating-promises` detecta promesas sin manejar y
  `@typescript-eslint/no-misused-promises`, callbacks async donde se espera una función síncrona (como `forEach`).

## Cuándo usar cada herramienta

- **`await` secuencial:** cuando cada paso depende del anterior o el orden es un requisito.
- **`Promise.all`:** operaciones independientes que necesitás todas para continuar.
- **`Promise.allSettled`:** lotes donde un fallo parcial es aceptable y debe reportarse.
- **`Promise.any`:** redundancia (la primera réplica o el primer proveedor que responda bien).
- **`Promise.race`:** rara vez sola; preferí `AbortSignal.timeout` para timeouts.
- **Concurrencia acotada:** cualquier lote cuyo tamaño no controlás (usuarios, mensajes, archivos).

<Callout type="interview" title="Cómo explicarlo en una entrevista">
  "Una Promise es eager: la operación ya está en curso cuando la tengo. Por eso lanzo en paralelo lo
  independiente y lo espero con el combinador cuya semántica de fallo necesito. Sé que `Promise.all` no
  cancela lo que queda en curso, así que para timeouts uso `AbortSignal`, y para lotes grandes acoto la
  concurrencia. A diferencia de .NET, en Node no puedo bloquear esperando un resultado, y un rechazo no
  manejado termina el proceso."
</Callout>
