## Goroutines

Una **goroutine** es una función que se ejecuta de forma concurrente. Se lanza con la palabra `go`:

```go
go sendConfirmationEmail(order)   // no espera: la función sigue en paralelo
```

Las goroutines son mucho más livianas que los hilos del sistema operativo: empiezan con un stack chico que crece
según haga falta. El **scheduler** de Go multiplexa muchas goroutines sobre pocos hilos del sistema (modelo M:N);
cuando una se bloquea esperando I/O, ejecuta otra. Un servidor HTTP de Go atiende **cada request en su propia
goroutine**.

Lanzar una goroutine es fácil; lo importante es **saber cuándo y cómo termina**. Para esperar a un grupo se usa
`sync.WaitGroup`:

```go
var wg sync.WaitGroup
for _, carrier := range carriers {
    wg.Add(1)
    go func() {                        // desde Go 1.22, cada iteración tiene su propia variable carrier
        defer wg.Done()
        quote(carrier)
    }()
}
wg.Wait()                              // espera a que todas terminen
```

## Channels

Un **channel** es un conducto tipado entre goroutines. El lema de Go: _no te comuniques compartiendo memoria;
compartí memoria comunicándote_.

```go
results := make(chan Rate)          // sin buffer
jobs := make(chan Order, 100)       // con buffer de 100

results <- rate                     // enviar
rate := <-results                   // recibir
close(jobs)                         // lo cierra el emisor cuando no hay más datos
for order := range jobs { }         // recibe hasta que el channel se cierra
```

| Operación | Channel sin buffer          | Con buffer                | Cerrado                                |
| --------- | --------------------------- | ------------------------- | -------------------------------------- |
| Enviar    | Espera a que alguien reciba | Espera sólo si está lleno | **panic**                              |
| Recibir   | Espera a que alguien envíe  | Espera sólo si está vacío | Devuelve el zero value y `ok == false` |

## select

`select` espera varias operaciones de channels a la vez y ejecuta la primera que esté lista:

```go
select {
case rate := <-results:
    return rate, nil
case <-time.After(2 * time.Second):
    return Rate{}, errors.New("timeout del proveedor")
case <-ctx.Done():
    return Rate{}, ctx.Err()          // el llamador canceló
}
```

## context: cancelación y timeouts

`context.Context` propaga **cancelación**, **deadlines** y valores de alcance de request. Por convención es el
**primer parámetro** de toda función que hace I/O:

```go
func (s *CheckoutService) Quote(ctx context.Context, cart Cart) (Rate, error) {
    ctx, cancel := context.WithTimeout(ctx, 800*time.Millisecond)
    defer cancel()                     // siempre: libera los recursos del contexto
    return s.carrier.Rate(ctx, cart)   // el cliente HTTP y el driver de base respetan ctx
}
```

En un servidor HTTP, `r.Context()` se cancela si el cliente se desconecta: todo lo que cuelga de ese contexto (consultas,
llamadas a otros servicios) se corta en lugar de trabajar para nadie.

## Patrones

### Worker pool

```go
func processAll(ctx context.Context, orders []Order, workers int) error {
    jobs := make(chan Order)
    g, ctx := errgroup.WithContext(ctx)      // golang.org/x/sync/errgroup

    for range workers {                       // Go 1.22+: range sobre un entero
        g.Go(func() error {
            for order := range jobs {
                if err := invoice(ctx, order); err != nil {
                    return err                // cancela ctx: los demás workers se detienen
                }
            }
            return nil
        })
    }

    g.Go(func() error {
        defer close(jobs)
        for _, order := range orders {
            select {
            case jobs <- order:
            case <-ctx.Done():
                return ctx.Err()
            }
        }
        return nil
    })
    return g.Wait()                           // primer error, si lo hubo
}
```

- **errgroup** espera a un grupo de goroutines, devuelve el primer error y cancela el contexto compartido.
- Limitar el número de workers acota la presión sobre la base o el proveedor externo (backpressure).
- `errgroup.Group.SetLimit(n)` es otra forma de limitar la concurrencia.

### Mutex

Cuando el estado compartido es simple (un contador, una caché en memoria), un `sync.Mutex` es más claro que un
channel:

```go
type Cache struct {
    mu    sync.RWMutex
    items map[string]Product
}

func (c *Cache) Get(sku string) (Product, bool) {
    c.mu.RLock()                    // varios lectores a la vez
    defer c.mu.RUnlock()
    p, ok := c.items[sku]
    return p, ok
}
```

## Data races y goroutine leaks

Una **data race** ocurre cuando dos goroutines acceden a la misma memoria, al menos una escribe y no hay
sincronización. El resultado es impredecible. El **race detector** las encuentra en ejecución:

```bash
go test -race ./...
go run -race ./cmd/api
```

Un **goroutine leak** es una goroutine bloqueada para siempre, por ejemplo esperando enviar a un channel que ya nadie
lee. Cada una retiene memoria. Se evitan dándole a toda goroutine una forma de terminar (cancelación por contexto,
channels cerrados o con buffer suficiente) y se detectan con `pprof` observando la cantidad de goroutines.

<Callout type="warning" title="La concurrencia no es gratis">
  Más goroutines no siempre es más rápido: si todas compiten por la misma base de datos o el mismo lock, el
  sistema se satura. Medí, limitá la concurrencia y propagá la cancelación.
</Callout>

## Resumen

Goroutines baratas, channels para comunicar, select para combinar, context para cancelar y sync para el estado
compartido. La regla de oro: toda goroutine necesita una forma clara de terminar, y el race detector es parte del
proceso normal de testing.
