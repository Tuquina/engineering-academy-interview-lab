## Structs y métodos

Go no tiene clases. Los datos se agrupan en **structs** y el comportamiento se agrega con **métodos**, que son
funciones con un **receptor**:

```go
type Money struct {
    Cents    int64
    Currency string
}

type Order struct {
    ID         string
    CustomerID string
    Items      []Item
    Status     string
}

// Constructor por convención: una función NewX
func NewOrder(id, customerID string) *Order {
    return &Order{ID: id, CustomerID: customerID, Status: "CREATED"}
}

// Receptor por puntero: modifica el pedido
func (o *Order) AddItem(item Item) {
    o.Items = append(o.Items, item)
}

// Receptor por valor: sólo lee
func (m Money) String() string {
    return fmt.Sprintf("%s %.2f", m.Currency, float64(m.Cents)/100)
}
```

## Punteros y receptores

Go pasa todo **por valor**: pasar un struct copia todos sus campos. Un **puntero** (`*Order`) permite compartir y
modificar el mismo valor. No hay aritmética de punteros, y el garbage collector se encarga de la memoria.

| Receptor             | Cuándo                                                                       |
| -------------------- | ---------------------------------------------------------------------------- |
| Puntero `(o *Order)` | El método modifica el struct, el struct es grande o contiene un `sync.Mutex` |
| Valor `(m Money)`    | Tipos chicos e inmutables                                                    |

Por consistencia, si un método del tipo usa puntero, en general todos lo hacen.

## Interfaces implícitas

Una **interfaz** declara métodos. Un tipo la implementa **por el solo hecho de tener esos métodos**, sin declarar
`implements`:

```go
type PaymentGateway interface {
    Charge(ctx context.Context, amountCents int64, token string) (string, error)
}

type StripeGateway struct{ apiKey string }

func (s *StripeGateway) Charge(ctx context.Context, amountCents int64, token string) (string, error) {
    // llamaría a la API del proveedor
    return "tx_123", nil
}

type CheckoutService struct {
    payments PaymentGateway        // depende de la interfaz, no del proveedor
}
```

Esto invierte la costumbre de Java o C#: las interfaces se definen **del lado de quien las usa** y suelen ser muy
chicas. La librería estándar está llena de interfaces de uno o dos métodos (`io.Reader`, `io.Writer`, `fmt.Stringer`).
El proverbio de Go lo resume: **aceptá interfaces, devolvé structs**.

<Callout type="warning" title="Una interfaz con un puntero nil no es nil">
  Un valor de interfaz guarda dos cosas: el **tipo dinámico** y el **valor**. Si una función devuelve una
  variable `var err *MyError = nil` como `error`, el resultado tiene tipo `*MyError` y no es igual a `nil`: el
  `if err != nil` del llamador es verdadero. Devolvé siempre el literal `nil` cuando no hay error.
</Callout>

## Composición con embedding

En lugar de herencia, Go **incrusta** tipos: los campos y métodos del tipo incrustado quedan disponibles en el que lo
contiene.

```go
type Timestamps struct {
    CreatedAt time.Time
    UpdatedAt time.Time
}

func (t *Timestamps) Touch() { t.UpdatedAt = time.Now() }

type Product struct {
    Timestamps                  // embedding: Product "tiene" Timestamps
    SKU   string
    Price Money
}

p := &Product{SKU: "SKU-1"}
p.Touch()                       // método promovido desde Timestamps
```

No es herencia: un `Product` no es un `Timestamps` y no hay polimorfismo por subtipos; el polimorfismo se logra con
interfaces.

## Errores idiomáticos

```go
var ErrNotFound = errors.New("no encontrado")      // error centinela

type ValidationError struct {                      // error con datos
    Field string
}
func (e *ValidationError) Error() string { return "campo inválido: " + e.Field }

func (r *Repo) Find(ctx context.Context, id string) (*Order, error) {
    order, err := r.query(ctx, id)
    if errors.Is(err, sql.ErrNoRows) {
        return nil, ErrNotFound
    }
    if err != nil {
        return nil, fmt.Errorf("repo.Find %s: %w", id, err)   // agrega contexto y conserva la causa
    }
    return order, nil
}

// Quien llama consulta la cadena de errores
order, err := repo.Find(ctx, id)
switch {
case errors.Is(err, ErrNotFound):
    http.Error(w, "pedido inexistente", http.StatusNotFound)
case err != nil:
    var validation *ValidationError
    if errors.As(err, &validation) {
        http.Error(w, validation.Error(), http.StatusBadRequest)
        return
    }
    http.Error(w, "error interno", http.StatusInternalServerError)
}
```

  caption="Cada capa envuelve el error con contexto usando %w; errors.Is recorre la cadena hasta encontrar el centinela."
  chart={`
flowchart LR

- `%w` en `fmt.Errorf` **envuelve** el error; `%v` sólo copia su texto y rompe la cadena.
- `errors.Is` compara con errores centinela; `errors.As` busca un tipo concreto.
- `panic` y `recover` existen para lo irrecuperable; un servidor HTTP recupera los panics de cada request para no caer
  entero.

## Genéricos

Desde **Go 1.18** hay parámetros de tipo con **restricciones**:

```go
import "cmp"

func Max[T cmp.Ordered](values []T) (T, bool) {
    var zero T
    if len(values) == 0 {
        return zero, false
    }
    best := values[0]
    for _, v := range values[1:] {
        if v > best {
            best = v
        }
    }
    return best, true
}

type Page[T any] struct {
    Items      []T
    NextCursor string
}

Max([]int64{1500, 900, 3000})   // 3000, true (T se infiere)
```

`any` acepta cualquier tipo; `comparable`, los que admiten `==` (y por lo tanto pueden ser claves de map);
`cmp.Ordered`, los que admiten `<`. Los paquetes `slices` y `maps` de la librería estándar ya traen funciones genéricas
como `slices.Sort`, `slices.Contains` y `maps.Keys`. La recomendación oficial: usar genéricos cuando se repite el mismo
código para distintos tipos, no por defecto.

## Resumen

En Go se modela con structs, métodos e interfaces implícitas, y se compone con embedding. Los errores se envuelven con
contexto y se consultan con errors.Is y errors.As. Los genéricos existen para eliminar duplicación, no para reemplazar
a las interfaces.
