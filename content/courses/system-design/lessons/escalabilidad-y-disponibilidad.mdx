## ¿Qué problema resuelve?

Black Friday en un comercio electrónico: la gente busca, compara y compra al mismo tiempo. El tráfico se multiplica
por diez durante tres días.
Un sistema escalable atiende ese pico sin degradarse; uno disponible sigue funcionando aunque se caiga una instancia o
una zona. Esta lección cubre las herramientas para ambas cosas y cómo **medir** si se está cumpliendo.

## Escalado vertical y horizontal

| Estrategia     | Cómo                                    | Ventajas                          | Límites                                           |
| -------------- | --------------------------------------- | --------------------------------- | ------------------------------------------------- |
| **Vertical**   | Una máquina más grande                  | Simple; sin cambios de diseño     | Techo físico y de costo; un único punto de falla  |
| **Horizontal** | Más instancias detrás de un balanceador | Sin techo práctico; tolera fallas | Requiere servicios sin estado y estado compartido |

Para escalar horizontalmente, los servicios deben ser **sin estado**: cualquier instancia puede atender cualquier
request. Las sesiones van a Redis o a la base, los archivos a almacenamiento de objetos, los trabajos a colas (lección
de performance del curso de Node.js).

| Algoritmo         | Cómo reparte                                | Cuándo                                         |
| ----------------- | ------------------------------------------- | ---------------------------------------------- |
| Round robin       | En turnos                                   | Requests homogéneas                            |
| Least connections | A la instancia con menos conexiones activas | Requests de duración variable (llamadas a LLM) |

El simulador [Load balancing](/system-design/simulators/load-balancing) muestra cómo least connections reparte mejor
cuando una réplica está degradada. Un **reverse proxy** (Nginx, Envoy, el balanceador de la nube) además termina TLS,
comprime, aplica límites y enruta por ruta o dominio.

## Datos: réplicas, particionado y sharding

Escalar la API es fácil; el cuello de botella suele terminar en **los datos**.

| Problema                       | Solución, de la más simple a la más compleja                    |
| ------------------------------ | --------------------------------------------------------------- |
| Muchas lecturas repetidas      | Caché (Redis, CDN para contenido público)                       |
| Muchas lecturas variadas       | Réplicas de lectura (con lag de replicación)                    |
| Tablas enormes                 | Particionado dentro de la misma base (por tiempo, por tenant)   |
| Escrituras que superan un nodo | Sharding: distribuir los datos entre varias bases por una clave |

**Sharding por tenant** es natural en plataformas multi-tenant: casi todas las consultas son de un tenant. Sus
costos: consultas globales (reportes de toda la plataforma) que cruzan shards, **hot spots** cuando un tenant es mucho
más grande que el resto y el **rebalanceo** al agregar shards.

## Capacidad, latencia y throughput

- **Latencia:** cuánto tarda una request. Se mide en **percentiles** (p50, p95, p99): el promedio esconde la cola.
- **Throughput:** cuántas requests se atienden por unidad de tiempo.
- Relación útil (**ley de Little**): concurrencia = throughput × latencia. Si la API atiende 200 requests por segundo y
  cada una tarda 2 s (porque espera al LLM), hay ~400 requests en vuelo: eso define pools, conexiones y memoria.

**Planificar capacidad** es combinar estimaciones con mediciones: cuánto atiende una instancia (load test), cuál es el
pico esperado, qué margen se deja (por ejemplo 2× el pico) y qué dependencias externas limitan (cuotas del proveedor de
LLM, límites de mensajería, conexiones de la base).

## Disponibilidad: SLI, SLO y SLA

| Término | Qué es                                   | Ejemplo                                                |
| ------- | ---------------------------------------- | ------------------------------------------------------ |
| **SLI** | Indicador medido                         | % de webhooks de pago procesados en menos de 5 s       |
| **SLO** | Objetivo interno sobre el SLI            | 99,9 % por mes                                         |
| **SLA** | Compromiso contractual con consecuencias | 99,5 % mensual con créditos al cliente si no se cumple |

El **presupuesto de error** es lo que queda: con un SLO de 99,9 % mensual, se "pueden" fallar 0,1 % de los eventos
(unos 43 minutos de indisponibilidad total al mes). Si el presupuesto se agota, se prioriza estabilidad sobre
funcionalidades nuevas; si sobra, se pueden tomar más riesgos en los despliegues.

| Disponibilidad | Indisponibilidad aproximada por mes |
| -------------- | ----------------------------------- |
| 99 %           | ~7,3 horas                          |
| 99,9 %         | ~43 minutos                         |
| 99,99 %        | ~4,4 minutos                        |

Cada "nueve" adicional cuesta mucho más (redundancia entre zonas o regiones, despliegues más cuidadosos, guardias).
Se elige según el impacto real: recibir webhooks de pagos merece más nueves que el panel de reportes.

La disponibilidad se construye con **redundancia** (varias instancias y zonas), **eliminación de puntos únicos de
falla**, **health checks y failover** automáticos, y **degradación** planificada (servir lo esencial cuando una
dependencia falla).

## Errores frecuentes

- **Escalar sin medir** el cuello de botella.
- **Estado en memoria** que impide escalar horizontalmente.
- **Leer de réplicas justo después de escribir** (lag de replicación).
- **Shardear antes de agotar** optimizaciones, caché y particionado.
- **Promedios** en lugar de percentiles.
- **SLOs sin medición** o iguales para todo el sistema.
- **Olvidar los límites de terceros** en la planificación de capacidad.
