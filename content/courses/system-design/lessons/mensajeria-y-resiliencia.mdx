## ¿Qué problema resuelve?

A las 9:00 una tienda online empieza a avisar a 500.000 clientes que arrancó su Black Friday. Al mismo tiempo, el
proveedor de WhatsApp empieza a responder con errores y el modelo de lenguaje del asistente de ventas se pone lento. Un sistema frágil responde a esto con reintentos en cascada, colas que
crecen sin control, la base saturada y, a las 9:20, todo caído. Un sistema resiliente **absorbe el pico, contiene la
falla y se recupera solo**. Esta lección reúne los mecanismos.

## Síncrono y asíncrono

| Aspecto               | Síncrono (HTTP, RPC)             | Asíncrono (colas, eventos)                          |
| --------------------- | -------------------------------- | --------------------------------------------------- |
| Respuesta             | Inmediata                        | Diferida                                            |
| Acoplamiento temporal | Ambos deben estar disponibles    | El consumidor puede estar caído un rato             |
| Picos                 | Se trasladan al servicio llamado | La cola los absorbe                                 |
| Fallas                | Se propagan en cadena            | Se aíslan y reintentan                              |
| Complejidad           | Menor                            | Consistencia eventual, idempotencia, observabilidad |

Regla práctica: **síncrono cuando el usuario necesita la respuesta ya** (consultar el estado de un pedido), **asíncrono para todo
lo que puede esperar** (enviar avisos masivos, recalcular métricas, notificar a otros módulos).

## Colas y sus garantías

Conceptos que aparecen en cualquier cola (SQS, RabbitMQ, BullMQ, Streams):

- **Entrega al menos una vez:** un mensaje puede procesarse más de una vez (el worker cae antes de confirmar). Los
  consumidores son **idempotentes**.
- **Visibilidad / confirmación:** al tomar un mensaje, queda invisible para otros durante un tiempo; si no se confirma,
  vuelve a la cola. Ese tiempo debe superar al procesamiento esperado.
- **Orden:** la mayoría no garantiza orden global; algunas lo garantizan por grupo o partición (útil para serializar
  por conversación).
- **Dead letter queue:** después de N intentos, el mensaje se aparta para no bloquear ni consumir recursos para
  siempre. Una DLQ necesita **alertas y un proceso de reprocesamiento**.
- **Retrasos y prioridades:** programar un recordatorio para dentro de 2 días, priorizar respuestas a clientes sobre
  envíos masivos.

## Reintentos y circuit breakers

Los reintentos mal diseñados **amplifican** las fallas: si cada una de tres capas reintenta tres veces, una falla se
convierte en 27 requests contra un servicio que ya está mal.

Reglas:

1. **Timeouts en todo**, con presupuestos coherentes entre capas.
2. **Reintentar en una sola capa**, sólo errores transitorios, con **backoff exponencial y jitter** y un máximo.
3. **Circuit breaker** por dependencia: tras un umbral de fallas, se deja de llamar durante un tiempo y se prueba de a
   poco antes de volver a la normalidad.
4. **Fallback** decidido de antemano: encolar para más tarde, otro proveedor, respuesta degradada o escalar a humano.

El simulador [Circuit breaker](/system-design/simulators/circuit-breaker) muestra la diferencia entre seguir llamando
a un proveedor caído y abrir el circuito.

## Backpressure y control de admisión

Una cola sin límite no resuelve una sobrecarga: la **posterga** y la convierte en un backlog que tal vez nunca se
vacíe. **Backpressure** es que el componente saturado **frene a quien le envía trabajo**.

Métricas que importan: **largo de la cola, edad del mensaje más viejo** y tasa de entrada frente a tasa de
procesamiento. Si la edad crece de forma sostenida, el sistema no está alcanzando y hay que escalar consumidores,
reducir la entrada o priorizar. El simulador [Procesamiento de colas](/system-design/simulators/queue-processing)
explora estas dinámicas.

## Rate limiting en varios niveles

| Nivel                | Para qué                                                         |
| -------------------- | ---------------------------------------------------------------- |
| Borde (API gateway)  | Proteger la plataforma de abuso y clientes defectuosos           |
| Por tenant           | Que un cliente no consuma la capacidad de todos (noisy neighbor) |
| Por destinatario     | Límites legales y de buena práctica de mensajes por día          |
| Hacia cada proveedor | Respetar sus cuotas (mensajería, LLM, pagos)                     |

## Webhooks confiables

**Recibidos** (de proveedores): verificar la firma sobre el body crudo, persistir con deduplicación por ID, responder
2xx rápido y procesar de forma asíncrona (curso de Node.js).

**Enviados** (la plataforma notifica a los sistemas de sus clientes):

- Firmar cada envío (HMAC con un secreto por cliente) e incluir un timestamp.
- Reintentar con backoff durante horas o días ante errores o timeouts, y mover a una DLQ por cliente al agotarse.
- Incluir un **ID de evento** para que el cliente deduplique.
- Proteger contra **SSRF**: validar las URLs de destino (no permitir direcciones internas).
- Un panel o API para que el cliente vea entregas fallidas y las reenvíe.

El desafío de arquitectura [Webhooks confiables](/system-design/challenges/reliable-webhooks) recorre este diseño
completo.

## Recuperación ante desastres

| Concepto | Pregunta                                     | Ejemplo                                        |
| -------- | -------------------------------------------- | ---------------------------------------------- |
| **RPO**  | ¿Cuántos datos (en tiempo) se pueden perder? | 5 minutos de pagos: no; 1 hora de métricas: sí |
| **RTO**  | ¿Cuánto puede tardar en volver el servicio?  | Webhooks de pagos: 30 minutos                  |

| Estrategia                                | RPO / RTO típicos  | Costo |
| ----------------------------------------- | ------------------ | ----- |
| Backups y restauración                    | Horas              | Bajo  |
| Pilot light / warm standby en otra región | Minutos a una hora | Medio |
| Activo-activo multirregión                | Segundos a minutos | Alto  |

Para la mayoría de los sistemas, **multi-zona** dentro de una región (base con réplica síncrona en otra zona, varias
instancias) cubre las fallas comunes; **multi-región** se justifica por requisitos fuertes de disponibilidad o
regulatorios. Y un plan de recuperación **que nunca se probó no es un plan**: restauraciones periódicas y simulacros.

## Errores frecuentes

- **Llamadas síncronas en cadena** para trabajo que podía ser asíncrono.
- **Consumidores no idempotentes** con colas de entrega al menos una vez.
- **DLQ sin alertas** ni reprocesamiento.
- **Reintentos en varias capas** y sin jitter.
- **Colas sin límite** y sin métricas de antigüedad.
- **Webhooks salientes sin firma, sin reintentos o sin protección SSRF.**
- **RPO y RTO no definidos** o planes de recuperación nunca probados.
