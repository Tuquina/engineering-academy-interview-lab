## ¿Qué problema resuelve?

Un SaaS de turnos e historias clínicas atiende a cientos de clínicas y consultorios que **compiten entre sí** y le
confían datos de salud de sus pacientes. El requisito número uno es que **ninguna clínica pueda ver datos de otra bajo
ninguna circunstancia**. Y además: que la carga masiva de turnos de una red hospitalaria no deje sin servicio a un
consultorio chico, que cada clínica tenga su configuración y que se pueda saber cuánto cuesta atender a cada una. El
mismo problema aparece en un SaaS para escuelas (alumnos y calificaciones de cada institución) o en una plataforma de
tiendas online (catálogo y pedidos de cada comercio). Este es el diseño de una **plataforma multi-tenant**.

## Modelos de tenancy

| Modelo                   | Aislamiento | Costo por tenant | Operación (migraciones, monitoreo) | Cuándo                                                         |
| ------------------------ | ----------- | ---------------- | ---------------------------------- | -------------------------------------------------------------- |
| Compartido (`tenant_id`) | Lógico      | Muy bajo         | Simple: un esquema                 | Muchos tenants chicos y medianos                               |
| Esquema por tenant       | Medio       | Bajo             | N esquemas que migrar              | Pocos cientos de tenants con algo de personalización           |
| Base por tenant          | Alto        | Medio-alto       | N bases que operar                 | Requisitos regulatorios, residencia de datos, clientes grandes |
| Stack por tenant         | Máximo      | Alto             | N despliegues                      | Clientes enterprise con exigencias contractuales               |

El enfoque más común es **híbrido**: compartido por defecto, y base o stack dedicados para los clientes que lo
requieren (y lo pagan). Para eso, el código debe **resolver la conexión a partir del tenant** desde el principio.

Los lugares donde más se olvida el tenant:

- **Claves de caché** (`patient:42` en lugar de `tenant:7:patient:42`).
- **Mensajes de colas** y eventos sin `tenantId`, procesados por workers que no lo verifican.
- **Archivos** en almacenamiento de objetos con rutas o permisos compartidos.
- **Índices vectoriales y RAG** sin filtro por tenant (el asistente cita el protocolo de otra clínica).
- **Logs y herramientas internas** (un panel de soporte que permite buscar en todos los tenants sin auditoría).
- **Jobs de mantenimiento** que recorren datos de todos los tenants.

Se testea explícitamente: **tests de aislamiento** que intentan leer recursos de otro tenant por cada endpoint,
herramienta del agente y consulta.

## Noisy neighbor

En recursos compartidos, un tenant con mucha actividad puede degradar a todos.

| Recurso compartido         | Mecanismo de aislamiento                                                                 |
| -------------------------- | ---------------------------------------------------------------------------------------- |
| API                        | Rate limiting por tenant (y por plan)                                                    |
| Workers de recordatorios   | Colas o particiones por tenant; concurrencia máxima por tenant; reparto justo            |
| Cuota del proveedor de LLM | Presupuesto de tokens y concurrencia por tenant                                          |
| Base de datos              | Límites de consultas pesadas, réplicas para reportes, base dedicada para los más grandes |
| Proveedores de mensajería  | Rate limits por tenant y por número emisor                                               |

El **reparto justo** (_fair scheduling_) evita que la cola se llene con 500.000 trabajos de un tenant y los demás
esperen horas: por ejemplo, los workers toman trabajos de forma intercalada entre tenants (round robin por tenant) en
lugar de FIFO global.

## Identidad y autorización

- **Usuarios de cada tenant** (médicos, recepción, administradores): roles por tenant; un mismo usuario podría
  pertenecer a varios tenants con roles distintos.
- **Usuarios de la plataforma** (soporte interno): acceso a datos de clientes **excepcional, justificado, temporal y
  auditado**.
- **Federación:** clientes enterprise que quieren iniciar sesión con su propio proveedor de identidad (SSO con OIDC o
  SAML).
- **Autorización por recurso** siempre incluye el tenant (lección de autenticación del curso de Node.js).

## Seguridad de APIs para clientes

Los clientes integran sus sistemas (laboratorios, prepagas, facturación) con la plataforma:

| Aspecto            | Práctica                                                                                 |
| ------------------ | ---------------------------------------------------------------------------------------- |
| Credenciales       | API keys por tenant con scopes, rotables, guardadas con hash; o OAuth client credentials |
| Autorización       | Cada key sólo opera sobre su tenant y sus scopes                                         |
| Límites            | Rate limits y cuotas por key y por tenant                                                |
| Contrato           | API versionada con OpenAPI, cambios compatibles y deprecaciones anunciadas               |
| Webhooks salientes | Firmados por tenant, con reintentos y panel de entregas                                  |
| Auditoría          | Registro de cada operación con la key, el actor y el resultado                           |

La lista de OWASP API Security Top 10 pone en primer lugar la autorización a nivel de objeto (BOLA): en multi-tenant,
es el error más grave posible.

## Configuración por tenant

Cada clínica configura sus agendas, plantillas de recordatorio, horarios, políticas de cancelación y canales. Buenas prácticas:
configuración **versionada y validada con esquemas**, cambios **auditados**, valores por defecto de la plataforma con
**overrides** acotados por tenant, y **feature flags por tenant** para habilitar funcionalidades de forma gradual.

## Observabilidad y costos por tenant

El tenant es una **dimensión de primera clase**:

- Métricas de latencia, errores y uso **por tenant** (con cuidado de la cardinalidad en el sistema de métricas).
- Logs y trazas con `tenantId` para investigar incidentes de un cliente.
- **Costo por tenant:** tokens de LLM, mensajes enviados, almacenamiento, cómputo de recordatorios. Es la base del pricing,
  de la detección de abusos y de la rentabilidad de cada cliente.
- SLOs por tier de cliente cuando los contratos lo exigen.

El desafío [Plataforma multi-tenant de agentes](/system-design/challenges/multi-tenant-agents) del Studio integra
todos estos elementos.

## Errores frecuentes

- **Tomar el tenant de un header o del body** sin validarlo contra la identidad.
- **Olvidar el tenant** en caché, colas, archivos, índices vectoriales o jobs.
- **Colas FIFO globales** donde un tenant grande bloquea a todos.
- **Acceso de soporte sin auditoría** a datos de clientes.
- **API keys sin scopes, sin rotación** o guardadas en texto plano.
- **Métricas sin dimensión de tenant** y costos imposibles de atribuir.
- **Elegir base por tenant para cientos de tenants chicos**, multiplicando la operación sin necesidad.
