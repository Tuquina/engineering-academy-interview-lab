## Interfaces funcionales y lambdas

Una **interfaz funcional** tiene un único método abstracto. Una **lambda** es una forma corta de implementarla. El
paquete `java.util.function` trae las más comunes:

| Interfaz        | Firma       | Ejemplo                   |
| --------------- | ----------- | ------------------------- |
| `Function`      | T → R       | `o -> o.totalCents()`     |
| `Predicate`     | T → boolean | `o -> o.isPaid()`         |
| `Supplier`      | () → T      | `() -> UUID.randomUUID()` |
| `Consumer`      | T → void    | `o -> log.info(o.id())`   |
| `BiFunction`    | (T, U) → R  | `(a, b) -> a + b`         |
| `UnaryOperator` | T → T       | `s -> s.trim()`           |

```java
Predicate<Appointment> isCompleted = appointment -> appointment.status() == AppointmentStatus.COMPLETED;
Function<Appointment, Long> fee = Appointment::feeCents;           // referencia a método
Comparator<Doctor> byRating = Comparator.comparingDouble(Doctor::rating)
                                        .thenComparing(Doctor::name);
```

Las lambdas pueden usar variables locales del método que las contiene sólo si son **efectivamente finales** (no se
reasignan). Es la misma idea de closure de JavaScript, pero con esa restricción.

## La Stream API

Un stream procesa una secuencia de elementos en tres partes: **fuente**, **operaciones intermedias** y una
**operación terminal**.

```java
record Appointment(String id, String doctorId, AppointmentStatus status, long feeCents) {}

List<Appointment> appointments = repository.findAll();

// Total facturado de los turnos atendidos
long revenue = appointments.stream()
    .filter(t -> t.status() == AppointmentStatus.COMPLETED)
    .mapToLong(Appointment::feeCents)
    .sum();

// Turnos agrupados por profesional
Map<String, List<Appointment>> byDoctor = appointments.stream()
    .collect(Collectors.groupingBy(Appointment::doctorId));

// Total por profesional
Map<String, Long> totalByDoctor = appointments.stream()
    .collect(Collectors.groupingBy(Appointment::doctorId, Collectors.summingLong(Appointment::feeCents)));

// Top 3 consultas más caras
List<Appointment> top3 = appointments.stream()
    .sorted(Comparator.comparingLong(Appointment::feeCents).reversed())
    .limit(3)
    .toList();                                   // Java 16+: lista inmutable

String ids = appointments.stream().map(Appointment::id).collect(Collectors.joining(", "));
```

### Evaluación perezosa

Las operaciones intermedias **no hacen nada** hasta que aparece la terminal. Eso permite cortocircuitar:
`findFirst`, `anyMatch` o `limit` dejan de procesar en cuanto tienen la respuesta. Un stream **se consume una sola
vez**: reutilizarlo lanza `IllegalStateException`.

<Callout type="warning" title="Cuidado con los efectos secundarios y con toMap">
  Modificar estado externo dentro de `map` o `forEach` de un stream paralelo produce resultados no deterministas.
  `Collectors.toMap` lanza `IllegalStateException` si hay claves duplicadas: pasá una función de merge,
  `toMap(k, v, (a, b) -> a)`.
</Callout>

`parallelStream()` reparte el trabajo en el ForkJoinPool común. Sólo conviene con colecciones grandes, operaciones
de CPU sin estado compartido y midiendo: en un servidor web casi nunca es una buena idea por defecto.

## Cuándo un for es mejor

Los streams brillan en transformaciones y agregaciones. Un bucle clásico es más claro cuando hay varias salidas
tempranas, excepciones checked dentro del cuerpo, o se modifica más de una variable. Elegí lo más legible, no lo más
"funcional".

## Excepciones

En Java todo error es un objeto que hereda de `Throwable`:

| Tipo      | Hereda de          | ¿Obliga a manejarla?       | Ejemplos                                           |
| --------- | ------------------ | -------------------------- | -------------------------------------------------- |
| Checked   | `Exception`        | Sí: `throws` o `try/catch` | `IOException`, `SQLException`                      |
| Unchecked | `RuntimeException` | No                         | `IllegalArgumentException`, `NullPointerException` |
| Error     | `Error`            | No (no se manejan)         | `OutOfMemoryError`, `StackOverflowError`           |

```java
public class InsufficientStockException extends RuntimeException {
    public InsufficientStockException(String sku, int requested) {
        super("Stock insuficiente de " + sku + ": pedido " + requested);
    }
}

try {
    inventory.reserve(sku, quantity);
} catch (InsufficientStockException e) {
    return Result.rejected(e.getMessage());
} catch (InventoryUnavailableException e) {
    throw new CheckoutFailedException("No se pudo reservar stock", e);  // conservar la causa
} finally {
    metrics.increment("checkout.attempt");
}
```

Buenas prácticas:

- **No tragar excepciones**: un `catch` vacío esconde errores.
- **Envolver conservando la causa** (`new X("mensaje", e)`) para no perder el stack trace.
- **Capturar lo específico**, no `Exception`, salvo en el borde de la aplicación.
- Las checked no se llevan bien con las lambdas de los streams: muchas APIs modernas prefieren unchecked y un
  **manejador central** (en Spring, `@ControllerAdvice`).

## try-with-resources

Todo lo que implementa `AutoCloseable` (conexiones, archivos, streams de I/O) se cierra solo al salir del bloque,
incluso si hay una excepción:

```java
try (var reader = Files.newBufferedReader(Path.of("appointments.csv"));
     var lines = reader.lines()) {
    return lines.skip(1).map(AppointmentCsv::parse).toList();
} // reader y lines se cierran en orden inverso
```

Antes de Java 7 había que cerrar en un `finally`, con riesgo de fugas si el cierre también fallaba.

## Resumen

Lambdas y referencias a métodos implementan interfaces funcionales; la Stream API encadena operaciones perezosas
hasta una terminal. Para errores: unchecked para el dominio, checked donde el llamador realmente puede recuperarse,
nunca tragar excepciones y try-with-resources para liberar recursos.
