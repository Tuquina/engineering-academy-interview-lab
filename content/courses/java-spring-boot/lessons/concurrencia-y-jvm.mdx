## Hilos y executors

Un **hilo** (`Thread`) es una línea de ejecución concurrente. Crear un hilo por tarea a mano es costoso y difícil de
controlar; en su lugar se usa un **ExecutorService**, que administra un pool de hilos y una cola de tareas.

```java
try (ExecutorService executor = Executors.newFixedThreadPool(8)) {   // ExecutorService es AutoCloseable desde Java 19
    Future<Invoice> invoice = executor.submit(() -> billing.createInvoice(orderId));
    Future<Shipment> shipment = executor.submit(() -> logistics.schedule(orderId));
    send(invoice.get(), shipment.get());   // get() bloquea hasta tener el resultado
}
```

### CompletableFuture

`CompletableFuture` permite **componer** tareas asíncronas sin bloquear en cada paso, parecido a las promesas de
JavaScript:

```java
CompletableFuture<Product> product = CompletableFuture.supplyAsync(() -> catalog.find(sku), executor);
CompletableFuture<Price> price = CompletableFuture.supplyAsync(() -> pricing.priceFor(sku), executor);

CompletableFuture<ProductView> view = product
    .thenCombine(price, ProductView::new)                    // combina dos resultados
    .orTimeout(500, TimeUnit.MILLISECONDS)                   // Java 9+
    .exceptionally(error -> ProductView.unavailable(sku));   // fallback
```

Pasá siempre tu propio executor: sin él se usa el `ForkJoinPool` común, compartido por toda la aplicación.

## Condiciones de carrera y sincronización

Cuando varios hilos modifican estado compartido, el resultado puede depender del orden de ejecución:

```java
class Counter {
    private long count = 0;
    void increment() { count++; }   // ¡no es atómico! leer, sumar y escribir son tres pasos
}
```

Con dos hilos incrementando un millón de veces cada uno, el resultado suele ser menor a dos millones. Soluciones:

| Herramienta                     | Uso                                                                              |
| ------------------------------- | -------------------------------------------------------------------------------- |
| `synchronized`                  | Un solo hilo a la vez dentro del bloque o método; también garantiza visibilidad. |
| `ReentrantLock`                 | Como synchronized, con `tryLock`, timeouts y condiciones.                        |
| `AtomicLong`, `AtomicReference` | Operaciones atómicas sin locks (compare-and-set).                                |
| `ConcurrentHashMap`             | Mapa seguro para concurrencia con operaciones atómicas como `merge` y `compute`. |
| Inmutabilidad                   | Objetos que no cambian no necesitan sincronización.                              |

**`volatile`** garantiza que la escritura de un hilo sea **visible** para los demás, pero no hace atómicas las
operaciones compuestas como `count++`.

<Callout type="danger" title="Deadlock">
  Si el hilo A toma el lock 1 y espera el 2, mientras el hilo B toma el 2 y espera el 1, ambos quedan
  bloqueados para siempre. Se evita tomando los locks siempre en el mismo orden, usando timeouts (`tryLock`) o
  diseñando sin estado compartido. Un thread dump (`jstack`) muestra los hilos bloqueados.
</Callout>

## Virtual threads

Un hilo de plataforma corresponde a un hilo del sistema operativo: cada uno reserva memoria para su stack, y un
servidor no puede tener cientos de miles. Durante años la respuesta fue la programación reactiva (callbacks, WebFlux).

Los **virtual threads** (JEP 444, estables desde **Java 21**) son hilos livianos que administra la JVM. Muchos
virtual threads se montan sobre pocos hilos de plataforma; cuando uno se bloquea esperando I/O (una consulta a la
base, una llamada HTTP), libera el hilo de plataforma para otro.

```java
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    List<Future<Rate>> rates = providers.stream()
        .map(p -> executor.submit(() -> p.quote(shipment)))   // un virtual thread por proveedor
        .toList();
}
```

- Permiten escribir **código bloqueante simple** (un hilo por request) con escalabilidad similar a la asíncrona.
- **No aceleran el cómputo de CPU**: sólo ayudan cuando el tiempo se va en esperar.
- No se hace _pooling_ de virtual threads: se crea uno por tarea.
- Spring Boot los habilita con `spring.threads.virtual.enabled=true`.

- **Stack**: uno por hilo; guarda los frames de los métodos con variables locales y referencias. Una recursión
  infinita lo desborda (`StackOverflowError`).
- **Heap**: compartido; ahí viven los objetos. Su tamaño se configura con `-Xms` y `-Xmx`, o como porcentaje de la
  memoria del contenedor con `-XX:MaxRAMPercentage`.
- **Metaspace**: metadatos de las clases cargadas.

### Garbage collection

El recolector libera los objetos que ya no son **alcanzables** desde las raíces (stacks, campos estáticos). Se basa
en la **hipótesis generacional**: la mayoría de los objetos muere joven, así que la generación joven se recolecta
seguido y barato, y los objetos que sobreviven pasan a la vieja.

| Recolector | Cuándo                                                                |
| ---------- | --------------------------------------------------------------------- |
| G1         | Por defecto en servidores. Buen equilibrio entre throughput y pausas. |
| ZGC        | Heaps grandes y pausas de muy pocos milisegundos.                     |
| Parallel   | Máximo throughput en procesos batch, tolerando pausas más largas.     |

Un **memory leak** en Java no es memoria sin liberar como en C, sino **referencias que se retienen sin querer**: una
caché estática sin límite, listeners que nunca se quitan, `ThreadLocal` sin limpiar en pools de hilos. Se diagnostica
con un heap dump y herramientas como Eclipse MAT o JDK Flight Recorder.

### JIT

La JVM empieza interpretando el bytecode y, a medida que detecta métodos "calientes", los compila a código nativo con
optimizaciones basadas en cómo se usa el programa realmente. Por eso una aplicación Java tarda un poco en alcanzar su
mejor rendimiento (_warm-up_), y por eso los benchmarks se hacen con JMH y no con un `System.nanoTime()` aislado.

## Resumen

Usá executors y CompletableFuture para concurrencia, protegé el estado compartido o evitalo, y considerá virtual
threads para servicios con mucha I/O. Entender heap, stack, GC y JIT te permite explicar y diagnosticar problemas de
memoria y latencia, una pregunta muy común en entrevistas de Java.
