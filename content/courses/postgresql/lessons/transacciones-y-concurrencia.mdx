## ¿Qué problema resuelve?

En un backend ocurren muchas cosas a la vez sobre los mismos datos: webhooks de pagos (a veces duplicados), dos
clientes comprando la última unidad de un producto, dos personas eligiendo el mismo asiento de un vuelo, dos débitos
simultáneos de una billetera, un proceso nocturno que vence reservas sin confirmar. Sin un buen manejo de la
concurrencia aparecen los bugs más caros: **pagos aplicados dos veces, saldos perdidos, stock negativo, asientos
vendidos dos veces, eventos publicados sobre datos que nunca se guardaron**.

## Transacciones y ACID

Una **transacción** agrupa varias operaciones en una unidad con cuatro garantías:

| Propiedad        | Significado                                                         |
| ---------------- | ------------------------------------------------------------------- |
| **Atomicidad**   | Todo o nada: si algo falla, no queda ningún cambio parcial.         |
| **Consistencia** | Al terminar, se cumplen todas las constraints.                      |
| **Aislamiento**  | Las transacciones concurrentes no se ven a medias (según el nivel). |
| **Durabilidad**  | Una vez confirmada, sobrevive a una caída (se escribe en el WAL).   |

```ts
import type { Pool, PoolClient } from "pg";

/** Ejecuta `work` en una transacción: COMMIT si termina, ROLLBACK si lanza. */
export async function inTransaction<T>(pool: Pool, work: (client: PoolClient) => Promise<T>): Promise<T> {
  const client = await pool.connect(); // la transacción vive en UNA conexión
  try {
    await client.query("BEGIN");
    const result = await work(client);
    await client.query("COMMIT");
    return result;
  } catch (error) {
    await client.query("ROLLBACK");
    throw error;
  } finally {
    client.release();
  }
}
```

Un error frecuente en Node.js: usar `pool.query` dentro de lo que se cree una transacción. Cada `pool.query` puede ir
por **una conexión distinta**, fuera de la transacción. Todas las consultas de la transacción usan el mismo `client`.
Las transacciones deben ser **cortas**: nada de llamadas HTTP a proveedores o a un LLM con la transacción abierta.

## Niveles de aislamiento

| Nivel           | Previene                                   | Puede ocurrir                                                                | En PostgreSQL                      |
| --------------- | ------------------------------------------ | ---------------------------------------------------------------------------- | ---------------------------------- |
| Read Committed  | Lecturas sucias                            | Lecturas no repetibles, fantasmas, lost update en patrones read-modify-write | **Por defecto**                    |
| Repeatable Read | Además, lecturas no repetibles y fantasmas | Write skew                                                                   | Instantánea de toda la transacción |
| Serializable    | Todas las anomalías                        | Errores de serialización a reintentar                                        | SSI: detecta conflictos y aborta   |

- En **Read Committed**, cada sentencia ve los datos confirmados al momento en que empieza. Dos sentencias de la
  misma transacción pueden ver datos distintos.
- En **Repeatable Read** y **Serializable**, cuando hay un conflicto la transacción falla con un **error de
  serialización** (`40001`): la aplicación debe **reintentar** la transacción completa.

## MVCC: cómo lo hace PostgreSQL

PostgreSQL implementa el aislamiento con **MVCC** (_Multi-Version Concurrency Control_): un `UPDATE` no sobrescribe la
fila, **crea una versión nueva**. Cada transacción ve las versiones visibles según su instantánea.

  DB-->>A: 100.000 (versión 1)

  Note over DB: versión 2 creada, todavía no confirmada
  A->>DB: SELECT balance

  DB-->>A: 60.000 (versión 2)
`}
/>

Consecuencias:

- **Los lectores no bloquean a los escritores, ni los escritores a los lectores.**
- **Dos escrituras sobre la misma fila sí se esperan**: la segunda espera a que la primera confirme o cancele.
- Las versiones viejas (filas muertas) las limpia **VACUUM** (automático con autovacuum). Una **transacción abierta
  durante horas** impide limpiar y produce _bloat_.

## El lost update y cómo evitarlo

```ts
// ❌ Read-modify-write en la aplicación: dos débitos concurrentes de una billetera pierden uno
const { rows } = await client.query("SELECT balance_cents FROM wallets WHERE id = $1", [walletId]);
await client.query("UPDATE wallets SET balance_cents = $1 WHERE id = $2", [
  rows[0].balance_cents - amount,
  walletId,
]);
```

Tres soluciones, en orden de preferencia (cada una con el caso donde suele aparecer):

```sql
-- 1. Operación atómica: la base calcula sobre el valor actual (y la segunda espera a la primera)
UPDATE wallets SET balance_cents = balance_cents - $1 WHERE id = $2 AND balance_cents >= $1 RETURNING balance_cents;
UPDATE products SET stock = stock - $1 WHERE id = $2 AND stock >= $1;   -- 0 filas = sin stock suficiente

-- 2. Pesimista: bloquear la fila antes de leerla para decidir (elegir un asiento de un vuelo)
SELECT status, held_until FROM seats WHERE flight_id = $1 AND seat_number = $2 FOR UPDATE;
-- ... decidir con el valor actual: ¿está libre o venció la retención? ...
UPDATE seats SET status = 'held', held_until = now() + interval '10 minutes' WHERE flight_id = $1 AND seat_number = $2;

-- 3. Optimista: columna version; si nadie la cambió, se actualiza (un artículo editado en un formulario)
UPDATE articles SET body = $3, version = version + 1 WHERE id = $1 AND version = $2;
-- 0 filas afectadas = alguien editó el artículo: recargar y reintentar, o informar el conflicto (409)
```

| Enfoque   | Cuándo                                                                             |
| --------- | ---------------------------------------------------------------------------------- |
| Atómico   | La operación se expresa en una sentencia (incrementos, decrementos, condiciones)   |
| Pesimista | Conflictos frecuentes, sección corta, hay que decidir con el valor actual          |
| Optimista | Conflictos raros, o la edición involucra tiempo de usuario (un formulario abierto) |

## Locks, colas y deadlocks

`SELECT ... FOR UPDATE SKIP LOCKED` permite usar una tabla como **cola de trabajo** con varios workers sin que dos
tomen la misma fila:

```sql
-- Cada worker toma hasta 10 trabajos pendientes que nadie más tomó
UPDATE outbox SET status = 'processing', locked_at = now()
 WHERE id IN (
   SELECT id FROM outbox
    WHERE status = 'pending'
    ORDER BY id
    LIMIT 10
    FOR UPDATE SKIP LOCKED
 )
RETURNING id, type, payload;
```

Un **deadlock** ocurre cuando dos transacciones se esperan mutuamente: en una transferencia entre billeteras, A bloqueó la
billetera 1 y quiere la 2; B (la transferencia inversa) bloqueó la 2 y quiere la 1. PostgreSQL lo detecta y **aborta una de las dos** (error `40P01`). Prevención:

- **Orden consistente:** bloquear siempre en el mismo orden (por ejemplo, por ID ascendente).
- **Transacciones cortas** y con pocos locks.
- **Reintentar** la transacción abortada.
- **`lock_timeout`** para no esperar indefinidamente.

## Idempotencia con constraints y UPSERT

La forma más robusta de hacer idempotente una operación es que **la base lo garantice**:

```sql
INSERT INTO payments (provider, external_id, order_id, amount_cents, paid_at)
VALUES ($1, $2, $3, $4, $5)
ON CONFLICT (provider, external_id) DO NOTHING
RETURNING id;
```

```ts
await inTransaction(pool, async (client) => {
  const inserted = await client.query(INSERT_PAYMENT_SQL, [
    provider,
    externalId,
    orderId,
    amountCents,
    paidAt,
  ]);
  if (inserted.rowCount === 0) return { status: "duplicate" }; // otro request ya lo aplicó: no repetir efectos
  await client.query("UPDATE orders SET status = 'paid' WHERE id = $1 AND status = 'pending'", [orderId]);
  return { status: "applied" };
});
```

`ON CONFLICT DO UPDATE` (_upsert_) actualiza la fila existente; `DO NOTHING` la ignora. En ambos casos la verificación
y la escritura son **atómicas**: no hay ventana de carrera. El Database Lab tiene un ejercicio sobre este patrón.

## Transactional Outbox

Después de registrar un pago hay que **publicar un evento** (para confirmar el pedido, avisar al depósito que
prepare el envío, notificar al cliente). Hacerlo con dos escrituras separadas (base y broker) tiene un problema: si una falla, el
sistema queda inconsistente.

Los consumidores deben ser **idempotentes**, porque el relay puede publicar el mismo evento más de una vez. La Pattern
Library tiene el patrón [Transactional Outbox](/patterns/transactional-outbox) con su diagrama interactivo.

## Comparación con C# y Java

| Concepto                     | .NET                                     | Java / Spring              | Node.js + PostgreSQL                            |
| ---------------------------- | ---------------------------------------- | -------------------------- | ----------------------------------------------- |
| Transacción                  | `BeginTransaction`, `TransactionScope`   | `@Transactional`           | `BEGIN`/`COMMIT` en un client, o la API del ORM |
| Concurrencia optimista       | `[ConcurrencyCheck]`, `RowVersion` en EF | `@Version` en JPA          | Columna `version` + `WHERE version = $v`        |
| Lock pesimista               | `FOR UPDATE` en SQL crudo o hints        | `@Lock(PESSIMISTIC_WRITE)` | `SELECT ... FOR UPDATE`                         |
| Reintentos por serialización | Políticas de reintento de Npgsql/EF      | Spring Retry               | Reintento propio ante `40001`/`40P01`           |

Una diferencia práctica: `@Transactional` en Spring propaga la transacción por el hilo de forma implícita. En Node.js
**no hay transacción implícita**: la conexión de la transacción se pasa explícitamente (o con `AsyncLocalStorage`).

## Errores frecuentes

- **Read-modify-write en la aplicación** sin atomicidad ni locks.
- **`pool.query` dentro de una "transacción"**, que en realidad usa otras conexiones.
- **Transacciones largas** con llamadas HTTP o a un LLM adentro.
- **Chequear con `SELECT` antes de insertar** en lugar de usar una constraint.
- **No reintentar** errores de serialización o deadlocks.
- **Publicar eventos fuera de la transacción** sin outbox.
- **Consumidores no idempotentes.**
