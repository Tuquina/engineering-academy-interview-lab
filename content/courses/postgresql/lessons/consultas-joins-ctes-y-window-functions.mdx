## ¿Qué problema resuelve?

Las preguntas de negocio reales rara vez son "traer una fila por ID":

- ¿Cuál es el último estado de cada envío? (logística)
- ¿Qué porcentaje de los tickets de cada prioridad se respondió dentro del plazo? (soporte)
- ¿Cómo evolucionaron las ventas de cada vendedor mes a mes? (e-commerce)
- Dame la siguiente página de 50 jugadores del ranking, ordenados por puntaje. (juegos)

Resolverlas en SQL (en lugar de traer miles de filas y procesarlas en la aplicación) es más rápido, consistente y
simple. El **Database Lab** de la plataforma (`/database-lab`) tiene ejercicios con preguntas de este tipo sobre el
dataset de un marketplace. Los ejemplos de joins, subconsultas, CTEs y window functions de esta lección usan sus
tablas (`customers`, `orders`, `order_items`, `products`, `sellers`, `payments`, `shipments`, `shipment_events`,
`support_tickets`, `ticket_messages`) y se pueden ejecutar ahí tal cual.

```sql
-- INNER: clientes con al menos un pedido cancelado
SELECT DISTINCT c.id, c.full_name
  FROM customers c
  JOIN orders o ON o.customer_id = c.id AND o.status = 'cancelled';

-- LEFT: todos los clientes, con la cantidad de pedidos (0 si no tienen)
SELECT c.id, c.full_name, count(o.id) AS orders   -- count(o.id) ignora los NULL
  FROM customers c
  LEFT JOIN orders o ON o.customer_id = c.id
 GROUP BY c.id, c.full_name;

-- Anti-join: clientes que nunca abrieron un ticket de soporte
SELECT c.id, c.full_name
  FROM customers c
 WHERE NOT EXISTS (SELECT 1 FROM support_tickets t WHERE t.customer_id = c.id);
```

Dos trampas clásicas:

1. **Un filtro sobre la tabla derecha en el `WHERE` convierte un `LEFT JOIN` en `INNER`.** Si escribís
   `LEFT JOIN orders o ... WHERE o.status = 'delivered'`, los clientes sin pedidos entregados (con `o.status` en
   `NULL` o con otro estado) desaparecen. El filtro va en el `ON`.
2. **El join multiplica filas (fan-out).** Si unís productos con ítems vendidos y con reseñas (dos relaciones 1:N
   del mismo producto), cada ítem se repite por cada reseña:

```sql
-- ❌ Las unidades se suman una vez por cada reseña del producto, y las reseñas una vez por cada ítem
SELECT p.name, sum(oi.quantity) AS units, count(r.id) AS reviews
  FROM products p
  LEFT JOIN order_items oi ON oi.product_id = p.id
  LEFT JOIN reviews r ON r.product_id = p.id
 GROUP BY p.id, p.name;

-- ✅ Agregar cada relación primero y unir después
SELECT p.name, coalesce(s.units, 0) AS units, coalesce(rv.reviews, 0) AS reviews
  FROM products p
  LEFT JOIN (SELECT product_id, sum(quantity) AS units FROM order_items GROUP BY product_id) s
         ON s.product_id = p.id
  LEFT JOIN (SELECT product_id, count(*) AS reviews FROM reviews GROUP BY product_id) rv
         ON rv.product_id = p.id;
```

## Subconsultas, EXISTS y LATERAL

```sql
-- Subconsulta escalar: el precio de cada producto junto con el promedio de su categoría
SELECT p.name, p.price_cents,
       (SELECT avg(x.price_cents) FROM products x WHERE x.category = p.category) AS category_avg
  FROM products p;

-- LATERAL: para cada envío, sus 2 eventos de seguimiento más recientes
SELECT s.id, recent.status, recent.occurred_at
  FROM shipments s
  CROSS JOIN LATERAL (
    SELECT e.status, e.occurred_at
      FROM shipment_events e
     WHERE e.shipment_id = s.id
     ORDER BY e.occurred_at DESC
     LIMIT 2
  ) recent;
```

`LATERAL` permite que la subconsulta de la derecha use columnas de la izquierda: es la forma natural de expresar
"para cada fila, los N más recientes".

## CTEs: consultas por pasos

Una **CTE** (`WITH`) da nombre a un resultado intermedio. Hace legibles las consultas largas, como variables en
código:

```sql
-- Porcentaje de tickets respondidos dentro de las 4 horas, por prioridad
WITH first_response AS (
  SELECT t.id, t.priority, t.created_at,
         min(m.sent_at) FILTER (WHERE m.author = 'agent') AS responded_at
    FROM support_tickets t
    LEFT JOIN ticket_messages m ON m.ticket_id = t.id
   GROUP BY t.id, t.priority, t.created_at
),
by_priority AS (
  SELECT priority,
         count(*) AS total,
         count(*) FILTER (WHERE responded_at - created_at <= interval '4 hours') AS fast
    FROM first_response
   GROUP BY priority
)
SELECT priority, total, fast, round(100.0 * fast / nullif(total, 0), 1) AS fast_pct
  FROM by_priority
 ORDER BY fast_pct DESC NULLS LAST;
```

Desde PostgreSQL 12, el planificador puede **incorporar** las CTEs no recursivas a la consulta principal (ya no son
una barrera de optimización por defecto). Las **CTEs recursivas** (`WITH RECURSIVE`) recorren jerarquías: el árbol
de categorías de un catálogo, el organigrama de una empresa o la cadena de respuestas de un hilo de comentarios.

## Window functions

Una **window function** calcula un valor sobre un conjunto de filas relacionadas **sin colapsarlas** (a diferencia
de `GROUP BY`):

```sql
-- Pedidos de cada cliente con su número de compra, el gasto acumulado y la fecha de la compra anterior
SELECT o.customer_id, o.id AS order_id, o.created_at, p.amount_cents,
       row_number() OVER w AS purchase_number,
       sum(p.amount_cents) OVER w AS running_total,
       lag(o.created_at) OVER w AS previous_order_at
  FROM orders o
  JOIN payments p ON p.order_id = o.id
WINDOW w AS (PARTITION BY o.customer_id ORDER BY o.created_at);
```

| Función                                                        | Uso típico                                                    |
| -------------------------------------------------------------- | ------------------------------------------------------------- |
| `row_number()`                                                 | "La primera de cada grupo": el último evento de cada envío    |
| `rank()`, `dense_rank()`                                       | Rankings con empates: productos más vendidos por categoría    |
| `sum(...) OVER (ORDER BY ...)`                                 | Acumulados: ventas acumuladas mes a mes                       |
| `lag()`, `lead()`                                              | Comparar con la fila anterior o siguiente: días entre compras |
| `avg(...) OVER (... ROWS BETWEEN 6 PRECEDING AND CURRENT ROW)` | Promedios móviles: lecturas de un sensor, ventas diarias      |

El patrón "la primera fila de cada grupo" es muy frecuente:

```sql
-- Último evento de seguimiento de cada envío
SELECT *
  FROM (
    SELECT e.*, row_number() OVER (PARTITION BY e.shipment_id ORDER BY e.occurred_at DESC) AS rn
      FROM shipment_events e
  ) ranked
 WHERE rn = 1;

-- Alternativa propia de PostgreSQL
SELECT DISTINCT ON (e.shipment_id) e.shipment_id, e.status, e.occurred_at
  FROM shipment_events e
 ORDER BY e.shipment_id, e.occurred_at DESC;
```

## Paginación: OFFSET frente a keyset

El ejemplo usa la tabla de puntajes de un juego en línea (`scores`, con millones de filas por temporada):

```sql
-- OFFSET: simple, pero el costo crece con la página
SELECT player_id, points FROM scores
 WHERE season_id = 7
 ORDER BY points DESC, player_id DESC
 LIMIT 50 OFFSET 50000;           -- lee y descarta 50.000 filas

-- Keyset: continuar desde el último elemento visto
SELECT player_id, points FROM scores
 WHERE season_id = 7
   AND (points, player_id) < ($1, $2)   -- valores de la última fila de la página anterior
 ORDER BY points DESC, player_id DESC
 LIMIT 50;
-- Con un índice en (season_id, points DESC, player_id DESC), cada página cuesta lo mismo.
```

| Aspecto                  | OFFSET                          | Keyset (cursor)                         |
| ------------------------ | ------------------------------- | --------------------------------------- |
| Costo de la página N     | Crece con N                     | Constante con el índice adecuado        |
| Inserciones concurrentes | Puede repetir u omitir filas    | Estable                                 |
| Saltar a la página 37    | Sí                              | No (se navega por "siguiente")          |
| Uso típico               | Tablas chicas, paneles internos | APIs, listados grandes, scroll infinito |

En una API, el cursor se devuelve **opaco** (codificado) para que el cliente no dependa de su estructura. El orden
siempre incluye una columna única (el `id`) para desempatar.

## Comparación con C# y Java

| Necesidad         | .NET (LINQ / EF Core)             | Java (JPA / Streams)                    | SQL en PostgreSQL                 |
| ----------------- | --------------------------------- | --------------------------------------- | --------------------------------- |
| Join              | `join` / navegación con `Include` | `JOIN FETCH`, relaciones                | `JOIN`, `LEFT JOIN`               |
| Anti-join         | `!Any()`                          | `NOT EXISTS` en JPQL                    | `NOT EXISTS`                      |
| Ranking por grupo | `GroupBy` + `OrderBy` en memoria  | Streams en memoria o SQL nativo         | `row_number() OVER (...)`         |
| Paginación        | `Skip/Take` (OFFSET)              | `setFirstResult/setMaxResults` (OFFSET) | Keyset con `WHERE (a, b) < (...)` |

Los ORMs facilitan las consultas simples, pero las window functions, `LATERAL` o el keyset suelen requerir SQL
explícito o el soporte avanzado del query builder.

## Errores frecuentes

- **Filtros de la tabla derecha en el `WHERE`** de un `LEFT JOIN`.
- **Sumar después de un join 1:N** y duplicar montos.
- **`NOT IN` con subconsultas** que pueden devolver `NULL`.
- **Traer todo a la aplicación** para rankear o acumular.
- **OFFSET en listados grandes** de APIs.
- **Orden de paginación sin desempate único**, que repite u omite filas.
