## ¿Qué problema resuelve?

El esquema está bien modelado, las consultas tienen índices y las transacciones son correctas. Aun así, en
producción aparecen otros problemas: la base rechaza conexiones cuando se escala la aplicación, una tabla de eventos
de 2.000 millones de filas se vuelve imposible de mantener, un parámetro de ordenamiento permite inyección SQL, o una
consulta olvidó filtrar por tenant y mostró datos de otro cliente. Esta lección cubre la operación y la seguridad.

## Conexiones y pooling

En PostgreSQL, **cada conexión es un proceso** en el servidor, con su propia memoria. Abrir una conexión cuesta
(TCP, TLS, autenticación) y mantener miles degrada a la base. Por eso:

- La aplicación usa un **pool** acotado por réplica (lección de performance del curso de Node.js).
- El total es **réplicas × tamaño del pool**, y debe entrar holgadamente en `max_connections`.
- Con **funciones serverless** (cada invocación puede abrir sus propias conexiones) o muchas réplicas, se usa un
  **pooler externo**: PgBouncer o el pooler del proveedor gestionado.

## Particionado

El **particionado** divide una tabla lógica en tablas físicas según una clave:

```sql
CREATE TABLE conversation_events (
  id          bigint GENERATED ALWAYS AS IDENTITY,
  tenant_id   bigint NOT NULL,
  occurred_at timestamptz NOT NULL,
  type        text NOT NULL,
  payload     jsonb NOT NULL,
  PRIMARY KEY (id, occurred_at)                 -- la clave de partición debe estar en la PK
) PARTITION BY RANGE (occurred_at);

CREATE TABLE conversation_events_2026_11 PARTITION OF conversation_events
  FOR VALUES FROM ('2026-11-01') TO ('2026-12-01');
```

| Beneficio                                                                      | Ejemplo                                                               |
| ------------------------------------------------------------------------------ | --------------------------------------------------------------------- |
| Consultas por rango leen sólo las particiones relevantes (_partition pruning_) | Eventos de la última semana                                           |
| Borrar datos viejos es instantáneo                                             | `DROP TABLE conversation_events_2024_01` en vez de un `DELETE` masivo |
| Mantenimiento por partición                                                    | VACUUM e índices más chicos                                           |

No es una optimización por defecto: agrega complejidad (la clave de partición en la PK y en las consultas, crear
particiones futuras). Se justifica en **tablas muy grandes** con una clave natural de acceso, típicamente **tiempo**
(eventos, mensajes, logs de auditoría).

## Inyección SQL

La **inyección SQL** ocurre cuando un valor del usuario se concatena en el texto de la consulta y termina
interpretado como SQL:

```ts
// ❌ Inyección: name = "x' OR '1'='1" devuelve todos los clientes
await pool.query(`SELECT * FROM customers WHERE full_name = '${name}'`);

// ✅ Parametrizado: el valor viaja separado y nunca se interpreta como SQL
await pool.query("SELECT * FROM customers WHERE full_name = $1", [name]);
```

Los **identificadores** (nombres de columnas o tablas) no se pueden parametrizar. Para un ordenamiento dinámico, se
valida contra una **lista permitida**:

```ts
const SORTABLE_COLUMNS = { balance: "balance_cents", due: "due_date", created: "created_at" } as const;

export function orderByClause(sort: string): string {
  const column = SORTABLE_COLUMNS[sort as keyof typeof SORTABLE_COLUMNS];
  if (!column) throw new InvalidSortError(sort); // nunca se concatena el input original
  return `ORDER BY ${column} DESC, id DESC`;
}
```

Los ORMs y query builders parametrizan automáticamente, **salvo** en sus funciones de SQL crudo, donde vuelve a ser
responsabilidad del desarrollador.

## Row Level Security para multi-tenancy

La primera barrera de aislamiento entre tenants es la aplicación (repositorios que exigen el tenant). **Row Level
Security** agrega una **segunda barrera en la base**: aunque una consulta olvide el filtro, la base no devuelve filas
de otro tenant.

```sql
ALTER TABLE debts ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON debts
  USING (tenant_id = current_setting('app.tenant_id')::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);
```

```ts
await inTransaction(pool, async (client) => {
  // Fija el tenant para esta transacción (true = local a la transacción: seguro con poolers en modo transacción)
  await client.query("SELECT set_config('app.tenant_id', $1, true)", [String(user.tenantId)]);
  return client.query("SELECT * FROM debts WHERE status = 'pending'"); // sólo filas del tenant
});
```

Requisitos para que sirva: el rol de la aplicación **no es dueño de la tabla** ni tiene `BYPASSRLS` (los dueños y
superusuarios ignoran las políticas salvo que se fuerce con `FORCE ROW LEVEL SECURITY`), y el tenant se fija **en
cada transacción**, nunca a nivel de sesión compartida.

## Mantenimiento: VACUUM, backups y réplicas

- **VACUUM y autovacuum** limpian las versiones muertas que deja MVCC y actualizan estadísticas. Se vigilan el
  _bloat_, las transacciones abiertas durante mucho tiempo (impiden limpiar) y el progreso de autovacuum en tablas
  con muchas escrituras.
- **Backups:** backups físicos con WAL (recuperación a un punto en el tiempo, PITR) en los servicios gestionados; un
  backup sólo cuenta si se **probó restaurarlo**.
- **Réplicas de lectura:** descargan consultas de reportes; la replicación es asíncrona por defecto, así que una
  réplica puede estar levemente atrasada (no leer de ahí justo después de escribir).
- **Monitoreo:** conexiones, consultas lentas (`pg_stat_statements`), locks en espera, retraso de réplicas, espacio
  en disco.

## Errores frecuentes

- **Pools grandes en muchas réplicas** que agotan `max_connections`.
- **Funciones serverless conectando directo** a PostgreSQL sin pooler.
- **Concatenar valores o identificadores** en el SQL.
- **RLS con el rol dueño de la tabla**, que ignora las políticas.
- **Fijar el tenant a nivel de sesión** con un pooler en modo transacción.
- **La aplicación conectada como superusuario.**
- **Backups nunca restaurados** en una prueba.
