## ¿Qué problema resuelve?

El panel de supervisores muestra "deudas vencidas de la campaña, ordenadas por saldo". Con 10.000 deudas tardaba 20
ms; con 8 millones tarda 9 segundos. La consulta no cambió: cambió el volumen. Sin un índice adecuado, PostgreSQL
**lee la tabla entera** para encontrar unas pocas filas. Esta lección explica cómo se diseñan índices **a partir de
las consultas** y cómo se verifica con evidencia que funcionan.

## Qué es un índice B-tree

Un índice es una **estructura separada** que mantiene los valores de una o más columnas **ordenados**, con punteros a
las filas de la tabla. El tipo por defecto, **B-tree**, es un árbol balanceado que permite:

- Búsquedas por igualdad (`=`) y por rango (`<`, `>`, `BETWEEN`).
- Devolver filas ya ordenadas (`ORDER BY`) sin un paso de sort.
- Encontrar valores con `IS NULL` y prefijos de texto (con el operador adecuado).

El costo: cada índice **ocupa espacio** y **se actualiza en cada escritura**. Una tabla con diez índices escribe
mucho más lento que una con dos.

## Índices compuestos y el orden de las columnas

```sql
-- Consulta frecuente del panel
SELECT id, customer_id, balance_cents
  FROM debts
 WHERE tenant_id = $1 AND status = 'pending' AND due_date < $2
 ORDER BY due_date
 LIMIT 100;

-- Índice que la soporta: igualdades primero, después la columna de rango y orden
CREATE INDEX debts_tenant_status_due_idx ON debts (tenant_id, status, due_date);
```

La **regla del prefijo izquierdo**: un índice en `(a, b, c)` sirve para filtros sobre `a`, sobre `a, b` y sobre
`a, b, c`, pero en general **no** para filtros sólo sobre `b` o sobre `c`. Es como una guía telefónica ordenada por
apellido y nombre: buscar por apellido es rápido; buscar sólo por nombre obliga a leerla toda.

Criterio práctico de orden:

1. Columnas filtradas por **igualdad** (`tenant_id`, `status`).
2. La columna de **rango** (`due_date < ...`) o de **orden** (`ORDER BY due_date`).
3. Si hace falta, columnas extra para cubrir la consulta (`INCLUDE`).

## Índices parciales, de cobertura y por expresión

```sql
-- Parcial: sólo las deudas abiertas, que son las que se consultan (y un índice más chico)
CREATE INDEX debts_open_due_idx ON debts (tenant_id, due_date) WHERE status <> 'paid';

-- De cobertura: incluye columnas para responder sin ir a la tabla (index-only scan)
CREATE INDEX debts_tenant_due_cover_idx ON debts (tenant_id, due_date) INCLUDE (balance_cents, customer_id);

-- Por expresión: búsquedas por email sin distinguir mayúsculas
CREATE INDEX customers_email_lower_idx ON customers (lower(email));
SELECT * FROM customers WHERE lower(email) = lower($1);   -- la consulta debe usar la misma expresión
```

| Tipo de índice | Cuándo                                                              |
| -------------- | ------------------------------------------------------------------- |
| Parcial        | Se consulta siempre un subconjunto (abiertas, activas, no borradas) |
| De cobertura   | Consultas muy frecuentes que leen pocas columnas                    |
| Por expresión  | Filtros sobre funciones (`lower`, `date_trunc`, campos de JSONB)    |
| Único parcial  | Reglas de unicidad condicional (lección de modelado)                |

### Otros tipos

| Tipo                      | Para qué                                                                                             |
| ------------------------- | ---------------------------------------------------------------------------------------------------- |
| GIN                       | JSONB (`@>`), arrays, búsqueda de texto completo, trigramas (`pg_trgm`)                              |
| GiST                      | Rangos, geometrías, exclusión de solapamientos                                                       |
| BRIN                      | Tablas enormes con datos correlacionados con el orden físico (eventos por tiempo): índices diminutos |
| Hash                      | Sólo igualdad; rara vez mejor que B-tree                                                             |
| HNSW / IVFFlat (pgvector) | Búsqueda aproximada de vecinos para embeddings                                                       |

## Selectividad, estadísticas y el planificador

PostgreSQL tiene un **planificador basado en costos**: estima cuántas filas devuelve cada paso usando
**estadísticas** de las columnas (que recolecta `ANALYZE`, automáticamente con autovacuum) y elige el plan más barato
**estimado**.

- La **selectividad** es qué fracción de filas cumple un filtro. `status = 'paid'` sobre una tabla donde el 90 % está
  pagado es **poco selectivo**: leer la tabla secuencialmente puede ser más barato que saltar del índice a la tabla
  millones de veces. Por eso, a veces, **el planificador ignora un índice a propósito**.
- Si las estimaciones están muy lejos de la realidad (estadísticas viejas, columnas correlacionadas), el plan puede
  ser malo. Se corre `ANALYZE` y, para correlaciones, se pueden crear estadísticas extendidas (`CREATE STATISTICS`).

## EXPLAIN y EXPLAIN ANALYZE

`EXPLAIN` muestra el plan elegido; `EXPLAIN ANALYZE` **además ejecuta** la consulta y muestra tiempos y filas reales
(cuidado con `UPDATE` y `DELETE`: se ejecutan de verdad, conviene envolverlos en `BEGIN` ... `ROLLBACK`).

```sql
EXPLAIN (ANALYZE, BUFFERS)
SELECT id, balance_cents FROM debts
 WHERE tenant_id = 3 AND status = 'pending' AND due_date < '2026-11-01'
 ORDER BY due_date LIMIT 100;
```

```text
-- Sin el índice adecuado
Limit  (actual time=8412.3..8412.4 rows=100 loops=1)
  ->  Sort  (actual time=8412.3..8412.3 rows=100 loops=1)
        Sort Key: due_date
        ->  Seq Scan on debts  (actual time=0.02..8301.7 rows=412339 loops=1)
              Filter: ((tenant_id = 3) AND (status = 'pending') AND (due_date < '2026-11-01'))
              Rows Removed by Filter: 7587661

-- Con el índice (tenant_id, status, due_date)
Limit  (actual time=0.04..0.31 rows=100 loops=1)
  ->  Index Scan using debts_tenant_status_due_idx on debts  (actual time=0.04..0.30 rows=100 loops=1)
        Index Cond: ((tenant_id = 3) AND (status = 'pending') AND (due_date < '2026-11-01'))
```

| Nodo / señal                                | Qué indica                                                                      |
| ------------------------------------------- | ------------------------------------------------------------------------------- |
| `Seq Scan` en tabla grande                  | Lectura completa; malo si el filtro es selectivo                                |
| `Index Scan`                                | Recorre el índice y va a la tabla por cada fila                                 |
| `Index Only Scan`                           | Responde sólo con el índice (cobertura)                                         |
| `Bitmap Heap Scan`                          | Combina índices y lee las páginas de la tabla en orden                          |
| `Nested Loop` con muchos `loops`            | Un join que repite la búsqueda muchas veces: falta un índice en el lado interno |
| `Rows Removed by Filter` alto               | Se leyeron muchas filas para descartarlas                                       |
| `Sort Method: external merge`               | El sort no entró en memoria (`work_mem`)                                        |
| Filas estimadas muy distintas de las reales | Estadísticas desactualizadas o correlaciones                                    |

En producción, la extensión **`pg_stat_statements`** muestra qué consultas consumen más tiempo total: es el punto de
partida para saber **qué** optimizar.

## El problema N+1

```ts
// ❌ N+1: 1 consulta para las deudas + 1 por cada deuda para su cliente
const debts = await db.query("SELECT * FROM debts WHERE campaign_id = $1", [campaignId]);
for (const debt of debts.rows) {
  debt.customer = (await db.query("SELECT * FROM customers WHERE id = $1", [debt.customer_id])).rows[0];
}

// ✅ Una consulta con join, o dos consultas por lote
const customers = await db.query("SELECT * FROM customers WHERE id = ANY($1)", [
  debts.rows.map((d) => d.customer_id),
]);
```

El N+1 es la causa más común de endpoints lentos en aplicaciones con ORM, porque la carga perezosa de relaciones lo
esconde. Se detecta en las trazas (decenas de spans de consultas idénticas) o en los logs de consultas.

## Comparación con C# y Java

| Tema                   | SQL Server / .NET                  | Java / JPA                                   | PostgreSQL                              |
| ---------------------- | ---------------------------------- | -------------------------------------------- | --------------------------------------- |
| Plan de ejecución      | Execution plan (SSMS)              | Plan de la base subyacente                   | `EXPLAIN (ANALYZE, BUFFERS)`            |
| Índice de cobertura    | `INCLUDE` en SQL Server            | Según la base                                | `INCLUDE`                               |
| Índice filtrado        | Filtered index                     | Según la base                                | Índice parcial (`WHERE`)                |
| Consultas más costosas | Query Store                        | Según la base                                | `pg_stat_statements`                    |
| N+1 en el ORM          | Lazy loading de EF Core; `Include` | `FetchType.LAZY`; `JOIN FETCH`, `@BatchSize` | Joins explícitos, `ANY($1)`, DataLoader |

## Errores frecuentes

- **Indexar columnas sueltas "por si acaso"** en lugar de diseñar a partir de las consultas.
- **Índices compuestos con el orden equivocado.**
- **Filtrar con una función** (`lower(email)`) sin un índice por expresión.
- **Optimizar sin `EXPLAIN ANALYZE`** ni datos de volumen realista.
- **Ignorar las escrituras**: cada índice extra las encarece.
- **Foreign keys sin índice** en el lado hijo.
- **N+1 escondidos en el ORM.**
