## ¿Qué problema resuelve?

Un servicio de cobranzas tenía la regla "una deuda puede tener a lo sumo una promesa de pago vigente". Estaba en el
código: antes de insertar, se consultaba si existía una. Con dos mensajes casi simultáneos del deudor, ambos chequeos
pasaron y quedaron dos promesas vigentes; el agente después mencionaba fechas contradictorias. Una sola línea en el
esquema lo habría hecho imposible:

```sql
CREATE UNIQUE INDEX one_active_promise_per_debt ON payment_promises (debt_id) WHERE status = 'active';
```

El modelado relacional consiste en que **el esquema exprese las reglas del dominio**, para que los estados inválidos
no se puedan guardar, sin importar qué código escriba.

- **1:N** (un cliente tiene muchas deudas): foreign key en el lado "muchos" (`debts.customer_id`).
- **N:M** (campañas y deudas): tabla intermedia (`campaign_targets`) con las dos foreign keys y, a menudo, atributos
  propios de la relación (fecha de inclusión, resultado).
- **1:1** es raro y suele indicar que se puede fusionar o que una parte es opcional y pesada.

## Normalización y desnormalización

**Normalizar** es organizar los datos para que **cada hecho se guarde una sola vez**. Las formas normales formalizan
la idea; en la práctica, la regla es: si un dato se repite en muchas filas, probablemente debería estar en otra
tabla.

```sql
-- ❌ Desnormalizado: el nombre del cliente se repite en cada deuda
CREATE TABLE debts_bad (id bigint, customer_name text, customer_email text, balance_cents bigint);
-- Si el cliente cambia el email, hay que actualizar N filas; si se olvida una, hay datos contradictorios.

-- ✅ Normalizado: el cliente se guarda una vez y las deudas lo referencian
-- (customers y debts de la lección anterior)
```

**Desnormalizar** (duplicar a propósito) es válido con un motivo concreto, normalmente de lectura, y con un
mecanismo que mantenga la copia sincronizada:

| Desnormalización                                                     | Motivo                             | Cómo se mantiene                                          |
| -------------------------------------------------------------------- | ---------------------------------- | --------------------------------------------------------- |
| `debts.balance_cents` (en lugar de calcularlo de los pagos cada vez) | Lectura frecuente y barata         | Se actualiza en la misma transacción que registra el pago |
| Tabla de resumen por campaña                                         | Dashboards sobre millones de filas | Vista materializada o proceso asíncrono                   |
| Copia del nombre del cliente en un evento                            | El evento debe reflejar el momento | Inmutable a propósito: es historia                        |

## Claves primarias

| Opción                                | Ventajas                                       | Desventajas                                       |
| ------------------------------------- | ---------------------------------------------- | ------------------------------------------------- |
| `bigint generated always as identity` | Compacta, rápida, ordenada                     | Revela volumen; se genera en la base              |
| `uuid` (v4 aleatorio)                 | Se genera en cualquier lado; no revela volumen | Más grande; inserciones dispersas en el índice    |
| `uuid` v7 (ordenado por tiempo)       | Se genera en cualquier lado y es ordenado      | Más grande que bigint                             |
| Clave natural (DNI, email)            | Significado de negocio                         | Cambia, se repite entre tenants, es dato personal |

Recomendación habitual: **clave sustituta** como primaria (identity o uuid) y la clave natural como **`UNIQUE`**
(por ejemplo, `UNIQUE (tenant_id, document_number)`).

## Foreign keys

```sql
CREATE TABLE payments (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  debt_id       bigint NOT NULL REFERENCES debts (id) ON DELETE RESTRICT,
  provider_payment_id text NOT NULL,
  amount_cents  bigint NOT NULL CHECK (amount_cents > 0),
  paid_at       timestamptz NOT NULL,
  UNIQUE (provider_payment_id)              -- el mismo pago del proveedor no se registra dos veces
);
```

| `ON DELETE`                            | Efecto al borrar la fila referenciada | Cuándo                                                          |
| -------------------------------------- | ------------------------------------- | --------------------------------------------------------------- |
| `RESTRICT` / `NO ACTION` (por defecto) | Impide el borrado                     | Datos financieros y de auditoría                                |
| `CASCADE`                              | Borra también las filas dependientes  | Datos que no tienen sentido sin el padre (ítems de un borrador) |
| `SET NULL`                             | Deja la referencia en NULL            | Relaciones opcionales                                           |

En dominios financieros, casi nunca se borra: se **marca** (estado, `archived_at`) y las foreign keys con `RESTRICT`
evitan perder historia por accidente. PostgreSQL **no crea índices automáticamente** en las columnas de foreign key:
hay que crearlos, porque los joins y los borrados del padre los necesitan.

## Constraints: hacer imposibles los estados inválidos

```sql
CREATE TABLE payment_promises (
  id            bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  debt_id       bigint NOT NULL REFERENCES debts (id),
  promised_for  date   NOT NULL,
  amount_cents  bigint NOT NULL CHECK (amount_cents > 0),
  status        text   NOT NULL CHECK (status IN ('active', 'kept', 'broken', 'cancelled')),
  created_at    timestamptz NOT NULL DEFAULT now(),
  kept_at       timestamptz,
  -- Regla entre columnas: kept_at existe si y sólo si la promesa se cumplió
  CHECK ((status = 'kept') = (kept_at IS NOT NULL))
);

-- Una sola promesa activa por deuda (índice único parcial)
CREATE UNIQUE INDEX one_active_promise_per_debt ON payment_promises (debt_id) WHERE status = 'active';
```

| Constraint           | Expresa                                                             |
| -------------------- | ------------------------------------------------------------------- |
| `NOT NULL`           | El dato es obligatorio                                              |
| `CHECK`              | Rangos, conjuntos de valores y reglas entre columnas de la fila     |
| `UNIQUE`             | Unicidad (también compuesta: `UNIQUE (tenant_id, email)`)           |
| Índice único parcial | Unicidad condicional ("una activa por deuda")                       |
| `FOREIGN KEY`        | La referencia existe                                                |
| `EXCLUDE`            | Que no haya solapamientos (por ejemplo, rangos de fechas de planes) |

Las constraints son **seguras ante concurrencia**: dos transacciones simultáneas no pueden violarlas, a diferencia de
un "consultar y después insertar" en la aplicación. La aplicación igual valida antes, para devolver buenos mensajes;
la constraint es la red de seguridad.

## JSONB: cuándo sí y cuándo no

`jsonb` guarda JSON en un formato binario que se puede consultar e indexar:

```sql
CREATE TABLE webhook_events (
  id                 bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  provider_event_id  text NOT NULL UNIQUE,
  type               text NOT NULL,
  payload            jsonb NOT NULL,          -- el payload completo del proveedor, tal como llegó
  received_at        timestamptz NOT NULL DEFAULT now()
);

SELECT payload ->> 'debt_reference' AS debt_reference      -- ->> extrae como texto
  FROM webhook_events
 WHERE payload @> '{"status": "succeeded"}';               -- @> "contiene", indexable con GIN

CREATE INDEX webhook_events_payload_idx ON webhook_events USING gin (payload jsonb_path_ops);
```

| Usá JSONB para...                                       | Usá columnas para...                                |
| ------------------------------------------------------- | --------------------------------------------------- |
| Payloads crudos de webhooks y respuestas de proveedores | Datos que se filtran, ordenan o unen con frecuencia |
| Configuración y metadatos variables por tenant          | Datos con reglas (constraints, FKs)                 |
| Atributos dispersos que cambian seguido                 | Montos, estados, fechas y referencias               |

JSONB no tiene esquema: la forma del contenido se valida en la aplicación (por ejemplo con Zod) al escribir y al leer.

## Migraciones

El esquema evoluciona con **migraciones versionadas**: archivos ordenados que se aplican una sola vez por entorno y
se guardan en el repositorio. Herramientas: Drizzle Kit, Prisma Migrate, node-pg-migrate, Flyway, Liquibase.

Durante un despliegue, **conviven la versión vieja y la nueva del código**. Por eso los cambios incompatibles se
hacen en varios pasos (**expand and contract**):

Cuidados en tablas grandes:

- **Crear índices con `CREATE INDEX CONCURRENTLY`**, que no bloquea las escrituras (no puede ir dentro de una
  transacción).
- **Agregar `NOT NULL` o una FK** sobre datos existentes en dos pasos: primero `NOT VALID` y después `VALIDATE
CONSTRAINT`, que valida sin el bloqueo más fuerte.
- **Backfills por lotes**, no un `UPDATE` de diez millones de filas en una transacción.
- **`lock_timeout`** en las migraciones para que no queden esperando un lock y bloqueen todo detrás.

## Comparación con C# y Java

| Concepto           | .NET                                            | Java                                    | Node.js                                      |
| ------------------ | ----------------------------------------------- | --------------------------------------- | -------------------------------------------- |
| Definir el esquema | Entidades EF Core + Fluent API                  | Entidades JPA + anotaciones             | Esquema Drizzle/Prisma o SQL                 |
| Migraciones        | EF Core Migrations                              | Flyway, Liquibase                       | Drizzle Kit, Prisma Migrate, node-pg-migrate |
| Constraints        | `HasCheckConstraint`, índices únicos con filtro | `@Column(unique)`, `@Check` (Hibernate) | Declaradas en el esquema o en SQL            |
| JSON               | Columnas JSON mapeadas a tipos owned            | `@JdbcTypeCode(SqlTypes.JSON)`          | `jsonb` + validación con Zod                 |

## Errores frecuentes

- **Reglas de negocio sólo en la aplicación** ("consulto y después inserto").
- **Foreign keys sin índice.**
- **`ON DELETE CASCADE`** en datos financieros.
- **Todo en JSONB** para "ganar flexibilidad", perdiendo tipos e integridad.
- **Claves naturales como primaria** (DNI, email) que después cambian.
- **Migraciones que bloquean tablas grandes** (índices sin `CONCURRENTLY`, backfills gigantes).
- **Renombrar o borrar columnas en un solo paso** mientras el código viejo sigue corriendo.
