## Qué vas a aprender en este curso

En el stack de una plataforma de agentes, Redis aparece en casi todos los lugares donde la base relacional sería
demasiado lenta o inadecuada: caché de configuración de agentes, rate limiting de mensajes salientes, deduplicación
de webhooks, locks para no procesar dos veces una conversación, colas de trabajo.

## Qué es Redis

**Redis** es un almacén de datos **en memoria** que guarda pares **clave → valor**, donde el valor puede ser una
**estructura de datos**: un string, un hash, una lista, un set, un sorted set o un stream. Sus características
centrales:

- **Latencia muy baja** (operaciones típicas por debajo del milisegundo dentro de la misma red), porque los datos
  están en memoria.
- **Operaciones atómicas sobre estructuras:** incrementar un contador, agregar a un set, tomar el primero de una
  lista; sin leer-modificar-escribir desde la aplicación.
- **Expiración por clave (TTL):** los datos pueden caducar solos.
- **Persistencia opcional:** puede guardar snapshots o un log de escrituras, pero su fortaleza es la memoria.

Después de un cambio de licencia de Redis en 2024, la comunidad creó **Valkey**, un fork open source compatible con
los comandos de Redis que ofrecen varios proveedores de nube. Para lo que cubre este curso, son intercambiables.

## Ejecutarlo en Docker y usar redis-cli

```bash
docker run --name collections-redis -p 6379:6379 -d redis:8

docker exec -it collections-redis redis-cli
```

```bash
127.0.0.1:6379> SET agent:config:42 '{"tone":"cordial"}'
OK
127.0.0.1:6379> GET agent:config:42
"{\"tone\":\"cordial\"}"
127.0.0.1:6379> SET session:abc123 "usr_7" EX 3600      # expira en una hora
OK
127.0.0.1:6379> TTL session:abc123
(integer) 3598
127.0.0.1:6379> INCR sms:sent:tnt_1:2026-11-19           # contador atómico
(integer) 1
127.0.0.1:6379> SET webhook:evt_91 1 NX EX 86400         # sólo si no existe
OK
127.0.0.1:6379> SET webhook:evt_91 1 NX EX 86400
(nil)                                                    # ya existía: duplicado
127.0.0.1:6379> DEL agent:config:42
(integer) 1
```

| Comando                    | Qué hace                                                                                            |
| -------------------------- | --------------------------------------------------------------------------------------------------- |
| `SET clave valor`          | Guarda un valor (con `EX` segundos, `PX` milisegundos, `NX` sólo si no existe, `XX` sólo si existe) |
| `GET clave`                | Lee un valor (`nil` si no existe)                                                                   |
| `DEL clave`                | Borra                                                                                               |
| `EXPIRE clave seg`         | Define un TTL                                                                                       |
| `TTL clave`                | Segundos restantes (`-1` sin expiración, `-2` no existe)                                            |
| `INCR` / `INCRBY`          | Incrementa un entero atómicamente                                                                   |
| `EXISTS clave`             | Si existe                                                                                           |
| `SCAN cursor MATCH patrón` | Recorre claves de a poco (en lugar de `KEYS`)                                                       |

### Convención de nombres

Las claves se nombran con prefijos separados por `:` que expresan una jerarquía: `tenant:42:agent:7:config`,
`ratelimit:sms:tnt_1:2026-11-19T10`. En un sistema multi-tenant, **el tenant forma parte de la clave**: una clave de
caché sin tenant puede devolver datos de otro cliente.

## El modelo de ejecución: comandos atómicos

Redis procesa los comandos que modifican y leen datos **de a uno por vez** (el núcleo de ejecución de comandos es
secuencial, aunque las versiones modernas usan hilos para la I/O de red). Dos consecuencias opuestas:

1. **Atomicidad gratis:** `INCR`, `SET NX` o `HINCRBY` no pueden intercalarse con otro comando a mitad de camino. Un
   contador incrementado por mil clientes a la vez termina en el número correcto.
2. **Un comando lento bloquea a todos:** `KEYS *` sobre millones de claves, un `SMEMBERS` de un set gigante o un script
   Lua largo detienen al resto de los clientes mientras corren. Se usa `SCAN` para recorrer y se evita trabajo O(N)
   sobre colecciones grandes.

Para ejecutar **varios comandos como una unidad atómica** existen `MULTI`/`EXEC` (transacciones) y los **scripts
Lua** (`EVAL`), que se ven en la lección de patrones.

## Usarlo desde Node.js

```ts
import { createClient } from "redis";

const redis = createClient({ url: process.env.REDIS_URL });
redis.on("error", (error) => logger.error({ error }, "redis_error")); // evita que un error sin listener tire el proceso
await redis.connect();

await redis.set(`tenant:${tenantId}:agent:${agentId}:config`, JSON.stringify(config), { EX: 300 });
const cached = await redis.get(`tenant:${tenantId}:agent:${agentId}:config`);
const sentToday = await redis.incr(`sms:sent:${tenantId}:${today}`);
```

- **Una conexión compartida** por proceso suele alcanzar: Redis multiplexa bien y el cliente encola los comandos.
- **Pipelining:** enviar varios comandos sin esperar cada respuesta reduce los viajes de red. Los clientes lo hacen
  automáticamente con comandos concurrentes, o explícitamente con `multi()`/pipelines.
- Los valores son **strings o bytes**: los objetos se serializan (JSON) y se **validan al leer**, como cualquier dato
  externo.
- Clientes habituales: **node-redis** (oficial) e **ioredis**.

## Errores frecuentes

- **Usar Redis como fuente de verdad** de datos de negocio sin persistencia ni respaldo.
- **`KEYS *` en producción.**
- **Claves sin tenant** en sistemas multi-tenant.
- **Datos sin TTL** que crecen hasta agotar la memoria.
- **Leer-modificar-escribir desde la aplicación** en lugar de usar comandos atómicos (`INCR`, `SET NX`).
- **No escuchar el evento `error`** del cliente en Node.js.
- **Una conexión nueva por request.**
