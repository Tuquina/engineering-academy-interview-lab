## ¿Qué problema resuelve?

Usar Redis sólo con `SET` y `GET` de JSON desperdicia su mayor ventaja: **estructuras de datos con operaciones
atómicas**. El ranking de un juego, el conjunto de clientes que ya recibieron hoy una
promoción, una ventana deslizante de requests o una cola de notificaciones tienen una estructura natural en Redis que evita leer, modificar y reescribir desde la
aplicación (y las carreras que eso trae).

### Strings

El tipo básico: texto, números o bytes (hasta 512 MB, aunque conviene mucho menos).

```bash
SET search:flights:EZE-MAD:2026-12-20 '[{"flight":"XY123","price_cents":98000000}]' EX 120
INCRBY views:product:42 25
GETDEL otp:usr_7                  # leer y borrar en un paso
```

### Hashes

Un objeto con campos; permite leer o modificar un campo sin reescribir todo:

```bash
HSET cart:usr_7 prod_42 1 prod_9 2        # carrito: producto → cantidad
HINCRBY cart:usr_7 prod_9 1
HGET cart:usr_7 prod_9
HGETALL cart:usr_7
```

### Lists

Listas enlazadas: inserción y extracción en los extremos en O(1). Sirven como colas simples:

```bash
LPUSH outbound:push '{"to":"...","text":"..."}'    # productor
BRPOP outbound:push 5                              # consumidor: espera hasta 5 s si está vacía
LRANGE recent:viewed:usr_7 0 9                     # últimos 10 productos vistos
LTRIM recent:viewed:usr_7 0 99                     # conservar sólo los 100 más recientes
```

Una lista como cola **no tiene confirmación**: si el consumidor toma un mensaje y se cae, se pierde. Para colas
confiables se usan Streams (o patrones como `LMOVE` a una lista de "en proceso").

### Sets

Colecciones de miembros **únicos**, con pertenencia en O(1):

```bash
SADD promo:sent:2026-11-19 cus_42 cus_77
SISMEMBER promo:sent:2026-11-19 cus_42             # 1: ya recibió la promoción hoy
SCARD promo:sent:2026-11-19                        # cuántos
SINTER promo:91:audience optout:marketing          # intersección: destinatarios que pidieron no recibir promociones
```

### Sorted sets

Miembros únicos con un **score** numérico, siempre ordenados. Son la estructura más versátil:

```bash
ZINCRBY leaderboard:season:7 150 player_7              # sumar puntos de una partida
ZRANGE leaderboard:season:7 0 9 REV WITHSCORES          # top 10
ZADD scheduled:reminders 1795080000 appt_551            # score = timestamp: recordatorio de un turno médico
ZRANGE scheduled:reminders -inf 1795075000 BYSCORE      # los que ya vencieron
ZREMRANGEBYSCORE ratelimit:usr_7 0 1795069940            # quitar entradas fuera de la ventana
```

| Uso                                  | Score                     |
| ------------------------------------ | ------------------------- |
| Rankings                             | Puntaje                   |
| Tareas programadas                   | Timestamp de ejecución    |
| Ventanas deslizantes (rate limiting) | Timestamp de cada request |
| Colas con prioridad                  | Prioridad                 |

### Streams

Un **stream** es un **log append-only** de entradas con ID creciente. Admite **consumer groups**: varios consumidores
se reparten las entradas y cada una debe **confirmarse** (`XACK`); las no confirmadas quedan pendientes y se pueden
reasignar si un consumidor cae.

```bash
XADD events:payments * order_id ord_42 amount 4000000      # * = ID automático
XGROUP CREATE events:payments notifier $ MKSTREAM
XREADGROUP GROUP notifier worker-1 COUNT 10 BLOCK 5000 STREAMS events:payments >
XACK events:payments notifier 1795070000000-0
XPENDING events:payments notifier                             # entregadas y no confirmadas
```

## Complejidad de los comandos

| Operación                                | Complejidad                           |
| ---------------------------------------- | ------------------------------------- |
| `GET`, `SET`, `HGET`, `SADD`, `LPUSH`    | O(1)                                  |
| `ZADD`, `ZRANK`, `ZINCRBY`               | O(log N)                              |
| `ZRANGE` (M elementos)                   | O(log N + M)                          |
| `HGETALL`, `SMEMBERS`, `LRANGE` completo | O(N): cuidado con colecciones grandes |
| `KEYS`                                   | O(N) sobre todas las claves: evitar   |

## Expiración

Cualquier clave puede tener un **TTL**. Al vencer, deja de ser visible.

```bash
SET session:abc "usr_7" EX 3600
EXPIRE contacted:tnt_1:2026-11-19 172800     # el set diario vive dos días
PERSIST session:abc                          # quitar la expiración
```

- El TTL se define **por clave**, no por campo de un hash ni por miembro de un set (para eso se usan claves separadas
  o sorted sets con timestamps). Versiones recientes agregaron comandos de expiración por campo de hash (`HEXPIRE`).
- Las claves vencidas se eliminan de forma **perezosa** (al intentar leerlas) y con un proceso **activo** que muestrea
  claves con TTL periódicamente.
- **Toda clave de caché tiene TTL.** Una caché sin TTL es una fuga de memoria con otro nombre.

## Persistencia

| Modo             | Cómo funciona                                    | Posible pérdida ante una caída                 |
| ---------------- | ------------------------------------------------ | ---------------------------------------------- |
| Sin persistencia | Todo en memoria                                  | Todo                                           |
| **RDB**          | Snapshots periódicos del dataset                 | Lo escrito desde el último snapshot            |
| **AOF**          | Log de cada escritura; se reproduce al reiniciar | Según `appendfsync`: hasta ~1 s con `everysec` |
| RDB + AOF        | Ambos                                            | Como AOF, con reinicios más rápidos            |

Aun con AOF, Redis **no es una base transaccional**: no tiene constraints, relaciones ni transacciones con rollback.
Lo que se guarda en Redis debería poder **reconstruirse** desde la fuente de verdad, salvo que se haya decidido
conscientemente lo contrario (por ejemplo, una cola de Streams con AOF y réplicas).

## Eviction: cuando se llena la memoria

Con `maxmemory` configurado, al llegar al límite Redis aplica la **`maxmemory-policy`**:

| Política                                         | Qué hace                                      | Uso típico                                            |
| ------------------------------------------------ | --------------------------------------------- | ----------------------------------------------------- |
| `noeviction`                                     | Rechaza escrituras con error                  | Colas, locks, datos que no deben perderse en silencio |
| `allkeys-lru`                                    | Elimina las claves menos usadas recientemente | Caché general                                         |
| `allkeys-lfu`                                    | Elimina las menos usadas con frecuencia       | Caché con claves muy populares                        |
| `volatile-lru` / `volatile-lfu` / `volatile-ttl` | Sólo entre claves con TTL                     | Caché y datos persistentes en la misma instancia      |

Una práctica común es **separar instancias**: una para caché (con eviction) y otra para colas, locks y rate limiting
(sin eviction).

## Comparación con C# y Java

| Estructura de Redis | Equivalente en memoria (.NET) | Equivalente en memoria (Java)       |
| ------------------- | ----------------------------- | ----------------------------------- |
| Hash                | `Dictionary<string, string>`  | `Map<String, String>`               |
| List                | `LinkedList<T>`, `Queue<T>`   | `Deque<T>`                          |
| Set                 | `HashSet<T>`                  | `Set<T>`                            |
| Sorted set          | `SortedSet<T>` con score      | `TreeMap` / `ConcurrentSkipListMap` |
| Stream              | Channels / Kafka              | Kafka, Reactive streams             |

La diferencia: en Redis estas estructuras son **compartidas entre procesos y réplicas** y sus operaciones son
atómicas, lo que las hace aptas para coordinación distribuida.

## Errores frecuentes

- **Todo como string JSON**, leyendo y reescribiendo objetos completos.
- **Listas como colas confiables** sin confirmación.
- **Comandos O(N) sobre colecciones gigantes** (`HGETALL`, `SMEMBERS`).
- **Claves de caché sin TTL.**
- **Asumir que la persistencia convierte a Redis en la fuente de verdad.**
- **`allkeys-lru` en una instancia que también guarda locks o colas.**
