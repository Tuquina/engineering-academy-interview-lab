## ¿Qué problema resuelve?

Casi todo backend termina usando Redis para los mismos problemas: aliviar a la base con una caché, limitar cuántos
mensajes se envían, no procesar dos veces el mismo evento, evitar que dos workers trabajen sobre la misma conversación
y comunicar procesos. Cada uno tiene una implementación correcta y varias trampas que aparecen bajo carga. Esta
lección cubre los patrones y, sobre todo, **sus límites**.

## Cache aside

El patrón más común: la aplicación consulta la caché; si no está, va a la fuente y la guarda.

```ts
export async function getAgentConfig(tenantId: string, agentId: string): Promise<AgentConfig> {
  const key = `tenant:${tenantId}:agent:${agentId}:config:v3`; // tenant y versión del formato en la clave
  const cached = await redis.get(key);
  if (cached) return AgentConfigSchema.parse(JSON.parse(cached)); // validar también lo que viene de la caché

  const config = await agentConfigRepository.getPublished(tenantId, agentId); // fuente de verdad
  await redis.set(key, JSON.stringify(config), { EX: 300 + Math.floor(Math.random() * 60) }); // TTL con jitter
  return config;
}

export async function publishAgentConfig(tenantId: string, agentId: string, config: AgentConfig) {
  await agentConfigRepository.publish(tenantId, agentId, config);
  await redis.del(`tenant:${tenantId}:agent:${agentId}:config:v3`); // invalidar después de escribir
}
```

### Invalidación

| Estrategia         | Cómo                                               | Riesgo                                                   |
| ------------------ | -------------------------------------------------- | -------------------------------------------------------- |
| Sólo TTL           | La entrada vence sola                              | Datos viejos hasta el vencimiento                        |
| Borrar al escribir | `DEL` después de actualizar la fuente              | Carrera: un lector lento puede reescribir el valor viejo |
| Eventos            | Un evento de cambio invalida en todas las réplicas | Más infraestructura                                      |
| Versionar la clave | `config:v{versión}` y se lee la versión vigente    | Requiere conocer la versión                              |

Se combina casi siempre **borrar al escribir + TTL** como red de seguridad. Se **borra** en lugar de escribir el
valor nuevo para reducir carreras entre escrituras concurrentes. Y se decide **qué tan viejo puede estar** cada dato:
la configuración de un agente puede tolerar minutos; el saldo de una deuda, nada (no se cachea, o se cachea con
invalidación precisa).

## Cache stampede

Cuando una clave **muy pedida** expira, cientos de requests no la encuentran a la vez y **todas van a la base** con la
misma consulta costosa, justo en el pico de carga. El simulador [Cache stampede](/system-design/simulators/cache-stampede)
lo muestra con números.

Mitigaciones:

1. **Un solo recálculo:** la primera request toma un lock corto (`SET lock:key token NX PX 5000`) y recalcula; las
   demás esperan brevemente y reintentan la lectura, o sirven el valor anterior.
2. **Single-flight en el proceso:** dentro de una réplica, las requests concurrentes por la misma clave comparten la
   misma Promise (no se repite la consulta).
3. **Refresco anticipado:** recalcular antes del vencimiento (por ejemplo, cuando queda el 10 % del TTL), con cierta
   probabilidad que aumenta al acercarse al final.
4. **TTL con jitter:** que no venzan miles de claves en el mismo segundo.
5. **Stale-while-revalidate:** servir el valor viejo mientras uno solo lo refresca, si el dominio lo tolera.

```ts
/** Single-flight: requests concurrentes por la misma clave comparten la misma carga. */
const inFlight = new Map<string, Promise<unknown>>();

export function singleFlight<T>(key: string, load: () => Promise<T>): Promise<T> {
  const existing = inFlight.get(key);
  if (existing) return existing as Promise<T>;
  const promise = load().finally(() => inFlight.delete(key));
  inFlight.set(key, promise);
  return promise;
}
```

## Rate limiting

Con varias réplicas, el contador debe estar en un **almacén compartido**. Redis es la elección habitual porque sus
operaciones son atómicas y rápidas.

```ts
// Ventana fija: máximo `limit` envíos por deudor por hora
export async function allowFixedWindow(key: string, limit: number, windowSeconds: number): Promise<boolean> {
  const windowKey = `${key}:${Math.floor(Date.now() / 1000 / windowSeconds)}`;
  const [count] = await redis.multi().incr(windowKey).expire(windowKey, windowSeconds).exec();
  return Number(count) <= limit;
}
```

La ventana fija permite **hasta el doble del límite** en el borde entre dos ventanas. La **ventana deslizante** con un
sorted set guarda el timestamp de cada request y cuenta sólo las de los últimos N segundos:

```lua
-- KEYS[1] = clave; ARGV = ahora (ms), ventana (ms), límite, id único de la request
redis.call('ZREMRANGEBYSCORE', KEYS[1], 0, ARGV[1] - ARGV[2])
local count = redis.call('ZCARD', KEYS[1])
if count < tonumber(ARGV[3]) then
  redis.call('ZADD', KEYS[1], ARGV[1], ARGV[4])
  redis.call('PEXPIRE', KEYS[1], ARGV[2])
  return 1
end
return 0
```

El script Lua se ejecuta **atómicamente**: nadie se intercala entre contar y agregar. El **token bucket** (fichas que se
recargan a tasa constante hasta una capacidad) se implementa igual, con un hash que guarda las fichas y el último
recargo; permite ráfagas controladas. El simulador [Rate limiting](/system-design/simulators/rate-limiting) compara
los algoritmos.

## Deduplicación e idempotencia

`SET clave valor NX EX ttl` detecta duplicados de forma atómica y muy rápida:

```ts
const firstTime = await redis.set(`webhook:seen:${provider}:${eventId}`, "1", { NX: true, EX: 86_400 });
if (!firstTime) return; // duplicado reciente: ignorar
```

Es útil como **primera barrera** (evita trabajo repetido), pero tiene límites:

- Si el proceso marca el evento como visto y **se cae antes de procesarlo**, el reintento se ignora y el evento se
  pierde. Por eso se marca después de procesar, o se guarda un estado (`processing`, `done`).
- Si Redis pierde datos (reinicio sin persistencia, eviction), la deduplicación se olvida.

La **garantía fuerte** de idempotencia para efectos de negocio (aplicar un pago) está en la **constraint única de la
base** dentro de la misma transacción (curso de PostgreSQL). Redis complementa; no reemplaza.

## Locks distribuidos

Un lock evita que dos procesos hagan la misma tarea a la vez (procesar la misma conversación, correr el mismo job):

```ts
import { randomUUID } from "node:crypto";

const RELEASE_SCRIPT = `
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
end
return 0`;

export async function withLock<T>(
  resource: string,
  ttlMs: number,
  work: () => Promise<T>,
): Promise<T | null> {
  const token = randomUUID();
  const acquired = await redis.set(`lock:${resource}`, token, { NX: true, PX: ttlMs });
  if (!acquired) return null; // otro proceso lo tiene
  try {
    return await work();
  } finally {
    await redis.eval(RELEASE_SCRIPT, { keys: [`lock:${resource}`], arguments: [token] }); // sólo libera el dueño
  }
}
```

- El **TTL** evita que un proceso caído deje el lock tomado para siempre.
- El **token** evita liberar un lock que ya expiró y tomó otro proceso.

<Callout type="danger" title="Un lock con TTL no garantiza exclusión mutua">
  Si el proceso que tiene el lock se pausa más que el TTL (una pausa larga del garbage collector, una red
  lenta, una máquina virtual suspendida), el lock expira, otro proceso lo toma y **los dos creen tenerlo**.
  Para operaciones donde la corrección importa, el recurso protegido debe verificar un **fencing token** (un
  número creciente que rechaza escrituras con tokens viejos) o apoyarse en las **constraints y transacciones
  de la base**. Los locks en Redis son excelentes para **eficiencia** (no hacer trabajo duplicado), no como
  única garantía de **corrección**.
</Callout>

## Errores frecuentes

- **Cachear sin estrategia de invalidación** ni límite de "vejez" aceptable por dato.
- **Claves de caché sin tenant.**
- **TTL idénticos** para muchas claves populares.
- **Rate limiting en memoria** con varias réplicas, o contar y escribir en dos comandos no atómicos.
- **Confiar la idempotencia de un pago sólo a Redis.**
- **Locks sin TTL o sin token** de dueño, o usarlos como única garantía de corrección.
- **Pub/Sub para mensajes que no se pueden perder.**
