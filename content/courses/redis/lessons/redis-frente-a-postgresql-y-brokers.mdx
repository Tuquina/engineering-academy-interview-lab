## ¿Qué problema resuelve?

En una entrevista de diseño, "uso Redis para la caché" no alcanza: el entrevistador pregunta **por qué** y **qué pasa
si se cae**. Y en un equipo real, cada tecnología agregada suma monitoreo, backups, actualizaciones y nuevos modos de
falla. Esta lección da criterios para decidir **dónde vive cada dato y cada mensaje** y para justificarlo.

## Redis frente a PostgreSQL

| Criterio         | PostgreSQL                               | Redis                                              |
| ---------------- | ---------------------------------------- | -------------------------------------------------- |
| Rol natural      | Fuente de verdad                         | Datos efímeros, derivados o de coordinación        |
| Durabilidad      | Fuerte (WAL, réplicas, PITR)             | Opcional (RDB/AOF); puede perder la última ventana |
| Transacciones    | ACID completas con rollback              | `MULTI/EXEC` y Lua: atómicos, sin rollback         |
| Integridad       | Constraints, foreign keys, tipos         | No hay esquema                                     |
| Consultas        | SQL ad hoc, joins, agregaciones, índices | Por clave y por estructura; sin consultas ad hoc   |
| Latencia típica  | Milisegundos                             | Sub-milisegundo                                    |
| Volumen de datos | Limitado por disco                       | Limitado por memoria (más caro por GB)             |

La pregunta clave es: **"si este dato desaparece de Redis ahora, ¿qué pasa?"**

- Una caché: se reconstruye desde la base. ✅ Redis.
- Un contador de rate limit: se reinicia la ventana; durante un rato el límite es más permisivo. ✅ Redis, aceptable.
- Una sesión: el usuario vuelve a iniciar sesión. ✅ Redis, aceptable en la mayoría de los casos.
- Un pago recibido: se pierde dinero. ❌ PostgreSQL.

### Cuando PostgreSQL alcanza

Muchos sistemas agregan Redis antes de necesitarlo. PostgreSQL resuelve bien, a escala moderada:

- **Colas de trabajo** con `FOR UPDATE SKIP LOCKED` (y el outbox, que de todos modos vive en la base).
- **Idempotencia** con constraints únicas (más fuerte que Redis).
- **Caché de resultados** con vistas materializadas o tablas de resumen.
- **Locks** con advisory locks.
- **Búsqueda** de texto completo, trigramas o vectores (pgvector).

Agregar Redis se justifica cuando hay **evidencia**: latencias que la base no alcanza, volumen de lecturas que la
satura, o necesidades propias de Redis (estructuras en memoria, rate limiting de alto volumen).

## Redis frente a un message broker

| Criterio                  | Redis Pub/Sub        | Redis Streams                     | RabbitMQ                       | Kafka                              | SQS (gestionada)        |
| ------------------------- | -------------------- | --------------------------------- | ------------------------------ | ---------------------------------- | ----------------------- |
| Persistencia              | No                   | Sí (memoria + RDB/AOF)            | Sí (disco)                     | Sí (log en disco, replicado)       | Sí                      |
| Confirmación / reintentos | No                   | Consumer groups, XACK, pendientes | Acks, reintentos, dead letters | Offsets por consumer group         | Visibility timeout, DLQ |
| Ruteo                     | Por canal            | Por stream                        | Exchanges, colas, bindings     | Por topic y partición              | Por cola                |
| Retención                 | Ninguna              | Limitada por memoria              | Hasta consumir                 | Configurable (días, indefinida)    | Hasta 14 días           |
| Reprocesar el pasado      | No                   | Limitado                          | No (una vez consumido)         | Sí (rebobinar offsets)             | No                      |
| Orden                     | Por canal            | Por stream                        | Por cola                       | Por partición                      | FIFO opcional           |
| Escala                    | Alta, efímera        | Moderada                          | Media-alta                     | Muy alta                           | Muy alta, sin operar    |
| Operación                 | Ya está si hay Redis | Ya está si hay Redis              | Un cluster más                 | Un cluster complejo (o gestionado) | Ninguna                 |

En un comercio electrónico típico: la **generación de etiquetas de envío** encaja en una cola de trabajo (SQS,
RabbitMQ o BullMQ sobre Redis) con reintentos y límites; los **eventos de dominio** (pedido pagado, envío entregado)
para varios consumidores (notificaciones, analítica, facturación) encajan en un log de eventos o en un bus gestionado;
el **seguimiento en vivo del repartidor** en el mapa encaja en Pub/Sub o WebSockets.

## Cómo defender la decisión

Una respuesta sólida en una entrevista nombra los **criterios** y los **compromisos**:

> "Los pedidos y los pagos viven en PostgreSQL porque necesito transacciones y constraints para la idempotencia.
> Uso Redis para la caché del catálogo y para el rate limiting de los SMS de verificación, porque son datos que puedo
> reconstruir y necesitan latencia baja con varias réplicas. Si Redis se cae, el rate limiting se degrada a un límite
> conservador local y el catálogo se lee de la base. Los eventos de pago se publican con un outbox
> hacia una cola gestionada, porque no se pueden perder y quiero reintentos y dead letters sin operar un cluster."

## Errores frecuentes

- **Datos de negocio sólo en Redis.**
- **Agregar Redis o Kafka "por si acaso"** sin una necesidad medida.
- **Pub/Sub para eventos que no se pueden perder.**
- **Kafka para una cola de trabajos simple** de bajo volumen.
- **No definir la degradación** cuando Redis no está disponible.
- **Justificar con "es más rápido"** sin nombrar garantías, costos ni modos de falla.
