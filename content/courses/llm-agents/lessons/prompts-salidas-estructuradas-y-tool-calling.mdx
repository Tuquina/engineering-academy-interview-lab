## ¿Qué problema resuelve?

Un modelo sin instrucciones responde "como le parece": tono variable, formatos inventados, datos supuestos. Un
sistema de producción necesita lo contrario: **comportamiento especificado**, **salidas que el código pueda leer** y
**acciones controladas**. Para eso hay tres herramientas: el **system prompt**, las **salidas estructuradas** y el
**tool calling**.

## System prompts

El **system prompt** es la especificación del comportamiento del asistente. Una estructura que funciona:

```ts
export const BOOKING_AGENT_PROMPT_V3 = `
Sos el asistente de reservas de {{tenantName}}. Conversás por WhatsApp con huéspedes que tienen una reserva o quieren
hacer una.

## Objetivo
Ayudar a la persona con su reserva: informar fechas y estado, cambiar fechas dentro de la política y registrar
pedidos especiales.

## Contexto
- Muchas personas escriben apuradas o en pleno viaje. Una fecha mal entendida es una noche perdida o una habitación
  vendida dos veces: confirmá siempre fechas y noches antes de cambiar algo.
- Los datos de la reserva los obtenés SIEMPRE con la herramienta get_booking_summary; nunca los supongas.

## Reglas
- Sólo podés ofrecer las habitaciones y tarifas que devuelva la herramienta get_availability.
- Si la persona reporta un problema de seguridad o de salud durante la estadía, usá escalate_to_human.
- Si la persona pide no recibir más mensajes, registralo con register_contact_preference y despedite.
- No compartas datos de la reserva con terceros: verificá identidad con verify_identity antes de dar detalles.

## Formato
Mensajes breves (máximo 3 oraciones), en español rioplatense, sin emojis, sin markdown.
`;
```

Principios que sostienen esta estructura:

- **Explicar el porqué.** "Una fecha mal entendida es una noche perdida" funciona mejor que "SÉ PRECISO". Los modelos
  actuales siguen bien las instrucciones explícitas y razonadas; las mayúsculas y las amenazas suelen producir
  comportamientos exagerados.
- **Ser específico sobre el formato** del canal (WhatsApp no renderiza markdown).
- **Las reglas críticas también se aplican en código.** El prompt dice "sólo ofrecé tarifas de la herramienta"; el
  código, además, valida que cualquier tarifa registrada exista.
- **Ejemplos** (pocos y variados) ayudan en formatos o tonos difíciles de describir.
- **Separar lo estable de lo variable:** el prompt base es estable (y cacheable); los datos del tenant y del huésped
  se inyectan en lugares definidos.
- **Versionar** el prompt como código: `BOOKING_AGENT_PROMPT_V3`, con cambios revisados y evaluados (lección de
  configuración y versionado).

## Salidas estructuradas

Cuando el resultado lo va a leer código, se pide **en un formato con esquema**. Pedir "respondé en JSON" dentro del
prompt no garantiza un JSON válido ni que respete los campos. Las **salidas estructuradas** restringen la generación
al esquema. Con el SDK de Anthropic y Zod:

```ts
import Anthropic from "@anthropic-ai/sdk";
import { zodOutputFormat } from "@anthropic-ai/sdk/helpers/zod";
import { z } from "zod";

const DateChangeSchema = z.object({
  isDateChange: z.boolean(),
  newCheckIn: z.string().nullable(), // fecha ISO o null si no la mencionó
  nights: z.number().int().nullable(),
  confidence: z.enum(["low", "medium", "high"]),
});

const client = new Anthropic();

const response = await client.messages.parse({
  model: "claude-opus-5-5",
  max_tokens: 16000,
  system: `Extraés pedidos de cambio de fecha de mensajes de huéspedes. Hoy es ${today}.`,
  messages: [{ role: "user", content: "¿la podemos pasar al viernes que viene? serían dos noches nomás" }],
  output_config: { format: zodOutputFormat(DateChangeSchema) },
});

const extraction = response.parsed_output; // tipado según el esquema; null si no se pudo parsear
```

<Callout type="warning" title="Estructurado no significa correcto">
  El esquema garantiza la **forma**, no la **verdad**: la fecha puede estar mal calculada o las noches mal
  interpretadas. Después del parseo se aplican reglas de negocio en código: la fecha está dentro del rango
  permitido, hay disponibilidad para esas noches, y con confianza baja se pide confirmación al huésped.
</Callout>

## Tool calling

El **tool calling** (o _function calling_) es el mecanismo por el que el modelo **pide** que se ejecute una acción.
El modelo nunca ejecuta nada: devuelve un bloque con el nombre de la herramienta y los argumentos, y **tu código**
decide qué hacer.

### Definir herramientas

```ts
const tools: Anthropic.Tool[] = [
  {
    name: "get_booking_summary",
    description:
      "Devuelve las fechas, la habitación, la tarifa y el estado de pago de la reserva del huésped de la " +
      "conversación. Usala antes de mencionar cualquier fecha o monto.",
    strict: true, // los argumentos respetan exactamente el esquema
    input_schema: { type: "object", properties: {}, required: [], additionalProperties: false },
  },
  {
    name: "change_booking_dates",
    description:
      "Cambia las fechas de la reserva cuando la persona las confirmó explícitamente. No la uses si la persona " +
      "sólo está consultando o duda.",
    strict: true,
    input_schema: {
      type: "object",
      properties: {
        new_check_in: { type: "string", format: "date", description: "Nueva fecha de entrada (AAAA-MM-DD)" },
        nights: { type: "integer", description: "Cantidad de noches" },
      },
      required: ["new_check_in", "nights"],
      additionalProperties: false,
    },
  },
];
```

La **descripción es parte del prompt**: le dice al modelo cuándo usar la herramienta y cuándo no. Herramientas mal
descriptas producen usos incorrectos.

### El loop

```ts
async function runAgentTurn(
  messages: Anthropic.MessageParam[],
  session: ConversationSession,
): Promise<string> {
  for (let iteration = 0; iteration < MAX_ITERATIONS; iteration++) {
    const response = await client.messages.create({
      model: "claude-opus-5-5",
      max_tokens: 16000,
      system: renderSystemPrompt(session),
      tools,
      messages,
    });

    if (response.stop_reason === "refusal") return FALLBACK_MESSAGE;
    if (response.stop_reason !== "tool_use") return extractText(response); // end_turn: respuesta final

    messages.push({ role: "assistant", content: response.content }); // el pedido del modelo queda en el historial

    const toolResults: Anthropic.ToolResultBlockParam[] = [];
    for (const block of response.content) {
      if (block.type !== "tool_use") continue;
      const result = await executeTool(block.name, block.input, session); // valida, autoriza y ejecuta
      toolResults.push({
        type: "tool_result",
        tool_use_id: block.id,
        content: JSON.stringify(result.ok ? result.value : { error: result.error }),
        is_error: !result.ok,
      });
    }
    messages.push({ role: "user", content: toolResults }); // todos los resultados en un único mensaje
  }
  return escalateBecauseOfLoopLimit(session); // límite de iteraciones: nunca un loop infinito
}
```

Puntos importantes del loop:

- **El contexto de la sesión lo pone tu código**, no el modelo: `get_booking_summary` no recibe un `bookingId`; usa
  el de la conversación autenticada. Así el modelo no puede consultar la reserva de otra persona aunque se lo pidan.
- **Los argumentos son datos externos**: se validan con un esquema (Zod) aunque la herramienta sea `strict`, y se
  aplican reglas de negocio (fecha permitida, cantidad de noches razonable, disponibilidad).
- **Los errores vuelven al modelo** como `tool_result` con `is_error: true` y un mensaje accionable ("no hay
  disponibilidad para esas noches; hay lugar desde el sábado"), para que pueda corregir o explicarle al usuario. No se lanzan excepciones que corten la
  conversación.
- **Si el modelo pide varias herramientas a la vez**, se ejecutan y se devuelven **todos los resultados en un único
  mensaje**.
- **Hay un límite de iteraciones** y, al alcanzarlo, una salida controlada (escalar a un humano).

Los SDK ofrecen helpers que implementan este loop (en el de Anthropic, un _tool runner_), pero conviene entenderlo
porque las decisiones de seguridad viven en `executeTool`.

```ts
const ChangeDatesArgs = z.object({
  new_check_in: z.iso.date(),
  nights: z.number().int().positive().max(30),
});

async function executeTool(name: string, input: unknown, session: ConversationSession): Promise<ToolResult> {
  switch (name) {
    case "get_booking_summary":
      return ok(await bookings.getSummary(session.tenantId, session.bookingId));
    case "change_booking_dates": {
      const args = ChangeDatesArgs.safeParse(input);
      if (!args.success) return err("Argumentos inválidos: revisá la fecha (AAAA-MM-DD) y las noches.");
      return changeBookingDates.execute({
        ...args.data,
        bookingId: session.bookingId,
        actor: session.agentActor,
      });
    }
    default:
      return err(`Herramienta desconocida: ${name}`);
  }
}
```

## Errores frecuentes

- **Prompts gigantes con reglas contradictorias**, sin estructura ni versión.
- **Pedir JSON en el prompt** y parsearlo con la esperanza de que sea válido.
- **Herramientas que reciben IDs del modelo** para datos sensibles en lugar de tomarlos de la sesión.
- **Ejecutar los argumentos del modelo sin validar** ni autorizar.
- **Lanzar excepciones ante errores de herramientas** en lugar de devolverlos como resultado.
- **Loops sin límite de iteraciones.**
- **Muchas herramientas parecidas** que confunden al modelo; mejor pocas, con nombres y descripciones claras.
