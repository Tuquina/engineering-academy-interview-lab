## ¿Qué problema resuelve?

Un modelo sin instrucciones responde "como le parece": tono variable, formatos inventados, datos supuestos. Un
sistema de producción necesita lo contrario: **comportamiento especificado**, **salidas que el código pueda leer** y
**acciones controladas**. Para eso hay tres herramientas: el **system prompt**, las **salidas estructuradas** y el
**tool calling**.

## System prompts

El **system prompt** es la especificación del comportamiento del asistente. Una estructura que funciona:

```ts
export const COLLECTIONS_AGENT_PROMPT_V3 = `
Sos el asistente de cobranzas de {{tenantName}}. Conversás por WhatsApp con personas que tienen una deuda vencida.

## Objetivo
Ayudar a la persona a regularizar su deuda: informar el saldo, ofrecer opciones de pago y registrar compromisos.

## Contexto
- Muchas personas atraviesan dificultades económicas. Un trato respetuoso aumenta la probabilidad de acuerdo y es
  una obligación legal.
- Los datos de la deuda los obtenés SIEMPRE con la herramienta get_debt_summary; nunca los supongas.

## Reglas
- Sólo podés ofrecer planes que devuelva la herramienta get_payment_options.
- Si la persona menciona una situación de vulnerabilidad (salud, duelo, violencia), usá escalate_to_human.
- Si la persona pide no ser contactada, registralo con register_contact_preference y despedite.
- No compartas información de la deuda con terceros: verificá identidad con verify_identity antes de dar detalles.

## Formato
Mensajes breves (máximo 3 oraciones), en español rioplatense, sin emojis, sin markdown.
`;
```

Principios que sostienen esta estructura:

- **Explicar el porqué.** "Un trato respetuoso aumenta la probabilidad de acuerdo y es una obligación legal" funciona
  mejor que "SÉ AMABLE". Los modelos actuales siguen bien las instrucciones explícitas y razonadas; las mayúsculas y
  las amenazas suelen producir comportamientos exagerados.
- **Ser específico sobre el formato** del canal (WhatsApp no renderiza markdown).
- **Las reglas críticas también se aplican en código.** El prompt dice "sólo ofrecé planes de la herramienta"; el
  código, además, valida que cualquier plan registrado exista.
- **Ejemplos** (pocos y variados) ayudan en formatos o tonos difíciles de describir.
- **Separar lo estable de lo variable:** el prompt base es estable (y cacheable); los datos del tenant y del deudor
  se inyectan en lugares definidos.
- **Versionar** el prompt como código: `COLLECTIONS_AGENT_PROMPT_V3`, con cambios revisados y evaluados (lección de
  configuración y versionado).

## Salidas estructuradas

Cuando el resultado lo va a leer código, se pide **en un formato con esquema**. Pedir "respondé en JSON" dentro del
prompt no garantiza un JSON válido ni que respete los campos. Las **salidas estructuradas** restringen la generación
al esquema. Con el SDK de Anthropic y Zod:

```ts
import Anthropic from "@anthropic-ai/sdk";
import { zodOutputFormat } from "@anthropic-ai/sdk/helpers/zod";
import { z } from "zod";

const PromiseExtractionSchema = z.object({
  isPaymentPromise: z.boolean(),
  promisedDate: z.string().nullable(), // fecha ISO o null si no la mencionó
  amount: z.number().nullable(),
  confidence: z.enum(["low", "medium", "high"]),
});

const client = new Anthropic();

const response = await client.messages.parse({
  model: "claude-opus-5-5",
  max_tokens: 16000,
  system: `Extraés compromisos de pago de mensajes de deudores. Hoy es ${today}.`,
  messages: [{ role: "user", content: "el viernes que viene te deposito la mitad, unos 40 mil" }],
  output_config: { format: zodOutputFormat(PromiseExtractionSchema) },
});

const extraction = response.parsed_output; // tipado según el esquema; null si no se pudo parsear
```

<Callout type="warning" title="Estructurado no significa correcto">
  El esquema garantiza la **forma**, no la **verdad**: la fecha puede estar mal calculada o el monto mal
  interpretado. Después del parseo se aplican reglas de negocio en código: la fecha está dentro del rango
  permitido, el monto no supera el saldo, y con confianza baja se pide confirmación al deudor.
</Callout>

## Tool calling

El **tool calling** (o _function calling_) es el mecanismo por el que el modelo **pide** que se ejecute una acción.
El modelo nunca ejecuta nada: devuelve un bloque con el nombre de la herramienta y los argumentos, y **tu código**
decide qué hacer.

### Definir herramientas

```ts
const tools: Anthropic.Tool[] = [
  {
    name: "get_debt_summary",
    description:
      "Devuelve el saldo actual, la cantidad de cuotas vencidas y la promesa de pago vigente del deudor de la " +
      "conversación. Usala antes de mencionar cualquier monto o fecha.",
    strict: true, // los argumentos respetan exactamente el esquema
    input_schema: { type: "object", properties: {}, required: [], additionalProperties: false },
  },
  {
    name: "register_payment_promise",
    description:
      "Registra un compromiso de pago confirmado explícitamente por la persona. No la uses si la persona sólo " +
      "está consultando o duda.",
    strict: true,
    input_schema: {
      type: "object",
      properties: {
        promised_date: { type: "string", format: "date", description: "Fecha comprometida (AAAA-MM-DD)" },
        amount_cents: { type: "integer", description: "Monto comprometido en centavos" },
      },
      required: ["promised_date", "amount_cents"],
      additionalProperties: false,
    },
  },
];
```

La **descripción es parte del prompt**: le dice al modelo cuándo usar la herramienta y cuándo no. Herramientas mal
descriptas producen usos incorrectos.

### El loop

```ts
async function runAgentTurn(
  messages: Anthropic.MessageParam[],
  session: ConversationSession,
): Promise<string> {
  for (let iteration = 0; iteration < MAX_ITERATIONS; iteration++) {
    const response = await client.messages.create({
      model: "claude-opus-5-5",
      max_tokens: 16000,
      system: renderSystemPrompt(session),
      tools,
      messages,
    });

    if (response.stop_reason === "refusal") return FALLBACK_MESSAGE;
    if (response.stop_reason !== "tool_use") return extractText(response); // end_turn: respuesta final

    messages.push({ role: "assistant", content: response.content }); // el pedido del modelo queda en el historial

    const toolResults: Anthropic.ToolResultBlockParam[] = [];
    for (const block of response.content) {
      if (block.type !== "tool_use") continue;
      const result = await executeTool(block.name, block.input, session); // valida, autoriza y ejecuta
      toolResults.push({
        type: "tool_result",
        tool_use_id: block.id,
        content: JSON.stringify(result.ok ? result.value : { error: result.error }),
        is_error: !result.ok,
      });
    }
    messages.push({ role: "user", content: toolResults }); // todos los resultados en un único mensaje
  }
  return escalateBecauseOfLoopLimit(session); // límite de iteraciones: nunca un loop infinito
}
```

Puntos importantes del loop:

- **El contexto de la sesión lo pone tu código**, no el modelo: `get_debt_summary` no recibe un `debtId`; usa el de
  la conversación autenticada. Así el modelo no puede consultar la deuda de otra persona aunque se lo pidan.
- **Los argumentos son datos externos**: se validan con un esquema (Zod) aunque la herramienta sea `strict`, y se
  aplican reglas de negocio (fecha permitida, monto razonable).
- **Los errores vuelven al modelo** como `tool_result` con `is_error: true` y un mensaje accionable ("la fecha supera
  el máximo de 30 días"), para que pueda corregir o explicarle al usuario. No se lanzan excepciones que corten la
  conversación.
- **Si el modelo pide varias herramientas a la vez**, se ejecutan y se devuelven **todos los resultados en un único
  mensaje**.
- **Hay un límite de iteraciones** y, al alcanzarlo, una salida controlada (escalar a un humano).

Los SDK ofrecen helpers que implementan este loop (en el de Anthropic, un _tool runner_), pero conviene entenderlo
porque las decisiones de seguridad viven en `executeTool`.

```ts
const RegisterPromiseArgs = z.object({
  promised_date: z.iso.date(),
  amount_cents: z.number().int().positive(),
});

async function executeTool(name: string, input: unknown, session: ConversationSession): Promise<ToolResult> {
  switch (name) {
    case "get_debt_summary":
      return ok(await debts.getSummary(session.tenantId, session.debtId));
    case "register_payment_promise": {
      const args = RegisterPromiseArgs.safeParse(input);
      if (!args.success) return err("Argumentos inválidos: revisá la fecha (AAAA-MM-DD) y el monto.");
      return registerPaymentPromise.execute({
        ...args.data,
        debtId: session.debtId,
        actor: session.agentActor,
      });
    }
    default:
      return err(`Herramienta desconocida: ${name}`);
  }
}
```

## Errores frecuentes

- **Prompts gigantes con reglas contradictorias**, sin estructura ni versión.
- **Pedir JSON en el prompt** y parsearlo con la esperanza de que sea válido.
- **Herramientas que reciben IDs del modelo** para datos sensibles en lugar de tomarlos de la sesión.
- **Ejecutar los argumentos del modelo sin validar** ni autorizar.
- **Lanzar excepciones ante errores de herramientas** en lugar de devolverlos como resultado.
- **Loops sin límite de iteraciones.**
- **Muchas herramientas parecidas** que confunden al modelo; mejor pocas, con nombres y descripciones claras.
