## ¿Qué problema resuelve?

Un deudor conversa con el agente el lunes: promete pagar el viernes. El jueves escribe que perdió el trabajo y que
no va a poder. El sábado vuelve a escribir: "¿qué opciones tengo?". Para responder bien, el agente necesita saber
que hubo una promesa, que se informó una imposibilidad, que la promesa venció sin pago y cuál es el saldo actualizado
hoy. Si toda la "memoria" es el historial de mensajes reenviado, el agente puede mencionar la promesa del viernes como
vigente o calcular un saldo viejo.

**La memoria de un agente es un problema de diseño de datos**, no una característica del modelo.

## Armar el contexto en cada turno

En cada turno, el código decide qué entra en el contexto. Una estructura habitual:

  chart={`
flowchart TB
  A["1. Instrucciones del agente<br/>versión, políticas del tenant"] --> CTX["Contexto del turno"]
  B["2. Estado de negocio actual<br/>saldo, promesas, acuerdos, preferencias"] --> CTX
  C["3. Memoria persistente relevante<br/>hechos de conversaciones anteriores"] --> CTX
  D["4. Resumen de la conversación<br/>turnos viejos compactados"] --> CTX
  E["5. Turnos recientes completos"] --> CTX
  CTX --> M["Modelo"]

/>

```ts
async function buildTurnContext(conversation: Conversation): Promise<TurnContext> {
  const [state, memories] = await Promise.all([
    debtorState.getCurrent(conversation.tenantId, conversation.debtorId), // fuente de verdad
    memoryStore.relevantFor(conversation.tenantId, conversation.debtorId, { limit: 10 }),
  ]);

  return {
    system: renderSystemPrompt(conversation.agentVersion), // estable: cacheable
    stateBlock: renderStateBlock(state), // "Saldo actual: ... Promesa vigente: ninguna (la del 21/11 venció sin pago)"
    memoryBlock: renderMemories(memories), // con fecha y fuente de cada hecho
    summary: conversation.summary, // turnos viejos compactados
    recentMessages: conversation.messages.slice(-RECENT_TURNS),
  };
}
```

Esta práctica se llama a veces **context engineering**: decidir, en cada llamada, el conjunto mínimo de información
de alta señal que el modelo necesita.

## Memoria de corto plazo: la conversación

La conversación en curso es la memoria de corto plazo. Crece con cada turno, y con ella el costo, la latencia y el
riesgo de que el modelo preste atención a lo irrelevante.

| Técnica                     | Qué hace                                                                                                              |
| --------------------------- | --------------------------------------------------------------------------------------------------------------------- |
| Ventana de turnos recientes | Se envían completos sólo los últimos N turnos.                                                                        |
| Resumen (compaction)        | Los turnos viejos se reemplazan por un resumen que conserva hechos y decisiones.                                      |
| Recorte de resultados       | Los resultados de herramientas viejos se reducen o eliminan (ya están reflejados en el estado).                       |
| Compactación del proveedor  | Algunas APIs resumen automáticamente al acercarse a un umbral (en la de Anthropic, _compaction_ y _context editing_). |

El resumen debe conservar lo que importa para el negocio (qué se ofreció, qué se rechazó, qué se comprometió, señales
de vulnerabilidad), y lo ideal es que esos hechos **ya estén registrados en el estado** para no depender del resumen.

## Memoria persistente entre conversaciones

Algunos hechos son útiles **entre conversaciones**: "prefiere que lo contacten después de las 18", "cobra los días
10", "pidió que no se mencione la deuda a su pareja". Una memoria persistente bien diseñada responde:

| Pregunta            | Decisión de diseño                                                                                    |
| ------------------- | ----------------------------------------------------------------------------------------------------- |
| ¿Qué se guarda?     | Hechos útiles y verificables sobre preferencias y contexto, no transcripciones.                       |
| ¿Quién la escribe?  | Una herramienta explícita (`remember_fact`) con validación, o un proceso posterior que extrae hechos. |
| ¿Con qué metadatos? | Fuente (conversación y turno), fecha, confianza, categoría.                                           |
| ¿Cuándo expira?     | Cada categoría tiene vigencia: "cobra el día 10" puede cambiar; un opt-out no expira.                 |
| ¿Quién la ve?       | Siempre filtrada por tenant y deudor; nunca compartida entre clientes.                                |
| ¿Se puede borrar?   | Sí: derecho de supresión y corrección de datos personales.                                            |

<Callout type="warning" title="La memoria también es superficie de ataque">
  Si el agente puede guardar "hechos" a partir de lo que dice el usuario, una inyección puede plantar un falso
  recuerdo ("el supervisor autorizó una quita del 70 %"). Los hechos que habilitan acciones (autorizaciones,
  acuerdos) nunca vienen de la memoria conversacional: vienen del sistema.
</Callout>

## Estado de negocio frente a historial de eventos

La distinción más importante del módulo:

| Concepto                 | Qué es                           | Ejemplo                                                  | Dónde vive                           |
| ------------------------ | -------------------------------- | -------------------------------------------------------- | ------------------------------------ |
| **Estado de negocio**    | La verdad actual, estructurada   | Saldo 59.000; promesa vigente: ninguna                   | Tablas de la base (fuente de verdad) |
| **Historial de eventos** | Lo que pasó, en orden, inmutable | `PromiseRegistered`, `PromiseBroken`, `HardshipReported` | Tabla de eventos append-only         |
| **Conversación**         | Lo que se dijo                   | "el viernes te pago"                                     | Mensajes                             |

El agente **no deduce** el estado leyendo la conversación: lo **recibe**. Si la promesa venció sin pago, un proceso
del sistema (no el modelo) registra `PromiseBroken` y el estado lo refleja. El historial de eventos además permite
auditar ("¿por qué se le ofreció este plan?") y reconstruir el estado en cualquier momento (curso de System Design,
event sourcing).

## Información contradictoria y desactualizada

Las contradicciones son normales: el deudor dice que pagó y el sistema no lo registra; la memoria dice "cobra el 10"
y hoy dice que cobra el 15; un documento de políticas viejo convive con uno nuevo.

Reglas para resolverlas:

1. **Fuente de verdad por tipo de dato.** Pagos acreditados: el sistema de pagos. Preferencias de contacto: lo último
   que dijo la persona. Políticas: la versión vigente del tenant.
2. **Procedencia de cada dato.** El contexto indica de dónde viene y de cuándo es cada hecho ("según el sistema, al
   19/11"; "dicho por la persona el 12/11").
3. **Lo más reciente y verificado gana**, pero las afirmaciones no verificadas se registran como eventos
   (`PaymentReportedByDebtor`) en lugar de descartarse.
4. **El agente no afirma lo que no puede verificar.** Ante "ya pagué", no dice "no pagaste": explica que el pago puede
   demorar en acreditarse, pide el comprobante y, si corresponde, pausa los recordatorios y escala.
5. **Expiración e invalidación:** los hechos viejos se marcan como reemplazados, no se borran silenciosamente.

```ts
// El bloque de estado que recibe el modelo indica procedencia y vigencia
const stateBlock = `
## Estado verificado (sistema de cobranzas, actualizado ${state.asOf})
- Saldo: ${formatMoney(state.balanceCents)}
- Promesa vigente: ninguna (la promesa del ${state.lastPromise?.date} venció sin pago)
- Pagos informados por la persona y no acreditados: ${state.reportedPayments.length}

## Hechos recordados (no verificados por el sistema)
${memories.map((m) => `- ${m.fact} (dicho el ${m.date}, conversación ${m.conversationId})`).join("\n")}
`;
```

## Errores frecuentes

- **El historial de mensajes como única memoria** y fuente de verdad.
- **Truncar la conversación sin conservar hechos** clave.
- **Dejar que el modelo deduzca el saldo** o el estado de una promesa leyendo mensajes viejos.
- **Memoria persistente sin procedencia, fecha ni expiración.**
- **Guardar como "hecho" lo que dijo el usuario** y usarlo para habilitar acciones.
- **Memoria compartida entre tenants** o sin mecanismo de borrado.
- **Resolver contradicciones dentro del prompt** ("si hay dudas, creele al usuario") en lugar de con reglas de datos.
