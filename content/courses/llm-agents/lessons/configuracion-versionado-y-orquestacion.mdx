## ¿Qué problema resuelve?

Un agente en una demo es un prompt y un loop. Una **plataforma** de agentes de atención para decenas de empresas
(aerolíneas, tiendas, clínicas) necesita responder preguntas que la demo no tiene:

- ¿Qué prompt, modelo y herramientas usó **esta** conversación del martes, que terminó en una queja?
- ¿Cómo cambia el tono para una aerolínea de bandera sin afectar a una low cost?
- ¿Cómo se publica un prompt nuevo sin romper lo que funciona?
- ¿Qué pasa cuando el proveedor del modelo está lento o caído?
- ¿Cómo se garantiza que el agente nunca dé detalles de una reserva antes de verificar la identidad?

## La configuración del agente como dato versionado

```ts
export const AgentConfigSchema = z.object({
  agentId: z.string(),
  version: z.number().int().positive(),
  tenantId: z.string(),
  model: z.object({ primary: z.string(), fallback: z.string().optional() }),
  promptTemplateId: z.string(), // referencia a una plantilla versionada
  promptVariables: z.record(z.string(), z.string()), // tono, nombre comercial, horario de atención
  allowedTools: z.array(z.enum(TOOL_NAMES)),
  policies: z.object({
    maxFeeWaiverPercent: z.number().min(0).max(100), // bonificación máxima del cargo por cambio
    maxRebookingDays: z.number().int().min(1).max(365),
    contactHours: z.object({ from: z.string(), to: z.string(), timezone: z.string() }),
  }),
  limits: z.object({
    maxIterationsPerTurn: z.number().int().max(10),
    maxTurnsPerConversation: z.number().int(),
  }),
  status: z.enum(["draft", "candidate", "published", "retired"]),
  createdBy: z.string(),
  createdAt: z.string(),
});
```

Principios:

1. **Versiones inmutables.** Editar es crear la versión `n + 1`; la versión `n` no cambia nunca.
2. **Cada conversación registra la versión** con la que corrió (`agentId` + `version`). Sin eso no hay auditoría ni
   forma de reproducir un problema.
3. **Ciclo de publicación:** `draft` → `candidate` (corre la suite de evals) → `published` (sólo si pasa el quality
   gate) → `retired`. Es el equivalente a un pipeline de CI/CD, pero para comportamiento.
4. **Despliegue gradual:** la versión nueva atiende un porcentaje de conversaciones (canary) y se compara con la
   anterior antes de pasar al 100 %.
5. **Rollback** es apuntar el agente a la versión publicada anterior.

## Prompts y políticas por cliente

Cada tenant quiere su tono, su nombre comercial, sus planes de pago y sus restricciones legales. Copiar el agente por
tenant multiplica el mantenimiento; la alternativa es **una plantilla base versionada con variables validadas**:

- La plantilla define estructura, reglas generales y el lugar de cada variable.
- Las variables del tenant (nombre comercial, tono, horario) se **validan** con un esquema: longitud máxima, sin
  instrucciones (una variable "tono" que contenga "ignorá las reglas anteriores" es una inyección del lado del
  operador).
- Las **políticas numéricas** (descuento máximo, plazos) no van sólo en el prompt: se aplican en el código de las
  herramientas.

## Herramientas permitidas y seguridad

El riesgo que OWASP llama **agencia excesiva** aparece cuando un agente tiene más capacidad de la que necesita.

| Control                         | Ejemplo                                                                                             |
| ------------------------------- | --------------------------------------------------------------------------------------------------- |
| Lista permitida por agente      | El agente de recordatorios de check-in no tiene `waive_change_fee`.                                 |
| Lista permitida por etapa       | Antes de verificar identidad, sólo `verify_identity` y `escalate_to_human`.                         |
| Contexto inyectado              | `tenantId`, `passengerId` y `conversationId` salen de la sesión, nunca de los argumentos.           |
| Validación y límites de negocio | Bonificación ≤ `policies.maxFeeWaiverPercent`; nueva fecha ≤ hoy + `maxRebookingDays`.              |
| Idempotencia                    | `confirm_change` usa una clave por conversación y turno: un reintento no cambia el vuelo dos veces. |
| Rate limits por herramienta     | Máximo de mensajes salientes por pasajero por día.                                                  |
| Confirmación humana             | Reembolsos mayores a un umbral pasan a revisión (lección de guardrails).                            |

## Model routing

No todas las tareas necesitan el mismo modelo. Un **router** elige según el tipo de tarea, el tenant o el riesgo:

```ts
function selectModel(task: AgentTask, config: AgentConfig): string {
  switch (task.kind) {
    case "classify_inbound_message":
    case "summarize_for_operator":
      return MODELS.fast; // alto volumen, tarea acotada
    case "negotiate":
      return config.model.primary; // conversación con reglas y decisiones
    case "review_settlement_offer":
      return MODELS.mostCapable; // alto impacto, bajo volumen
  }
}
```

El routing se decide **con evaluaciones**: se mide calidad y costo por tarea para cada modelo candidato. Un router
mal calibrado ahorra en la factura y pierde en recupero.

## Timeouts, reintentos y fallbacks

Un proveedor de modelos es una dependencia remota: puede ser lento, devolver `429` (límite de tasa), `529`/`5xx`
(sobrecarga) o cortar la conexión.

- Los SDK oficiales ya reintentan errores transitorios con backoff (configurable); no conviene duplicar reintentos en
  varias capas, porque se multiplican.
- El **fallback a otro modelo** debe estar **evaluado**: un prompt optimizado para un modelo puede comportarse
  distinto en otro.
- Algunos proveedores ofrecen mecanismos propios: por ejemplo, la API de Anthropic tiene un parámetro para reintentar
  automáticamente con otro modelo cuando el principal rechaza una solicitud por políticas de seguridad.
- En flujos asíncronos (avisos masivos de reprogramación de vuelos), la mejor degradación suele ser **reencolar** el trabajo con backoff en lugar de
  responder algo de menor calidad.
- Un **circuit breaker** evita seguir llamando a un proveedor que está fallando (curso de System Design).

## Orquestación con máquinas de estado

Un agente con un único prompt y todas las herramientas disponibles depende de que el modelo **elija bien** el orden
de las cosas. En una aerolínea, algunos órdenes son obligatorios: verificar la identidad antes de dar detalles de la
reserva, informar las opciones antes de cambiar, confirmar antes de emitir. Una **máquina de estados** hace explícitas esas etapas:

<MermaidDiagram
  caption="Cada estado define las instrucciones, las herramientas disponibles y las transiciones permitidas."
  chart={`
stateDiagram-v2
  [*] --> greeting
  greeting --> identity_check
  identity_check --> informing: identidad verificada
  identity_check --> handoff: falla 3 veces
  informing --> negotiating: quiere cambiar el vuelo o pide opciones
  informing --> closing: sólo quería información
  negotiating --> confirming: cambio propuesto
  confirming --> closing: cambio emitido
  negotiating --> handoff: caso especial o pedido de humano
  closing --> [*]
  handoff --> [*]
`}
/>

```ts
const STAGES = {
  identity_check: {
    instructions:
      "Verificá la identidad pidiendo los datos que indique verify_identity. No des información de la reserva.",
    tools: ["verify_identity", "escalate_to_human"],
  },
  negotiating: {
    instructions:
      "Ofrecé sólo las opciones de get_change_options. Si la persona elige una, pasá a confirmar.",
    tools: ["get_booking_summary", "get_change_options", "propose_change", "escalate_to_human"],
  },
  // ...
} as const satisfies Record<ConversationStage, StageDefinition>;
```

En cada turno, el orquestador (código determinista) arma el contexto con las **instrucciones y herramientas del
estado actual**, y las transiciones ocurren por **resultados de herramientas** (por ejemplo, `verify_identity`
exitoso), no porque el modelo "diga" que avanzó. Ventajas: el modelo no puede saltear etapas, cada estado se evalúa por
separado, la conversación se puede **reanudar** días después desde el estado guardado y los logs muestran en qué
etapa se trabó cada conversación.

## Errores frecuentes

- **Configuración editable en el lugar**, sin versiones ni registro de cuál usó cada conversación.
- **Publicar prompts sin evaluarlos.**
- **Un agente por tenant copiado y modificado a mano.**
- **Todas las herramientas disponibles todo el tiempo.**
- **Reintentos en varias capas** que multiplican la carga sobre un proveedor caído.
- **Fallback a un modelo nunca evaluado** con ese prompt.
- **Un loop sin estructura** para procesos con etapas obligatorias.
