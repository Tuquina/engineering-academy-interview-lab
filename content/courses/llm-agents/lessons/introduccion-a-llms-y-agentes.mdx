## Qué vas a aprender en este curso

Este curso apunta a construir productos donde **agentes de IA** conversan con personas reales y actúan sobre sistemas
de negocio: un asistente de soporte que consulta pedidos y programa devoluciones, uno de reservas que busca
disponibilidad, uno de turnos médicos que agenda y deriva a un profesional, uno de finanzas personales que explica
movimientos. Está pensado para ingenieros que nunca integraron
un LLM y quieren entenderlo con la misma rigurosidad que cualquier otra dependencia de un sistema.

| Evaluaciones          | Saber si un cambio mejora o empeora un agente no determinista.                                                                                               |

## Qué es un LLM, en términos de ingeniería

Un **LLM** (_large language model_) es una función entrenada con enormes cantidades de texto que, dado un texto de
entrada, **genera el texto que probablemente sigue**, de a un fragmento (token) por vez. Todo lo demás (responder
preguntas, resumir, clasificar, escribir código, decidir qué herramienta usar) emerge de esa capacidad.

Para un ingeniero, lo útil es tratarlo como una dependencia con propiedades conocidas:

| Propiedad                       | Consecuencia de diseño                                                            |
| ------------------------------- | --------------------------------------------------------------------------------- |
| Entrada y salida son texto      | Todo lo que necesita saber tiene que estar en el contexto que le enviás.          |
| La salida es probabilística     | La misma entrada puede producir respuestas distintas: se evalúa estadísticamente. |
| Puede equivocarse con confianza | Alucinaciones: las salidas se validan como datos externos.                        |
| No tiene memoria entre llamadas | El historial y el estado los gestiona tu sistema.                                 |
| No actúa por sí mismo           | Sólo propone acciones (tool calls); tu código decide si ejecutarlas.              |
| Cuesta y tarda por token        | Contexto y salidas largas impactan en costo y latencia.                           |

<Callout type="warning" title="El modelo no es la fuente de verdad">
  Si un agente "dice" que el saldo de un cliente es $15.000, ese número sólo es confiable si vino de una
  herramienta que lo leyó del sistema. El modelo redacta; los datos de negocio vienen de tu backend.
</Callout>

- **Llamada simple:** clasificar la intención de un mensaje entrante, extraer la fecha y la cantidad de huéspedes de un
  pedido de reserva.
- **Workflow:** el código orquesta pasos fijos (clasificar el mensaje, si es un pedido de reserva extraer las fechas,
  consultar disponibilidad, redactar la confirmación). Previsible y fácil de evaluar por partes.
- **Agente:** el modelo recibe un objetivo ("resolver la consulta de este cliente sobre su pedido") y herramientas
  (`getOrder`, `scheduleReturn`, `escalateToHuman`), y decide en un loop qué hacer.

La recomendación de la industria es **empezar por lo más simple que funcione**. Un agente se justifica cuando los
pasos no se pueden especificar de antemano y el valor compensa el costo y el riesgo. En soporte al cliente, una
conversación abierta sobre un pedido con problemas suele justificarlo; extraer una fecha de un mensaje, no.

## Llamar a un modelo desde código

Las APIs de los proveedores siguen un modelo de **mensajes**: se envía una lista de turnos con roles (`user`,
`assistant`) y un **system prompt** con las instrucciones generales, y se recibe el siguiente turno del asistente.
Con el SDK oficial de Anthropic en TypeScript:

```ts
import Anthropic from "@anthropic-ai/sdk";

const client = new Anthropic(); // lee las credenciales del entorno (ANTHROPIC_API_KEY)

const response = await client.messages.create({
  model: "claude-opus-5-5",
  max_tokens: 16000,
  system:
    "Sos un asistente de atención al cliente de una tienda online. Respondés en español, con tono cordial y breve.",
  messages: [{ role: "user", content: "Hola, ¿dónde está mi pedido?" }],
});

for (const block of response.content) {
  if (block.type === "text") console.log(block.text);
}
console.log(response.stop_reason); // "end_turn", "max_tokens", "tool_use", "refusal"...
console.log(response.usage); // tokens de entrada y salida: la base del costo
```

Lo que hay que notar:

- **La API no tiene estado.** Para continuar la conversación se reenvía el historial completo
  (`[user, assistant, user, ...]`). La "memoria" es responsabilidad de tu sistema.
- **La respuesta es una lista de bloques** (texto, pedidos de herramienta, otros tipos), no un string. Se recorre
  verificando el tipo de cada bloque.
- **`stop_reason`** dice por qué terminó: terminó de responder, se quedó sin tokens, quiere usar una herramienta o
  rechazó la solicitud. El código siempre lo revisa antes de usar el contenido.
- **`usage`** informa los tokens consumidos: se registra por conversación para controlar costos.

<Callout type="info" title="Sobre los ejemplos del curso">
  Los ejemplos usan el SDK de Anthropic porque es el que se documenta con precisión acá; los conceptos
  (mensajes, tools, salidas estructuradas, tokens) son equivalentes en otros proveedores con nombres
  distintos. Los IDs de modelos y precios cambian con frecuencia: consultá siempre la documentación vigente.
</Callout>

## Un puerto propio para el modelo

En una arquitectura hexagonal, el modelo es una **dependencia externa** más, como la base o el proveedor de SMS. El
dominio define lo que necesita; un adaptador lo implementa con un proveedor concreto:

```ts
// application/ports/llm-client.ts: lo que el dominio necesita, sin tipos del proveedor
export interface LlmMessage {
  role: "user" | "assistant";
  content: string;
}

export interface LlmCompletion {
  text: string;
  stopReason: "end_turn" | "max_tokens" | "tool_use" | "refusal" | "other";
  usage: { inputTokens: number; outputTokens: number };
  model: string;
}

export interface LlmClient {
  complete(input: { system: string; messages: LlmMessage[]; signal?: AbortSignal }): Promise<LlmCompletion>;
}
```

```ts
// infrastructure/llm/anthropic-llm-client.ts
import Anthropic from "@anthropic-ai/sdk";

export class AnthropicLlmClient implements LlmClient {
  constructor(
    private readonly client: Anthropic,
    private readonly model: string,
  ) {}

  async complete({ system, messages, signal }: Parameters<LlmClient["complete"]>[0]): Promise<LlmCompletion> {
    const response = await this.client.messages.create(
      { model: this.model, max_tokens: 16000, system, messages },
      { signal },
    );
    const text = response.content.flatMap((block) => (block.type === "text" ? [block.text] : [])).join("");
    return {
      text,
      stopReason: mapStopReason(response.stop_reason),
      usage: { inputTokens: response.usage.input_tokens, outputTokens: response.usage.output_tokens },
      model: response.model,
    };
  }
}
```

Beneficios: cambiar de modelo o de proveedor no toca los casos de uso; los timeouts, reintentos, logging y costos
se centralizan en el adaptador; y los tests usan un **fake determinista** que devuelve respuestas predefinidas.

Un buen diseño **minimiza lo que depende del modelo**: las reglas de negocio (plazos de devolución, fechas
permitidas, horarios de contacto, quién puede recibir qué información) se aplican en código, no se "piden" en el prompt.

## Casos de uso en distintos dominios

| Caso                                                             | Nivel recomendado                       |
| ---------------------------------------------------------------- | --------------------------------------- |
| Clasificar un ticket de soporte por tema y urgencia              | Llamada simple                          |
| Extraer fechas y huéspedes de un pedido de reserva               | Llamada simple con salida estructurada  |
| Resumir una conversación para el operador humano                 | Llamada simple                          |
| Recordatorio de turnos médicos: seleccionar, redactar, enviar    | Workflow                                |
| Moderar comentarios de una red social con reglas y apelación     | Workflow                                |
| Resolver un pedido con problemas: consultar, compensar, devolver | Agente con herramientas y guardrails    |
| Asistente de finanzas personales que explica y categoriza gastos | Agente con herramientas de sólo lectura |

## Errores frecuentes

- **Usar el modelo como fuente de datos** (saldos, fechas, políticas) en lugar de herramientas.
- **Construir un agente** donde alcanzaba una llamada o un workflow.
- **Ignorar `stop_reason`**: tratar como completa una respuesta cortada por `max_tokens` o rechazada.
- **Acoplar el dominio al SDK** del proveedor.
- **Poner reglas de negocio sólo en el prompt.**
- **No registrar el uso de tokens** por conversación y por tenant.
