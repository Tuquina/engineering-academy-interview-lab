## ¿Qué problema resuelve?

Una campaña de cobranzas envía 50.000 conversaciones por semana. Si cada una usa un agente que hace 6 llamadas al
modelo con 8.000 tokens de contexto, son 2.400 millones de tokens de entrada por semana. Una decisión de diseño que
agrega 2.000 tokens al system prompt cambia la factura de forma visible; una que reduce las iteraciones del agente
de 6 a 4 también. Y cada segundo de latencia es un deudor esperando una respuesta en WhatsApp.

Para diseñar con LLMs hay que razonar en sus unidades: **tokens, contexto, tiempo y dinero**.

## Tokens

Los modelos no procesan caracteres ni palabras: procesan **tokens**, fragmentos de texto definidos por un
_tokenizer_. En español, una palabra suele ser uno o dos tokens; los números largos, los IDs y el JSON con muchos
símbolos consumen más tokens de lo que parece.

```text
"Hola, ¿cuánto debo?"          → unos pocos tokens
"debt_8f3k2j9x4q"              → varios tokens: los IDs aleatorios se parten mucho
{"amountCents": 1500000}       → llaves, comillas y nombres también cuentan
```

Reglas prácticas:

- **Medí, no estimes**: los proveedores ofrecen endpoints de conteo de tokens (en la API de Anthropic,
  `messages.countTokens`), y cada respuesta informa `usage`.
- **Cada modelo puede tener su propio tokenizer**: al cambiar de modelo, se vuelve a medir.
- **El formato importa**: un JSON con nombres de campo largos repetido en cada mensaje es costoso; una tabla compacta
  o datos ya resumidos pueden transmitir lo mismo con menos tokens.

## La ventana de contexto

La **ventana de contexto** es el máximo de tokens que el modelo puede considerar en una llamada. Todo cuenta:

/>

Los modelos actuales tienen ventanas grandes (cientos de miles o un millón de tokens), pero eso **no significa que
convenga llenarlas**: más contexto es más costo, más latencia y, en la práctica, más riesgo de que el modelo preste
atención a lo irrelevante.

Cuando una conversación crece, las estrategias son:

| Estrategia                          | Idea                                                                                                         |
| ----------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| Estado fuera del historial          | El saldo, la promesa vigente y el plan viven en la base; se inyectan resumidos y actualizados en cada turno. |
| Resumir (compaction)                | Reemplazar los turnos viejos por un resumen que conserve decisiones y datos clave.                           |
| Recortar resultados de herramientas | Devolver sólo los campos necesarios, no la fila completa ni el JSON del proveedor.                           |
| Recuperar en lugar de cargar        | Buscar los fragmentos relevantes (RAG) en vez de incluir todos los documentos.                               |

**Truncar a ciegas** (borrar los mensajes más viejos) es la peor opción: se pierde, sin saberlo, que el deudor dijo
que estaba desempleado o que pidió no ser contactado por la mañana. El módulo de memoria profundiza en esto.

## Por qué las salidas varían

En cada paso, el modelo calcula una **distribución de probabilidad** sobre el siguiente token y se elige uno
**muestreando** esa distribución. Por eso la misma entrada puede producir respuestas distintas.

Históricamente, parámetros como **`temperature`** (aplanar o concentrar la distribución) y **`top_p`** (limitar la
elección a los tokens más probables) controlaban esa variabilidad. Hoy depende del proveedor y del modelo: varios
modelos actuales **no aceptan** esos parámetros (en la API de Anthropic, los modelos recientes devuelven un error si
se envían) y controlan el comportamiento con otros mecanismos, como el nivel de esfuerzo o de razonamiento.

La conclusión de ingeniería no cambia: **no se diseña contando con el determinismo**. La variabilidad se maneja con:

- **Salidas estructuradas** que restringen el formato (próxima lección).
- **Validación** de todo lo que el modelo produce.
- **Reglas de negocio en código**, no en el prompt.
- **Evaluaciones sobre muchas corridas**, no sobre una prueba manual (módulo de evals).

## Latencia

La latencia de una llamada tiene dos componentes:

| Componente                              | De qué depende                                                                      |
| --------------------------------------- | ----------------------------------------------------------------------------------- |
| **Tiempo hasta el primer token** (TTFT) | Tamaño del contexto a procesar, carga del proveedor, razonamiento previo del modelo |
| **Velocidad de generación**             | Tokens por segundo del modelo; los modelos más grandes suelen ser más lentos        |

`latencia total ≈ TTFT + tokens de salida / tokens por segundo`

En un **agente**, se paga **por cada iteración del loop**: un turno con 3 tool calls son 4 llamadas, y cada una
procesa el historial completo. Reducir iteraciones (herramientas que devuelven lo necesario en una sola llamada,
instrucciones claras) suele ser la mejora más grande.

### Streaming

Con **streaming**, el modelo envía los tokens a medida que los genera. La latencia total es la misma, pero el usuario
ve texto casi de inmediato:

```ts
const stream = client.messages.stream({
  model: "claude-opus-5-5",
  max_tokens: 64000,
  system: SYSTEM_PROMPT,
  messages,
});

stream.on("text", (delta) => sendToClient(delta)); // reenviar cada fragmento (SSE, WebSocket)
const finalMessage = await stream.finalMessage(); // mensaje completo, con stop_reason y usage
```

Además de la experiencia, el streaming evita timeouts HTTP en respuestas largas. En canales que no admiten respuestas
parciales (un SMS), no aporta: hay que esperar el mensaje completo.

## Costo

`costo ≈ tokens de entrada × precio de entrada + tokens de salida × precio de salida`

La **salida suele costar varias veces más** que la entrada (por ejemplo, 5 veces en los precios publicados de varios
modelos). Los precios cambian seguido y varían mucho entre modelos de una misma familia: se consultan en la página
oficial y se registran en la configuración, no se escriben en el código.

```ts
/** Registra el consumo de cada llamada para atribuir costo por conversación y por tenant. */
function recordUsage(conversationId: string, tenantId: string, model: string, usage: Anthropic.Usage) {
  metrics.increment("llm.input_tokens", usage.input_tokens, { tenantId, model });
  metrics.increment("llm.output_tokens", usage.output_tokens, { tenantId, model });
  metrics.increment("llm.cache_read_tokens", usage.cache_read_input_tokens ?? 0, { tenantId, model });
  costLedger.add({ conversationId, tenantId, model, usage }); // el precio se aplica desde la configuración
}
```

### Prompt caching

Muchas llamadas comparten un **prefijo** idéntico: las definiciones de herramientas, el system prompt con las
políticas del tenant. Con **prompt caching**, el proveedor guarda ese prefijo procesado y las llamadas siguientes lo
leen de la caché, mucho más barato y con menor tiempo hasta el primer token.

```ts
const response = await client.messages.create({
  model: "claude-opus-5-5",
  max_tokens: 16000,
  cache_control: { type: "ephemeral" }, // cachea automáticamente el último bloque cacheable
  tools: AGENT_TOOLS, // estable: siempre en el mismo orden
  system: tenantPolicyPrompt, // estable por tenant
  messages, // lo variable va al final
});

console.log(response.usage.cache_read_input_tokens); // si es 0 en llamadas repetidas, algo invalida la caché
```

La regla clave: **la caché es un match de prefijo**. Cualquier cambio en un byte del prefijo invalida todo lo que
sigue. Poner la fecha y hora actual o un ID de request **al principio del system prompt** anula la caché en cada
llamada. Lo estable va primero; lo variable, al final.

## Elegir modelo y esfuerzo

Las familias de modelos ofrecen variantes más capaces y más rápidas o baratas, y muchos modelos permiten ajustar el
**esfuerzo** de razonamiento. La decisión se toma **midiendo** sobre casos reales:

- Tareas simples y de alto volumen (clasificar un mensaje): un modelo rápido o un esfuerzo bajo suele alcanzar.
- Negociación con reglas complejas o decisiones de alto impacto: más capacidad y esfuerzo.
- Se compara el **costo por tarea completada**, no por llamada: un modelo barato que necesita más iteraciones o
  reintentos puede terminar costando más.

## Errores frecuentes

- **Estimar tokens "a ojo"** en lugar de medirlos.
- **Llenar el contexto "por las dudas"** con documentos o resultados completos.
- **Truncar el historial sin criterio.**
- **Esperar respuestas idénticas** entre corridas y escribir tests que dependen de eso.
- **Contenido variable al principio del prompt**, que invalida la caché.
- **Precios escritos en el código.**
- **Medir costo por llamada** en lugar de por conversación o tarea completada.
