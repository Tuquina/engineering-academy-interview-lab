## ¿Qué problema resuelve?

En el software tradicional, un test unitario verifica que `calculateInterest(1000, 0.05)` devuelva `50`. Siempre. Un
agente no funciona así: la misma conversación puede terminar bien nueve veces y mal una; un cambio de prompt que
mejora el tono puede empeorar el cumplimiento de políticas; y el proveedor puede actualizar el modelo y cambiar el
comportamiento sin que cambie una línea de tu código.

Sin evaluaciones, cada cambio es una apuesta y la única forma de detectar problemas son las quejas. Las **evals** son
el equivalente a la suite de tests para sistemas no deterministas, y son probablemente **la habilidad más valorada**
en ingeniería de agentes.

## Casos de prueba y golden datasets

Un **caso de prueba** de un agente es una situación con su contexto y lo que se espera:

```ts
export interface AgentEvalCase {
  id: string;
  category: "typical" | "edge" | "adversarial" | "compliance" | "regression";
  description: string;
  initialState: DebtorStateFixture; // saldo, promesas, preferencias: datos controlados
  conversation: Array<{ role: "debtor"; content: string }>; // mensajes del deudor (o un simulador de usuario)
  expectations: {
    mustCallTools?: Array<{ name: string; argsMatch?: Record<string, unknown> }>;
    mustNotCallTools?: string[];
    mustEscalate?: boolean;
    forbiddenContent?: string[]; // por ejemplo, el saldo antes de verificar identidad
    rubric?: string[]; // criterios para evaluación semántica
  };
}
```

| Categoría    | Ejemplos                                                                               |
| ------------ | -------------------------------------------------------------------------------------- |
| Típicos      | Promesa clara de pago, consulta de saldo, pedido de plan de cuotas                     |
| Bordes       | Fecha ambigua ("a fin de mes"), monto mayor al saldo, mensajes en varias partes        |
| Adversarios  | Prompt injection, tercero que se hace pasar por el deudor, presión para obtener quitas |
| Cumplimiento | Opt-out, horario prohibido, vulnerabilidad, lenguaje prohibido por normativa           |
| Regresión    | Cada incidente de producción convertido en un caso                                     |

**Golden dataset** es el conjunto de casos con la respuesta o el comportamiento correcto definido (**ground truth**)
por expertos (en cobranzas, el equipo de compliance y los supervisores). Se **versiona** como código y **crece**: cada
conversación problemática de producción se convierte en un caso.

Para conversaciones de varios turnos, se usa un **simulador de usuario**: otro modelo que actúa como deudor siguiendo
un perfil ("dice que ya pagó, se enoja si se lo contradice"), lo que permite evaluar el diálogo completo.

## Evaluadores: determinista, semántico y LLM as judge

| Tipo                | Qué mide                                    | Ejemplos                                                                                                           |
| ------------------- | ------------------------------------------- | ------------------------------------------------------------------------------------------------------------------ |
| **Determinista**    | Hechos verificables con código              | Llamó a `verify_identity` antes de `get_debt_summary`; el monto registrado es 4.000.000; no envió fuera de horario |
| **Semántico**       | Similitud de significado con una referencia | La respuesta contiene la información esencial (embeddings, comparación de hechos)                                  |
| **LLM as judge**    | Criterios cualitativos con una rúbrica      | Tono respetuoso; explicó las opciones con claridad; no presionó                                                    |
| **Revisión humana** | Calibración y casos difíciles               | Muestras etiquetadas por supervisores                                                                              |

**Regla:** si algo se puede verificar con código, se verifica con código. Es más barato, más rápido y no tiene
sesgos. LLM as judge se reserva para lo que de verdad es cualitativo.

### Correctitud de tool calls

En agentes, gran parte de la calidad está en **qué herramientas usa, en qué orden y con qué argumentos**, y eso es
mayormente determinista:

```ts
export function evaluateToolCalls(
  trace: AgentRunTrace,
  expected: AgentEvalCase["expectations"],
): CriterionResult[] {
  const calls = trace.toolCalls.map((call) => call.name);
  const results: CriterionResult[] = [];

  for (const required of expected.mustCallTools ?? []) {
    const call = trace.toolCalls.find((c) => c.name === required.name);
    results.push({
      criterion: `llama a ${required.name}`,
      passed: call !== undefined && matchesArgs(call.args, required.argsMatch),
    });
  }
  for (const forbidden of expected.mustNotCallTools ?? []) {
    results.push({ criterion: `no llama a ${forbidden}`, passed: !calls.includes(forbidden) });
  }

  // Orden obligatorio: nunca consultar la deuda antes de verificar identidad
  const verifiedAt = calls.indexOf("verify_identity");
  const summaryAt = calls.indexOf("get_debt_summary");
  results.push({
    criterion: "verifica identidad antes de consultar la deuda",
    passed: summaryAt === -1 || (verifiedAt !== -1 && verifiedAt < summaryAt),
    critical: true,
  });
  return results;
}
```

### LLM as judge bien hecho

Un **juez** es un modelo que califica la salida de otro con una rúbrica. Funciona si se diseña con cuidado:

- **Criterios concretos y, de ser posible, binarios:** "¿menciona al menos una opción de pago concreta? sí/no" es mejor
  que "calificá la calidad del 1 al 10".
- **Un criterio por evaluación** en lugar de un puntaje global.
- **Razonamiento antes del veredicto** y salida estructurada con el veredicto y la justificación.
- **Calibración:** se compara el juez contra etiquetas humanas en una muestra y se mide su acuerdo; si no coincide, se
  ajusta la rúbrica.
- **Sesgos conocidos:** preferencia por respuestas largas, por la primera opción presentada (en comparaciones) y por
  textos de su propia familia de modelos. Se mitigan alternando el orden y controlando la longitud.


## Seguridad y cumplimiento

Los casos adversarios y de cumplimiento se evalúan con criterios **críticos**: no se promedian con el resto.

- Prompt injection directa e indirecta: el agente no ejecuta acciones fuera de política.
- Suplantación: no revela información sin verificación de identidad.
- Opt-out y horarios: nunca contacta a quien pidió no ser contactado ni fuera de horario.
- Lenguaje prohibido por la normativa de cobranzas del país del tenant.
- Datos personales: no revela datos de un deudor a otro ni de un tenant a otro.

Un criterio crítico se exige **en todas las corridas**: un 99 % de cumplimiento en "no revelar datos sin verificar
identidad" significa una filtración cada cien conversaciones.

## Pruebas repetidas y estadística

Como las salidas varían, **cada caso se corre varias veces** y se estima una **tasa de éxito**:

Ideas estadísticas mínimas:

- **El tamaño de muestra importa:** con 50 casos, pasar de 82 % a 86 % puede ser ruido. Un intervalo de confianza (por
  ejemplo, de Wilson para proporciones) muestra el rango plausible de la tasa real.
- **Comparación pareada:** se comparan las dos versiones **sobre los mismos casos**, mirando en qué casos mejoró y en
  cuáles empeoró, lo que reduce el ruido frente a comparar promedios sueltos.
- **Reportar por categoría:** una mejora global puede esconder una caída en casos de cumplimiento.
- **Costo y latencia** también son resultados: una versión que mejora 1 punto y cuesta el doble puede no convenir.

## Regresión, quality gates y drift

- **Suite de regresión:** se corre ante cada cambio de prompt, herramientas, modelo, plantilla o políticas, igual que
  la suite de tests en CI. Un **prompt regression** es una caída en casos que antes pasaban.
- **Quality gate:** la versión candidata se publica sólo si no empeora ningún criterio crítico y mejora o mantiene los
  demás dentro de un margen definido. Es la puerta del ciclo `candidate → published` de la lección de configuración.
- **Model drift:** los proveedores actualizan y retiran modelos. Cambiar de versión de modelo es un cambio como
  cualquier otro: se corre la suite completa. Además, se monitorean métricas de producción por versión para detectar
  cambios de comportamiento.
- **Evaluación en producción:** muestreo de conversaciones reales evaluadas por jueces y humanos, que alimenta el
  dataset.

El Interview Arena de esta plataforma aplica la misma idea a tus respuestas: criterios explícitos verificables en
lugar de un puntaje vago.

## Errores frecuentes

- **Probar a mano un par de conversaciones** y publicar.
- **Un único puntaje global** del 1 al 10 que nadie sabe interpretar.
- **LLM as judge para todo**, incluido lo verificable con código, y sin calibrar.
- **Una corrida por caso** y conclusiones sobre diferencias de un par de puntos.
- **Promediar criterios críticos** con criterios de estilo.
- **Dataset estático** que no incorpora los incidentes de producción.
- **Cambiar de versión de modelo** sin correr la suite.
