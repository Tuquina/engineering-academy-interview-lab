## ¿Qué problema resuelve?

Un agente de una red de clínicas habla con pacientes, muchas veces preocupados o con dolor, en nombre de una
organización regulada. Un error puede ser una respuesta fría ante una urgencia, un turno con el profesional
equivocado, un contacto en horario prohibido o información de salud revelada a un familiar. En un comercio los
riesgos son otros (un reembolso fuera de política, un descuento inventado), pero la estructura de la solución es la
misma. Para operar con responsabilidad hacen falta tres cosas: **guardrails**
que impidan lo inaceptable, **personas** en los puntos donde el criterio humano es necesario y **observabilidad** para
saber qué pasó en cada conversación.

| Punto       | Ejemplos                                                                                                                            | Tipo de control       |
| ----------- | ----------------------------------------------------------------------------------------------------------------------------------- | --------------------- |
| **Entrada** | "No me escriban más" → registrar opt-out y cortar; síntomas de urgencia (dolor en el pecho) → derivar a emergencias y a una persona | Reglas + clasificador |
| **Acción**  | Cupón mayor al permitido → rechazar; reembolso mayor a un umbral → aprobación humana                                                | Código determinista   |
| **Salida**  | El mensaje menciona un turno o un monto que no coincide con el sistema → bloquear; fuera del horario legal → no enviar              | Código + clasificador |

**Preferí controles deterministas.** Que un monto coincida con el pedido, que un turno exista en la agenda, que la hora esté dentro del horario
permitido o que una herramienta no esté disponible son verificaciones exactas. Los **clasificadores basados en
modelos** (detectar tono agresivo, señales de vulnerabilidad, intentos de manipulación) son útiles como capa
adicional, pero son probabilísticos: tienen falsos positivos y negativos, y se evalúan como cualquier otro componente.

```ts
/** Guardrail de salida: todo monto mencionado debe existir en los datos verificados del turno. */
export function verifyMentionedAmounts(message: string, verified: VerifiedTurnData): GuardrailResult {
  const mentioned = extractAmounts(message); // parseo determinista de montos en el texto
  const allowed = new Set([verified.orderTotalCents, ...verified.offeredRefunds.map((r) => r.amountCents)]);
  const unknown = mentioned.filter((amount) => !allowed.has(amount));
  return unknown.length === 0
    ? { action: "allow" }
    : { action: "block", reason: "amount_not_verified", details: { unknown } };
}
```

Cuando un guardrail bloquea, el sistema tiene una **respuesta segura predefinida** (o regenera con la corrección, o
escala); nunca envía el mensaje bloqueado.

## Human in the loop

| Modalidad              | Cuándo                                                         | Ejemplo                                                                            |
| ---------------------- | -------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| **Aprobación previa**  | Acciones irreversibles o de alto impacto                       | Un reembolso de más de $500.000 queda pendiente hasta que un supervisor lo aprueba |
| **Escalamiento**       | Señales de riesgo, conflicto, baja confianza, pedido explícito | "Quiero hablar con una persona"                                                    |
| **Handoff**            | La conversación pasa a un operador                             | La persona no reconoce un cargo de su tarjeta                                      |
| **Revisión posterior** | Muestreo de conversaciones para control de calidad             | 2 % de las conversaciones cerradas se revisan                                      |

Un buen **handoff** transfiere **contexto**: un resumen de la conversación, el estado estructurado (identidad
verificada, pedido consultado, compensaciones ofrecidas, motivo del escalamiento) y el historial completo accesible. El operador
no debería tener que preguntar lo que la persona ya contestó.

Las aprobaciones también son una parte del diseño de la experiencia: mientras un reembolso espera aprobación, el agente
informa con honestidad que el pedido está en revisión y cuándo habrá respuesta.

## Trazabilidad

Para responder "¿por qué el agente dijo esto?" hace falta una **traza por turno**:

```ts
interface AgentTurnTrace {
  conversationId: string;
  tenantId: string;
  turn: number;
  agent: { agentId: string; version: number }; // qué configuración corrió
  stage: ConversationStage; // en qué etapa de la máquina de estados
  modelCalls: Array<{
    model: string;
    inputTokens: number;
    outputTokens: number;
    cacheReadTokens: number;
    latencyMs: number;
    stopReason: string;
    requestId: string; // para correlacionar con el proveedor
  }>;
  toolCalls: Array<{ name: string; argsRedacted: unknown; ok: boolean; latencyMs: number; error?: string }>;
  guardrails: Array<{ name: string; action: "allow" | "block" | "escalate"; reason?: string }>;
  outcome: "replied" | "escalated" | "blocked" | "error";
}
```

Con **OpenTelemetry** cada turno es una traza con spans para las llamadas al modelo, las herramientas y los
guardrails; existen convenciones semánticas específicas para IA generativa (nombres de atributos para modelo, tokens,
operación). Así una conversación se sigue de punta a punta junto con el resto del sistema (curso de Node.js).

<Callout type="warning" title="Los logs de un agente contienen datos personales">
  Mensajes de pacientes y clientes, montos, situaciones personales y de salud. Se **redactan** los datos
  sensibles en los logs operativos, se separan los registros de auditoría (con acceso restringido) y se define
  una **retención** acorde a la normativa y al contrato con el cliente.
</Callout>

## Métricas: calidad, costo y riesgo

| Dimensión | Métricas                                                                                            |
| --------- | --------------------------------------------------------------------------------------------------- |
| Negocio   | Resolución en el primer contacto, devoluciones gestionadas, turnos confirmados, satisfacción (CSAT) |
| Calidad   | Tasa de escalamiento, conversaciones bloqueadas por guardrails, puntaje de revisión humana, quejas  |
| Costo     | Tokens y costo por conversación, por caso resuelto, por tenant y por versión del agente             |
| Operación | Latencia por turno (p50, p95), errores del proveedor, fallbacks usados                              |
| Riesgo    | Intentos de inyección detectados, opt-outs, contactos fuera de horario bloqueados                   |

Todas se cortan **por versión del agente**: es la forma de saber si una versión nueva mejoró o empeoró en producción
(y alimenta la comparación de versiones del módulo de evals). El **costo por resultado** (por caso resuelto) es más
significativo que el costo por mensaje.

## Errores frecuentes

- **Guardrails sólo en el prompt** ("no ofrezcas más del 20 %").
- **Clasificadores con modelos como único control** de algo crítico, sin evaluar sus errores.
- **Escalar sin contexto**: el operador empieza de cero.
- **Aprobaciones que bloquean al agente** sin informar a la persona qué está pasando.
- **No registrar la versión del agente** en cada traza.
- **Logs con datos personales sin redactar** y sin retención definida.
- **Medir sólo costo por mensaje**, sin calidad ni resultado de negocio.
