## El GIL

CPython tiene un **Global Interpreter Lock (GIL)**: en el build estándar, un solo hilo ejecuta bytecode Python a la
vez. Simplifica la implementación del intérprete y de las extensiones en C, pero tiene una consecuencia directa:

| Tipo de trabajo              | ¿Varios threads ayudan? | Por qué                                              |
| ---------------------------- | ----------------------- | ---------------------------------------------------- |
| I/O (red, disco, base)       | Sí                      | El GIL se libera mientras el hilo espera             |
| CPU en Python puro           | No                      | Los threads se turnan el GIL: no usan varios núcleos |
| CPU en extensiones C (NumPy) | A menudo sí             | Muchas extensiones liberan el GIL en sus cálculos    |

El PEP 703 hizo el GIL **opcional**: Python 3.13 incluyó un build experimental sin GIL (_free-threaded_) y desde
**Python 3.14** ese build tiene soporte oficial. No es el build por defecto: hay que instalarlo explícitamente, y
algunas extensiones todavía pueden no ser compatibles. Para la mayoría de los servicios web, el modelo clásico sigue
siendo el punto de partida.

## Threads, procesos y concurrent.futures

```python
from concurrent.futures import ThreadPoolExecutor, ProcessPoolExecutor

# I/O con una librería bloqueante: varios threads
with ThreadPoolExecutor(max_workers=10) as pool:
    rates = list(pool.map(fetch_shipping_rate, carriers))

# CPU intensivo: varios procesos, cada uno con su intérprete y su GIL
with ProcessPoolExecutor() as pool:
    thumbnails = list(pool.map(resize_image, image_paths))
```

Los procesos no comparten memoria: los argumentos y resultados se **serializan** (pickle) para enviarse, lo que tiene
un costo. Por eso conviene repartir tareas de cómputo relativamente grandes, no millones de operaciones mínimas.

Con threads hay que proteger el estado compartido con `threading.Lock`: aunque exista el GIL, una operación como
`counter += 1` no es atómica y puede perder incrementos.

## asyncio

**asyncio** implementa concurrencia con un **event loop** en un solo hilo, como Node.js. Las funciones `async def`
son **corrutinas**: cada `await` cede el control al loop mientras se espera una operación de I/O, y el loop avanza
otras tareas.

```python
import asyncio
import httpx

async def fetch_rate(client: httpx.AsyncClient, carrier: str) -> dict:
    response = await client.get(f"https://rates.example/{carrier}", timeout=2.0)
    response.raise_for_status()
    return response.json()

async def best_rate(carriers: list[str]) -> dict:
    async with httpx.AsyncClient() as client:
        results = await asyncio.gather(
            *(fetch_rate(client, c) for c in carriers),
            return_exceptions=True,            # un proveedor caído no cancela a los demás
        )
    valid = [r for r in results if not isinstance(r, Exception)]
    return min(valid, key=lambda r: r["price_cents"])

asyncio.run(best_rate(["dhl", "fedex", "correo"]))
```

### Herramientas principales

| Herramienta                   | Para qué                                                                   |
| ----------------------------- | -------------------------------------------------------------------------- |
| `asyncio.gather(*corrutinas)` | Ejecutar varias y esperar todas                                            |
| `asyncio.TaskGroup` (3.11+)   | Lo mismo con cancelación estructurada: si una falla, se cancelan las demás |
| `asyncio.timeout(s)` (3.11+)  | Límite de tiempo para un bloque                                            |
| `asyncio.Semaphore(n)`        | Limitar la concurrencia (por ejemplo, 10 requests a la vez)                |
| `asyncio.Queue`               | Productor/consumidor entre tareas                                          |
| `asyncio.to_thread(f, ...)`   | Ejecutar una función bloqueante sin frenar el loop                         |

```python
async def notify_all(customers):
    limit = asyncio.Semaphore(10)

    async def notify(customer):
        async with limit:                        # como máximo 10 a la vez
            async with asyncio.timeout(3):
                await push.send(customer.device_token, "Tu pedido fue enviado")

    async with asyncio.TaskGroup() as group:
        for customer in customers:
            group.create_task(notify(customer))
```

<Callout type="danger" title="No bloquees el event loop">
  `time.sleep`, `requests.get` o un driver de base síncrono dentro de una función `async` frenan **todo** el
  loop: ninguna otra request avanza. Usá equivalentes async (`asyncio.sleep`, `httpx.AsyncClient`, `asyncpg`)
  o `asyncio.to_thread` para el código bloqueante. Lo mismo vale para cálculos largos de CPU.
</Callout>

## Cómo elegir

- **API web con mucha I/O** y librerías async disponibles: asyncio (FastAPI con endpoints `async`).
- **Código existente síncrono** o librerías bloqueantes: threads (o endpoints `def` comunes en FastAPI, que se
  ejecutan en un pool de threads).
- **Cómputo intensivo**: procesos, o mover ese trabajo a workers separados (Celery, colas) para no afectar la API.

## Resumen

El GIL condiciona el paralelismo en CPython: threads y asyncio para I/O, procesos para CPU. asyncio ofrece mucha
concurrencia en un hilo siempre que no se bloquee el loop. Saber explicar estas diferencias es una de las preguntas más
frecuentes en entrevistas de backend con Python.
