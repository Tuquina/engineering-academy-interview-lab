## ¿Qué problema resuelve?

El sistema de turnos de una red de clínicas cambia todo el tiempo: reglas de agenda por profesional, nuevos canales de
recordatorio, nuevas normativas, nuevas prepagas y proveedores de pagos. Los principios de diseño existen para que
**esos cambios sean baratos y localizados**: que agregar WhatsApp no obligue a tocar el cálculo de disponibilidad, y
que cambiar el proveedor de SMS no toque las reglas de la agenda. Esta lección presenta los principios clásicos **con criterio**: cuándo ayudan y cuándo
se convierten en ceremonia.

## SOLID

| Principio                 | Idea                                                            | Ejemplo en una red de clínicas                                                          |
| ------------------------- | --------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| **S**ingle Responsibility | Un módulo tiene una sola razón para cambiar                     | El cálculo de disponibilidad de la agenda no sabe nada de cómo se envía un recordatorio |
| **O**pen/Closed           | Abierto a extensión, cerrado a modificación                     | Agregar un canal (RCS) implementando `Notifier`, sin tocar el orquestador               |
| **L**iskov Substitution   | Un subtipo puede reemplazar al tipo base sin romper el contrato | Un `Notifier` que "a veces no envía y no avisa" rompe a quien confía en el contrato     |
| **I**nterface Segregation | Interfaces chicas y específicas                                 | `ScheduleReader` y `ScheduleWriter` en lugar de un `ScheduleService` con 30 métodos     |
| **D**ependency Inversion  | Los módulos de alto nivel dependen de abstracciones             | El caso de uso depende de `PaymentGateway`, no del SDK del proveedor                    |

```ts
// Open/Closed + Dependency Inversion: el orquestador depende de una abstracción
export interface Notifier {
  readonly channel: Channel;
  send(message: OutboundMessage, signal: AbortSignal): Promise<SendResult>;
}

export class ReminderDispatcher {
  constructor(private readonly notifiers: ReadonlyMap<Channel, Notifier>) {}

  async dispatch(reminder: Reminder, signal: AbortSignal): Promise<SendResult> {
    const notifier = this.notifiers.get(reminder.channel);
    if (!notifier) return { ok: false, error: "channel_not_configured" };
    return notifier.send(reminder.message, signal); // agregar un canal = registrar otro Notifier
  }
}
```

**Con criterio:** SOLID aplicado mecánicamente produce interfaces con una sola implementación y capas de indirección
sin beneficio. La pregunta útil es "¿esto va a cambiar por razones distintas?" y "¿necesito sustituir esta pieza?".

## DRY, KISS y YAGNI

- **DRY** (_Don't Repeat Yourself_): cada **conocimiento** del sistema tiene una única representación. La regla de
  "duración mínima de un turno" vive en un solo lugar. Ojo: DRY trata de **conocimiento**, no de texto. Dos funciones que
  se parecen pero representan conceptos distintos (un recordatorio de turno y un aviso legal de consentimiento) no deben unificarse: van
  a cambiar por motivos distintos. **La duplicación es más barata que la abstracción equivocada.**
- **KISS** (_Keep It Simple_): la solución más simple que cumple los requisitos. Un `switch` claro puede ser mejor que
  una jerarquía de estrategias.
- **YAGNI** (_You Aren't Gonna Need It_): no construir para requisitos hipotéticos. "Por si algún día usamos otra
  base" no justifica una capa genérica de persistencia.

## Separación de responsabilidades, acoplamiento y cohesión

**Cohesión** es cuánto tienen que ver entre sí las cosas que están juntas; **acoplamiento** es cuánto depende un
módulo de otro.

Formas de acoplamiento, de peor a más aceptable: compartir tablas de la base entre módulos, depender de detalles
internos de otro módulo, llamar a su API pública, y comunicarse por eventos. Regla práctica: **lo que cambia junto,
vive junto** (cohesión) y **las dependencias apuntan hacia lo más estable** (el dominio).

## Composición sobre herencia

La herencia acopla fuertemente al hijo con los detalles del padre. La composición combina comportamientos pequeños:

```ts
// ❌ Herencia: cada combinación es una subclase
class SmsReminder extends Reminder {}
class SmsReminderWithRetry extends SmsReminder {}
class SmsReminderWithRetryAndAudit extends SmsReminderWithRetry {}

// ✅ Composición: decoradores combinables sobre la misma interfaz
const notifier: Notifier = withAudit(withRetry(new SmsNotifier(client), { maxAttempts: 3 }), auditLog);
```

Es el patrón **Decorator**, que la Pattern Library detalla. En TypeScript, con funciones y objetos, la composición es
todavía más natural que en C# o Java.

## Inversión e inyección de dependencias

- **Inversión de dependencias** (el principio): el núcleo define las interfaces que necesita (puertos); la
  infraestructura las implementa (adaptadores). El dominio no importa nada de la infraestructura.
- **Inyección de dependencias** (la técnica): las dependencias se reciben desde afuera (constructor o parámetros) en
  lugar de crearse adentro.
- **Composition root**: el único lugar donde se crean las implementaciones concretas y se conectan.

```ts
// infrastructure/composition/appointments.ts: el único lugar que conoce las implementaciones
export function createAppointmentsModule(deps: { db: Database; smsClient: SmsClient; clock: Clock }) {
  const schedules = new PostgresScheduleRepository(deps.db);
  const notifier = withRetry(new SmsNotifier(deps.smsClient), { maxAttempts: 3 });
  return {
    bookAppointment: new BookAppointment(schedules, deps.clock),
    dispatchReminder: new ReminderDispatcher(new Map([["sms", notifier]])),
  };
}
```

En C# y Java es habitual un contenedor de DI (Microsoft.Extensions.DependencyInjection, Spring). En TypeScript suele
alcanzar con constructores y fábricas; existen contenedores (o NestJS) cuando la aplicación crece mucho.

## Clean code, refactoring y la pirámide de testing

El diseño se sostiene con **refactoring continuo**: cambios pequeños que mejoran la estructura sin cambiar el
comportamiento, protegidos por tests. La **pirámide de testing** indica la proporción:

## Domain-Driven Design en lo esencial

**DDD** propone que la estructura del software refleje el **dominio** del negocio, trabajando con los expertos.

| Concepto          | Qué es                                                                  | Ejemplo en una red de clínicas                              |
| ----------------- | ----------------------------------------------------------------------- | ----------------------------------------------------------- |
| Lenguaje ubicuo   | Los mismos términos en el código y en las conversaciones con el negocio | "Turno", "sobreturno", "agenda", "prestación"               |
| Bounded context   | Un límite dentro del cual un modelo y su lenguaje son consistentes      | "Paciente" en Turnos no es lo mismo que en Facturación      |
| Entidad           | Objeto con identidad que persiste en el tiempo                          | `Appointment`, `Patient`                                    |
| Value object      | Objeto definido por sus valores, inmutable                              | `Money`, `DateRange`, `PhoneNumber`                         |
| Agregado          | Grupo que se modifica como unidad y protege invariantes, con una raíz   | `Schedule` (agenda de un profesional) con sus `Appointment` |
| Evento de dominio | Algo relevante que ocurrió                                              | `AppointmentBooked`, `AppointmentCancelled`                 |

```ts
/** Agregado Schedule: la regla 'no hay dos turnos superpuestos' vive acá, no en el handler ni en el repositorio. */
export class Schedule {
  private constructor(
    readonly id: ScheduleId,
    private readonly workingHours: WorkingHours,
    private appointments: Appointment[],
  ) {}

  book(request: NewAppointment, now: Instant): Result<DomainEvent, BookingError> {
    if (request.slot.startsBefore(now)) return err({ kind: "slot_in_past" });
    if (!this.workingHours.contains(request.slot)) return err({ kind: "outside_working_hours" });
    if (this.appointments.some((a) => a.isActive() && a.slot.overlaps(request.slot))) {
      return err({ kind: "slot_taken" });
    }
    this.appointments.push(Appointment.create(request));
    return ok({ type: "AppointmentBooked", scheduleId: this.id, ...request });
  }
}
```

Regla clave de los agregados: **una transacción modifica un solo agregado**; la consistencia entre agregados
(cobrar el copago y actualizar las estadísticas de ocupación) se logra con **eventos**, de forma eventual.

## Comparación con C# y Java

| Concepto                | C#                                         | Java                             | TypeScript                                                |
| ----------------------- | ------------------------------------------ | -------------------------------- | --------------------------------------------------------- |
| Inyección               | Contenedor integrado de .NET               | Spring                           | Constructores/fábricas; NestJS si se quiere un contenedor |
| Value objects           | `record struct`                            | `record`                         | Objetos inmutables, branded types                         |
| Interfaces              | Nominales, `I` como prefijo por convención | Nominales                        | Estructurales, sin prefijo por convención                 |
| Herencia vs composición | Herencia frecuente en frameworks           | Herencia frecuente en frameworks | Composición y funciones más idiomáticas                   |

## Errores frecuentes

- **Interfaces para todo** aunque haya una sola implementación y ningún puerto real.
- **DRY sobre código parecido** que representa conceptos distintos.
- **Abstracciones para requisitos hipotéticos** (YAGNI).
- **Módulos `utils` y `helpers`** que acoplan todo con todo.
- **Jerarquías de herencia profundas.**
- **Agregados gigantes** que bloquean demasiado o transacciones que modifican varios agregados.
- **Reglas de negocio en el handler o en el repositorio** en lugar del dominio.
