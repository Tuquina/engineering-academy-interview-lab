## Qué vas a aprender en este curso

En la entrevista para una plataforma de agentes van a pedirte que **defiendas decisiones**: por qué un monolito
modular y no microservicios, por qué un outbox, cómo aislar tenants, qué pasa si un proveedor se cae. Este curso da el
vocabulario y los criterios.

| Módulo                   | Qué vas a poder hacer                                                                               |
| ------------------------ | --------------------------------------------------------------------------------------------------- |
| Introducción             | Razonar sobre decisiones con atributos de calidad y documentarlas.                                  |
| Principios fundamentales | Aplicar SOLID, acoplamiento y cohesión, inversión de dependencias y DDD con criterio.               |
| Patrones de diseño       | Reconocer y aplicar los patrones clásicos en TypeScript, sin sobreingeniería.                       |
| Patrones de arquitectura | Elegir estilos (hexagonal, monolito modular, microservicios, event-driven) y patrones distribuidos. |

La **Pattern Library** (`/patterns`) complementa el curso con diagramas interactivos, ejemplos y el comparador de
arquitecturas.

## Qué es arquitectura (y qué no)

Una definición útil, popularizada por Martin Fowler: la arquitectura son **las decisiones importantes**, y "importante"
suele significar **difícil de cambiar después**. Ejemplos en una plataforma de venta de entradas
para recitales:

| Decisión arquitectónica                           | Decisión de diseño local               |
| ------------------------------------------------- | -------------------------------------- |
| Monolito modular o microservicios                 | Nombre de una función                  |
| Base compartida o base por organizador            | Estructura de un componente de React   |
| Comunicación síncrona o por eventos entre módulos | Algoritmo para formatear montos        |
| Cómo se retienen los asientos durante el pago     | Un helper de fechas                    |
| Proveedor de nube y modelo de despliegue          | Orden de los parámetros de una función |

La arquitectura **no** es un diagrama inicial que se congela: evoluciona con el producto, el equipo y lo que se
aprende en producción.

## Atributos de calidad

Las decisiones se comparan con **atributos de calidad** (también llamados requisitos no funcionales):

| Atributo       | Pregunta concreta en una plataforma de entradas                                   |
| -------------- | --------------------------------------------------------------------------------- |
| Disponibilidad | ¿Qué pasa con la venta si cae el proveedor de pagos?                              |
| Rendimiento    | ¿El mapa de asientos carga en menos de un segundo?                                |
| Escalabilidad  | ¿Soportamos 50 veces más tráfico en el minuto en que abre la venta de un recital? |
| Seguridad      | ¿Un organizador puede ver datos de compradores de otro bajo algún fallo?          |
| Mantenibilidad | ¿Un equipo puede cambiar las reglas de precios sin romper los pagos?              |
| Observabilidad | ¿Podemos explicar por qué se liberó el asiento que alguien tenía retenido?        |
| Costo          | ¿Cuánto cuesta en infraestructura cada entrada vendida?                           |
| Cumplimiento   | ¿Respetamos la normativa de devoluciones y la retención de datos?                 |

Un atributo sólo sirve si se vuelve **medible**: "alta disponibilidad" no ayuda a decidir; "99,9 % mensual para
recibir webhooks de pagos" sí.

## Compromisos: no hay decisiones gratis

  caption="Cada decisión mejora algunos atributos a costa de otros: el trabajo arquitectónico es elegir qué se paga."

Una respuesta arquitectónica madura **nombra lo que se pierde**. "Uso microservicios porque escalan" es una respuesta
débil; "uso un monolito modular porque el equipo es chico y las transacciones entre asientos y pagos son críticas;
acepto escalar todo junto, y dejo los límites de módulos claros para extraer un servicio si los datos lo justifican"
es una respuesta fuerte. El comparador de arquitecturas de la plataforma (`/patterns/compare`) presenta estos
compromisos dimensión por dimensión.

## Decisiones reversibles e irreversibles

No todas las decisiones merecen el mismo análisis:

- **Reversibles** ("puertas de dos sentidos"): una librería de logging, la estructura de una carpeta, un formato
  interno. Se deciden rápido y se corrigen si hace falta.
- **Irreversibles o costosas de revertir** ("puertas de un sentido"): el modelo de datos de pagos, el esquema de
  aislamiento de tenants, un contrato público de API, la elección de base de datos. Merecen alternativas escritas,
  prototipos y revisión.

Una buena arquitectura además **hace más decisiones reversibles**: un puerto propio para el LLM vuelve reversible la
elección del proveedor; un límite de módulo claro vuelve reversible la decisión de no tener microservicios.

## Architecture Decision Records

Un **ADR** es un documento breve que registra una decisión. Formato habitual:

```text
# ADR-0012: Outbox para publicar eventos de pagos

Estado: Aceptado — 2026-11-19

## Contexto
Los pagos se registran en PostgreSQL y otros módulos deben reaccionar (detener recordatorios, notificar).
Publicar directo al broker después del commit pierde eventos si el proceso cae entre ambos pasos.

## Decisión
Guardar los eventos en una tabla outbox en la misma transacción y publicarlos con un relay.

## Alternativas consideradas
- Publicar después del commit: simple, pierde eventos ante caídas.
- Transacciones distribuidas (2PC): el broker no las soporta y acopla disponibilidades.

## Consecuencias
- Entrega al menos una vez: los consumidores deben ser idempotentes.
- Un proceso más que operar (relay) y una tabla que purgar.
```

Los ADRs se guardan **junto al código** (este proyecto los tiene en `docs/adr/`), son **inmutables** (una decisión
nueva crea un ADR que reemplaza al anterior) y responden la pregunta que siempre aparece meses después: **"¿por qué
se hizo así?"**.

## Comparación con C# y Java

Los conceptos de arquitectura son independientes del lenguaje. Lo que cambia es el ecosistema:

| Aspecto                     | .NET                                           | Java                         | TypeScript / Node.js                                                    |
| --------------------------- | ---------------------------------------------- | ---------------------------- | ----------------------------------------------------------------------- |
| Frameworks con opinión      | ASP.NET Core, plantillas de Clean Architecture | Spring Boot, Spring Modulith | NestJS (opinado), Next.js; muchos equipos sin framework de arquitectura |
| Verificar dependencias      | NetArchTest, ArchUnitNET                       | ArchUnit                     | dependency-cruiser, tests de arquitectura propios                       |
| Documentación de decisiones | ADRs (igual)                                   | ADRs (igual)                 | ADRs (igual)                                                            |

## Errores frecuentes

- **Elegir por moda** ("todos usan microservicios") en lugar de por atributos de calidad.
- **Atributos de calidad vagos** que no permiten decidir.
- **Presentar una decisión sin su costo.**
- **Analizar igual una decisión reversible que una irreversible.**
- **No documentar el porqué** y perderlo con la rotación del equipo.
- **Diagramas que mezclan niveles** de detalle y no sirven a nadie.
