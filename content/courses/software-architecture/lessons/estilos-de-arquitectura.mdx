## ¿Qué problema resuelve?

A medida que un sistema crece, la pregunta deja de ser "cómo escribo esta función" y pasa a ser "cómo se organiza
todo para que cinco equipos puedan cambiarlo sin pisarse, testearlo sin levantar toda la infraestructura y escalarlo
donde hace falta". Los estilos de arquitectura son respuestas a esa pregunta, cada una con sus costos.

## Arquitectura en capas

El estilo más conocido: **presentación → aplicación → dominio → datos**, donde cada capa usa a la de abajo.

El problema clásico de las capas tradicionales: **el dominio depende de la capa de datos** (entidades anotadas del
ORM, repositorios concretos). Cambiar la persistencia o testear las reglas obliga a arrastrar la base.

## Clean, Hexagonal y Onion: el dominio en el centro

Las tres son variantes de la misma idea:

- **Hexagonal (Ports and Adapters, Alistair Cockburn):** la aplicación expone **puertos** (interfaces); el mundo
  exterior se conecta con **adaptadores**. Hay adaptadores **de entrada** (HTTP, colas, CLI, tests) que llaman a la
  aplicación, y **de salida** (base, proveedores, LLM) que la aplicación usa a través de puertos que ella define.
- **Onion:** el dominio en el núcleo, rodeado por servicios de dominio, aplicación e infraestructura.
- **Clean Architecture (Robert C. Martin):** entidades, casos de uso, adaptadores de interfaz y frameworks; con la
  **regla de dependencia**: el código fuente sólo depende hacia adentro.

Esta plataforma sigue exactamente esta estructura: cada módulo de `src/modules` tiene las carpetas `domain`,
`application`, `infrastructure` y `presentation`, con un test que verifica que el dominio no importe infraestructura, y la composición en
`src/infrastructure/composition`. La Pattern Library tiene el diagrama interactivo de
[Arquitectura hexagonal](/patterns/hexagonal-architecture).

**Cuándo no:** un CRUD simple o un script interno no necesita puertos y adaptadores. La estructura se justifica cuando
hay reglas de negocio que proteger y dependencias externas que cambian.

## Monolito modular

Un **monolito modular** es **una sola aplicación desplegable** dividida en **módulos con límites estrictos**:

| Regla del módulo                      | Cómo se verifica                                         |
| ------------------------------------- | -------------------------------------------------------- |
| API pública explícita (`index.ts`)    | Lint o test de arquitectura que prohíbe imports internos |
| Datos propios (sus tablas o esquema)  | Ningún módulo consulta tablas de otro                    |
| Comunicación por la API o por eventos | Revisión y tests de dependencias                         |
| Sin ciclos entre módulos              | dependency-cruiser o equivalente                         |

Ventajas: **transacciones locales**, refactors entre módulos baratos, un solo pipeline, depuración simple y operación
mínima. Si los límites se respetan, extraer un módulo a un servicio más adelante es viable. Es el **punto de partida
recomendado** para la mayoría de los productos nuevos (el consejo _Monolith First_).

## Microservicios

**Microservicios** son servicios desplegables por separado, cada uno con **sus propios datos**, organizados alrededor
de capacidades de negocio y comunicados por la red.

| Ganan                                     | Pagan                                                         |
| ----------------------------------------- | ------------------------------------------------------------- |
| Despliegue independiente por equipo       | Latencia y fallas de red en cada llamada                      |
| Escalado por servicio                     | Consistencia eventual entre servicios (sagas, outbox)         |
| Aislamiento de fallas (si se diseña bien) | Observabilidad distribuida, trazas obligatorias               |
| Tecnologías distintas donde se justifica  | Contratos versionados, pruebas de integración entre servicios |
| Autonomía de equipos grandes              | Más infraestructura: despliegue, descubrimiento, colas        |

Razones válidas para separar un servicio: **equipos** que necesitan desplegar de forma independiente, partes con
**requisitos de escala o disponibilidad muy distintos** (el procesamiento de webhooks de pagos frente al panel de
administración), **aislamiento** de un componente riesgoso o con dependencias pesadas (un servicio de evaluaciones que
corre modelos). Razones débiles: "es más moderno", "así escala", "lo hace Netflix".

El antipatrón a evitar es el **monolito distribuido**: servicios que comparten base de datos o que deben desplegarse
juntos. Tiene todos los costos de los microservicios y ninguno de sus beneficios.

El **comparador** (`/patterns/compare`) presenta capas, monolito modular, microservicios y event-driven dimensión por
dimensión.

## Migrar de forma incremental

- **Strangler Fig:** en lugar de una reescritura completa (que suele fracasar), se reemplaza funcionalidad por
  funcionalidad detrás de una fachada.
- **Anti-Corruption Layer:** una capa de traducción entre el modelo del sistema legado (o de un proveedor externo) y el
  modelo propio, para que sus conceptos y nombres no se filtren. En una plataforma logística, la integración con el
  sistema de cada transportista es un caso típico.

## Comparación con C# y Java

| Estilo            | .NET                                                     | Java                                  | Node.js / TypeScript                            |
| ----------------- | -------------------------------------------------------- | ------------------------------------- | ----------------------------------------------- |
| Clean / Hexagonal | Plantillas de Clean Architecture con proyectos separados | Paquetes por capa, Spring con puertos | Carpetas por capa en cada módulo                |
| Monolito modular  | Proyectos por módulo en una solución                     | Spring Modulith (verifica módulos)    | Módulos con `index.ts` + reglas de dependencias |
| Verificación      | NetArchTest, ArchUnitNET                                 | ArchUnit                              | dependency-cruiser, tests propios               |
| Microservicios    | ASP.NET + .NET Aspire, Dapr                              | Spring Cloud                          | Fastify/NestJS + infraestructura de nube        |

En .NET, la separación en **proyectos** hace que el compilador impida dependencias prohibidas. En TypeScript, sin esa
barrera, los límites se verifican con **herramientas o tests de arquitectura**, como hace esta plataforma.

## Errores frecuentes

- **El dominio dependiendo del ORM** o de tipos del framework.
- **Hexagonal en un CRUD trivial**, con puertos y adaptadores sin propósito.
- **Monolito "modular" sin límites verificados**, que termina siendo una gran bola de barro.
- **Microservicios con base de datos compartida.**
- **Partir en microservicios antes de entender los límites del dominio.**
- **Reescrituras completas** en lugar de migraciones incrementales.
