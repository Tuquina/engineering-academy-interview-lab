## ¿Qué problema resuelve?

Una plataforma de cobranzas reacciona a eventos todo el tiempo: llega un pago, vence una promesa, el deudor responde,
un proveedor de mensajería confirma la entrega. Varios módulos tienen que enterarse (detener recordatorios, actualizar
el agente, recalcular métricas, notificar al cliente) sin que el que registra el pago los conozca a todos. Y cuando
algo falla (un proveedor caído, un consumidor con un bug), el resto del sistema tiene que seguir funcionando. Los
patrones de esta lección resuelven esos problemas.

## Arquitectura orientada a eventos

| Concepto    | Qué es                                     | Ejemplo           | Quién decide                       |
| ----------- | ------------------------------------------ | ----------------- | ---------------------------------- |
| **Evento**  | Algo que **ocurrió**, en pasado, inmutable | `PaymentReceived` | Los consumidores deciden qué hacer |
| **Comando** | Un pedido de que algo **ocurra**           | `SendReminder`    | El emisor espera un efecto         |

Ventajas: **bajo acoplamiento** (pagos no conoce a sus consumidores), extensibilidad (un consumidor nuevo no toca al
productor), absorción de picos (la cola amortigua). Costos: **consistencia eventual** (durante un instante, analítica
no refleja el pago), flujos más difíciles de seguir (hacen falta trazas y correlation IDs) y la necesidad de diseñar
para duplicados y desorden.

## Event sourcing

En lugar de guardar el **estado actual**, se guarda la **secuencia de eventos**, y el estado se **deriva** de ellos:

```text
DebtCreated(amount: 150.000)
PaymentPromiseRegistered(date: 2026-11-27, amount: 40.000)
PaymentReceived(amount: 40.000)
DiscountApplied(percent: 10)
→ estado actual: saldo 99.000, sin promesa vigente
```

| Ventajas                                          | Costos                                                           |
| ------------------------------------------------- | ---------------------------------------------------------------- |
| Auditoría completa por diseño (ideal en finanzas) | Modelo mental y herramientas más complejos                       |
| Reconstruir el estado a cualquier fecha           | Evolucionar el esquema de eventos viejos (versionado, upcasting) |
| Nuevas proyecciones a partir de la historia       | Consultas requieren proyecciones (CQRS casi siempre)             |

Es potente para dominios donde **la historia es el negocio** (cuentas, deudas, acuerdos), pero es una decisión costosa
de revertir. Una alternativa más liviana: estado actual en tablas **más** una tabla de eventos de auditoría.

## CQRS

**CQRS** (_Command Query Responsibility Segregation_) separa el **modelo de escritura** (que protege invariantes) del
**modelo de lectura** (optimizado para consultas):

Vale la pena cuando lecturas y escrituras tienen necesidades **muy distintas** (dashboards sobre millones de
conversaciones frente a escrituras con reglas complejas). En muchos sistemas, una versión liviana alcanza: consultas de
lectura directas con SQL optimizado o vistas materializadas, sin un segundo modelo completo. La Pattern Library tiene
el patrón [CQRS](/patterns/cqrs).

## Sagas: procesos de varios pasos

Cuando un proceso abarca varios servicios o módulos con sus propias transacciones, no hay rollback global. Una
**saga** es una secuencia de transacciones locales con **compensaciones**:

<MermaidDiagram
  caption="Saga orquestada para formalizar un acuerdo de pago, con compensaciones si un paso falla."
  chart={`
sequenceDiagram
  participant O as Orquestador
  participant P as Planes de pago
  participant L as Links de pago
  participant N as Notificaciones
  O->>P: reservar plan de 6 cuotas
  P-->>O: plan reservado
  O->>L: generar link de la primera cuota
  L-->>O: error del proveedor
  O->>P: compensar: liberar plan
  P-->>O: plan liberado
  O->>N: avisar al deudor que se reintentará
`}
/>

| Estilo            | Cómo                                                | Cuándo                                         |
| ----------------- | --------------------------------------------------- | ---------------------------------------------- |
| **Orquestada**    | Un coordinador indica a cada participante qué hacer | Procesos con muchos pasos y lógica de decisión |
| **Coreografiada** | Cada participante reacciona a eventos de los demás  | Pocos pasos, alta independencia                |

Las compensaciones son **acciones de negocio** (liberar, anular, reembolsar), no un "deshacer" técnico. Ver
[Saga](/patterns/saga) en la Pattern Library.

## Entrega confiable: outbox, inbox y DLQ

| Patrón                          | Problema                                                | Solución                                                                            |
| ------------------------------- | ------------------------------------------------------- | ----------------------------------------------------------------------------------- |
| **Transactional Outbox**        | Guardar y publicar son dos escrituras: una puede fallar | Guardar el evento en la misma transacción y publicarlo con un relay                 |
| **Inbox / Idempotent Consumer** | El mismo mensaje llega más de una vez                   | Registrar los IDs procesados (con constraint) en la misma transacción que el efecto |
| **Dead Letter Queue**           | Un mensaje falla siempre (bug, datos inválidos)         | Tras N intentos, moverlo a una cola aparte para revisión y reprocesamiento          |

```ts
/** Consumidor idempotente: el efecto y el registro del mensaje van en la misma transacción. */
export async function handlePaymentReceived(message: PaymentReceivedMessage): Promise<void> {
  await inTransaction(pool, async (client) => {
    const fresh = await client.query(
      "INSERT INTO processed_messages (consumer, message_id) VALUES ('reminders', $1) ON CONFLICT DO NOTHING",
      [message.id],
    );
    if (fresh.rowCount === 0) return; // ya procesado: ignorar el duplicado
    await client.query(
      "UPDATE reminders SET status = 'cancelled' WHERE debt_id = $1 AND status = 'scheduled'",
      [message.debtId],
    );
  });
}
```

Un mensaje en la DLQ no es "basura": es un incidente a investigar. Hace falta alerta, una forma de inspeccionarlo y un
mecanismo para reprocesarlo una vez corregido el problema.

## Resiliencia: circuit breaker, retry y bulkhead

| Patrón                         | Qué hace                                                                                                      |
| ------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| **Timeout**                    | Ninguna llamada espera indefinidamente.                                                                       |
| **Retry con backoff y jitter** | Reintenta errores transitorios sin sincronizar a los clientes.                                                |
| **Circuit breaker**            | Tras muchas fallas, deja de llamar (abierto); prueba de a poco (semiabierto); vuelve a cerrar si se recupera. |
| **Bulkhead**                   | Aísla recursos (pools, colas, concurrencia) por dependencia o tenant: una falla no consume todo.              |
| **Fallback**                   | Respuesta degradada planificada: valor en caché, mensaje seguro, escalar a humano.                            |
| **Rate limiting**              | Protege recursos propios y respeta los límites de terceros.                                                   |

  Abierto --> SemiAbierto: pasa el tiempo de espera

Un ejemplo de bulkhead en cobranzas: cada tenant tiene un límite de conversaciones concurrentes con el LLM, para que
la campaña masiva de un cliente no deje sin capacidad a los demás (el problema del _noisy neighbor_). Los simuladores
de [Circuit breaker](/system-design/simulators/circuit-breaker) y
[Retry y backoff](/system-design/simulators/retry-backoff) muestran estos comportamientos.

## Caché: cache aside y write through

- **Cache aside:** la aplicación lee de la caché y, si falta, de la base, y la guarda (curso de Redis).
- **Write through:** cada escritura actualiza la base y la caché en el mismo paso; las lecturas siempre encuentran el
  dato, a costa de escrituras más lentas y caché llena de datos que quizá nadie lee.
- **Write behind:** se escribe en la caché y se persiste después de forma asíncrona; rápido pero con riesgo de pérdida.

## API Gateway y Backend for Frontend

- **API Gateway:** un punto de entrada que centraliza preocupaciones de borde (autenticación, rate limiting, ruteo,
  TLS, logging) delante de uno o varios servicios.
- **Backend for Frontend (BFF):** un backend específico para cada tipo de cliente (panel web, app móvil, integración de
  clientes) que adapta y agrega datos a lo que ese cliente necesita. En una aplicación Next.js, los Server Components y
  Route Handlers suelen cumplir el rol de BFF del panel web.

## Errores frecuentes

- **Eventos que son comandos encubiertos** ("NotificationShouldBeSent").
- **Event sourcing o CQRS completos** sin un problema que los justifique.
- **Sagas sin compensaciones** o compensaciones que no son idempotentes.
- **Publicar eventos fuera de la transacción** y consumidores no idempotentes.
- **DLQ sin alertas** ni proceso de reprocesamiento.
- **Reintentos sin circuit breaker** que agravan la caída de un proveedor.
- **Recursos compartidos sin bulkhead**: un tenant o una dependencia lenta consume todo.
