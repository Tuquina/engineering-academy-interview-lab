## ¿Qué problema resuelve?

En un SaaS, el proveedor de pagos avisa con un webhook cada vez que se cobra la renovación de una suscripción. Ese
webhook es la única fuente que extiende el plan y detiene los avisos de pago pendiente. Si se pierde, el sistema
bloquea a un cliente que ya pagó. Si se procesa dos veces, el plan se extiende dos períodos. Y el proveedor **va a reintentar** cada vez que tu endpoint tarde demasiado o
devuelva un error, así que los duplicados no son una rareza: son el caso normal.

El mismo problema existe en la otra dirección: cuando tu frontend o un agente llama `POST /payments` y la conexión
se corta antes de la respuesta, ¿se cobró o no? ¿Es seguro reintentar?

## Garantías de entrega: al menos una vez

Casi todos los sistemas de webhooks y colas ofrecen entrega **al menos una vez** (_at-least-once_): un evento puede
llegar más de una vez, y no necesariamente en orden. "Exactamente una vez" de punta a punta no se puede garantizar
a través de una red; lo que sí se puede es **procesamiento efectivamente una vez**, combinando reintentos con un
receptor **idempotente**.

## Verificar la firma

Cualquiera puede hacer un POST a tu endpoint público. El proveedor firma cada webhook con un secreto compartido
(HMAC), normalmente sobre `timestamp + "." + body`:

```ts
import { createHmac, timingSafeEqual } from "node:crypto";

const TOLERANCE_SECONDS = 300;

/** Verifica la firma HMAC-SHA256 del webhook y rechaza eventos viejos (replay). */
export function verifyWebhookSignature(
  rawBody: string,
  signatureHeader: string,
  timestamp: string,
  secret: string,
): boolean {
  const age = Math.abs(Date.now() / 1000 - Number(timestamp));
  if (!Number.isFinite(age) || age > TOLERANCE_SECONDS) return false;

  const expected = createHmac("sha256", secret).update(`${timestamp}.${rawBody}`).digest();
  const received = Buffer.from(signatureHeader, "hex");
  return received.length === expected.length && timingSafeEqual(received, expected);
}
```

Tres detalles que se preguntan en entrevistas:

1. **Body crudo:** la firma se calcula sobre los bytes exactos recibidos. Si primero parseás el JSON y lo volvés a
   serializar, cambian espacios u orden y la firma no coincide. Hay que leer el body como texto antes de parsearlo.
2. **Comparación de tiempo constante:** `===` termina en el primer carácter distinto; midiendo tiempos, un atacante
   puede adivinar la firma byte a byte. `timingSafeEqual` tarda siempre lo mismo.
3. **Timestamp:** sin él, alguien que capturó un webhook válido puede reenviarlo (_replay_) indefinidamente.

## Responder rápido, procesar después

Los proveedores esperan la respuesta pocos segundos. Si tu endpoint aplica el pago, recalcula el scoring y envía un
email antes de responder, cualquier lentitud dispara reintentos y duplica trabajo.

```ts
export async function POST(request: Request): Promise<Response> {
  const rawBody = await request.text();
  const valid = verifyWebhookSignature(
    rawBody,
    request.headers.get("x-signature") ?? "",
    request.headers.get("x-timestamp") ?? "",
    env.PAYMENTS_WEBHOOK_SECRET,
  );
  if (!valid) return problem(401, "invalid_signature");

  const event = PaymentEventSchema.parse(JSON.parse(rawBody));

  // INSERT ... ON CONFLICT (provider_event_id) DO NOTHING: deduplica de forma atómica
  await webhookEvents.saveIfNew({
    providerEventId: event.id,
    type: event.type,
    payload: event,
    status: "pending",
  });

  return new Response(null, { status: 200 }); // el worker lo procesa después
}
```

Un worker toma los eventos `pending`, los procesa dentro de una transacción y los marca `processed`. Si falla, el
evento queda para un reintento posterior; si falla muchas veces, va a una cola de errores (_dead letter_) para
revisión. El procesamiento también debe ser idempotente: "aplicar el pago `pay_9`" debe chequear si ese pago ya se
aplicó.

<Callout type="warning" title="Orden de llegada">
  Un `payment.refunded` puede llegar antes que el `payment.succeeded` correspondiente. No asumas orden: usá el
  timestamp o la versión del evento, o consultá el estado actual al proveedor antes de actuar.
</Callout>

Practicá este diseño en el challenge [Webhook idempotente](/challenges/idempotent-webhook) y en el desafío de
arquitectura [Webhooks confiables](/system-design/challenges/reliable-webhooks).

## Idempotency-Key para tus propios POST

Para operaciones que no deben duplicarse (cobrar, enviar un mensaje, crear una reserva), el cliente envía
una clave única por **operación lógica**. Si reintenta, envía **la misma clave**:

```text
POST /bookings
Idempotency-Key: 6f1c2a9e-8b7d-4c1e-9f3a-2d5e7b8c9a01
```

```ts
export async function withIdempotency(
  key: string,
  requestHash: string,
  execute: () => Promise<StoredResponse>,
): Promise<StoredResponse> {
  const reserved = await idempotencyStore.reserve(key, requestHash); // INSERT ... ON CONFLICT DO NOTHING
  if (!reserved) {
    const existing = await idempotencyStore.get(key);
    if (existing?.requestHash !== requestHash)
      return { status: 422, body: { error: "idempotency_key_reused" } };
    if (existing.status === "in_progress") return { status: 409, body: { error: "request_in_progress" } };
    return existing.response!; // mismo resultado que la primera vez, sin repetir el efecto
  }
  const response = await execute();
  await idempotencyStore.complete(key, response);
  return response;
}
```

Las claves expiran (por ejemplo, a las 24 horas) y se asocian al usuario o tenant para que nadie pueda leer la
respuesta de otro usando su clave.

## Rate limiting

Limitar cuántas requests acepta la API protege contra abuso, picos y clientes defectuosos, y protege a las
**dependencias** (la base, el proveedor de LLM con su propia cuota).

| Algoritmo          | Idea                                                        | Comportamiento                              |
| ------------------ | ----------------------------------------------------------- | ------------------------------------------- |
| Ventana fija       | Contador por ventana de N segundos                          | Simple; permite hasta el doble en el borde  |
| Ventana deslizante | Cuenta en los últimos N segundos (log o contador ponderado) | Más precisa                                 |
| Token bucket       | Fichas que se recargan a tasa constante, hasta un máximo    | Permite ráfagas cortas y una tasa sostenida |
| Leaky bucket       | Cola que se vacía a tasa constante                          | Suaviza el tráfico de salida                |

El simulador [Rate limiting](/system-design/simulators/rate-limiting) muestra la ráfaga en el borde de la ventana
fija frente a la deslizante.

Decisiones prácticas:

- **Clave del límite:** por usuario, por tenant, por IP, por API key, o por endpoint sensible (login, envío de SMS).
- **Estado compartido:** con varias réplicas, un contador en memoria limita por réplica, no globalmente. Se usa
  Redis con operaciones atómicas (curso de Redis).
- **Respuesta:** `429 Too Many Requests` con `Retry-After`, y opcionalmente cabeceras `RateLimit-*` que informan
  el límite y lo que queda.
- **Hacia afuera también:** si el proveedor de SMS acepta 100 requests por segundo, tu cliente necesita un limitador
  de salida, no sólo reintentos.

## Timeouts coherentes

Toda llamada a una dependencia necesita un timeout, y los timeouts deben formar un **presupuesto** coherente:

```text
Cliente → API: 30 s
  API → LLM: 20 s
  API → base de datos: 2 s por consulta
  API → proveedor de SMS: 5 s
```

Si la API espera al LLM 60 segundos pero el balanceador corta a los 30, el cliente recibe un error mientras la API
sigue trabajando para nadie. Regla: **los timeouts internos son menores que los externos**, y la cancelación se
propaga (con `AbortSignal`, lección de control de la asincronía).

## Errores frecuentes

- **Verificar la firma sobre el JSON re-serializado** en lugar del body crudo.
- **Comparar firmas con `===`.**
- **Procesar todo antes de responder** al webhook.
- **Deduplicar con un `SELECT` previo** en lugar de una constraint única: dos requests concurrentes pasan ambas el
  chequeo.
- **Asumir orden** entre eventos.
- **Idempotency-Key sin reserva atómica**, o sin validar que el body sea el mismo.
- **Rate limiting en memoria con varias réplicas.**
- **Llamadas salientes sin timeout.**
