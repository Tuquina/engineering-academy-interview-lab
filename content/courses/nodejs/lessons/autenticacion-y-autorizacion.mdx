## ¿Qué problema resuelve?

Una plataforma de historias clínicas maneja datos de salud de miles de pacientes, para varias clínicas clientes
(tenants). Un solo error de autorización (un endpoint que devuelve la historia de `pat_123` sin chequear a qué
clínica pertenece) es una filtración de datos. La lista de riesgos de seguridad de APIs de OWASP pone ese error en
el **primer lugar**: _Broken Object Level Authorization_.

Esta lección cubre los conceptos que se esperan de un backend senior: cómo se establece la identidad, cómo se
decide qué puede hacer cada uno y cómo se aíslan los datos entre clientes.

## Autenticación y autorización

| Concepto          | Pregunta           | Falla típica                            | Status                          |
| ----------------- | ------------------ | --------------------------------------- | ------------------------------- |
| **Autenticación** | ¿Quién sos?        | Token ausente, vencido o inválido       | `401`                           |
| **Autorización**  | ¿Podés hacer esto? | Sin permiso para la acción o el recurso | `403` (o `404` para no revelar) |

| Aspecto    | Sesión con cookie                    | Token (JWT)                                                  |
| ---------- | ------------------------------------ | ------------------------------------------------------------ |
| Estado     | En el servidor (Redis, base)         | En el token, firmado                                         |
| Revocación | Inmediata: se borra la sesión        | Difícil: vale hasta que expira                               |
| Escalado   | Requiere un almacén compartido       | Cualquier instancia verifica con la clave                    |
| Uso típico | Aplicaciones web propias (navegador) | APIs entre servicios, apps móviles, terceros                 |
| Riesgos    | CSRF (mitigado con SameSite)         | Robo de token, almacenamiento en localStorage expuesto a XSS |

Para una aplicación web propia, las **sesiones con cookies `HttpOnly`, `Secure` y `SameSite`** siguen siendo la
opción más segura y simple. Los tokens brillan entre servicios y con clientes que no son navegadores.

## JWT por dentro

Un JWT tiene tres partes en base64url separadas por puntos: `header.payload.signature`.

```json
{ "alg": "RS256", "typ": "JWT", "kid": "2026-11" }
```

```json
{
  "sub": "usr_42",
  "tenant_id": "tnt_clinica_norte",
  "roles": ["physician"],
  "iss": "https://auth.example.com",
  "aud": "clinical-records-api",
  "exp": 1795070000
}
```

La firma garantiza que nadie modificó el contenido, **pero el payload no está cifrado**: cualquiera puede leerlo.

```ts
import { createRemoteJWKSet, jwtVerify } from "jose";

const jwks = createRemoteJWKSet(new URL("https://auth.example.com/.well-known/jwks.json"));

export async function authenticate(request: Request): Promise<AuthenticatedUser | null> {
  const header = request.headers.get("authorization");
  if (!header?.startsWith("Bearer ")) return null;
  try {
    const { payload } = await jwtVerify(header.slice(7), jwks, {
      issuer: "https://auth.example.com",
      audience: "clinical-records-api",
      algorithms: ["RS256"], // nunca aceptar el algoritmo que diga el token
    });
    return AuthenticatedUserSchema.parse(payload); // los claims también son datos externos
  } catch {
    return null;
  }
}
```

Reglas para JWT:

- **Validar todo:** firma, algoritmo esperado, `exp`, `iss` y `aud`. Una librería mantenida (`jose`) lo hace bien.
- **Access tokens cortos** (minutos) y **refresh tokens** para renovarlos; los refresh tokens se guardan del lado
  del servidor y se pueden revocar.
- **Nada sensible en el payload.**
- **Firmas asimétricas** (RS256, ES256) cuando muchos servicios verifican: sólo el emisor tiene la clave privada.

## OAuth 2.0 y OpenID Connect

- **OAuth 2.0** es un protocolo de **autorización delegada**: una aplicación obtiene un _access token_ para actuar
  sobre recursos de un usuario sin conocer su contraseña.
- **OpenID Connect (OIDC)** agrega **identidad** encima de OAuth: un _ID token_ que dice quién es el usuario. Es lo
  que usás al "iniciar sesión con Google" o con el proveedor corporativo.

| Flujo                     | Cuándo                                                          |
| ------------------------- | --------------------------------------------------------------- |
| Authorization Code + PKCE | Usuarios humanos en apps web, SPA y móviles                     |
| Client Credentials        | Servicio a servicio, sin usuario (un worker que llama a la API) |
| Device Code               | Dispositivos sin teclado                                        |

Los flujos _implicit_ y _password_ están desaconsejados. En la práctica, la autenticación de usuarios se delega a
un proveedor de identidad (Auth0, Entra ID, Keycloak, Cognito, Clerk) y la API **sólo verifica tokens**.

## Contraseñas

Si el sistema guarda contraseñas propias, se guardan con un **hash lento, con sal**, diseñado para eso:

```ts
import { hash, verify } from "@node-rs/argon2";

const passwordHash = await hash(password); // argon2id, con sal aleatoria incluida en el resultado
const valid = await verify(passwordHash, attempt);
```

- **Sí:** argon2id (recomendado por OWASP), scrypt, bcrypt.
- **No:** SHA-256 o MD5 directos (demasiado rápidos: permiten miles de millones de intentos por segundo con GPU),
  ni cifrado reversible.
- Comparar secretos (tokens, firmas) con **comparación de tiempo constante** (`crypto.timingSafeEqual`).

## Autorización

### Por rol (RBAC) y por atributos (ABAC)

```ts
const PERMISSIONS = {
  admin: ["clinic:configure", "appointment:create", "appointment:cancel", "record:read", "record:write"],
  physician: ["appointment:create", "record:read", "record:write"],
  receptionist: ["appointment:create", "appointment:cancel"],
} as const satisfies Record<Role, readonly Permission[]>;

export function can(user: AuthenticatedUser, permission: Permission): boolean {
  return user.roles.some((role) => (PERMISSIONS[role] as readonly Permission[]).includes(permission));
}
```

RBAC responde "¿este rol puede hacer esta acción?". Muchas reglas reales dependen además de **atributos**: "un
médico sólo ve la historia clínica de los pacientes que atiende", "recepción puede cancelar turnos sólo con más de 24
horas de anticipación". Eso es ABAC, y
esas reglas viven en el **dominio o el caso de uso**, no en el middleware.

### Por recurso: el error número uno

```ts
// ❌ BOLA / IDOR: cualquier usuario autenticado puede leer cualquier historia clínica cambiando el ID
export async function GET(request: Request, { params }: { params: Promise<{ patientId: string }> }) {
  const user = await authenticate(request);
  if (!user) return problem(401, "unauthenticated");
  const patient = await patients.findById((await params).patientId);
  return Response.json(patient);
}

// ✅ La consulta incluye el tenant de la identidad: un recurso de otro tenant "no existe"
const patient = await patients.findById(user.tenantId, (await params).patientId);
if (!patient) return problem(404, "patient_not_found");
```

## Aislamiento multi-tenant

- El **tenant se deriva de la identidad**. Un header `X-Tenant-Id` que manda el cliente es un pedido, no un hecho:
  sólo se acepta si el usuario pertenece a ese tenant.
- Los repositorios **exigen** el tenant en su firma, así es imposible olvidarlo.
- **Row Level Security** de PostgreSQL agrega una barrera en la base (curso de PostgreSQL).
- Los logs, cachés y colas también llevan el tenant: una clave de caché sin tenant puede mezclar datos.

## Defensas básicas de una API

| Riesgo                               | Defensa                                                 |
| ------------------------------------ | ------------------------------------------------------- |
| Secretos en el repositorio           | Variables de entorno o un gestor de secretos; rotación  |
| Inyección (SQL, comandos)            | Consultas parametrizadas, nunca concatenar input        |
| Datos excesivos en respuestas        | DTOs explícitos; nunca serializar la entidad completa   |
| Mass assignment                      | Esquemas que aceptan sólo los campos permitidos         |
| Abuso y fuerza bruta                 | Rate limiting por usuario, IP y endpoint sensible       |
| CORS demasiado abierto               | Lista explícita de orígenes; nunca `*` con credenciales |
| CSRF con cookies                     | `SameSite=Lax/Strict` y tokens anti-CSRF en formularios |
| SSRF (URLs provistas por el usuario) | Lista de destinos permitidos para webhooks y descargas  |
| Dependencias vulnerables             | Lockfile, auditoría y actualizaciones regulares         |

## Comparación con C# y Java

| Concepto            | ASP.NET Core                         | Spring Boot                           | Node.js                                         |
| ------------------- | ------------------------------------ | ------------------------------------- | ----------------------------------------------- |
| Autenticación       | `AddAuthentication().AddJwtBearer()` | Spring Security + Resource Server     | Middleware propio con `jose`, Passport, Auth.js |
| Autorización        | Policies, `[Authorize(Roles = ...)]` | `@PreAuthorize`, method security      | Funciones `can()`, chequeos en casos de uso     |
| Hash de contraseñas | `PasswordHasher` (PBKDF2)            | `BCryptPasswordEncoder`, Argon2       | argon2, bcrypt, `crypto.scrypt`                 |
| Identidad           | ASP.NET Identity, Entra ID           | Spring Authorization Server, Keycloak | Proveedor externo + verificación de tokens      |

En .NET y Spring la seguridad viene integrada y configurada por convención. En Node.js se arma con piezas, lo que
da flexibilidad y también más formas de equivocarse: conviene usar librerías mantenidas y no implementar
criptografía propia.

## Errores frecuentes

- **Chequear permisos sólo en el frontend.** Cualquiera puede llamar a la API directamente.
- **Tomar el tenant o el userId del body.** La identidad sale del token o la sesión.
- **Aceptar el `alg` del token** o no validar `aud` e `iss`.
- **Guardar tokens en `localStorage`** en aplicaciones expuestas a XSS.
- **Hashear contraseñas con SHA-256.**
- **Responder 403 a recursos de otro tenant**, revelando que existen; 404 es más seguro.
- **Loguear tokens, contraseñas o datos personales completos.**
