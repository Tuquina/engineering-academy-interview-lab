## ¿Qué problema resuelve?

Soporte reporta: "a algunos clientes les llegaron dos SMS de 'tu pedido está en camino' ayer a la tarde". Para
responder hace falta saber qué eventos de tracking llegaron del transportista, qué decidió el servicio de
notificaciones, qué devolvió el proveedor de SMS y en qué orden. Si los logs son líneas sueltas como
`console.log("enviado")`, sin cliente, sin envío y sin forma de unir los pasos de
una misma request, la investigación es imposible.

La **observabilidad** es la capacidad de responder preguntas sobre el sistema en producción sin desplegar código
nuevo. Y los **tests de integración** son la forma de detectar antes de producción los errores que los tests
unitarios con mocks no pueden ver.

## Logging estructurado

Un log estructurado es un **objeto JSON** con campos consistentes, no un string. Se puede filtrar, agregar y
buscar:

```ts
import pino from "pino";

export const logger = pino({
  level: env.LOG_LEVEL, // "info" en producción, "debug" en desarrollo
  redact: ["req.headers.authorization", "*.phone", "*.email", "*.documentNumber"], // datos sensibles
});

logger.info(
  { shipmentId, customerId, channel: "sms", providerMessageId, durationMs: 182 },
  "shipment_notification_sent", // mensaje corto y estable: un nombre de evento, no una frase con datos interpolados
);
```

```json
{
  "level": 30,
  "time": 1795070000000,
  "requestId": "9f2c...",
  "tenantId": "tnt_acme",
  "shipmentId": "shp_7",
  "customerId": "cus_42",
  "channel": "sms",
  "durationMs": 182,
  "msg": "shipment_notification_sent"
}
```

| Nivel   | Cuándo                                                                          |
| ------- | ------------------------------------------------------------------------------- |
| `error` | Algo falló y requiere atención (un evento no se pudo procesar tras reintentos). |
| `warn`  | Situación anómala pero manejada (reintento, degradación, input sospechoso).     |
| `info`  | Eventos de negocio relevantes (envío despachado, pago aplicado).                |
| `debug` | Detalle para desarrollo; apagado en producción.                                 |

Reglas: **nunca loguear secretos ni datos personales completos** (tokens, contraseñas, teléfonos, documentos); los
mensajes son **nombres de eventos estables**; los datos van en campos; y los errores se loguean con su stack y
`cause`.

## Correlation IDs con AsyncLocalStorage

Para unir todos los logs de una request hace falta un **ID común**. Pasarlo como parámetro a cada función es
inviable. `AsyncLocalStorage` guarda un contexto que **sobrevive a través de los `await`** de la misma ejecución,
similar a `AsyncLocal<T>` en .NET o al MDC de los loggers de Java:

```ts
import { AsyncLocalStorage } from "node:async_hooks";
import { randomUUID } from "node:crypto";

interface RequestContext {
  requestId: string;
  tenantId?: string;
}

export const requestContext = new AsyncLocalStorage<RequestContext>();

/** Middleware: crea el contexto al inicio de cada request. */
export function withRequestContext(handler: (request: Request) => Promise<Response>) {
  return (request: Request) => {
    const requestId = request.headers.get("x-request-id") ?? randomUUID();
    return requestContext.run({ requestId }, () => handler(request));
  };
}

/** Logger que agrega el contexto automáticamente a cada línea. */
export const log = () => logger.child(requestContext.getStore() ?? {});
```

```ts
// En cualquier capa, sin recibir el ID por parámetro:
log().info({ orderId }, "payment_applied");
```

El ID también se propaga **hacia afuera**: en el header de las llamadas a otros servicios y en los metadatos de los
mensajes de colas, para que el worker que procesa el evento loguee con el mismo ID.

| Señal    | Qué es                                        | Pregunta que responde                      | Costo            |
| -------- | --------------------------------------------- | ------------------------------------------ | ---------------- |
| Métricas | Números agregados en el tiempo                | ¿Está sano el sistema? ¿Empeoró?           | Bajo             |
| Trazas   | Árbol de spans de una request entre servicios | ¿Dónde se fue el tiempo? ¿Qué tramo falló? | Medio (muestreo) |

### Métricas que importan

Para cada servicio, el método **RED**: **R**ate (requests por segundo), **E**rrors (tasa de errores) y **D**uration
(latencia en percentiles: p50, p95, p99; nunca sólo el promedio, que esconde la cola). Para recursos (CPU, memoria,
pool de conexiones, event loop lag), el método USE: utilización, saturación y errores. Y **métricas de negocio**:
notificaciones enviadas por canal, pedidos confirmados por minuto, costo de tokens de LLM por tenant.

**Se alerta sobre síntomas** que afectan a usuarios (latencia p95 por encima del objetivo, tasa de errores) y no
sobre cada causa posible (CPU al 80 %), que generan ruido.

### Trazas distribuidas con OpenTelemetry

Una **traza** es el recorrido de una request: un árbol de **spans** (tramos con inicio, duración y atributos).
**OpenTelemetry** es el estándar abierto para generar logs, métricas y trazas, independiente del proveedor
(Datadog, Grafana, Honeycomb, New Relic...). Su instrumentación automática para Node.js crea spans para HTTP, `pg`,
Redis y otras librerías sin tocar el código:

```ts
import { trace } from "@opentelemetry/api";

const tracer = trace.getTracer("shipping-api");

export async function syncCarrierEvents(shipmentId: string) {
  return tracer.startActiveSpan("shipment.sync_carrier_events", async (span) => {
    span.setAttribute("shipment.id", shipmentId);
    try {
      return await fetchAndApplyEvents(shipmentId); // los spans de HTTP y DB quedan como hijos
    } catch (error) {
      span.recordException(error as Error);
      throw error;
    } finally {
      span.end();
    }
  });
}
```

El contexto viaja entre servicios en el header estándar `traceparent` (W3C Trace Context), así una traza puede
cruzar la API, la cola y el worker.

## Testing de integración

Un test unitario con un repositorio falso no puede detectar un SQL inválido, una constraint que falta, un índice
único que no existe o un comportamiento distinto bajo concurrencia. Para eso están los **tests de integración**:
prueban los adaptadores contra **la dependencia real**.

```ts
import { afterAll, beforeAll, beforeEach, describe, expect, it } from "vitest";
import { PostgreSqlContainer, type StartedPostgreSqlContainer } from "@testcontainers/postgresql";

describe("PostgresWebhookEventStore", () => {
  let container: StartedPostgreSqlContainer;
  let store: PostgresWebhookEventStore;

  beforeAll(async () => {
    container = await new PostgreSqlContainer("postgres:17-alpine").start(); // base real y desechable
    const db = await connectAndMigrate(container.getConnectionUri());
    store = new PostgresWebhookEventStore(db);
  }, 60_000);

  afterAll(() => container.stop());
  beforeEach(() => store.truncateForTests());

  it("ignora un evento duplicado aunque lleguen dos a la vez", async () => {
    const event = { providerEventId: "evt_1", type: "payment.succeeded", payload: {} };
    const results = await Promise.all([store.saveIfNew(event), store.saveIfNew(event)]);
    expect(results.filter(Boolean)).toHaveLength(1); // sólo uno se insertó: la constraint funciona
  });
});
```

Opciones para la dependencia real:

- **Testcontainers:** levanta contenedores desechables (PostgreSQL, Redis) desde el test.
- **Motores embebidos:** este proyecto usa **PGlite** (PostgreSQL compilado a WebAssembly) en su SQL Lab, útil
  también para tests rápidos.
- **Base compartida de CI** con un esquema por ejecución.

<Callout type="tip" title="Qué cubrir con cada tipo de test">
  Unitarios: reglas de dominio y casos de uso con fakes (muchos y rápidos). Integración: cada adaptador contra
  su dependencia real y los handlers HTTP con su validación (algunos). End-to-end: los flujos críticos
  completos (pocos).
</Callout>

## Comparación con C# y Java

| Concepto             | .NET                                     | Java                               | Node.js                          |
| -------------------- | ---------------------------------------- | ---------------------------------- | -------------------------------- |
| Logging estructurado | `ILogger` + Serilog                      | SLF4J + Logback (JSON encoder)     | Pino, Winston                    |
| Contexto por request | `AsyncLocal<T>`, scopes de `ILogger`     | MDC (ThreadLocal), scoped values   | `AsyncLocalStorage`              |
| Telemetría           | OpenTelemetry .NET (`Activity`)          | OpenTelemetry Java agent           | OpenTelemetry JS                 |
| Tests de integración | `WebApplicationFactory` + Testcontainers | `@SpringBootTest` + Testcontainers | Vitest + Testcontainers / PGlite |

## Errores frecuentes

- **`console.log` con strings interpolados** en lugar de logs estructurados.
- **Loguear datos personales o tokens.** Los logs se copian a muchos sistemas y personas.
- **Sin correlation ID**: imposible seguir una request entre logs.
- **Mirar sólo el promedio de latencia.** El p99 es lo que sufren los usuarios más afectados.
- **Alertar sobre todo**: las alertas que nadie atiende entrenan a ignorarlas.
- **Mockear la base en todos los tests**: los errores de SQL y de constraints llegan a producción.
