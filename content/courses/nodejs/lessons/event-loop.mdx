## ¿Qué problema resuelve?

Un endpoint de la API de cobranzas genera un reporte de deudas y, para "proteger" los datos, firma el archivo derivando
una clave con `crypto.pbkdf2Sync` con 600.000 iteraciones. En las pruebas tarda unos 300 ms y nadie se preocupa. En
producción, cuando un operador pide un reporte, **todas** las conversaciones de los agentes se congelan durante esos
300 ms: webhooks, health checks y respuestas al cliente esperan en fila.

No es un problema de ese endpoint: es el modelo de ejecución de Node.js. Entender el event loop permite explicar
por qué pasa, predecir el orden en que corre el código y diseñar servicios que no se degraden así.

## Arquitectura: un hilo de JavaScript y mucha I/O delegada

- **V8** ejecuta JavaScript: compila, gestiona la pila de llamadas (call stack) y la memoria.
- **libuv** implementa el event loop y la I/O asíncrona. Para la red usa los mecanismos del sistema operativo
  (epoll, kqueue, IOCP); para lo que no tiene una API asíncrona nativa (sistema de archivos, `dns.lookup`, zlib,
  partes de crypto) usa un **thread pool** de 4 hilos por defecto (`UV_THREADPOOL_SIZE`).
- **El event loop** toma callbacks listos y los ejecuta de a uno en el hilo de JavaScript.

La consecuencia: **hay concurrencia (miles de operaciones en vuelo) pero no paralelismo de JavaScript**. En cada
instante, como mucho un callback está ejecutando código tuyo.

## Las fases del event loop

<MermaidDiagram
  caption="Cada vuelta del loop recorre las fases en orden. Entre callback y callback se vacían nextTick y las microtasks."
  chart={`

  P --> C[check: callbacks de setImmediate]
  C --> CL[close callbacks: por ejemplo socket.on close]
  CL --> T
  M[[Después de CADA callback: vaciar process.nextTick y luego microtasks]] -.-> T
  M -.-> P
  M -.-> C

/>

| Fase                  | Qué ejecuta                                                                         |
| --------------------- | ----------------------------------------------------------------------------------- |
| **timers**            | Callbacks de `setTimeout` / `setInterval` cuyo tiempo mínimo ya pasó                |
| **pending callbacks** | Algunos callbacks de I/O diferidos (por ejemplo, ciertos errores de TCP)            |
| **poll**              | Espera y procesa eventos de I/O; es donde el proceso pasa la mayor parte del tiempo |
| **check**             | Callbacks de `setImmediate`                                                         |
| **close callbacks**   | Eventos de cierre como `socket.on("close")`                                         |

Fuera de las fases hay dos colas con prioridad: la de **`process.nextTick`** y la de **microtasks** (continuaciones
de promesas y `queueMicrotask`). Desde Node.js 11 ambas se vacían **después de cada callback**, no sólo entre fases.

## Predecir el orden de ejecución

```js
// order.cjs (CommonJS)
console.log("A: síncrono");
setTimeout(() => console.log("B: timeout"), 0);
setImmediate(() => console.log("C: immediate"));
Promise.resolve().then(() => console.log("D: promise"));
process.nextTick(() => console.log("E: nextTick"));
console.log("F: síncrono");
```

Salida:

```text
A: síncrono
F: síncrono
E: nextTick
D: promise
B: timeout      ← B y C pueden invertirse
C: immediate
```

1. Primero termina todo el código síncrono (**A**, **F**).
2. Se vacía la cola de `nextTick` (**E**) y después la de microtasks (**D**).
3. El orden entre **B** y **C** **no está garantizado** en el módulo principal: depende de si, al entrar al loop, ya
   pasó el milisegundo mínimo del timer.

Dentro de un callback de I/O el orden sí es determinista, porque después de la fase poll siempre viene check:

```js
const fs = require("node:fs");
fs.readFile(__filename, () => {
  setTimeout(() => console.log("timeout"), 0);
  setImmediate(() => console.log("immediate")); // siempre primero dentro de un callback de I/O
});
```

<Callout type="info" title="Módulos ES cambian un detalle">
  En un módulo ES (`.mjs` o `"type": "module"`), el código principal ya se evalúa dentro de una microtask. Por
  eso un `Promise.then` agendado ahí puede ejecutarse **antes** que `process.nextTick`. En un servidor real
  esto rara vez importa; en una entrevista, mencionar el matiz suma.
</Callout>

## Ejemplo incorrecto

```ts
// ❌ Trabajo CPU-bound síncrono dentro de un handler HTTP.
import { pbkdf2Sync } from "node:crypto";

export async function POST(request: Request): Promise<Response> {
  const { reportId } = (await request.json()) as { reportId: string };
  const report = await reports.build(reportId);

  // Bloquea el único hilo de JS ~300 ms: ninguna otra request avanza mientras tanto.
  const key = pbkdf2Sync(report.secret, report.salt, 600_000, 32, "sha256");

  return Response.json({ signature: sign(report, key) });
}
```

Además del `as` sin validación (ver la lección de type erasure), el problema central es `pbkdf2Sync`: es CPU-bound y
síncrono. Mientras corre, el event loop no puede ejecutar callbacks: las demás requests esperan, los health checks
pueden fallar y el orquestador puede reiniciar un proceso que en realidad estaba sano.

## Implementación recomendada

```ts
import { pbkdf2 } from "node:crypto";
import { promisify } from "node:util";

const pbkdf2Async = promisify(pbkdf2);

export async function POST(request: Request): Promise<Response> {
  const { reportId } = ReportRequestSchema.parse(await request.json());
  const report = await reports.build(reportId);

  // La versión asíncrona corre en el thread pool de libuv: el event loop sigue atendiendo otras requests.
  const key = await pbkdf2Async(report.secret, report.salt, 600_000, 32, "sha256");

  return Response.json({ signature: sign(report, key) });
}
```

Según el tipo de trabajo:

- **Existe versión asíncrona** (crypto, zlib, fs): usala; corre en el thread pool.
- **Cálculo propio pesado** (parsear un CSV enorme, scoring de miles de deudas): `worker_threads`, o mejor, una cola
  con workers dedicados si el trabajo puede ser asíncrono para el usuario.
- **Trabajo divisible:** procesarlo en lotes cediendo el control entre lotes con `await setImmediate()` de
  `node:timers/promises`.

Y medirlo, porque lo que no se mide se descubre en un incidente:

```ts
import { monitorEventLoopDelay } from "node:perf_hooks";

const histogram = monitorEventLoopDelay({ resolution: 20 });
histogram.enable();

setInterval(() => {
  // Los valores están en nanosegundos.
  logger.info({ p99Ms: histogram.percentile(99) / 1e6, maxMs: histogram.max / 1e6 }, "event loop delay");
  histogram.reset();
}, 10_000).unref(); // unref: este timer no impide que el proceso termine
```

## Casos límite y errores frecuentes

- **Starvation por microtasks.** Una cadena que siempre agenda otra promesa (o un `nextTick` recursivo) nunca deja que
  el loop avance: timers e I/O quedan bloqueados aunque "todo sea asíncrono".
- **`setTimeout(fn, 0)` no es cero.** El mínimo efectivo es 1 ms y el callback corre cuando el loop llega a la fase
  de timers: si el hilo está ocupado, se atrasa. Los timers garantizan un mínimo, no un máximo.
- **Saturación del thread pool.** Con 4 hilos, muchas operaciones simultáneas de fs o crypto hacen cola entre sí;
  `dns.lookup` compite con ellas. Se puede ajustar `UV_THREADPOOL_SIZE`, pero conviene medir primero.
- **`JSON.parse` y `JSON.stringify` grandes** también son CPU-bound y síncronos: un payload de decenas de MB bloquea
  el loop. Limitá el tamaño de los requests.
- **Regex con backtracking catastrófico** (ReDoS): una expresión regular mal escrita sobre un input malicioso puede
  bloquear el proceso durante segundos.
- **En serverless** (como Vercel Functions), cada instancia atiende pocas requests a la vez, pero bloquear igual
  alarga la duración facturada y la latencia.

## Comparación con .NET y Java

| Aspecto                           | Node.js                                  | ASP.NET Core                                     | Spring (servlet clásico)                         |
| --------------------------------- | ---------------------------------------- | ------------------------------------------------ | ------------------------------------------------ |
| Hilos ejecutando tu código        | Uno (más workers si los creás)           | Varios del thread pool, en paralelo              | Uno por request del pool del contenedor          |
| Durante la I/O                    | El hilo queda libre para otros callbacks | Con `async`, el hilo vuelve al pool              | El hilo espera bloqueado (salvo virtual threads) |
| CPU-bound en una request          | Bloquea **todas** las requests           | Ocupa un hilo; las demás siguen en otros núcleos | Ocupa un hilo; las demás siguen                  |
| Condiciones de carrera en memoria | No entre callbacks (un solo hilo)        | Sí: requiere locks o estructuras concurrentes    | Sí: requiere sincronización                      |

Desde Java 21, los **virtual threads** permiten escribir código bloqueante sin ocupar un hilo del sistema operativo
durante la I/O: un objetivo parecido al de Node, con otro modelo de programación.

<Callout type="interview" title="Cómo explicarlo en una entrevista">
  "Node ejecuta JavaScript en un solo hilo y delega la I/O al sistema operativo o al thread pool de libuv, así
  que escala muy bien en I/O pero cualquier cálculo síncrono largo frena a todas las requests. Después de cada
  callback se vacían nextTick y las microtasks, y luego el loop sigue con sus fases: timers, poll, check. Para
  trabajo pesado uso APIs asíncronas, worker threads o una cola, y monitoreo el event loop lag como métrica de
  salud."
</Callout>
