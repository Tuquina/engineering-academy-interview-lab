## ¿Qué problema resuelve?

"La API está lenta" es la queja más común y la peor abordada. La reacción típica es optimizar lo que parece lento
(cambiar `forEach` por `for`, agregar caché a todo, subir el tamaño de la instancia) sin evidencia. A veces mejora
por casualidad; casi siempre agrega complejidad sin resolver la causa.

Esta lección propone un método y repasa las causas reales más frecuentes en servicios Node.js.

## El método: objetivo, medición, hipótesis, cambio

Los objetivos se expresan en **percentiles** (el promedio esconde a los usuarios afectados), **throughput** (requests
por segundo sostenidas) y **tasa de errores** bajo esa carga.

## Load testing

Un load test genera tráfico controlado para ver cómo responde el sistema. Herramientas habituales: **k6** (scripts
en JavaScript), autocannon (benchmarks HTTP simples en Node.js), Gatling o JMeter.

```js
// k6: escenario de carga sobre el listado de deudas
import http from "k6/http";
import { check } from "k6";

export const options = {
  stages: [
    { duration: "1m", target: 100 }, // ramp-up a 100 usuarios virtuales
    { duration: "5m", target: 100 }, // carga sostenida
    { duration: "1m", target: 0 },
  ],
  thresholds: {
    http_req_duration: ["p(95)<300"], // criterio de éxito
    http_req_failed: ["rate<0.001"],
  },
};

export default function () {
  const response = http.get(`${__ENV.BASE_URL}/customers/cus_42/debts`, {
    headers: { authorization: `Bearer ${__ENV.TOKEN}` },
  });
  check(response, { "status 200": (r) => r.status === 200 });
}
```

| Tipo de prueba | Objetivo                                                   |
| -------------- | ---------------------------------------------------------- |
| Load           | Comportamiento con la carga esperada                       |
| Stress         | Dónde y cómo se rompe al superar la capacidad              |
| Spike          | Reacción a picos bruscos (el inicio de una campaña masiva) |
| Soak           | Estabilidad durante horas: fugas de memoria, conexiones    |

Reglas: entorno parecido a producción (mismos límites de CPU y memoria, datos de volumen realista), el generador de
carga en otra máquina, y **observar el sistema durante la prueba** (métricas y trazas), no sólo el resumen final.

## Profiling de CPU y event loop

Si las trazas muestran que el tiempo se va **dentro del proceso** (no esperando I/O), hay que perfilar:

```bash
# Genera un perfil de CPU al terminar el proceso; se abre en Chrome DevTools
node --cpu-prof dist/main.js

# Inspector para perfilar en vivo con Chrome DevTools (no exponer el puerto en producción)
node --inspect=0.0.0.0:9229 dist/main.js
```

Un **flame graph** muestra las funciones por el tiempo de CPU que consumen: las barras anchas son los candidatos.
Causas típicas en backends: serializar o parsear JSON enormes, regex con backtracking catastrófico, validaciones
repetidas dentro de bucles, criptografía síncrona, logging excesivo y transformaciones de grandes colecciones.

El **event loop lag** (lección del event loop) indica que el hilo está ocupado: si sube junto con la latencia, el
problema es CPU en el proceso; si la latencia sube con lag bajo, el problema está en la I/O o en las dependencias.

## Las causas más comunes están en la I/O

### Consultas N+1

```ts
// ❌ 1 consulta para las deudas + 1 por cada deuda para su cliente: 201 consultas para 200 deudas
const debts = await db.query("SELECT * FROM debts WHERE campaign_id = $1", [campaignId]);
for (const debt of debts.rows) {
  debt.customer = (await db.query("SELECT * FROM customers WHERE id = $1", [debt.customer_id])).rows[0];
}

// ✅ Una consulta con JOIN (o dos consultas: deudas y clientes con ANY)
const rows = await db.query(
  `SELECT d.id, d.balance_cents, c.id AS customer_id, c.name
     FROM debts d
     JOIN customers c ON c.id = d.customer_id
    WHERE d.campaign_id = $1`,
  [campaignId],
);
```

Con 2 ms por consulta, la versión N+1 tarda 400 ms y ocupa una conexión todo ese tiempo; la versión con JOIN, unos
pocos milisegundos. En GraphQL o en loaders genéricos, el patrón **DataLoader** agrupa las búsquedas por ID de un
mismo tick en una sola consulta.

### Llamadas secuenciales independientes

```ts
// ❌ 3 llamadas independientes en serie: la latencia se suma
const customer = await customers.get(id);
const debts = await debtsRepo.listByCustomer(id);
const history = await contactHistory.list(id);

// ✅ En paralelo: la latencia es la de la más lenta
const [customer, debts, history] = await Promise.all([
  customers.get(id),
  debtsRepo.listByCustomer(id),
  contactHistory.list(id),
]);
```

### Connection pooling

Abrir una conexión a PostgreSQL cuesta (TCP, TLS, autenticación, un proceso en el servidor). Un **pool** mantiene
conexiones abiertas y las presta:

```ts
import { Pool } from "pg";

export const pool = new Pool({
  connectionString: env.DATABASE_URL,
  max: 10, // conexiones máximas POR RÉPLICA
  idleTimeoutMillis: 30_000,
  connectionTimeoutMillis: 2_000, // fallar rápido si el pool está agotado
});
```

Un pool más grande no siempre es mejor: la base tiene un límite de conexiones y rinde peor con demasiadas
concurrentes. Con muchas réplicas o funciones serverless, un **pooler externo** (PgBouncer, o el pooler del
proveedor) multiplexa muchas conexiones de cliente sobre pocas conexiones reales.

### Caché

Una caché evita repetir trabajo caro, pero agrega un problema: **invalidar**. Antes de cachear, responder:

- ¿Cuánto tiempo puede estar desactualizado el dato? (define el TTL)
- ¿Quién invalida cuando cambia? (escritura que borra la clave, eventos, sólo TTL)
- ¿Cuántas claves distintas hay? (límite de memoria; LRU)
- ¿Qué pasa cuando expira una clave muy pedida? (cache stampede)

| Nivel       | Ejemplo                                     | Cuidado                                       |
| ----------- | ------------------------------------------- | --------------------------------------------- |
| En proceso  | `Map` con LRU para configuración del tenant | Cada réplica tiene su copia; límite de tamaño |
| Distribuida | Redis                                       | Latencia de red; serialización                |
| HTTP        | `Cache-Control`, CDN                        | Datos por usuario no van a cachés compartidas |

El simulador [Cache stampede](/system-design/simulators/cache-stampede) muestra qué pasa cuando muchas requests
encuentran la misma clave expirada a la vez. El curso de Redis profundiza en los patrones.

## Escalabilidad horizontal

Escalar **verticalmente** es usar una máquina más grande; tiene un techo y un proceso Node.js sólo usa un núcleo
para JavaScript. Escalar **horizontalmente** es agregar réplicas detrás de un balanceador, y exige que el servicio
sea **sin estado** (_stateless_):

| Estado en memoria del proceso | Dónde debe vivir para escalar                                  |
| ----------------------------- | -------------------------------------------------------------- |
| Sesiones de usuario           | Redis o la base                                                |
| Rate limiting y locks         | Redis                                                          |
| Trabajos en curso             | Una cola (BullMQ, SQS, RabbitMQ)                               |
| Archivos subidos              | Almacenamiento de objetos (S3)                                 |
| Caché                         | Redis, o local sólo si es tolerable que difiera entre réplicas |

Además: **health checks** (el orquestador saca las réplicas que no responden), **apagado ordenado** (`SIGTERM`) y
**autoscaling** por CPU, latencia o largo de cola. Y recordar que al escalar la API el cuello de botella **se mueve**
a lo compartido: la base de datos, Redis o la cuota del proveedor de LLM.

## Comparación con C# y Java

| Herramienta           | .NET                                  | Java                             | Node.js                                 |
| --------------------- | ------------------------------------- | -------------------------------- | --------------------------------------- |
| Profiling             | dotnet-trace, PerfView, Visual Studio | async-profiler, JFR, VisualVM    | `--cpu-prof`, `--inspect`, flame graphs |
| Pool de conexiones    | Integrado en ADO.NET/Npgsql           | HikariCP                         | `pg.Pool`, poolers externos             |
| Paralelizar I/O       | `Task.WhenAll`                        | `CompletableFuture.allOf`        | `Promise.all`                           |
| Batching de consultas | EF Core `Include`, split queries      | JPA `JOIN FETCH`, `@BatchSize`   | JOIN explícito, DataLoader              |
| Uso de núcleos        | Un proceso usa todos los núcleos      | Un proceso usa todos los núcleos | Una réplica por núcleo o workers        |

## Errores frecuentes

- **Optimizar sin medir** o medir sólo en local con datos de juguete.
- **Mirar promedios** en lugar de percentiles.
- **N+1** escondidos en loops o en ORMs con carga perezosa.
- **Pools sobredimensionados** que agotan las conexiones de la base al escalar réplicas.
- **Caché sin invalidación ni límite**, que sirve datos viejos o agota la memoria.
- **Estado en memoria** que rompe al agregar la segunda réplica.
- **Escalar la API sin revisar las dependencias** que van a recibir más carga.
