## ¿Qué problema resuelve?

En la mayoría de los proyectos Node.js que fracasan en mantenibilidad, el problema no es Node.js: es que **toda la
lógica vive en los handlers HTTP**. El handler parsea el body a mano, consulta la base, aplica reglas de negocio,
llama a un proveedor de SMS y arma la respuesta. No se puede testear sin levantar un servidor, no se puede reusar
desde un worker de colas, y cada endpoint inventa su propio formato de error.

Esta lección presenta la estructura que evita eso: un diseño REST claro, capas con responsabilidades separadas y
convenciones uniformes para validación y errores.

## REST en lo esencial

REST organiza la API alrededor de **recursos** (sustantivos) identificados por URLs, y usa la **semántica de HTTP**
para las operaciones:

| Operación                     | Método y ruta                              | Respuesta típica     |
| ----------------------------- | ------------------------------------------ | -------------------- |
| Listar deudas de un cliente   | `GET /customers/{id}/debts?status=pending` | `200` con la lista   |
| Obtener una deuda             | `GET /debts/{id}`                          | `200` o `404`        |
| Registrar una promesa de pago | `POST /debts/{id}/payment-promises`        | `201` con `Location` |
| Reemplazar la configuración   | `PUT /agents/{id}/config`                  | `200` o `204`        |
| Modificar parcialmente        | `PATCH /debts/{id}`                        | `200`                |
| Cancelar una campaña          | `DELETE /campaigns/{id}`                   | `204`                |

### Propiedades de los métodos

| Método   | Seguro (no modifica) |   Idempotente   |
| -------- | :------------------: | :-------------: |
| `GET`    |          Sí          |       Sí        |
| `PUT`    |          No          |       Sí        |
| `DELETE` |          No          |       Sí        |
| `POST`   |          No          |       No        |
| `PATCH`  |          No          | No (en general) |

**Idempotente** significa que repetir la request deja el sistema en el mismo estado. Importa porque las redes
fallan: si un `PUT` no recibió respuesta, se puede repetir; si un `POST /payments` no recibió respuesta, repetirlo
puede cobrar dos veces. La solución para POST críticos es una **Idempotency-Key** (lección de webhooks).

### Códigos de estado que hay que dominar

| Código                | Significado                                                         |
| --------------------- | ------------------------------------------------------------------- |
| `200`                 | OK con body                                                         |
| `201`                 | Creado; incluir `Location` con la URL del recurso                   |
| `202`                 | Aceptado para procesar después (trabajo asíncrono)                  |
| `204`                 | OK sin body                                                         |
| `400`                 | Request mal formada (JSON inválido)                                 |
| `401`                 | No autenticado                                                      |
| `403`                 | Autenticado pero sin permiso                                        |
| `404`                 | No existe (o no se revela que existe)                               |
| `409`                 | Conflicto con el estado actual (versión vieja, transición inválida) |
| `422`                 | Bien formada pero inválida según las reglas                         |
| `429`                 | Demasiadas requests; incluir `Retry-After`                          |
| `500`                 | Error inesperado del servidor                                       |
| `502` / `503` / `504` | Dependencia caída, servicio no disponible, timeout de upstream      |

| Capa        | Sabe de                                   | No sabe de             |
| ----------- | ----------------------------------------- | ---------------------- |
| Handler     | HTTP, el framework, el esquema de entrada | Reglas de negocio, SQL |
| Caso de uso | El dominio y los puertos                  | HTTP, frameworks, SQL  |

```ts
// Handler: delgado. Un Route Handler de Next.js, pero sería igual en Fastify o Express.
export async function POST(request: Request, context: { params: Promise<{ debtId: string }> }) {
  const { debtId } = await context.params;
  const parsed = CreatePromiseSchema.safeParse(await request.json().catch(() => null));
  if (!parsed.success) return problem(422, "invalid_body", z.flattenError(parsed.error).fieldErrors);

  const result = await useCases.registerPaymentPromise.execute({
    debtId,
    ...parsed.data,
    actor: await currentUser(request),
  });

  if (!result.ok) return mapDomainError(result.error);
  return Response.json(toPromiseDto(result.value), {
    status: 201,
    headers: { location: `/debts/${debtId}/payment-promises/${result.value.id}` },
  });
}
```

El handler no tiene un solo `if` de negocio: valida, delega y traduce. El caso de uso se puede llamar igual desde
un worker que procesa una cola o desde un test.

## Validación y errores consistentes

**Validá una sola vez, en el borde**, con un esquema (Zod, o el JSON Schema integrado de Fastify). Adentro, los
tipos ya son confiables.

Para los errores, un formato único evita que cada cliente tenga que adivinar. El estándar **Problem Details**
(RFC 9457) define un JSON con `type`, `title`, `status`, `detail` e `instance`, extensible con campos propios:

```ts
/** Respuesta de error con formato Problem Details (RFC 9457). */
export function problem(
  status: number,
  code: string,
  errors?: Record<string, string[] | undefined>,
): Response {
  return Response.json(
    { type: `https://errors.example.com/${code}`, title: TITLES[code] ?? "Error", status, code, errors },
    { status, headers: { "content-type": "application/problem+json" } },
  );
}

/** Traduce errores esperables del dominio a HTTP en un único lugar. */
function mapDomainError(error: RegisterPromiseError): Response {
  switch (error.kind) {
    case "debt_not_found":
      return problem(404, "debt_not_found");
    case "debt_already_paid":
      return problem(409, "debt_already_paid");
    case "date_out_of_range":
      return problem(422, "promised_date_out_of_range");
  }
}
```

Y un manejador global para lo inesperado: registra el error completo con el correlation ID y responde un `500`
**genérico**, sin stack traces ni mensajes internos (que pueden filtrar SQL, rutas o datos).

## Middleware

Un **middleware** es una función que envuelve el procesamiento de la request para resolver preocupaciones
**transversales** (que aplican a muchos endpoints):

```ts
// Estilo Express: (req, res, next)
app.use((request, response, next) => {
  const requestId = request.header("x-request-id") ?? randomUUID();
  response.setHeader("x-request-id", requestId);
  next();
});

// Estilo funcional (Next.js Route Handlers u otros): componer funciones
type Handler = (request: Request) => Promise<Response>;
const withAuth =
  (handler: (request: Request, user: User) => Promise<Response>): Handler =>
  async (request) => {
    const user = await authenticate(request);
    return user ? handler(request, user) : problem(401, "unauthenticated");
  };
```

En Next.js, el archivo `middleware`/`proxy` corre antes de las rutas y es adecuado para redirecciones y chequeos
rápidos; la **autorización real** se verifica también en el handler o en el caso de uso, cerca del dato.

## Versionado y contratos

Un cambio es **compatible** si los clientes existentes siguen funcionando: agregar un endpoint, un campo opcional
en la respuesta o un parámetro opcional. Es **incompatible** si quita o renombra campos, cambia tipos o cambia el
significado de un valor. Sólo los cambios incompatibles requieren versión nueva.

| Estrategia     | Ejemplo                             | Comentario                                          |
| -------------- | ----------------------------------- | --------------------------------------------------- |
| En la URL      | `/v2/debts`                         | La más simple y visible; la más usada               |
| En un header   | `Api-Version: 2026-11-01`           | URLs estables; versionado por fecha (estilo Stripe) |
| Por media type | `Accept: application/vnd.x.v2+json` | Purista, más incómodo para clientes                 |

Un contrato **OpenAPI** describe endpoints, esquemas y errores. Sirve para documentar, generar clientes tipados y
correr tests de contrato. Se puede escribir a mano o generar desde los esquemas (por ejemplo, con integraciones de
Zod o con el JSON Schema de Fastify). Lo importante es que **el contrato y la validación salgan de la misma
fuente**.

## Comparación con C# y Java

| Concepto         | ASP.NET Core                    | Spring Boot                | Node.js                                 |
| ---------------- | ------------------------------- | -------------------------- | --------------------------------------- |
| Handler          | Controller / Minimal API        | `@RestController`          | Route Handler, ruta de Fastify/Express  |
| Validación       | Model binding + DataAnnotations | `@Valid` + Bean Validation | Zod / JSON Schema explícito             |
| Errores estándar | `ProblemDetails` integrado      | `ProblemDetail` (Spring 6) | Implementación propia o plugin          |
| Middleware       | Pipeline de middleware          | Filters / interceptors     | Middleware de Express, hooks de Fastify |
| Contrato         | Swashbuckle / OpenAPI integrado | springdoc-openapi          | OpenAPI desde esquemas o a mano         |

La diferencia práctica: en .NET y Spring el framework impone mucha estructura. En Node.js los frameworks
minimalistas no lo hacen, así que **la disciplina de capas depende del equipo**.

## Errores frecuentes

- **Lógica de negocio en el handler.** Imposible de testear y de reusar.
- **Devolver `200` con `{ "error": ... }`.** Los clientes, proxies y métricas dependen del status.
- **Mensajes de error con detalles internos** (stack traces, SQL, rutas del servidor).
- **Un formato de error distinto por endpoint.**
- **Verbos en las URLs** (`/getDebts`, `/createPromise`) en lugar de recursos y métodos.
- **Versionar por cualquier cambio**, incluso compatibles, o no versionar nunca y romper clientes.
- **Confiar la autorización sólo al middleware** de rutas sin chequear el acceso al recurso concreto.
