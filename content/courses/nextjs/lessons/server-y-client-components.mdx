## ¿Qué problema resuelve?

En una SPA tradicional, el navegador descarga una página vacía, descarga todo el JavaScript, lo ejecuta, recién
entonces pide los datos a una API y finalmente muestra la pantalla. Cuatro viajes y mucho JavaScript antes de ver
algo, y además hay que construir y proteger una API para cada dato que necesita la UI.

**React Server Components** (RSC) cambian ese modelo: los componentes que sólo **muestran datos** se ejecutan en el
servidor, cerca de la base, y envían el resultado ya renderizado. Sólo los componentes **interactivos** viajan al
navegador como JavaScript.

## Server Components

```tsx
// app/(app)/shipments/[shipmentId]/page.tsx: Server Component (es el valor por defecto)
import { db } from "@/infrastructure/db";

export default async function ShipmentPage({ params }: { params: Promise<{ shipmentId: string }> }) {
  const { shipmentId } = await params;
  const shipment = await db.shipments.findForCurrentMerchant(shipmentId); // acceso directo, sin API intermedia

  return (
    <main>
      <h1>Envío {shipment.trackingCode}</h1>
      <TrackingTimeline shipmentId={shipment.id} />
      <CarrierUpdates shipmentId={shipment.id} />
    </main>
  );
}
```

| Pueden                                                 | No pueden                                             |
| ------------------------------------------------------ | ----------------------------------------------------- |
| Ser `async` y esperar datos                            | Usar `useState`, `useEffect` ni otros hooks de estado |
| Acceder a la base, al sistema de archivos y a secretos | Tener event handlers (`onClick`)                      |
| Usar librerías pesadas sin enviarlas al navegador      | Usar APIs del navegador (`window`, `localStorage`)    |
| Renderizar Client Components                           |                                                       |

Ventajas: **menos JavaScript** en el cliente, **datos cerca del origen** (menos latencia y sin endpoints extra) y
**secretos seguros** (nunca salen del servidor).

## Client Components y el límite "use client"

`"use client"` al principio de un archivo marca un **límite**: ese módulo, y todo lo que importa, forma parte del
bundle que se envía al navegador.

```tsx
"use client";

import { useState } from "react";

export function DeliveryInstructions({ initialText }: { initialText: string }) {
  const [text, setText] = useState(initialText);
  return (
    <textarea value={text} onChange={(e) => setText(e.target.value)} aria-label="Instrucciones de entrega" />
  );
}
```

Los Client Components **también se prerenderizan en el servidor** para generar el HTML inicial. La diferencia es que
además se **hidratan** y ejecutan en el navegador.

**Regla de diseño:** el límite va **lo más abajo posible**. Si toda la página es cliente sólo porque tiene un botón
interactivo, se pierde el beneficio. Se extrae el botón a un Client Component pequeño y el resto queda en el servidor.

## Qué puede pasar del servidor al cliente

Las props de un Client Component que recibe datos desde un Server Component **viajan por la red**, así que deben ser
**serializables**: strings, números, booleanos, arrays, objetos planos, `Date`, `Map`, `Set`, Promises y JSX. No se
pueden pasar funciones comunes ni instancias de clases con métodos (con la excepción de las Server Functions, que
viajan como referencias invocables).

```tsx
// ❌ Una función común no es serializable
<RescheduleForm onSubmit={(data) => save(data)} />

// ✅ Una Server Action sí puede pasarse (viaja como referencia a una función del servidor)
<RescheduleForm action={rescheduleDeliveryAction} />
```

Un patrón importante: un Client Component puede recibir **Server Components como `children`**. Así un contenedor
interactivo (un panel desplegable, unas pestañas) puede envolver contenido renderizado en el servidor:

```tsx
// app/(app)/shipments/[shipmentId]/page.tsx
<CollapsiblePanel title="Novedades del transportista">
  {/* CarrierUpdates sigue siendo Server Component: llega ya renderizado */}
  <CarrierUpdates shipmentId={shipmentId} />
</CollapsiblePanel>
```

<Callout type="danger" title="Cuidado con lo que se envía al cliente">
  Todo lo que se pasa como prop a un Client Component termina en el HTML y en el payload de la página. Si
  pasás el objeto `shipment` completo de la base, también viajan los campos internos. Pasá DTOs con lo
  estrictamente necesario, y marcá los módulos con secretos con `import "server-only"` para que fallen si se
  importan desde el cliente.
</Callout>

## Prerenderizado, hidratación y streaming

1. **Prerenderizado:** el servidor genera HTML (en el build si la página es estática, o por request si es dinámica).
2. **Streaming:** el HTML se envía **por partes**. Lo que está listo sale primero; lo que espera datos se reemplaza
   por su fallback y llega cuando se resuelve.
3. **Hidratación:** React en el navegador recorre el HTML existente, adjunta los event handlers y toma el control
   de los Client Components.

### Errores de hidratación

La hidratación exige que **el primer render del cliente coincida con el HTML del servidor**. Si no coincide, React
avisa con un error de hidratación. Causas típicas:

- Fechas y horas formateadas con la zona horaria del navegador (`new Date().toLocaleString()`).
- Valores aleatorios o `Date.now()` durante el render.
- Leer `window` o `localStorage` durante el render.
- HTML inválido (un `div` dentro de un `p`).

Soluciones: calcular esos valores en el servidor y pasarlos como props, leer APIs del navegador en un efecto, o
renderizar esa parte sólo en el cliente. Esta plataforma, por ejemplo, guarda el progreso en `localStorage` y lo lee
después de hidratar, mostrando un estado neutro en el HTML inicial.

## Suspense y loading.tsx

En un Server Component `async`, cada `await` puede demorar la página entera. **Suspense** permite que cada sección
cargue de forma independiente:

```tsx
import { Suspense } from "react";

export default async function ShipmentPage({ params }: { params: Promise<{ shipmentId: string }> }) {
  const { shipmentId } = await params;
  return (
    <main>
      <ShipmentHeader shipmentId={shipmentId} /> {/* rápido */}
      <Suspense fallback={<TrackingTimelineSkeleton />}>
        <TrackingTimeline shipmentId={shipmentId} /> {/* consulta pesada: no bloquea al resto */}
      </Suspense>
      <Suspense fallback={<CarrierUpdatesSkeleton />}>
        <CarrierUpdates shipmentId={shipmentId} /> {/* consulta la API del transportista, que es lenta */}
      </Suspense>
    </main>
  );
}
```

`loading.tsx` es un atajo: envuelve automáticamente la página del segmento en un Suspense con ese archivo como
fallback, y se muestra al instante al navegar.

### Evitar cascadas

```tsx
// ❌ Cascada: la segunda consulta empieza cuando termina la primera
const shipment = await getShipment(id);
const events = await getTrackingEvents(id);

// ✅ En paralelo
const [shipment, events] = await Promise.all([getShipment(id), getTrackingEvents(id)]);

// ✅ O mejor: cada componente pide lo suyo dentro de su propio Suspense
```

Un patrón útil es **iniciar** la Promise en el componente padre y pasarla a un hijo que la lee con `use(promise)`
dentro de un Suspense: la request empieza antes y no bloquea al padre.

## Comparación con C# y Java

| Concepto               | ASP.NET Core / Blazor                          | Java                        | Next.js + RSC                |
| ---------------------- | ---------------------------------------------- | --------------------------- | ---------------------------- |
| Render en servidor     | Razor, Blazor SSR estático                     | Thymeleaf, JSP              | Server Components            |
| Interactividad         | Blazor Server (SignalR) / WebAssembly          | JavaScript aparte           | Client Components hidratados |
| Mezclar por componente | Modos de render por componente (`@rendermode`) | No nativo                   | Límite `"use client"`        |
| Streaming              | Streaming rendering de Blazor                  | Respuestas chunked manuales | Suspense + streaming         |

Blazor en .NET 8+ con modos de render por componente es probablemente la analogía más cercana: páginas en servidor
con islas interactivas. La diferencia es que en RSC los componentes interactivos se ejecutan en el navegador (no
por una conexión persistente al servidor como Blazor Server).

## Errores frecuentes

- **`"use client"` en la página o el layout** por un detalle interactivo.
- **Pasar objetos completos de la base** a Client Components.
- **Importar código con secretos** en un archivo que termina en el bundle del cliente.
- **Cascadas de `await`** en lugar de pedir en paralelo o con Suspense.
- **Un único `loading.tsx`** cuando partes de la página podrían mostrarse antes.
- **Valores no deterministas en el render** que causan errores de hidratación.
