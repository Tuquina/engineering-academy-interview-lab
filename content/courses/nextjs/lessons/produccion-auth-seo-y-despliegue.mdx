## ¿Qué problema resuelve?

Una aplicación que funciona en `localhost` todavía no está lista: falta saber quién es el usuario y qué puede ver,
que los buscadores y las redes la representen bien, que cargue rápido en un celular, que los secretos no lleguen al
navegador, que se despliegue de forma repetible y que se pueda observar cuando falla. Esta lección cubre esos
puntos con las herramientas de Next.js.

## Autenticación: sesiones con cookies

El patrón recomendado para una aplicación web propia es una **sesión en una cookie segura**, ya sea con el ID de una
sesión guardada en el servidor o con un token firmado y cifrado (sesión _stateless_):

```ts
// src/modules/auth/session.ts
import "server-only";
import { cookies } from "next/headers";

export async function createSession(userId: string, tenantId: string): Promise<void> {
  const token = await encryptSession({ userId, tenantId, expiresAt: Date.now() + 8 * 60 * 60 * 1000 });
  (await cookies()).set("session", token, {
    httpOnly: true, // no accesible desde JavaScript: mitiga robo por XSS
    secure: true, // sólo por HTTPS
    sameSite: "lax", // mitiga CSRF
    path: "/",
    maxAge: 8 * 60 * 60,
  });
}

export async function verifySession(): Promise<Session | null> {
  const token = (await cookies()).get("session")?.value;
  return token ? decryptAndValidateSession(token) : null; // firma, expiración y formato
}
```

En la práctica, la autenticación de usuarios se delega a un proveedor (OIDC) con una librería como **Auth.js** u
otra solución gestionada; Next.js sólo verifica la sesión. Los conceptos de sesiones, tokens, OIDC y autorización se
estudian en la lección de autenticación del curso de Node.js.

Un error frecuente es verificar la sesión **sólo en un layout**: los layouts se conservan entre navegaciones (no se
vuelven a ejecutar) y las Server Actions se pueden invocar sin pasar por ninguna página. La verificación pertenece a
la **capa de acceso a datos** que usan todas las lecturas y escrituras.

## Metadata y SEO

```tsx
// app/layout.tsx: valores por defecto
import type { Metadata } from "next";

export const metadata: Metadata = {
  title: { template: "%s · Bitácora Dev", default: "Bitácora Dev" },
  description: "Blog de una comunidad de desarrolladores: posts, videos y comentarios.",
};

// app/(public)/blog/[slug]/page.tsx: metadata dinámica
export async function generateMetadata({ params }: { params: Promise<{ slug: string }> }): Promise<Metadata> {
  const post = await getPublishedPost((await params).slug);
  return {
    title: post.title, // "Primeros pasos con TypeScript · Bitácora Dev"
    description: post.excerpt,
    alternates: { canonical: `/blog/${post.slug}` },
    openGraph: { title: post.title, description: post.excerpt, type: "article" },
  };
}
```

Next.js genera las etiquetas `<title>`, `<meta>` y Open Graph en el HTML del servidor. También existen convenciones
de archivos para `sitemap.ts`, `robots.ts` e imágenes Open Graph generadas (`opengraph-image.tsx`). Las páginas
privadas (borradores, panel de moderación) se excluyen de la indexación.

## Imágenes y fuentes

```tsx
import Image from "next/image";

<Image
  src="/covers/typescript-first-steps.png"
  alt="Portada del post: primeros pasos con TypeScript"
  width={640}
  height={360}
  priority
/>;
```

`next/image`:

- Genera **tamaños adecuados** para cada pantalla y **formatos modernos** (WebP, AVIF).
- **Reserva el espacio** con `width` y `height`, evitando que el contenido salte al cargar (métrica CLS).
- **Carga diferida** por defecto; `priority` para la imagen principal (métrica LCP).
- Las imágenes remotas requieren declarar los dominios permitidos en la configuración.

`next/font` descarga las fuentes en el build y las sirve desde el propio dominio, sin requests a terceros y sin
saltos de texto.

## Variables de entorno

| Variable                      | Disponible en            | Cuándo se resuelve      |
| ----------------------------- | ------------------------ | ----------------------- |
| `DATABASE_URL`, `LLM_API_KEY` | Sólo servidor            | En runtime              |
| `NEXT_PUBLIC_APP_URL`         | Servidor **y navegador** | Se incrusta en el build |

Todo lo que empieza con `NEXT_PUBLIC_` se **copia al JavaScript del cliente** durante el build: es público. Los
secretos nunca llevan ese prefijo. Y como las públicas se fijan en el build, cambiarlas requiere volver a construir.
Archivos: `.env` (valores por defecto), `.env.local` (locales, no se commitean), `.env.production`, etc. Como en
cualquier servicio, las variables se **validan al iniciar** con un esquema.

## Despliegue

**Vercel** (de los creadores de Next.js) es el camino más directo: conectar el repositorio, y cada push genera un
despliegue; cada rama o pull request tiene una **URL de preview**; `main` despliega a producción. Las variables de
entorno se configuran por entorno (production, preview, development) en el proyecto.

```bash
pnpm build   # lo mismo que ejecuta la plataforma; conviene correrlo en CI antes de desplegar
```

Para **contenedores** (Kubernetes, ECS, Cloud Run), `output: "standalone"` en `next.config.ts` genera una carpeta con
el servidor y sólo las dependencias necesarias, ideal para una imagen de Docker pequeña. En ese caso hay que proveer
la caché compartida y el almacenamiento que Vercel resuelve de forma gestionada si hay varias réplicas.

## Observabilidad, seguridad y performance

- **`instrumentation.ts`:** se ejecuta al iniciar el servidor; es el lugar para inicializar **OpenTelemetry** y
  conectar trazas y logs (lección de observabilidad del curso de Node.js). Su función `onRequestError` permite
  reportar errores del servidor a la herramienta de monitoreo.
- **Cabeceras de seguridad** (`headers()` en `next.config.ts` o desde proxy): `Content-Security-Policy`,
  `Strict-Transport-Security`, `X-Content-Type-Options`, `Referrer-Policy`, `frame-ancestors` para evitar que la
  aplicación se embeba en otros sitios.
- **Performance:** medir **Core Web Vitals** reales (LCP, INP, CLS) con `useReportWebVitals` o la analítica de la
  plataforma; analizar el tamaño del bundle; mantener el límite `"use client"` bajo y cachear lo que se pueda.
- **Dependencias:** actualizar Next.js con regularidad; las versiones corrigen vulnerabilidades del framework.

## Comparación con C# y Java

| Concepto          | ASP.NET Core                              | Spring Boot                              | Next.js                                          |
| ----------------- | ----------------------------------------- | ---------------------------------------- | ------------------------------------------------ |
| Sesión con cookie | Cookie authentication                     | Spring Session, `HttpSession`            | `cookies()` + sesión cifrada o en servidor       |
| Proteger rutas    | `[Authorize]`, policies                   | Spring Security                          | proxy + capa de datos + chequeos por acción      |
| Metadata / SEO    | Tag helpers, `ViewData["Title"]`          | Thymeleaf                                | `metadata`, `generateMetadata`                   |
| Configuración     | `appsettings.json` + variables de entorno | `application.yml` + variables de entorno | `.env*` + variables; `NEXT_PUBLIC_` públicas     |
| Despliegue        | Azure App Service, contenedores           | Contenedores, Kubernetes                 | Vercel, o `output: "standalone"` en contenedores |
| Telemetría        | OpenTelemetry .NET                        | OpenTelemetry Java agent                 | `instrumentation.ts` + OpenTelemetry             |

## Errores frecuentes

- **Secretos con `NEXT_PUBLIC_`.**
- **Verificar la sesión sólo en el layout** o sólo en proxy.
- **Cookies de sesión sin `HttpOnly` o sin `Secure`.**
- **Imágenes sin dimensiones**, que producen saltos de layout.
- **No configurar variables por entorno** y desplegar previews contra la base de producción.
- **Desplegar sin `pnpm build` en CI**: los errores de tipos o de prerenderizado aparecen en producción.
