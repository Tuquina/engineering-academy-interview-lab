## ¿Qué problema resuelve?

Una interfaz puede "funcionar" y aun así ser lenta al escribir, imposible de usar con teclado o lector de
pantalla, vulnerable a inyectar código desde un nombre de cliente y difícil de cambiar porque todo depende de todo.
En una plataforma interna que usan operadores ocho horas por día, esas cuatro cosas importan tanto como las
funcionalidades.

## Optimización de renders

El orden recomendado, de lo más barato a lo más complejo:

1. **Medir** con el **Profiler** de React DevTools: qué componentes se renderizan en cada interacción y cuánto
   tardan. Sin medición, no hay optimización.
2. **Mover el estado hacia abajo**: si el texto del buscador vive en la página, cada tecla re-renderiza la página
   completa. Si vive en el componente del buscador, sólo se re-renderiza él.
3. **Composición**: pasar como `children` las partes que no dependen del estado que cambia; React no las
   re-renderiza porque son elementos creados por el padre.
4. **Memoizar** (`memo`, `useMemo`) los componentes o cálculos costosos que reciben props estables, o dejar que lo
   haga el React Compiler.
5. **Virtualizar** listas largas: renderizar sólo las filas visibles (TanStack Virtual, react-window). Una tabla de
   10.000 filas con 50 visibles pasa de 10.000 componentes a ~60.
6. **Transiciones**: marcar actualizaciones como no urgentes para que la interfaz siga respondiendo.

```tsx
import { useDeferredValue, useState } from "react";

function CustomerSearch({ customers }: { customers: Customer[] }) {
  const [query, setQuery] = useState("");
  const deferredQuery = useDeferredValue(query); // el filtrado usa una versión "atrasada" del texto

  return (
    <>
      <input value={query} onChange={(e) => setQuery(e.target.value)} aria-label="Buscar cliente" />
      {/* El input responde en cada tecla; la lista se recalcula cuando hay tiempo */}
      <CustomerTable customers={customers} query={deferredQuery} />
    </>
  );
}
```

## Testing con Testing Library

Testing Library promueve un principio: **cuanto más se parezcan tus tests a cómo se usa el software, más confianza
te dan**. No se testea el estado interno ni cuántas veces se renderizó; se testea lo que el usuario ve y hace.

```tsx
import { render, screen } from "@testing-library/react";
import userEvent from "@testing-library/user-event";
import { describe, expect, it, vi } from "vitest";

describe("PromiseForm", () => {
  it("envía la fecha y el monto ingresados", async () => {
    const user = userEvent.setup();
    const onSubmit = vi.fn();
    render(<PromiseForm onSubmit={onSubmit} />);

    await user.type(screen.getByLabelText("Fecha"), "2026-12-01");
    await user.type(screen.getByLabelText("Monto"), "15000");
    await user.click(screen.getByRole("button", { name: "Registrar" }));

    expect(onSubmit).toHaveBeenCalledWith({ promisedFor: "2026-12-01", amount: 15000 });
  });

  it("muestra un error si el monto es inválido", async () => {
    const user = userEvent.setup();
    render(<PromiseForm onSubmit={vi.fn()} />);
    await user.click(screen.getByRole("button", { name: "Registrar" }));
    expect(await screen.findByRole("alert")).toHaveTextContent("Revisá la fecha y el monto");
  });
});
```

Prioridad de queries recomendada: `getByRole` (con `name`) → `getByLabelText` → `getByPlaceholderText` →
`getByText` → `getByTestId` como último recurso. Buscar por rol tiene un beneficio extra: **si el test no encuentra
el botón por su rol y nombre, probablemente un lector de pantalla tampoco**.

| Variante  | Si no encuentra el elemento | Uso                                       |
| --------- | --------------------------- | ----------------------------------------- |
| `getBy`   | Lanza error                 | El elemento debe estar                    |
| `queryBy` | Devuelve `null`             | Verificar que **no** está                 |
| `findBy`  | Espera (Promise)            | El elemento aparece después (datos async) |

## Accesibilidad

La accesibilidad (a11y) es que la interfaz se pueda usar con teclado, lector de pantalla, zoom o alto contraste. El
estándar de referencia es **WCAG 2.2**. Lo esencial para un desarrollador:

1. **HTML semántico primero.** Un `<button>` ya es focusable, se activa con Enter y Espacio y se anuncia como botón.
   Un `<div onClick>` no tiene nada de eso.
2. **Todo operable con teclado**, con foco visible y un orden lógico.
3. **Etiquetas**: cada input con su `<label>`; los botones de sólo ícono con `aria-label`.
4. **Gestión del foco**: al abrir un diálogo, el foco entra; al cerrarlo, vuelve al disparador.
5. **Anunciar cambios dinámicos**: mensajes de error o de estado con `role="alert"` o regiones `aria-live`.
6. **Contraste** suficiente y no transmitir información sólo con color.

```tsx
// ❌ No accesible: no es focusable, no responde a teclado, no se anuncia como botón
<div className="btn" onClick={markAsPaid}>
  <CheckIcon />
</div>

// ✅ Accesible
<button type="button" onClick={markAsPaid} aria-label="Marcar como pagada">
  <CheckIcon aria-hidden />
</button>
```

**ARIA** agrega semántica cuando no existe un elemento nativo (tabs, combobox, árbol). La primera regla de ARIA es
no usarlo si existe un elemento HTML que hace lo mismo: un ARIA incorrecto es peor que ninguno. Para componentes
complejos, librerías accesibles (Radix, React Aria) implementan los patrones de la _ARIA Authoring Practices Guide_.

## Seguridad: XSS y datos no confiables

**XSS** (_cross-site scripting_) es lograr que la página ejecute JavaScript de un atacante. React protege por
defecto: el texto insertado con llaves se **escapa**.

```tsx
const name = '<img src=x onerror="alert(document.cookie)">';
<p>{name}</p>; // ✅ se muestra literalmente como texto, no se ejecuta
```

Los casos que **siguen siendo peligrosos**:

| Caso                                     | Riesgo                                             | Defensa                                            |
| ---------------------------------------- | -------------------------------------------------- | -------------------------------------------------- |
| `dangerouslySetInnerHTML`                | Inserta HTML sin escapar                           | Evitarlo; si es necesario, sanitizar con DOMPurify |
| `href` con datos del usuario             | Una URL `javascript:` ejecuta código al hacer clic | Validar el esquema (sólo `https:`, `mailto:`)      |
| Markdown o HTML generado por un LLM      | Puede contener HTML o enlaces maliciosos           | Renderizar con un parser seguro, sin HTML crudo    |
| Datos en `<script>` (estado serializado) | Romper el contexto del script                      | Serialización segura del framework                 |
| Librerías que manipulan el DOM directo   | Saltan el escape de React                          | Revisar cómo insertan contenido                    |

En una plataforma de agentes, **las respuestas de un LLM son datos no confiables**: pueden contener cualquier cosa
que el modelo haya leído o generado. Se muestran como texto o con un renderizador de Markdown que no permita HTML
crudo. Una **Content Security Policy** (CSP) agrega una capa más de defensa a nivel del navegador.

## Arquitectura frontend

Organizar **por funcionalidad** escala mejor que organizar por tipo técnico (`components/`, `hooks/`, `utils/` con
cientos de archivos cada uno):

```text
src/
  shared/ui/              Button, Dialog, Table: genéricos, sin lógica de negocio
  features/
    debts/
      components/         DebtTable, DebtRow
      hooks/              useCustomerDebts, useRegisterPromise
      api.ts              llamadas al backend tipadas
      schemas.ts          esquemas Zod compartidos con el formulario
    campaigns/
  app/                    rutas y composición de pantallas
```

Principios: componentes de UI **genéricos y sin dominio**; la lógica de negocio fuera de los componentes (hooks,
funciones puras); dependencias entre features explícitas y mínimas; y el acceso a la API centralizado y tipado.
Esta plataforma sigue esa idea con `src/shared/ui` y `src/modules/<módulo>/presentation`.

## Comparación con C# y Java

| Tema                 | Blazor / .NET                                | Java (UI)                   | React                                     |
| -------------------- | -------------------------------------------- | --------------------------- | ----------------------------------------- |
| Profiling de UI      | Herramientas del navegador                   | Profilers de la JVM         | React DevTools Profiler                   |
| Tests de componentes | bUnit                                        | TestFX                      | Testing Library + Vitest/Jest             |
| Escape de HTML       | Razor escapa por defecto (`MarkupString` no) | JSF escapa por defecto      | JSX escapa (`dangerouslySetInnerHTML` no) |
| Accesibilidad        | Mismos estándares web (WCAG)                 | Accessibility API de JavaFX | Mismos estándares web (WCAG, ARIA)        |

## Errores frecuentes

- **Optimizar sin el Profiler.**
- **Tests que buscan por clases CSS** o verifican estado interno.
- **`div` y `span` con `onClick`** en lugar de botones y enlaces.
- **Inputs sin label**, íconos sin nombre accesible, foco perdido al cerrar modales.
- **`dangerouslySetInnerHTML` con contenido del usuario o de un LLM.**
- **Lógica de negocio dentro de los componentes de UI.**
