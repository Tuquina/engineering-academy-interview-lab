## ¿Qué problema resuelve?

Con el modelo de render de React, cada vez que un componente se renderiza se recalculan sus valores, se crean
funciones nuevas y se re-renderizan sus hijos. Casi siempre eso es barato. A veces no: una tabla de 2.000 filas que
se re-renderiza en cada tecla del buscador, o un cálculo de scoring que tarda 80 ms. Y hay lógica (suscripciones,
formularios, temporizadores) que se repite en muchos componentes.

Esta lección cubre las herramientas para esos casos y, sobre todo, **cuándo no usarlas**.

## Memoización: useMemo, useCallback y memo

```tsx
// useMemo: cachea el RESULTADO de un cálculo mientras no cambien las dependencias
const ranked = useMemo(() => rankDebtsByRecoveryScore(debts, weights), [debts, weights]);

// useCallback: cachea una FUNCIÓN (misma referencia entre renders)
const handleSelect = useCallback((id: string) => {
  setSelectedIds((previous) => new Set(previous).add(id));
}, []);

// memo: saltea el render del componente si sus props son iguales (comparación superficial)
const DebtRow = memo(function DebtRow({ debt, onSelect }: { debt: Debt; onSelect: (id: string) => void }) {
  return <tr onClick={() => onSelect(debt.id)}>{/* ... */}</tr>;
});
```

Estas herramientas trabajan juntas. `memo` compara las props con `Object.is`: si el padre pasa una función creada en
cada render, la prop "cambió" y `memo` no sirve. Por eso `useCallback` sólo tiene sentido cuando la función va a un
hijo memoizado o a las dependencias de un efecto.

### Cuándo vale la pena

- **Sí:** un cálculo medido como costoso (ordenar miles de elementos, scoring), listas grandes con filas
  memoizadas, valores que son dependencias de efectos y que de otro modo cambiarían en cada render, el valor de un
  Context.
- **No:** cálculos triviales (`a + b`, un `filter` de 20 elementos), funciones que se pasan a elementos HTML nativos
  (`<button onClick>` no es un componente memoizado).

Memoizar no es gratis: agrega comparaciones, memoria y complejidad. **Medí primero** con el Profiler de React
DevTools.

### El React Compiler

El **React Compiler** es una herramienta de build que analiza los componentes y **memoiza automáticamente** valores,
funciones y JSX donde es seguro. En proyectos que lo usan, gran parte del `useMemo`, `useCallback` y `memo` manual
deja de ser necesaria. Requiere que los componentes sigan las reglas de React (pureza, hooks en el nivel superior,
no mutar props ni estado): otra razón para escribir componentes puros.

## useRef: memoria sin renders y acceso al DOM

`useRef` devuelve un objeto `{ current }` que **persiste entre renders**, y cuyo cambio **no dispara un render**.

```tsx
// 1. Referencia a un nodo del DOM
function AmountInput() {
  const inputRef = useRef<HTMLInputElement>(null);
  return (
    <>
      <input ref={inputRef} type="number" />
      <button type="button" onClick={() => inputRef.current?.focus()}>
        Editar monto
      </button>
    </>
  );
}

// 2. Valor mutable que no afecta lo que se ve
function AutoSave({ draft }: { draft: string }) {
  const timerRef = useRef<ReturnType<typeof setTimeout> | null>(null);

  function scheduleSave(value: string) {
    if (timerRef.current) clearTimeout(timerRef.current);
    timerRef.current = setTimeout(() => saveDraft(value), 800); // debounce
  }
  // ...
}
```

| Necesitás...                                      | Usá        |
| ------------------------------------------------- | ---------- |
| Un valor que se muestra en pantalla               | `useState` |
| Un valor que persiste pero no afecta lo que se ve | `useRef`   |
| Acceso imperativo al DOM (foco, scroll, medidas)  | `useRef`   |

Regla: **no leas ni escribas `ref.current` durante el render** (salvo para inicializarlo); hacelo en handlers o
efectos. Si el valor afecta lo que se muestra, es estado.

## Context: datos para todo un subárbol

Context permite que un componente lea un valor de un ancestro sin recibirlo por props:

```tsx
interface TenantContextValue {
  tenantId: string;
  currency: "ARS" | "USD";
  timezone: string;
}

const TenantContext = createContext<TenantContextValue | null>(null);

export function TenantProvider({
  value,
  children,
}: {
  value: TenantContextValue;
  children: React.ReactNode;
}) {
  return <TenantContext value={value}>{children}</TenantContext>;
}

/** Hook de acceso: falla rápido si se usa fuera del provider. */
export function useTenant(): TenantContextValue {
  const value = useContext(TenantContext);
  if (!value) throw new Error("useTenant debe usarse dentro de TenantProvider");
  return value;
}
```

En React 19 el contexto se usa directamente como provider (`<TenantContext value={...}>`); en versiones
anteriores se escribía `<TenantContext.Provider value={...}>`.

### El costo de Context

**Cada vez que cambia el valor del provider, se re-renderizan todos los componentes que lo consumen.** Dos
consecuencias:

1. Si el provider crea un objeto nuevo en cada render (`value={{ tenantId, currency }}`), todos los consumidores
   se re-renderizan aunque los datos no hayan cambiado. Se memoiza el valor con `useMemo` (o lo hace el compiler).
2. Mezclar datos que cambian mucho (el texto de un buscador) con datos estables (el tenant) en un mismo contexto
   re-renderiza a todos por cada tecla. Se separan contextos por frecuencia de cambio.

Context es ideal para datos **poco cambiantes y ampliamente usados**: tema, usuario, tenant, idioma, configuración.
Para estado global muy dinámico, librerías con suscripciones selectivas (Zustand, Redux Toolkit, Jotai) son mejores;
para datos del servidor, una librería de server state.

## Custom hooks: reutilizar lógica con estado

Un **custom hook** es una función cuyo nombre empieza con `use` y que usa otros hooks. Extrae lógica para
reutilizarla y para dejar los componentes legibles:

```tsx
/** Valor que se actualiza sólo cuando el usuario deja de escribir durante `delayMs`. */
export function useDebouncedValue<T>(value: T, delayMs: number): T {
  const [debounced, setDebounced] = useState(value);

  useEffect(() => {
    const timer = setTimeout(() => setDebounced(value), delayMs);
    return () => clearTimeout(timer);
  }, [value, delayMs]);

  return debounced;
}

function CustomerSearch() {
  const [query, setQuery] = useState("");
  const debouncedQuery = useDebouncedValue(query, 300);
  const results = useCustomerSearch(debouncedQuery); // otro custom hook, por ejemplo con TanStack Query

  return <input value={query} onChange={(e) => setQuery(e.target.value)} aria-label="Buscar cliente" />;
}
```

Puntos clave:

- **Comparten lógica, no estado:** cada componente que llama a `useDebouncedValue` tiene su propio estado.
- Siguen las **reglas de los hooks** (nivel superior, sólo desde componentes o hooks).
- Una buena API de hook devuelve lo que el componente necesita, con nombres claros, y oculta los detalles.
- Se testean con `renderHook` de Testing Library.

| Concepto                    | Blazor / .NET                     | Java (UI)                    | React                  |
| --------------------------- | --------------------------------- | ---------------------------- | ---------------------- |
| Evitar renders innecesarios | `ShouldRender()`                  | No aplica                    | `memo`, React Compiler |
| Cachear un cálculo          | `Lazy<T>`, campos calculados      | Campos calculados            | `useMemo`              |
| Referencia a un elemento    | `@ref` / `ElementReference`       | `fx:id`, referencias a nodos | `useRef`               |
| Datos para un subárbol      | `CascadingValue`, DI con scope    | DI, singletons               | Context                |
| Reutilizar lógica           | Servicios inyectados, clases base | Clases helper, herencia      | Custom hooks           |

## Errores frecuentes

- **Memoizar todo por defecto.** Agrega complejidad sin beneficio medido.
- **`useCallback` sin un hijo memoizado** que lo aproveche.
- **Objetos y funciones literales como props de un componente memoizado**, que anulan `memo`.
- **Usar refs para datos que se muestran**: la pantalla no se actualiza.
- **Un único Context gigante** con datos de distinta frecuencia de cambio.
- **Custom hooks que no usan hooks**: son funciones comunes; no les pongas `use`.
