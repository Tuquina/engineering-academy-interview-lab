## ¿Qué problema resuelve?

`useState` y `useEffect` son los dos hooks más usados y los que más bugs producen. El patrón problemático típico de
quien empieza:

```tsx
function SensorSummary({ deviceId }: { deviceId: string }) {
  const [readings, setReadings] = useState<Reading[]>([]);
  const [alertCount, setAlertCount] = useState(0);

  useEffect(() => {
    fetch(`/api/devices/${deviceId}/readings`)
      .then((r) => r.json())
      .then(setReadings);
  }, []); // ❌ falta deviceId: al cambiar de dispositivo se muestran las lecturas del anterior

  useEffect(() => {
    setAlertCount(readings.filter((r) => r.celsius > 30).length); // ❌ estado derivado con un efecto
  }, [readings]);

  return <p>Lecturas sobre 30 °C: {alertCount}</p>;
}
```

Tiene tres errores: dependencias incompletas, una race condition al cambiar rápido de dispositivo y un efecto
innecesario. Esta lección explica cómo usar estos hooks correctamente.

## useState en profundidad

### Inmutabilidad

React decide si re-renderizar comparando **referencias** (`Object.is`). Si mutás un objeto y llamás al setter con
el mismo objeto, React ve la misma referencia y puede no actualizar.

```tsx
const [device, setDevice] = useState<Device>(initial);
const [alerts, setAlerts] = useState<SensorAlert[]>([]);

// ❌ Mutación
device.status = "offline";
setDevice(device);
alerts.push(newAlert);
setAlerts(alerts);

// ✅ Objetos y arrays nuevos
setDevice({ ...device, status: "offline" });
setAlerts([...alerts, newAlert]); // agregar
setAlerts(alerts.filter((a) => a.id !== id)); // quitar
setAlerts(alerts.map((a) => (a.id === id ? { ...a, status: "acknowledged" } : a))); // modificar uno
```

### Actualizaciones funcionales e inicialización perezosa

```tsx
setCount((previous) => previous + 1); // usa el valor más reciente, no el del render

const [draft, setDraft] = useState(() => loadDraftFromStorage()); // la función se ejecuta sólo en el primer render
```

Pasar `useState(loadDraftFromStorage())` ejecutaría la función **en cada render** aunque sólo se use la primera vez.

## useReducer: transiciones explícitas

Cuando el estado tiene varias partes relacionadas o reglas de transición, un **reducer** las centraliza en una
función pura `(estado, acción) → nuevo estado`:

```tsx
// Actualización de firmware de un dispositivo IoT, en pasos
type UpdateState =
  | { status: "idle" }
  | { status: "downloading"; startedAt: number }
  | { status: "installing"; startedAt: number; percent: number }
  | { status: "finished"; durationMs: number; outcome: "updated" | "failed" | "rolled_back" };

type UpdateAction =
  | { type: "start"; now: number }
  | { type: "downloaded" }
  | { type: "progress"; percent: number }
  | { type: "finish"; now: number; outcome: "updated" | "failed" | "rolled_back" };

function updateReducer(state: UpdateState, action: UpdateAction): UpdateState {
  switch (action.type) {
    case "start":
      return state.status === "idle" ? { status: "downloading", startedAt: action.now } : state;
    case "downloaded":
      return state.status === "downloading"
        ? { status: "installing", startedAt: state.startedAt, percent: 0 }
        : state;
    case "progress":
      return state.status === "installing" ? { ...state, percent: action.percent } : state;
    case "finish":
      return state.status === "downloading" || state.status === "installing"
        ? { status: "finished", durationMs: action.now - state.startedAt, outcome: action.outcome }
        : state;
  }
}

function FirmwareUpdatePanel() {
  const [state, dispatch] = useReducer(updateReducer, { status: "idle" });
  return <button onClick={() => dispatch({ type: "start", now: Date.now() })}>Actualizar</button>;
}
```

Ventajas: las transiciones inválidas son imposibles (la discriminated union del curso de TypeScript), el reducer se
testea sin React y las acciones documentan todo lo que puede pasar. Es el mismo patrón que Redux, a escala de un
componente.

## useEffect: sincronizar con sistemas externos

`useEffect` existe para **sincronizar un componente con algo que está fuera de React**: una conexión WebSocket, una
suscripción, un timer, una API del navegador, un widget de terceros.

```tsx
function LiveSensorReading({ sensorId }: { sensorId: string }) {
  const [reading, setReading] = useState<Reading | null>(null);

  useEffect(() => {
    const socket = new WebSocket(`wss://realtime.example.com/sensors/${sensorId}`);
    socket.addEventListener("message", (event) => setReading(parseReading(event.data)));

    return () => socket.close(); // limpieza: deshacer lo que hizo el efecto
  }, [sensorId]); // volver a sincronizar cuando cambia sensorId

  return <TemperatureGauge reading={reading} />;
}
```

### Dependencias

El array de dependencias debe incluir **todo valor reactivo** (props, estado, valores derivados de ellos) usado
dentro del efecto. No es una forma de decidir "cuándo correr": describe **de qué depende la sincronización**. La
regla de lint `react-hooks/exhaustive-deps` lo verifica; desactivarla casi siempre esconde un bug.

| Array        | Cuándo se ejecuta                          |
| ------------ | ------------------------------------------ |
| Sin array    | Después de cada render (rara vez correcto) |
| `[]`         | Al montar (y limpia al desmontar)          |
| `[sensorId]` | Al montar y cada vez que cambia `sensorId` |

Si una dependencia cambia "demasiado" (un objeto o función creados en cada render), la solución es moverla dentro
del efecto, derivarla de primitivos o estabilizarla, no quitarla del array.

### Race conditions al cargar datos

```tsx
useEffect(() => {
  const controller = new AbortController();
  fetch(`/api/devices/${deviceId}/readings`, { signal: controller.signal })
    .then((r) => r.json())
    .then(setReadings)
    .catch((error) => {
      if (error.name !== "AbortError") setError(error);
    });
  return () => controller.abort(); // si deviceId cambia, se cancela la request anterior
}, [deviceId]);
```

Sin la limpieza, si el usuario pasa del dispositivo A al B y la respuesta de A llega después, la pantalla de B
muestra las lecturas de A. Aun así, **cargar datos con efectos a mano** obliga a resolver caché, deduplicación, reintentos y
estados de carga: en aplicaciones reales se usa una librería de server state o Server Components (lección de datos).

## No necesitás un efecto para...

| Situación                                  | En lugar de un efecto                                       |
| ------------------------------------------ | ----------------------------------------------------------- |
| Calcular algo a partir de props o estado   | Calcularlo durante el render (`useMemo` si es costoso)      |
| Responder a un clic o un submit            | Hacerlo en el event handler                                 |
| Reiniciar el estado cuando cambia una prop | `key` en el componente                                      |
| Notificar al padre cuando cambia un estado | Llamar al callback en el mismo handler que cambia el estado |
| Enviar analytics al hacer una acción       | En el handler de esa acción                                 |
| Inicializar algo una vez en la aplicación  | Fuera del componente, en el módulo                          |

```tsx
// ❌ Efecto para reaccionar a un submit
const [submitted, setSubmitted] = useState(false);
useEffect(() => {
  if (submitted) saveAlertRule(form);
}, [submitted]);

// ✅ El trabajo va en el handler de la acción
async function handleSubmit() {
  await saveAlertRule(form);
}
```

La regla de la documentación oficial: **si algo ocurre porque el usuario hizo algo, va en el event handler; si
ocurre porque el componente se mostró y debe sincronizarse con algo externo, va en un efecto.**

corregir.

## Comparación con C# y Java

| Concepto                       | Blazor                                  | JavaFX                     | React                           |
| ------------------------------ | --------------------------------------- | -------------------------- | ------------------------------- |
| Estado local                   | Campos + `StateHasChanged`              | Properties observables     | `useState`                      |
| Transiciones complejas         | Fluxor (Redux para Blazor)              | Máquinas de estado propias | `useReducer`                    |
| Al aparecer / desaparecer      | `OnInitializedAsync`, `Dispose`         | Listeners de escena        | `useEffect` con limpieza        |
| Reaccionar a parámetros nuevos | `OnParametersSetAsync`                  | Listeners de propiedades   | Dependencias del efecto (o key) |
| Cancelación                    | `CancellationToken` en el ciclo de vida | Manual                     | Limpieza + `AbortController`    |

La diferencia mental importante: en Blazor o en frameworks con ciclo de vida se piensa en **momentos** ("al
inicializar", "al cambiar parámetros"). En React se piensa en **sincronización**: "este componente debe estar
conectado al sensor X mientras se muestre". React decide cuándo conectar y desconectar.

## Errores frecuentes

- **Mutar estado** y llamar al setter con la misma referencia.
- **Dependencias incompletas** para que el efecto "corra una sola vez".
- **Efectos para estado derivado** o para responder a eventos del usuario.
- **Fetch sin limpieza**, con race conditions al cambiar de parámetro.
- **Efectos que se disparan en cadena**: un efecto setea estado que dispara otro efecto que setea otro estado.
- **Funciones async directamente como efecto** (`useEffect(async () => ...)`): el efecto debe devolver una función
  de limpieza, no una Promise.
