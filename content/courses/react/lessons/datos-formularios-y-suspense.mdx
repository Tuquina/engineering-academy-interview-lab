## ¿Qué problema resuelve?

En la lección de efectos vimos que cargar datos con `useEffect` a mano obliga a resolver race conditions. Y eso es
sólo el principio: si dos componentes necesitan el mismo huésped, ¿se piden dos veces? Si el usuario confirma una
reserva, ¿cómo se actualiza la lista? ¿Qué pasa si la red falla? ¿Cuándo se considera viejo un dato?

La respuesta moderna es reconocer que **los datos del servidor son un tipo de estado distinto** y usar herramientas
diseñadas para él.

## Server state y client state

| Server state                                           | Client state                               |
| ------------------------------------------------------ | ------------------------------------------ |
| Pertenece al servidor; tenés una copia                 | Pertenece a la interfaz                    |
| Puede quedar desactualizado sin que lo sepas           | Siempre está al día                        |
| Se comparte entre pantallas y usuarios                 | Local a una pantalla o sesión              |
| Necesita caché, revalidación, reintentos, invalidación | Necesita sólo guardarse y actualizarse     |
| Ejemplos: reservas, habitaciones, tarifas              | Ejemplos: modal abierto, pestaña, borrador |

El error de diseño más común es guardar datos del servidor en un store global (Redux, Context) y reimplementar a
mano el `loading`, el `error`, la caché y la invalidación.

## Data fetching con una librería de server state

**TanStack Query** (antes React Query) es la librería más usada para server state en el cliente. Con Next.js y
Server Components, buena parte de la carga de datos se hace en el servidor (curso de Next.js); en el cliente, el
modelo es este:

```tsx
import { useMutation, useQuery, useQueryClient } from "@tanstack/react-query";

function useGuestBookings(guestId: string) {
  return useQuery({
    queryKey: ["guests", guestId, "bookings"], // identidad del dato en la caché
    queryFn: ({ signal }) => api.getGuestBookings(guestId, { signal }), // cancelable
    staleTime: 30_000, // durante 30 s se considera fresco y no se vuelve a pedir
  });
}

function useCreateBooking(guestId: string) {
  const queryClient = useQueryClient();
  return useMutation({
    mutationFn: api.createBooking,
    onSuccess: () => queryClient.invalidateQueries({ queryKey: ["guests", guestId] }), // refresca lo afectado
  });
}

function BookingsPanel({ guestId }: { guestId: string }) {
  const { data, isPending, isError, refetch } = useGuestBookings(guestId);
  if (isPending) return <Skeleton />;
  if (isError) return <ErrorState onRetry={refetch} />;
  return <BookingList bookings={data} />;
}
```

Lo que obtenés sin escribirlo: **deduplicación** (dos componentes con la misma key comparten la request),
**caché**, **revalidación** al volver a la pestaña o reconectar, **reintentos** con backoff, **cancelación** al
cambiar de key (sin race conditions) e **invalidación** tras mutaciones.

## Formularios

### No controlados: el DOM guarda el valor

```tsx
function BookingForm({ onSubmit }: { onSubmit: (input: BookingInput) => void }) {
  return (
    <form
      onSubmit={(event) => {
        event.preventDefault();
        const data = new FormData(event.currentTarget);
        onSubmit({ checkIn: String(data.get("checkIn")), nights: Number(data.get("nights")) });
      }}
    >
      <label>
        Llegada <input name="checkIn" type="date" required />
      </label>
      <label>
        Noches <input name="nights" type="number" min="1" required />
      </label>
      <button type="submit">Reservar</button>
    </form>
  );
}
```

Simple, sin renders por tecla, y aprovecha la validación nativa del navegador (`required`, `min`, `type`).

### Controlados: React guarda el valor

```tsx
const [nights, setNights] = useState("");
<input value={nights} onChange={(e) => setNights(e.target.value)} />;
```

Necesarios cuando el valor afecta otras partes de la interfaz en vivo: validación mientras se escribe, campos que
dependen de otros, formato en tiempo real. Cada tecla produce un render; en formularios grandes, una librería como
**React Hook Form** (no controlada por dentro, con suscripciones selectivas) mantiene la performance.

### Validación compartida

La validación del cliente es **para la experiencia**; la del servidor es **para la seguridad**. El mismo esquema
Zod puede usarse en ambos lados para que no diverjan:

```tsx
export const BookingInputSchema = z.object({
  checkIn: z.iso.date(),
  nights: z.number().int().positive().max(30),
});
```

## Actions de React 19: useActionState y useOptimistic

React 19 agregó soporte nativo para **acciones**: funciones async asociadas a un formulario, con estado de envío y
resultado manejados por React. Funcionan en el cliente y, con Next.js, con Server Actions.

```tsx
import { useActionState, useOptimistic } from "react";

type FormState = { error?: string; ok?: boolean };

function BookingForm({ roomId, bookings }: { roomId: string; bookings: Booking[] }) {
  const [optimisticBookings, addOptimistic] = useOptimistic(bookings, (current, added: Booking) => [
    ...current,
    added,
  ]);

  const [state, formAction, isPending] = useActionState(async (_previous: FormState, formData: FormData) => {
    const parsed = BookingInputSchema.safeParse({
      checkIn: formData.get("checkIn"),
      nights: Number(formData.get("nights")),
    });
    if (!parsed.success) return { error: "Revisá la fecha de llegada y las noches." };

    addOptimistic({ id: "temp", roomId, ...parsed.data, status: "pending" }); // se ve al instante
    const result = await createBooking(roomId, parsed.data); // si falla, la UI optimista se descarta
    return result.ok ? { ok: true } : { error: result.message };
  }, {});

  return (
    <form action={formAction}>
      {/* ...campos... */}
      <button disabled={isPending}>{isPending ? "Reservando…" : "Reservar"}</button>
      {state.error && <p role="alert">{state.error}</p>}
      <BookingList bookings={optimisticBookings} />
    </form>
  );
}
```

- `useActionState` devuelve el último resultado, la acción para el `form` y si está pendiente.
- `useOptimistic` muestra el resultado esperado **antes** de que el servidor confirme; si la acción falla, React
  vuelve al estado real.

## Suspense y error boundaries

**Suspense** declara qué mostrar **mientras** una parte de la interfaz espera (datos o código):

```tsx
<Suspense fallback={<BookingsSkeleton />}>
  <BookingsPanel guestId={guestId} />
</Suspense>
```

Los componentes "suspenden" cuando leen datos con una fuente compatible (Server Components, `use(promise)`,
`useSuspenseQuery` de TanStack Query, `lazy` para código). La ubicación del boundary es una decisión de diseño:
¿se muestra un esqueleto por panel o uno para toda la página?

Un **error boundary** declara qué mostrar si **falla** el render de sus hijos:

```tsx
import { ErrorBoundary } from "react-error-boundary";

<ErrorBoundary fallback={<PanelError message="No pudimos cargar las reservas." />}>
  <Suspense fallback={<BookingsSkeleton />}>
    <BookingsPanel guestId={guestId} />
  </Suspense>
</ErrorBoundary>;
```

Los error boundaries capturan errores **durante el render**, no en event handlers ni en código asíncrono suelto:
esos se manejan con `try/catch` y estado.

## Comparación con C# y Java

| Necesidad                | Blazor                              | Java (Vaadin / JSF)      | React                              |
| ------------------------ | ----------------------------------- | ------------------------ | ---------------------------------- |
| Cargar datos             | `OnInitializedAsync` + `HttpClient` | Servicios del backend    | TanStack Query o Server Components |
| Caché de datos remotos   | Manual o librerías                  | Caché del backend        | Caché por query key                |
| Formularios y validación | `EditForm` + DataAnnotations        | Binder + Bean Validation | FormData / React Hook Form + Zod   |
| Estado de carga          | `if (data == null)` en la plantilla | Indicadores manuales     | Suspense                           |
| Errores de render        | `ErrorBoundary` (Blazor)            | Páginas de error         | Error boundaries                   |

## Errores frecuentes

- **Guardar server state en un store global** y reimplementar caché a mano.
- **No invalidar tras mutaciones**: la lista no refleja la reserva recién creada.
- **Validar sólo en el cliente.**
- **Formularios controlados enormes** que re-renderizan todo por tecla.
- **Un único Suspense o error boundary** para toda la aplicación.
- **Esperar que un error boundary capture errores de un `onClick`.**
