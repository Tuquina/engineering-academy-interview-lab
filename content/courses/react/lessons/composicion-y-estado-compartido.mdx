## ¿Qué problema resuelve?

Pensá en la pantalla de gestión de una campaña: filtros arriba, una tabla de deudores, un panel lateral con el
detalle del deudor seleccionado y un contador de seleccionados en el encabezado. ¿Dónde vive el "deudor
seleccionado"? ¿Y los filtros? Si cada componente guarda su propia copia, el encabezado dice 3 seleccionados
mientras la tabla muestra 4.

Esta lección trata de **cómo dividir la interfaz** y **dónde vive cada estado** para que haya una sola verdad.

## Dividir la interfaz

El proceso recomendado por la documentación de React (_Thinking in React_):

1. **Dividir la pantalla en una jerarquía de componentes**, con un criterio parecido al de responsabilidad única.
2. **Construir una versión estática** con props, sin estado.
3. **Encontrar el estado mínimo**: lo que cambia con el tiempo, no viene por props y **no se puede calcular**.
4. **Decidir dónde vive** cada estado.
5. **Agregar el flujo inverso**: callbacks para que los hijos pidan cambios.

## Una sola fuente de verdad y estado derivado

El paso 3 es el que más errores evita: **no guardes en estado lo que se puede calcular**.

```tsx
// ❌ Estado duplicado: filteredDebts puede desincronizarse de debts o de filters
const [debts, setDebts] = useState<Debt[]>([]);
const [filters, setFilters] = useState<Filters>(initialFilters);
const [filteredDebts, setFilteredDebts] = useState<Debt[]>([]);
useEffect(() => setFilteredDebts(applyFilters(debts, filters)), [debts, filters]);

// ✅ Derivado durante el render: siempre consistente
const [filters, setFilters] = useState<Filters>(initialFilters);
const filteredDebts = applyFilters(debts, filters);
const selectedCount = selectedIds.size;
```

La versión derivada no puede desincronizarse y evita un render extra. Si el cálculo fuera realmente costoso (medido),
se memoiza con `useMemo`.

## Lifting state up

Cuando dos componentes necesitan el mismo estado, se **levanta** al ancestro común más cercano:

```tsx
export function CampaignPage({ debts }: { debts: Debt[] }) {
  const [filters, setFilters] = useState<Filters>(initialFilters);
  const [selectedIds, setSelectedIds] = useState<ReadonlySet<string>>(new Set());

  const visibleDebts = applyFilters(debts, filters);

  function toggle(id: string) {
    setSelectedIds((previous) => {
      const next = new Set(previous);
      if (next.has(id)) next.delete(id);
      else next.add(id);
      return next; // un Set nuevo: nunca mutar el anterior
    });
  }

  return (
    <>
      <Header selectedCount={selectedIds.size} />
      <FiltersBar value={filters} onChange={setFilters} />
      <DebtTable debts={visibleDebts} selectedIds={selectedIds} onToggle={toggle} />
    </>
  );
}
```

`FiltersBar` y `DebtTable` son ahora **componentes controlados**: no tienen estado propio para esos datos; los
reciben y avisan cambios. Eso los hace reutilizables y fáciles de testear.

¿Y si el estado se levanta demasiado? Cada cambio re-renderiza al ancestro y a todos sus hijos. La regla: el estado
vive **lo más abajo posible**, pero **lo suficientemente arriba** como para que todos los que lo necesitan lo vean.
Un input de búsqueda que sólo usa la tabla no debería vivir en la página.

## Composición con children y slots

React no usa herencia entre componentes. Para reutilizar estructura, se **componen** pasando elementos como props:

```tsx
// Un layout genérico con "slots" con nombre
function Panel({
  title,
  actions,
  children,
}: {
  title: string;
  actions?: React.ReactNode;
  children: React.ReactNode;
}) {
  return (
    <section className="panel">
      <header>
        <h2>{title}</h2>
        {actions}
      </header>
      <div className="panel-body">{children}</div>
    </section>
  );
}

// Especialización por configuración, no por herencia
<Panel title="Promesas de pago" actions={<Button onClick={openNewPromise}>Nueva</Button>}>
  <PromiseList debtId={debtId} />
</Panel>;
```

Si venís de WPF o JavaFX, la idea de heredar de un control base para especializarlo no aplica: en React se hace un
componente genérico configurable y se lo combina. La documentación oficial no recomienda herencia de componentes en
ningún caso.

## Render props y componentes compuestos

Cuando un componente necesita que el padre decida **cómo** renderizar una parte con datos que sólo el componente
conoce, se pasa una **función** que devuelve JSX (render prop):

```tsx
function VirtualList<T>({ items, renderItem }: { items: T[]; renderItem: (item: T) => React.ReactNode }) {
  const visible = useVisibleWindow(items); // lógica de virtualización interna
  return <div>{visible.map(renderItem)}</div>;
}

<VirtualList items={debts} renderItem={(debt) => <DebtRow key={debt.id} debt={debt} />} />;
```

Muchos usos históricos de render props (compartir lógica con estado) hoy se resuelven mejor con **custom hooks**
(lección de hooks). Siguen siendo útiles para delegar el renderizado, como en listas virtualizadas o tablas.

Los **componentes compuestos** son un conjunto de componentes que cooperan y comparten estado implícito (vía
contexto), con una API declarativa:

```tsx
<Tabs defaultValue="debts">
  <Tabs.List>
    <Tabs.Trigger value="debts">Deudas</Tabs.Trigger>
    <Tabs.Trigger value="history">Historial</Tabs.Trigger>
  </Tabs.List>
  <Tabs.Content value="debts">
    <DebtTable />
  </Tabs.Content>
  <Tabs.Content value="history">
    <ContactHistory />
  </Tabs.Content>
</Tabs>
```

Es el patrón de las librerías de componentes accesibles (Radix, React Aria, shadcn/ui).

## Prop drilling

**Prop drilling** es pasar una prop por varios niveles que no la usan, sólo para que llegue abajo. Con dos o tres
niveles es normal y explícito. Cuando molesta, la primera herramienta es **composición**:

```tsx
// ❌ Layout y Sidebar reciben `user` sólo para pasarlo
<Layout user={user} />

// ✅ El padre arma el componente que necesita user y lo pasa ya construido
<Layout sidebar={<UserMenu user={user} />} />
```

La segunda es **Context**, para datos que muchos componentes de un subárbol necesitan (tema, usuario actual,
tenant, configuración). Context no es una librería de estado general: cada cambio de su valor re-renderiza a todos
los consumidores (se ve en la lección de hooks). Para datos del servidor, una librería de server state es mejor
opción.

## Comparación con C# y Java

| Necesidad                     | WPF / Blazor                                       | JavaFX                  | React                          |
| ----------------------------- | -------------------------------------------------- | ----------------------- | ------------------------------ |
| Reutilizar estructura         | Herencia de controles, templates, `RenderFragment` | Herencia, FXML includes | Composición: `children`, slots |
| Compartir estado entre vistas | ViewModel compartido, `CascadingValue`             | Modelo compartido       | Lifting state, Context         |
| Delegar renderizado           | `DataTemplate`, `RenderFragment<T>`                | `CellFactory`           | Render props                   |
| Fuente de verdad              | ViewModel                                          | Modelo con propiedades  | Estado en el ancestro común    |

## Errores frecuentes

- **Duplicar estado** que se puede derivar, y sincronizarlo con efectos.
- **Copiar props en estado** (`useState(props.value)`): el estado no se actualiza si la prop cambia.
- **Levantar todo al componente raíz** "por las dudas", re-renderizando toda la pantalla en cada tecla.
- **Usar Context para todo**, incluidos datos que cambian a cada rato.
- **Intentar herencia de componentes.**
- **Componentes gigantes** con decenas de estados y responsabilidades.
