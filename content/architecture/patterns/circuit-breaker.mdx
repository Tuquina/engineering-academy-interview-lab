## Motivación

El servicio de contactos envía miles de mensajes por hora a través de un proveedor externo. Cuando el proveedor se
degrada, cada envío espera 10 segundos de timeout; los workers quedan bloqueados, la cola crece y los demás
canales, que funcionan bien, dejan de procesarse.

## Ejemplo incorrecto

```ts
export async function send(message: Message) {
  for (let attempt = 1; attempt <= 5; attempt++) {
    try {
      return await provider.send(message, { timeoutMs: 10_000 });
    } catch {
      // Con el proveedor caído: 5 intentos × 10 s = 50 s bloqueados por mensaje,
      // y cinco veces más carga sobre un proveedor que ya no responde.
    }
  }
  throw new Error("No se pudo enviar");
}
```

## Implementación correcta

```ts
type BreakerState =
  | { kind: "closed"; failures: number }
  | { kind: "open"; until: number }
  | { kind: "half-open"; inFlight: boolean };

export class CircuitOpenError extends Error {}

export class CircuitBreaker {
  private state: BreakerState = { kind: "closed", failures: 0 };

  constructor(
    private readonly options: { failureThreshold: number; openMs: number },
    private readonly now: () => number = Date.now,
  ) {}

  async execute<T>(operation: () => Promise<T>): Promise<T> {
    if (this.state.kind === "open") {
      if (this.now() < this.state.until) throw new CircuitOpenError("Circuito abierto");
      this.state = { kind: "half-open", inFlight: false };
    }
    if (this.state.kind === "half-open") {
      if (this.state.inFlight) throw new CircuitOpenError("Prueba en curso");
      this.state.inFlight = true;
    }
    try {
      const result = await operation();
      this.state = { kind: "closed", failures: 0 };
      return result;
    } catch (error) {
      this.recordFailure();
      throw error;
    }
  }

  private recordFailure() {
    const failures = this.state.kind === "closed" ? this.state.failures + 1 : this.options.failureThreshold;
    this.state =
      failures >= this.options.failureThreshold
        ? { kind: "open", until: this.now() + this.options.openMs }
        : { kind: "closed", failures };
  }
}

// Uso: un breaker por dependencia y un fallback de negocio
const whatsappBreaker = new CircuitBreaker({ failureThreshold: 5, openMs: 30_000 });

export async function send(message: Message): Promise<"sent" | "deferred"> {
  try {
    await whatsappBreaker.execute(() => provider.send(message, { timeoutMs: 3_000 }));
    return "sent";
  } catch {
    await retryQueue.enqueue(message, { notBefore: Date.now() + 60_000 }); // se reintenta más tarde
    return "deferred";
  }
}
```

Esta versión cuenta fallas consecutivas; las implementaciones de producción suelen usar una ventana deslizante
(porcentaje de fallas en las últimas N llamadas) y un mínimo de llamadas antes de abrir.

## Ejercicio

El proveedor responde `400 Bad Request` cuando el número de teléfono es inválido. ¿Debe contar como falla para el
breaker? ¿Y un `429 Too Many Requests`?

<Reveal>

Un `400` por un dato inválido no indica que el proveedor esté degradado: es un error de ese mensaje y no debe
abrir el circuito (de lo contrario, unos pocos números mal cargados cortarían todos los envíos). Un `429` sí indica
presión sobre la dependencia: debe contar, o mejor aún, respetar el header `Retry-After` y reducir el ritmo de
envío. En el código, `execute` debería recibir un predicado que decida qué errores cuentan.

</Reveal>
