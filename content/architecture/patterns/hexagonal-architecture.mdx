definition: "La arquitectura hexagonal (puertos y adaptadores) organiza la aplicación alrededor de un núcleo con el dominio y los casos de uso. problem: "La lógica de negocio queda acoplada al framework web, al ORM y a los SDKs de proveedores. No se puede probar sin levantar infraestructura, cambiar una tecnología es una reescritura y la misma lógica no se puede invocar desde otro punto de entrada (una cola, un job, un CLI)."

## Motivación

La plataforma registra pagos que llegan por tres caminos: el panel de operadores (HTTP), el webhook de la pasarela
(HTTP con firma) y un archivo de conciliación diario (job). Las reglas de imputación son las mismas en los tres
casos y son críticas: un error impacta en el saldo real de una persona.

## Ejemplo incorrecto

```ts
// app/api/payments/route.ts
import { db } from "@/lib/db";
import { payments, installments } from "@/lib/schema";

export async function POST(request: Request) {
  const body = await request.json();
  const pending = await db.select().from(installments).where(/* ... */);
  let remaining = body.amountCents;
  for (const installment of pending) {
    // reglas de imputación mezcladas con el ORM y con HTTP
  }
  await db.insert(payments).values({ ...body });
  await fetch("https://whatsapp.example/send", { method: "POST", body: "..." });
  return Response.json({ ok: true });
}
```

Para reutilizar la imputación en el webhook y en el job habría que copiarla, y probarla requiere base de datos y
un proveedor de mensajería.

## Implementación correcta

```ts
// application/register-payment.ts — núcleo: sin imports de Next.js, ORM ni SDKs
export interface PaymentRegistrationDeps {
  readonly debts: DebtRepository; // puerto de salida
  readonly notifier: Notifier; // puerto de salida
  readonly clock: () => Date;
}

export async function registerPayment(
  deps: PaymentRegistrationDeps,
  command: { debtId: string; amountCents: number; externalId: string },
): Promise<{ appliedToInstallments: number }> {
  const debt = await deps.debts.findById(command.debtId);
  if (!debt) throw new DomainError("debt-not-found");
  const result = debt.applyPayment(command.amountCents, command.externalId, deps.clock()); // regla de dominio
  await deps.debts.save(debt);
  await deps.notifier.paymentConfirmed(debt.debtorId, command.amountCents);
  return { appliedToInstallments: result.installmentsTouched };
}

// app/api/payments/route.ts — adaptador de entrada delgado
export async function POST(request: Request) {
  const parsed = paymentSchema.safeParse(await request.json());
  if (!parsed.success) return Response.json({ error: "invalid" }, { status: 422 });
  const result = await registerPayment(getPaymentDeps(), parsed.data); // composición en infraestructura
  return Response.json(result, { status: 201 });
}
```

El webhook y el job son otros adaptadores que invocan `registerPayment`. En los tests, `deps` se arma con un
repositorio en memoria, un `Notifier` falso y un reloj fijo.

## Ejercicio

Este proyecto usa la misma idea en `src/modules`. ¿Qué regla automática impide que un caso de uso importe un
adaptador? ¿Qué pasaría si no existiera?

<Reveal>

Un test de arquitectura (`tests/architecture/dependency-rules.test.ts`) analiza los imports de cada capa y falla
si `domain` o `application` importan `infrastructure`, `presentation`, React o Next.js. Sin esa verificación, el
primer atajo (importar el cliente de base desde un caso de uso "sólo esta vez") se copia y en pocos meses el núcleo
vuelve a estar acoplado a la infraestructura.

</Reveal>
