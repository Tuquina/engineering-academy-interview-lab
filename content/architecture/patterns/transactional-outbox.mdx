## Motivación

En un SaaS, cuando se registra el pago de la renovación de una suscripción, el servicio de avisos debe cancelar los
recordatorios de "tu suscripción vence" programados para ese cliente. Si el evento `PaymentRegistered` se pierde,
el cliente que ya pagó sigue recibiendo avisos de que va a perder el acceso: un problema de confianza y de soporte,
no sólo técnico.

## Ejemplo incorrecto

```ts
export async function registerPayment(db: Db, broker: Broker, payment: NewPayment) {
  await db.transaction(async (tx) => {
    await tx.insert(payments).values(payment);
    // Si el broker publica y luego el commit falla, se anunció un pago inexistente.
    await broker.publish("payments", { type: "PaymentRegistered", ...payment });
  });
  // Y si se publica después del commit y el proceso cae justo antes, el evento se pierde.
}
```

## Implementación correcta

```ts
// 1. Una sola transacción local
export async function registerPayment(db: Db, payment: NewPayment) {
  await db.transaction(async (tx) => {
    await tx.insert(payments).values(payment);
    await tx.insert(outbox).values({
      id: crypto.randomUUID(),
      type: "PaymentRegistered",
      aggregateId: payment.subscriptionId,
      payload: payment,
    });
  });
}

// 2. Relay: publica pendientes; varias réplicas pueden correr a la vez
export async function relayOnce(db: Db, broker: Broker, batchSize = 100) {
  await db.transaction(async (tx) => {
    const pending = await tx.execute(sql`
      SELECT id, type, aggregate_id, payload FROM outbox
      WHERE published_at IS NULL ORDER BY created_at
      LIMIT ${batchSize} FOR UPDATE SKIP LOCKED`);
    for (const event of pending) {
      await broker.publish("payments", { eventId: event.id, type: event.type, payload: event.payload });
    }
    if (pending.length > 0) {
      await tx.execute(
        sql`UPDATE outbox SET published_at = now() WHERE id = ANY(${pending.map((e) => e.id)})`,
      );
    }
  });
}

// 3. Consumidor idempotente (inbox)
export async function onPaymentRegistered(db: Db, message: { eventId: string; payload: NewPayment }) {
  await db.transaction(async (tx) => {
    const inserted = await tx.execute(sql`
      INSERT INTO inbox (event_id) VALUES (${message.eventId}) ON CONFLICT DO NOTHING RETURNING event_id`);
    if (inserted.length === 0) return; // duplicado: ya se procesó
    await tx.execute(sql`UPDATE scheduled_notices SET status = 'cancelled'
                         WHERE subscription_id = ${message.payload.subscriptionId} AND status = 'pending'`);
  });
}
```

Si el relay cae después de publicar y antes de marcar, el evento se publica de nuevo; la inbox lo descarta.

## Ejercicio

¿Qué métrica pondrías en una alerta para saber que el outbox dejó de funcionar, antes de que un usuario lo note?

<Reveal>

La antigüedad del evento pendiente más viejo: `now() - min(created_at) WHERE published_at IS NULL`. Contar
pendientes no alcanza (puede haber muchos en un pico y estar bien); que el más viejo tenga varios minutos indica
que el relay está caído o bloqueado. Del lado del consumidor, el lag de la cola y la cantidad de mensajes en la DLQ
completan el panorama.

</Reveal>
