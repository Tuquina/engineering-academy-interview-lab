## Motivación

Un editor de tableros (tipo Trello) permite mover tarjetas, renombrarlas y borrarlas, con **deshacer/rehacer**.
Además, cada acción se sincroniza con el servidor y debe poder reintentarse si no hay conexión.

## Ejemplo incorrecto

```ts
function moveCard(board: Board, cardId: string, toColumn: string) {
  board.columns.forEach((c) => (c.cards = c.cards.filter((id) => id !== cardId)));
  board.columns.find((c) => c.id === toColumn)!.cards.push(cardId);
  api.moveCard(cardId, toColumn); // si falla, se pierde; no hay forma de deshacer
}
```

## Implementación correcta

```ts
export interface Command {
  readonly type: string;
  execute(board: Board): Board;
  undo(board: Board): Board;
}

export const moveCard = (cardId: string, from: string, to: string): Command => ({
  type: "card.move",
  execute: (board) => relocate(board, cardId, from, to),
  undo: (board) => relocate(board, cardId, to, from),
});

export class History {
  private done: Command[] = [];
  private undone: Command[] = [];

  run(board: Board, command: Command): Board {
    this.done.push(command);
    this.undone = []; // una acción nueva invalida el rehacer
    outbox.enqueue(command); // se sincroniza y reintenta aparte
    return command.execute(board);
  }
  undo(board: Board): Board {
    const command = this.done.pop();
    if (!command) return board;
    this.undone.push(command);
    return command.undo(board);
  }
  redo(board: Board): Board {
    const command = this.undone.pop();
    if (!command) return board;
    this.done.push(command);
    return command.execute(board);
  }
}
```

Cada acción es un objeto con su inversa. El historial no conoce los detalles de cada una y la cola de sincronización
puede reintentarlas.

## Ejercicio

En el backend, el comando `SendInvoice` se encola y un worker lo ejecuta. Si el worker se cae después de enviar el
email pero antes de confirmar el job, el comando se reintenta. ¿Cómo evitás enviar dos emails?

<Reveal>

Haciendo el comando **idempotente**: incluye un ID único (`commandId`) y el worker registra los IDs procesados en la
misma transacción que el efecto local, o le pasa ese ID al proveedor de email como clave de idempotencia. Si el ID ya
fue procesado, el reintento no hace nada. La cola garantiza "al menos una vez"; la idempotencia convierte eso en un
efecto "exactamente una vez".

</Reveal>
