## Motivación

El caso de uso "inscribir a un alumno en una comisión" de una facultad necesita cargar la comisión con sus
inscripciones, aplicar las reglas "no superar el cupo y no inscribir dos veces al mismo alumno" y guardar. La regla es
lo importante; cómo se guarda es un detalle.

## Ejemplo incorrecto

```ts
export async function enroll(db: Db, sectionId: string, studentId: string) {
  const rows = await db.execute(sql`
    SELECT s.capacity, e.student_id
    FROM sections s LEFT JOIN enrollments e ON e.section_id = s.id AND e.status = 'active'
    WHERE s.id = ${sectionId}`);
  if (rows.length === 0) throw new Error("no existe");
  if (rows.some((r) => r.student_id === studentId)) throw new Error("ya inscripto");
  if (rows.filter((r) => r.student_id !== null).length >= Number(rows[0].capacity))
    throw new Error("sin cupo");
  await db.execute(sql`INSERT INTO enrollments (section_id, student_id, status)
                       VALUES (${sectionId}, ${studentId}, 'active')`);
}
```

La regla de negocio está mezclada con el SQL; probarla requiere una base con datos.

## Implementación correcta

```ts
// Dominio
export class Section {
  constructor(
    readonly id: string,
    private readonly capacity: number,
    private readonly enrollments: Enrollment[],
  ) {}

  enroll(studentId: string): Enrollment {
    const active = this.enrollments.filter((e) => e.status === "active");
    if (active.some((e) => e.studentId === studentId)) throw new DomainError("already-enrolled");
    if (active.length >= this.capacity) throw new DomainError("section-full");
    const enrollment: Enrollment = { id: crypto.randomUUID(), studentId, status: "active" };
    this.enrollments.push(enrollment);
    return enrollment;
  }

  get allEnrollments(): readonly Enrollment[] {
    return this.enrollments;
  }
}

// Puerto definido por la aplicación
export interface SectionRepository {
  findById(id: string): Promise<Section | null>;
  save(section: Section): Promise<void>;
}

// Caso de uso: sólo orquesta
export async function enrollStudent(
  repo: SectionRepository,
  input: { sectionId: string; studentId: string },
) {
  const section = await repo.findById(input.sectionId);
  if (!section) throw new DomainError("section-not-found");
  const enrollment = section.enroll(input.studentId);
  await repo.save(section);
  return enrollment;
}

// Implementación para tests
export class InMemorySectionRepository implements SectionRepository {
  private readonly items = new Map<string, Section>();
  async findById(id: string) {
    return this.items.get(id) ?? null;
  }
  async save(section: Section) {
    this.items.set(section.id, section);
  }
}
```

La implementación con PostgreSQL vive en infraestructura, mapea filas a `Section` y se prueba con tests de
integración. Además, la base mantiene su propia defensa: un índice único parcial
(`CREATE UNIQUE INDEX ... ON enrollments(section_id, student_id) WHERE status = 'active'`) evita dos inscripciones
activas del mismo alumno aunque dos requests lleguen a la vez. El cupo, que depende de contar filas, necesita además
un bloqueo de la comisión (`SELECT ... FOR UPDATE`) o un contador con una restricción `CHECK`.

## Ejercicio

La pantalla de la secretaría necesita listar 50 alumnos con su comisión, su última nota y si adeudan documentación,
ordenados por apellido. ¿Lo agregarías al `SectionRepository` como `findAll()` y ordenarías en memoria?

<Reveal>

No. Cargar agregados completos para una pantalla es costoso y obliga a filtrar en memoria. Es una consulta de
lectura: conviene una función dedicada (por ejemplo `StudentListQueries.list(facultyId, page)`) que ejecute un SQL
optimizado con paginación y devuelva un DTO plano. El repositorio queda para cargar y guardar agregados cuando hay
reglas que aplicar.

</Reveal>
