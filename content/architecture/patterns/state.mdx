## Motivación

Una reserva de hotel tiene un ciclo de vida: se crea pendiente, con la habitación retenida hasta una hora límite;
puede confirmarse (llegó el pago), vencer (pasó la hora límite sin pago) o cancelarse (la persona desistió). Una
reserva confirmada no puede volver a estar pendiente y una cancelada no puede confirmarse.

## Ejemplo incorrecto

```ts
interface Booking {
  id: string;
  amountCents: number;
  holdUntil: string;
  isConfirmed: boolean;
  isExpired: boolean;
  isCancelled: boolean;
  paidAt?: string;
  cancelReason?: string;
}

// En algún job:
booking.isExpired = new Date(booking.holdUntil) < new Date();
// En el webhook de pagos:
booking.isConfirmed = true;
booking.paidAt = new Date().toISOString();
```

Nada impide una reserva `isConfirmed && isExpired`, ni que el job marque como vencida una reserva cancelada.

## Implementación correcta

```ts
export type Booking =
  | { status: "pending"; id: string; amountCents: number; holdUntil: string }
  | { status: "confirmed"; id: string; amountCents: number; holdUntil: string; paidAt: string }
  | { status: "expired"; id: string; amountCents: number; holdUntil: string; detectedAt: string }
  | { status: "cancelled"; id: string; amountCents: number; holdUntil: string; reason: string };

export type BookingEvent =
  | { type: "payment-received"; at: string }
  | { type: "hold-expired"; at: string }
  | { type: "cancelled"; reason: string };

export class InvalidTransition extends Error {}

/** Única forma de cambiar el estado: pura, exhaustiva y fácil de probar como tabla. */
export function transition(booking: Booking, event: BookingEvent): Booking {
  if (booking.status !== "pending") {
    throw new InvalidTransition(`No se puede aplicar ${event.type} a una reserva ${booking.status}`);
  }
  const { id, amountCents, holdUntil } = booking;
  switch (event.type) {
    case "payment-received":
      return { status: "confirmed", id, amountCents, holdUntil, paidAt: event.at };
    case "hold-expired":
      return { status: "expired", id, amountCents, holdUntil, detectedAt: event.at };
    case "cancelled":
      return { status: "cancelled", id, amountCents, holdUntil, reason: event.reason };
  }
}
```

`paidAt` sólo existe en reservas confirmadas, y TypeScript obliga a verificar el estado antes de leerlo.

## Ejercicio

El negocio agrega un período de gracia: como la pasarela a veces tarda en confirmar, una reserva cuya retención venció
pasa primero a `grace` durante 15 minutos; si llega el pago en ese lapso se confirma, si no, vence. ¿Qué cambia?

<Reveal>

Se agrega la variante `{ status: "grace"; ...; graceUntil: string }`. La transición `hold-expired` desde `pending`
ahora lleva a `grace`; desde `grace`, `payment-received` lleva a `confirmed` y un nuevo evento `grace-expired` lleva
a `expired`. La guarda inicial deja de ser "sólo desde pending" y pasa a validar por estado (un `switch` sobre
`booking.status` con otro anidado por evento). Los tests de tabla agregan las filas nuevas y siguen verificando que
las transiciones inválidas lancen error. Mientras la reserva está en `grace`, la habitación sigue retenida.

</Reveal>
