## Motivación

En un e-commerce, confirmar un pedido dispara varias reacciones: email de confirmación, reserva de stock, puntos de
fidelidad y un evento para analítica. Las reacciones cambian seguido (marketing pide una nueva cada trimestre) y no
todas son críticas.

## Ejemplo incorrecto

```ts
class ConfirmOrder {
  constructor(
    private orders: OrderRepository,
    private mailer: Mailer,
    private stock: StockService,
    private loyalty: LoyaltyService,
    private analytics: Analytics,
  ) {}

  async execute(orderId: string) {
    const order = await this.orders.confirm(orderId);
    await this.mailer.sendConfirmation(order); // si falla el email, falla la confirmación
    await this.stock.reserve(order.items);
    await this.loyalty.addPoints(order.customerId, order.total);
    await this.analytics.track("order_confirmed", order);
  }
}
```

El caso de uso conoce a todos los interesados, cada reacción nueva lo modifica y un fallo en algo secundario rompe la
operación principal.

## Implementación correcta

```ts
type OrderConfirmed = { type: "order.confirmed"; orderId: string; customerId: string; totalCents: number };
type Listener<E> = (event: E) => void | Promise<void>;

export class EventBus<E extends { type: string }> {
  private listeners = new Map<E["type"], Set<Listener<E>>>();

  subscribe(type: E["type"], listener: Listener<E>): () => void {
    const set = this.listeners.get(type) ?? new Set();
    set.add(listener);
    this.listeners.set(type, set);
    return () => set.delete(listener); // desuscripción explícita
  }

  async publish(event: E): Promise<void> {
    const listeners = [...(this.listeners.get(event.type) ?? [])];
    // Cada observador se aísla: el error de uno no afecta a los demás ni al emisor.
    const results = await Promise.allSettled(listeners.map((listener) => listener(event)));
    for (const result of results) if (result.status === "rejected") logger.error(result.reason);
  }
}

class ConfirmOrder {
  constructor(
    private orders: OrderRepository,
    private events: EventBus<OrderConfirmed>,
  ) {}

  async execute(orderId: string) {
    const order = await this.orders.confirm(orderId);
    await this.events.publish({
      type: "order.confirmed",
      orderId: order.id,
      customerId: order.customerId,
      totalCents: order.totalCents,
    });
  }
}

// En la raíz de composición:
bus.subscribe("order.confirmed", (e) => mailer.sendConfirmation(e.orderId));
bus.subscribe("order.confirmed", (e) => loyalty.addPoints(e.customerId, e.totalCents));
```

El caso de uso sólo anuncia lo que pasó. Las reacciones se registran en un lugar y se prueban por separado.

## Ejercicio

La reserva de stock **no** es opcional: si falla, el pedido no debería quedar confirmado. ¿Sigue siendo un observador?

<Reveal>

No. Lo que forma parte de la invariante de la operación (confirmar sólo si hay stock) va **dentro** del caso de uso o
de la misma transacción, con llamadas explícitas. Observer es para reacciones que pueden ocurrir después y fallar sin
deshacer la operación principal (email, puntos, analítica).

Si el stock vive en otro servicio, la coordinación se resuelve con una **saga**: el pedido queda "pendiente", se
reserva el stock y recién entonces se confirma, o se compensa si la reserva falla.

</Reveal>
